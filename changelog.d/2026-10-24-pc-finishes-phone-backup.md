- **The phone finishes a backup on the PC with one tap (2026-10-24).** The owner upgraded his morning decision from "let the PC finish a backup the phone started" to one tap from the phone: after the code is shown and he ticks "I have written this code down somewhere safe", the phone's finish button makes the PC write the file - no step on the PC. The one-time code the phone holds IS the authorisation for the phone that minted the run; the write still happens on the PC's disk, by the PC's own backend. `POST /api/backup/commit` therefore no longer refuses a caller for not being the PC: a live run minted by `prepare`, its exact code and the 15-minute TTL are what authorise it, and a wrong or missing code (400) or a dead run (409) still writes nothing. This deliberately relaxes the 2026-10-13 rule "a phone may ask, only the PC may write"; the residual risk - the "I saved it" tick is a phone-side promise, so a modified or misused phone could make the PC write a backup whose code nobody kept and push the oldest of the five kept out - is recorded in `docs/DECISIONS.md` and `docs/ARCHITECTURE.md` section 8, with the owner's acceptance. The PC's typed-code block in Settings, Backups stays as the fallback for a run the phone left waiting, on the same route: no new route, and no approval card. The run is claimed under the module's lock before the write, so two presses write ONE file, and the phone's screen now says "Nothing has been written yet" before the press and "Your PC wrote the backup" only after the PC reports a file (the dialog used to claim it the moment it opened). **Hardened the same day on Gemini's ruling:** the finish is BOUND to the phone that minted the run or to the PC - `prepare` records the asking device's existing identity (`handler._jarvis_device`; no new header or token) and another paired device holding the same code is refused 403, writes nothing and does not spend the run, while a run minted with no recorded identity falls back to the code (said plainly in the code and the API doc); and a commit that cannot write now always records `last_attempt.ok: false` - including the 409 when the folder has gone, which used to record nothing - so a failed run is never shown as the previous run's success, while a truncated `.jbak` is never counted as a valid backup. The phone's screen, live run and TalkBack wording are a field-test row, not a pass.
