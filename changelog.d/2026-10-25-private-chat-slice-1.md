- **A private chat is strictly reads-only (backend Slice 1, 2026-10-25).** `"private": true` on `POST /api/chat` now implies the temporary chat - no memory used, nothing learned, nothing kept in history - and additionally refuses every disk write a turn can reach: chat history and its own housekeeping (the module is not called at all), the memory store and the background learner, the feedback turn row, `speed.jsonl`, the route audit line, `hud-budget.json`, `approvals.db`, `receipts.db`, the answer-sources row and the device's `last_seen` (held by the devices wrapper and dropped when the body says private). It runs no tool at all, denies any card-gated tool call without raising a card (so no approval or undo receipt exists for one), refuses every mutating fast-path command with one plain sentence BEFORE anything changes or is receipted, and leaves nothing in RAM-only registries either. The gate fails closed: a missing or broken shipped module still refuses the private turn instead of making it ordinary. The single gate and the sentence live in the new shipped `jarvis_private_chat.py`; `X-Jarvis-Route` carries `"private": true` and `/api/version` advertises `capabilities.private_chat`, false on an older server. The capability reports true only when both the hud patch and the shipped module are present. Neither app sends the flag yet and neither has a UI for it - Slice 2 is their half; the backend contract is already the one they will read (JARVIS-API section 156).
