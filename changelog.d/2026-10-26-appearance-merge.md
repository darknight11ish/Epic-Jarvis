- **A partial appearance save merges instead of erasing the other half (2026-10-26).** `POST /api/appearance` used to replace the whole stored document, and its writers send different shapes: the phone sends `bindings` on every push and a `face` only once its owner has picked one (`AppearanceStore.toSyncDocument` leaves a blank face out), and the Faces window sends a fresh document. So the first colour change pushed from a fresh phone wrote `face: null` and erased the face the desktop was wearing, and a face-only save erased every state binding the same way. The write now merges - a key the request carries replaces its stored value, a key it does not carry keeps the stored one - and clearing is explicit (`face: null` or `""` clears the face, `bindings: {}` clears the state bindings). Only the request is validated, so a stored document a newer spec would refuse cannot make a colour change fail. Proved by `backend/test_appearance.py`, 19 checks, five of them new for the merge; against the old text the suite fails at the first merge check with `KeyError: 'idle'`. **Two narrow limits are recorded, not claimed away:** the read-modify-write has no lock, so two saves that overlap inside the threaded server can still lose one side, and a stored file that cannot be read just now is treated as corrupt, so a save in that moment can lose the rest - both are in the patch's own docstring, `docs/APPEARANCE-API.md` and `backend/README.md`.
