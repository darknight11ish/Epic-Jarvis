- **A Windows Hello prompt now closes when its card stops waiting, can never be given more than 180 s, and only an action with written words can prompt (2026-10-26).** The measured defect (`.dsh-scratch/WINDOWS-HELLO-2026-10-26/FINDINGS.md`) was that `POST /api/approve` read the card's remaining seconds BEFORE waiting for the one-prompt-at-a-time lock and never read them again, so a queued card kept its original 900 s even with 2 s left; and nothing watched the card while the dialog was up, so a card that was denied, withdrawn or expired under an open prompt left the dialog on screen for the rest of that number. Now the card is read again after the lock - a card that has run out by then is a 409 with no prompt - and the prompt gets `min(the seconds left now, 180 s)`. While the prompt is up a watcher polls the card four times a second and tells the child to close when it stops waiting, so the dialog goes within about a quarter of a second instead of being waited out; a queue that cannot be read is not treated as a card that went away. The watcher can only close its OWN prompt: the prompt is tagged when it is raised and the cancel is matched by that tag, because a queue read can outlive the watcher's two-second stop and the next card's prompt could otherwise be the one on screen. The wait for the lock is bounded too (`_PROMPT_WAIT_MAX` = 210 s, covering the worst legitimate hold of about 194 s: 180 of prompt, ten for the child's answer, two for the cancel and two for the watcher's stop) and refuses with 409 rather than waiting for ever. The long-lived `--hello` child no longer reads an empty stdin line as `{}` (which gave a cardless prompt the 900 s default) and clamps any timeout it is given to `_PROMPT_MAX` itself. Separately, an action with no written title in `jarvis_card_words` is refused with 403 `owner_check: "unlabelled"` before any prompt is shown - checked again on the post-lock live row, and stamped for that live action - because the title could only quote the action's name back at the owner; `unclassified_tool`, `send_email` and every other action with a phrase still prompt. A clean backend shutdown now cancels a live prompt (an `atexit` hook writes "cancel" to the child's stdin, and the child's own watcher calls the Windows cancel), instead of leaving the dialog to its own deadline. **Deploying it means copying BOTH `jarvis_owner_check.py` and `jarvis_card_words.py` into the live backend in one go, then restarting the backend:** `has_written_title` lives in the words module, and a one-module copy makes every risky approval on this PC refuse with 403 `unlabelled` before any prompt - silently, and it looks like the new guard working. `scripts/apply-patches.ps1` copies every shipped module in one run, so use it rather than a hand copy. Proven with fake verifiers and a fake child process only - no real dialog was raised: `backend/test_owner_check.py` 214 passed, 1 skipped; `backend/test_card_words.py` 168 passed. Honest limits: the prompt is still a detached child process and is still not parented to the app's window (the next fix, needing a real-prompt half-day test), so a hard kill of the backend - the desktop's job object, Task Manager - runs no Python, cannot run the cancel or the watcher, and the dialog then ends only at its deadline; a queue read that keeps failing also leaves the dialog to its deadline (nothing is approved either way); the desktop's own prompt (`op.get()` with no timeout) is unchanged; and the off-Windows test that used to call the real verifier on Windows now skips before that call, so the suite can no longer raise a real prompt on the owner's PC.
