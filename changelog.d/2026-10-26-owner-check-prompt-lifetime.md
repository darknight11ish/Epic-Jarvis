- **A Windows Hello prompt can no longer outlive its card, and only an action with written words can prompt (2026-10-26).** The measured defect (`.dsh-scratch/WINDOWS-HELLO-2026-10-26/FINDINGS.md`) was that `POST /api/approve` read the card's remaining seconds BEFORE waiting for the one-prompt-at-a-time lock and never read them again, so a card queued behind another prompt kept its old, larger number. Now the card is read again after the lock: the queued prompt gets the seconds the card has left by its turn, a card that has run out by then is a 409 with no prompt, and the prompt is capped at 180 s (its only cancel is its own deadline, so that number is the dialog's lifetime; the card itself keeps waiting, so Approve can be pressed again). Separately, an action with no written title in `jarvis_card_words` is refused with 403 `owner_check: "unlabelled"` before any prompt is shown, because the title could only quote the action's name back at the owner; `unclassified_tool`, `send_email` and every other action with a phrase still prompt. A clean backend shutdown now cancels a live prompt (an `atexit` hook writes "cancel" to the child's stdin, and the child's own watcher calls the Windows cancel), instead of leaving the dialog to its own deadline. Proven with fake verifiers and a fake child process only - no real dialog was raised: `backend/test_owner_check.py` 141 passed, 1 skipped; `backend/test_card_words.py` 168 passed. Honest limits: the prompt is still a detached child process and is still not parented to the app's window (the next fix, needing a real-prompt half-day test), so a hard kill of the backend - the desktop's job object, Task Manager - cannot run the cancel and the dialog then ends only at its deadline; the desktop's own prompt (`op.get()` with no timeout) is unchanged; and the existing off-Windows test that called the real verifier on Windows now skips before that call, so the suite can no longer raise a real prompt on the owner's PC.
