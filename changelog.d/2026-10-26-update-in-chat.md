- **Jarvis can talk about an update in chat, and start one only through ONE approval card (2026-10-26).** "Is there an update?" and "what changed in the update?" are answered without the model from the same public release manifest the app's updater reads, using the version the desktop shell reports in the chat body; a release's changes come from the changelog, now published into `latest.json`'s notes by the release workflow, and an empty or one-release-only list says so rather than inventing changes. "Update Jarvis" raises ONE card (action `desktop_update`, tier ask, PC-only with Windows Hello) that names both halves, the version, the restart and the pace; only the owner's Approve makes the shell run the same `update_both` the Settings button runs - backend first, then the signed desktop release, then a restart - so no page, timer, page script or chat message can install anything, and the HUD gained no update command. The phone is one-sided on purpose: its reply points at Platform checks, its own update card, and the PC-only card refuses a phone approve with nothing changed. Proven by `backend/test_update_chat.py`, `jarvis-desktop/tests/update-chat.mjs`, `jarvis-desktop/tests/release-notes.mjs` and the existing Rust suite; a real signed install is the owner's field test, not a pass.
