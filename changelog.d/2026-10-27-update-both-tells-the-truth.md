- **"Update both halves" now says what really happened, and stops the backend before the Windows installer runs (2026-10-27).** The desktop half ends the app: the updater's Windows installer path launches the installer and then calls `std::process::exit(0)`, so the button could never report its own result - the Settings window vanished with no desktop line at all, and the chat path's "Both halves are updated" sentence was unreachable. That ending is now written down before the process goes: a record at `~/.openjarvis/pending-desktop-update.json` (beside the update lock; `OPENJARVIS_CONFIG_DIR` is honoured) names the version being replaced, the version being installed, which commit each half came from, and what the backend half did, and it is written in one step - a temporary file flushed to disk and moved into place - so the next start can never read half of it. The order is fixed and tested: the backend half must finish AND prove its own checks, then the desktop package is downloaded and its signature checked, then that record is written and read back, then the Python backend is stopped (waiting at most three seconds), and only then is the installer called, last. A backend that patched but skipped its checks is no longer enough to let the desktop half start; the card says so and points at the Install button for the desktop half on its own. The updater's own `on_before_exit` hook still stops the backend and only then marks the record "installer launched", and the backend this app runs is now also held in a Windows job object that ends it when this app's last handle closes, so a crash cannot leave a Python process behind holding the graphics card. The lone **Install** button gets the same treatment - it used to skip the backend stop entirely, leaving the model resident while the installer replaced files - and a start that fails before the installer says plainly that nothing was installed. "Both halves are done" can now only appear for a desktop half that landed AND a backend half that was patched and proven. Because the installer closes Jarvis, the app now says so before the button is pressed: "Jarvis closes while this installs, and starts again by itself when it is done. Save anything you are working on first." rides in the data the Updates card already reads, in the notification that announces a new version, in the desktop half's first line, and in the chat line an approved update starts with (the card itself still has to print that field - four lines in `settings.js` and `settings.html`, which another change owns). The backend patch log also names its commit beside the app's ("Backend at <sha>, app at <sha>; they differ"), because the two halves still share no version and an out-of-date program folder can still be patched under a newer app. Nothing installs itself, no new approval card is added, and nothing in this change pretends a rollback exists: a bad desktop release still has no "go back" button (the release workflow deletes the previous installers and downgrades are refused), which stays an owner decision. The ending logic, the order and the job object are unit-tested; only a real update on the owner's PC can prove the installer's exit is reported correctly and that the backend is really gone before it starts.
