- **Connecting an account by talking to Jarvis: one card, Credential Manager, one real test (2026-10-28).** The owner asked whether Jarvis could connect his accounts through chat, with a pop-up for a password — and the answer he had been given ("jarvis cannot connect directly to external calendars … Would you like instructions on exporting your calendar to ICS?") was false about Jarvis, which reads CalDAV and a private iCal link today. Now "connect my calendar", "set up github", "set my github token" and "is my calendar connected?" reach a deterministic answer with no model at all, and the first raise ONE card in the desktop HUD: the private iCal link, the CalDAV username and password, or a GitHub personal access token. The values never enter the chat, the model's context, a tool result, a log line, a file, a database or the clipboard — the HUD posts them to a host-only route (`/api/connect-account/{pending,save,cancel}`, loopback and pairing token checked before the body is read, the body never logged or echoed) and `jarvis_token_store.store_secret` writes them straight into Windows Credential Manager, with **no plaintext fallback**: a store that refuses says so and saves nothing anywhere else. The card is then tested once for real — one `GET` of the iCal link (200 **and** `BEGIN:VCALENDAR`), one authenticated `PROPFIND` on the saved CalDAV address (200/207), or `GET https://api.github.com/user` (200, with the login GitHub answers with) — and "connected" is only ever the verifier's verdict: a saved-but-broken link answers "saved, but it did not work just now — the private link answered HTTP 404". The same fix closes a rule 3 breach the audit found: the CalDAV username/password and the GitHub token had **no Credential Manager entry at all** and were read only from plain-text environment variables (`jarvis_calendar.login()` and `jarvis_research._token()` now resolve through `jarvis_token_store.resolve_secret`, so the environment variable still wins when one is set and nothing already working breaks). The model gains ONE tool, `connect_account`, which takes a service and a note and **refuses any argument that looks like a value**; it ships off like every tool not in the shipped `[tools].enabled` list, and the owner's sentences work without it. PC-only on purpose: there is no phone card and no phone route, because a phone-side card would have to send the credential over the network to reach this PC's store (`ARCHITECTURE.md` §8, `JARVIS-API.md` §161, `tools/check_parity.py` `deliberate`). `backend/test_connect_account.py` (153 checks), `backend/test_account_secrets.py` (the required `credential-manager` CI check, now covering the three new entries on real Windows under throwaway names) and the HUD card's fields plus its post path in `jarvis-desktop/tests/hud.mjs` prove it.
