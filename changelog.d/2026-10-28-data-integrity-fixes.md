- **A backup can no longer claim data it cannot restore, a damaged `manner.json` refuses writes instead of wiping itself, and every way a chat is deleted now scrubs receipts (2026-10-28).** The chat-history key is PROVED against the database before a backup carries it, and a backup never mints one: `get_existing_key()` is read-only, `get_or_create_key()` only makes a key for a brand-new empty history, and `verify_key_opens_db()` is the AES-GCM check-row proof. A history whose key is missing or does not verify is LEFT OUT, never carried unreadable, and named in `excluded_dbs`; `study.db` and `health.db` get the same rule when their own key cannot be read, and every database whose snapshot failed is named the same way, and "Backed up." becomes "Backed up N databases, except …, left out to prevent an unreadable backup." A restore refuses to overwrite the live `chat-history.db` when neither the archive's key nor this PC's key opens it, and leaves the live key alone either way - the receipt names the database. A damaged `manner.json` refuses every write in plain words, keeps `manner.json.corrupt-<stamp>`, and each valid write keeps `manner.json.bak` - the #881 merge shape is unchanged. Retention (`keep_days`) and an expired "Forget a time frame" Undo now purge receipts like a hand delete, and the old 200-turn cap is gone. Changing the window sweeps BEFORE it saves, so a failure cannot be reported as "could not save the setting". Data-integrity audit F1-F5, with regression tests for each; the audit's F6 (the Undo lives in memory) is unchanged.
