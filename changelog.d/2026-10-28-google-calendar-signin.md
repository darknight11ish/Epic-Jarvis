- **Google Calendar, both ways: the private iCal link or a real Google sign-in, and only one at a time (2026-10-28):** the owner picked "Both at once" - a read-only private iCal link *and* a read/write Google sign-in - with the app choosing one. The sign-in is the Google "installed app" flow with a **loopback redirect** (`http://127.0.0.1:<random port>/callback`, bound to 127.0.0.1 only - no ngrok, no Cloudflare Tunnel, no Tailscale Funnel), **PKCE (S256)** and a random `state` that is checked on the callback: a wrong or missing state is refused and nothing is exchanged. The scope is `calendar.events` alone (the narrowest that can list, create, change and delete). The refresh token lives in Windows Credential Manager through the existing `jarvis_token_store` helper, access tokens live in memory only, and neither is ever written to a file, a log line, a route answer, a card or a model prompt. Reads raise no card; creating, changing or deleting an event raises ONE approval card showing the exact event, sends nothing before the yes, and is refused outright when the last read of the calendar is stale. That card is a risky approval - Windows Hello on the PC, the phone's screen lock - and `google-calendar-gate.patch` writes that down in the gate's own risk table at the pair the shared "not classified" fallback already produced, so no prompt changes: what changes is that the card says what the write does instead of calling it unclassified, and the tier joins `[autonomy.tiers]` at the "ask" it already resolved to. (The security review's finding N1 said the missing row meant no Windows Hello; that half does not match the code - all three approve rules treat an unclassified card as risky - and JARVIS-API §161 carries the correction.) `backend/jarvis_google_calendar.py` (+ its `jarvis-backend/` twin) with routes from its own `install()`, called by `plugins/ready/google-calendar` - no `jarvis_hud.py` edit; the one patch is the gate's risk row.
