- **The hardware detector's cache is no longer born expired, so a card read costs one probe instead of ten seconds every time (2026-10-28).** `jarvis_hardware.detect()` stamps its cache with the timestamp taken BEFORE the probe runs; the probe can legitimately take seconds on this PC (one registry read has a 10 s timeout), so the fresh value was already older than `_CACHE_SECONDS` when stored and every caller paid the whole probe again. Measured on the owner's live backend today: three consecutive `detect()` calls at **10.17 s / 10.06 s / 10.08 s**, and the model advisor's `GET /api/models/recommendations` - which reads that measurement - took **10.07 s** on every open. The cache is now stamped after the probe returns; a second read inside the 10 s window is the cached value. The fix is one line in `backend/jarvis_hardware.py` (and its byte-identical `jarvis-backend/` twin), with a new `backend/test_hardware_cache.py` that stands in a slow probe and proves two calls inside the TTL probe once, a call after the TTL probes again, and `fresh=True` always probes - the check **bites** on the old code (the second call probes again). The advisor route still reads the same measured cards, so its answer is unchanged; only the wait is gone.
