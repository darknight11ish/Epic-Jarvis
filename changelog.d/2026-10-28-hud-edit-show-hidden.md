- **Edit HUD: a hidden card can be shown again, and the Hide button is a real toggle (2026-10-28).** The owner's own Edit HUD field test found that hiding a card was one-way: the card's Hide control sent `{type:"setVisible", id, visible:false}` on every press while the app painted it as a toggle, and a hidden card's shell is `display:none`, so the one toggling path (the `h` key, which needs focus on that card's own handle) could never be reached again - after a reload the only ways back were Undo / Discard changes (same editing session) or Reset to preset, and Reset replaces the arrangement of a layout that is not the base preset, so an owner's own layout could not be restored. Now the control sends `setVisible` with no fixed value through the same one reducer (the same door as the `h` key - no second mutation path), so it hides and shows, and while Edit HUD is on a hidden card is painted as a dimmed, dotted ghost: its header, the word "hidden", and its own Show control, with the card's body folded away so the card itself stays hidden. Outside edit mode the shell is hidden exactly as before, so the ordinary HUD looks unchanged. Protected cards are untouched - `approvals` and `bar_launcher` still refuse to be hidden or moved, in the same words, and the refusal is the reducer's, not the button's - and the layout store is unchanged: one document, no new action type, no new IPC command. Proven by `jarvis-desktop/tests/hud-edit.mjs` (82 passed), `jarvis-desktop/tests/hud-edit-fieldtest.mjs` (22 of 22, both scenarios, twice), `tests/hud-edit-geometry.mjs`, `tests/hud-layout.mjs` and `tests/hud-settings-layout.mjs`; the ghost's dimmed look is in the field test's screenshots but no check measures a colour or a pixel, and no real WebView2 window was driven.
