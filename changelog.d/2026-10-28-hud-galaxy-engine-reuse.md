- **The Galaxy's 3D engine caches its picture instead of rebuilding it every frame, and lets go of its WebGL renderer when the galaxy is hidden (2026-10-28).** The owner's guardrail for this wave: the Planetary Orrery really orbits, so `applyPositions` runs on every frame, and it used to rebuild the picture's bookkeeping each time - a fresh array of position objects, two fresh position maps, and a fresh link array out of `presetLinks` with a control object per link, about 1,500 objects a frame handed to the garbage collector while the GPU was already busy. `galaxy-cosmos.js` now caches the topology behind a dirty flag: the position objects and their map are reused (a moved planet writes three numbers into an object that already exists), the link plan is kept by id and rebuilt only when the SET changes (a new graph, another look, the zen-ring's chords toggle), and every link writes into its own existing `Float32Array` and raises `posAttr.needsUpdate = true`, so three.js re-uploads the vertices instead of the page building a new geometry, material and Line. Measured in Node on this PC against the pre-fix file, same graph and look, 300 frames each: **0.541 ms -> 0.232 ms per frame at 240 names** (2.34x cheaper) and 0.329 -> 0.206 ms at 121 names, with per-frame position-map constructions falling from 8 to 5 - the three removed are exactly the two id->position maps and `presetLinks`' own. The renderer is lazy now too: the page builds no `WebGLRenderer` until the Galaxy is really on screen, and disposes the engine (renderer, geometry, materials, the canvas's context-lost listener) when the owner hides the galaxy or the window is backgrounded; showing it again rebuilds one through the drawing loop's own switch. `tests/galaxy-engine-reuse.mjs` proves the cache with a counting stand-in for three.js (6 checks, no browser): sixty steady frames build no geometry, buffer, line, mesh, material or colour and do not move the engine's reported plan count. **Honest limits:** the layout function itself still runs on an orbiting frame - only the topology around it is cached - the milliseconds above are Node, not a browser, and the GPU frame is untouched; the canvas's GL context is disposed with its renderer but not force-lost, because a force-lost context cannot be handed to a new renderer on the same canvas without `webglcontextrestored` handling and that path is untested at this desk; the engine is deliberately NOT dropped for a mere conversation/map view switch, because the existing idle test measures the engine's draws stopping and resuming and rebuilding a GL context on every toggle would cost more than it saves; nothing here is Playwright-tested locally - CI's frontend job is the first browser run.
