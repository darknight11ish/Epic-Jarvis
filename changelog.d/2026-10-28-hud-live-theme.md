- **The HUD window now follows a theme picked in Settings while it is open, without a reload (2026-10-28 field test).** Driving the installed 0.2.351 app over WebView2 CDP found the theme picker repainting Settings, the main window, the widget and the Brain at once, while the HUD stayed on Reactor until the page was reloaded (`.dsh-scratch/MAXOUT-2026-10-28/FIELDTEST-DESKTOP-2026-10-28/REPORT.md`, row "Theme picker (#theme-list) + fan-out"). The cause was source-visible: `jarvis_hud.html` painted `document.documentElement["data-theme"]` once from `localStorage["jarvis.theme"]` at load and listened for nothing, while every other window subscribes to the `theme-changed` event Rust fans out (`jarvis-link.js` `followTheme`, called by `main.js`, `brain.js`, `settings.js` and `widget.js`). The HUD now listens for that same event with the same payload - the effective theme id, so "Match Windows light or dark mode" arrives already resolved and nothing here reads the OS - and applies it the way `applyTheme` does: normalise, set `data-theme`, write the anti-flash cache so the next load still paints the right theme first. Nothing reloads and no layout moves: the only colours baked into pixels are re-taken (the canvas ink cache, the legend's swatches, and the 3D Galaxy, which bakes its vertex colours when it builds and is rebuilt only while it was drawing - a freshly built engine re-frames its own camera from the look's preset, so a dragged or zoomed 3D view returns to that framing) - the pre-paint read at the top of the page is untouched, so the first frame still has no flash. `jarvis_hud.html`'s three byte-identical copies are updated together. Tests: two new checks in `jarvis-desktop/tests/hud.mjs` - the stored theme is on the root at the first painted frame, and the real `theme-changed` event (driven through the page's own registered listener) changes the window without a reload, with the surface, the ink cache and the legend's swatches all following and the layout rectangles unchanged. Honest limit: the page path and the fan-out are proved in the browser harness here, and the event grant was already in `capabilities/hud.json`, but no build from this branch has been run on the installed app, so the desktop field row is confirmed by the next release.
