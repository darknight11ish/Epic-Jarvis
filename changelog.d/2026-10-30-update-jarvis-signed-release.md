- **Updating Jarvis now downloads the signed release instead of silently building from source, and no longer rebuilds after an update (2026-10-30).** The desktop update was taking the slow route for two measured reasons, and both are fixed. GitHub serves the release page's small manifest as a download rather than a web page, so Windows handed the script its raw bytes; the script piped those bytes straight into its JSON reader, which read one number per byte and found no version - so it concluded no release existed and built the app from source instead, silently, on every run. The ancestry check had the other half of the same trouble: it asked git whether the released commit was already in the folder's history, and that answer is yes BOTH when the folder is exactly the release and when it has moved past it, so a folder sitting on the released commit rebuilt instead of installing the signed release that is that same code. The reply is now decoded as text before it is parsed, and the comparison asks "equal" before it asks "older": a folder standing on the released commit installs the signed release, a folder with genuinely newer local commits still builds and is never downgraded, and an unzipped folder or an unrelated history still installs the published one and says it cannot tell. Every safety rule is unchanged - nothing unsigned is installed, nothing is approved for you, a download that does not verify is refused, and the backend keeps its backup and its rehearsal. Proved by `scripts\test-update-jarvis.ps1` in Windows PowerShell 5.1 (the owner's version), which lifts the functions out of the script as written and runs them against synthetic replies and a throwaway repository: 15 of its checks fail against the old script and all 21 pass against this one. What no desk can prove is one real round trip to the release page, which is the Lead's call.
