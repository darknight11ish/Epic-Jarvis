- **DEF-020: the updater no longer treats a dirty working tree as the released code (fixed in code, machine-proven).** The route decision asked only about commits: a folder standing on the release's own commit answered "same" even with uncommitted work on top of it, so `update-jarvis.ps1` installed the signed release over that work and silently replaced it - against the function's own rule that only a folder which has moved past the release keeps its own build. `Get-LocalVsRelease` now asks `git status --porcelain --untracked-files=no` after the commit equality and returns a fifth answer, **"dirty"**: a tracked change (staged or not) or a deletion means this is not the released code, so the updater builds this folder and says why, keeping the work. Untracked files are deliberately ignored (build output and scratch, and a build does not ship them), and a failing `git status` returns "dirty" rather than assuming the tree is clean. A clean folder at the commit still installs the signed release, a genuinely newer local build is still never downgraded, and release-ahead/unknown are untouched. Pinned in `scripts/test-update-jarvis.ps1` (21 -> 28 checks): a throwaway repo at the release commit with one tracked file modified, then with that change staged, must answer "dirty"; an untracked file alone and the restored tree must answer "same"; plus source pins that the caller branches on it and says why. Measured: the pre-fix updater fails 5 of 28 (the dirty cases come back "same", exit 1), this branch passes 28 of 28, exit 0, in both pwsh 7.6.9 and Windows PowerShell 5.1. The CI powershell-5 job's own comment now names the fifth answer.
