- **Obsidian plugin packaging follows the binary rule: source, `manifest.json` and a committed `main.js`, with a build-drift check and no packaged zips in the tree (2026-10-31).** The committed `main.js` stays exactly where it is, on purpose, so the owner can copy `obsidian-plugin/` into a test vault without installing Node or running a build. `npm run check:build-drift` (a new script running `node tests/check-build-drift.mjs`) rebuilds the bundle with `node esbuild.config.mjs` and fails if `obsidian-plugin/main.js` changes at all - the zero-drift proof that the committed file is exactly the build of `src/` - and the exact step a CI lane could add to the informational `audit` job (`cd obsidian-plugin`, `npm ci --no-audit --no-fund`, `npm run check:build-drift`; Node 20 is enough and it takes seconds) is written in the README, although this change edits no workflow file. No packaged binaries are tracked: `*.zip` and `dist/` are in `obsidian-plugin/.gitignore`, packages are built into a scratch/release folder and never committed, and their sizes and SHA-256 values are recorded in `BUILD-VERIFICATION.txt` (0.1.3's exact size and SHA-256 are recorded there after the package is built; 0.1.2: 86,666 bytes, SHA-256 `7FA8BE04ADF83ED3BA50826C32D95F249B7164743D349D85F08479A5CB1EE5E6`; 0.1.1 kept for history: 80,765 bytes, SHA-256 `52504033CD3D6529129C868623109D013D17FABE40F2CB104F0AD03685146AB1`). The node tests now include a fake-Jarvis integration suite that stands up a real local HTTP server on `127.0.0.1` and drives the plugin's own request builders and answer interpreters through the wave-2 routes - read then insert (waiting to saved), format saved, replace conflict, customize unchanged, tag saved, create waiting to saved, capture waiting to filed, chat answer, templates, wrong token 401, pre-deploy templates 404, query and path encoding, invalid-JSON handling - plus the first-run checklist (no token gives the Settings sentence, the default backend is loopback, and requests carry the `hud`/`desktop` headers). The first-run checklist is now a tested state list: `firstRunChecklist` in `src/protocol.ts` feeds the panel's numbered **First run** block, which stays until the connection is `connected` and otherwise names the ONE next action, with tests for no token, checking, unreachable, token refused, routes not deployed and an unexpected HTTP answer. The suite also covers the remaining honesty shapes rather than only the happy paths: a card that arrives with no change id (the plugin says it cannot follow it instead of pretending it can), unknown write/capture state words (never reported as saved or filed), denied/failed/conflict status polls, a vanished job id, 400/403/409/413/429/500/503 errors, malformed read/chat/template answers, and a server closed while a card was waiting. Two honesty bugs were found by the new tests and fixed rather than blessed: a capture-status 404 for an unknown job id used to claim "not_filed" although the PC merely has no record of that job (it is now an error with the route's own sentence), and a 403 used to be blamed on the token although on this backend 403 is the protected-note refusal (only 401 is the token refusal now). A new `tests/accessibility.test.mjs` (20 tests) and `src/a11y.ts` pin what the panel asks a screen reader for: an accessible name on every control the plugin creates itself, live regions plus `aria-busy` on the ask answer, write result, Test connection result and dialog answers, a named group for the selection buttons, the reason a disabled button is disabled, and a live-region status bar; the replace dialog's selected words are read-only rather than disabled so a keyboard user can still focus and read them. An independent read-only accessibility audit then drove a second pass in the same change: errors are announced as `role="alert"`, every action gives focus back after it disables its own button, the panel refuses to rebuild while a field in it has focus, the selection buttons are no longer disabled from a stale one-time selection read (the handlers refuse and say why in the live result line), unavailable insert/create actions explain themselves, the template preview is a live region a keyboard can scroll, a cut list says how many items are hidden, a clipped replace preview says so, and a command-palette failure is explained in the panel's live line instead of only in a toast. Honest limits: the plugin has still never been loaded by Obsidian, so no keyboard and no screen reader has been used against it, and these tests check the attributes and source pins, not what Obsidian's webview renders; the wave-2 routes await the #1049 deploy to the live backend; and the integration suite drives a stand-in server, not the real backend.
