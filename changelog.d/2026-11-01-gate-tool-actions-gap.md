- **Four tools the model can pick - send a file to the phone, protect something from Jarvis, connect an account, investigate a program with REA - reached the approval gate with no action of their own, so the card they raised was never their card (2026-11-01).** `jarvis_agent.py` offers `send_file_to_phone`, `protect_from_jarvis`, `connect_account` and `rea_investigate`, and none of them had a line in `jarvis_gate._TOOL_ACTIONS`; no patch in `backend/` named any of the four either, so no run of `apply-patches.ps1` could ever have added them. `action_for_tool()` therefore answered `unclassified_tool` for every one - fail-safe, because that name takes `unknown_action_tier` ("ask", so nothing ran unattended), and wrong in two ways you could see: the card showed a generic worst case instead of the tool's own words, and "What can Jarvis reach" listed all four as unclassified, which reads as "cannot be undone and can leave this PC". Each is now mapped onto an action that already existed and already owned its tier and card wording - `send_file_to_phone` itself, `protect_item`, `change_own_config`, `run_shell_on_host` - so no new action, tier or card wording was invented, and nothing about how often you are asked changes. The CI blind spot is closed too: the check written for exactly this needs `import jarvis_gate`, which no plain clone can do, so it printed `skip` in CI and could only ever fail at the desk. A new suite rebuilds the table an install really gets from the published base plus every patch's added lines, and fails if any tool the model can be offered resolves to no real gate action. Against a copy of the installed backend, `backend/test_agent.py` went from 311 passed / 4 failed to 315 passed / 0 failed.
