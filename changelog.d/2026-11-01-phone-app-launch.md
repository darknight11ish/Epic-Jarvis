- **Jarvis can open one of your own apps on your phone, and start a media search in it (2026-11-01).** The owner asked in these words: "id like jarvis live to be able to open certain apps on my android phone if i ask it (during a live session on my android phone) and to be able to perform certain actions like if i aaid 'hey jarvis open yourube music and play the weekend'". The `control_phone` tool's list of actions stopped at tap, swipe, key, text and screenshot, so the one thing the module underneath had known how to do since 5A could not be asked for at all; it now also offers `open_app` (Android's own launcher: `adb shell monkey -p <package> -c android.intent.category.LAUNCHER 1`), `play` (`am start -a android.intent.action.VIEW -d <the app's own search address> -p <package>`, so "play The Weeknd" opens YouTube Music on `https://music.youtube.com/search?q=The%20Weeknd`) and the read-only `list_apps`. The owner's permission is a new `[phone_apps]` table in `jarvis-framework.toml`, one line per app - the name you would say out loud, and the package behind it - and it ships EMPTY, so a fresh install can open nothing; anything not on that list is refused in plain words before any card exists, and the refusal names the apps that are allowed. The words of a search are percent-encoded (`;`, `&`, quotes and `$(...)` arrive as `%3B`, `%26`, `%22`, `%24%28...`) and the finished address is checked against a strict pattern, so nothing the owner says can become a second command on the phone's own shell. A list-only call and a refusal raise **no** approval card (there is nothing to approve); a real plan still goes to the same `jarvis_android_control_run` action at the same `ask` tier, with every literal command printed on the card, and the tool is still opt-in - `control_phone` is not in the shipped `[tools].enabled`. Two gaps found on the way and fixed in the same change: `device` is now optional and resolved from `adb devices` (exactly one connected phone, or a plain refusal - before this the tool was unusable by voice, because "open YouTube Music" carries no serial and the model was never told one), and `am start`/`monkey` report a launch they could not make on stdout while still exiting 0, so `run()` now reads that instead of reporting `done` for an app that never opened. A third was worse and closer to the point: `run()` refused every step that sends input while the Jarvis app is in front - which is exactly where it is during a Live session on the phone - so `open_app` and `play` are now `PACKAGE_PINNED_ACTIONS` and skip that guard, because both name the package in the command itself and a `com.jarvis.` package is refused before a command exists, so neither can tap inside Jarvis (a `tap` is still refused there). Honest limits: `play` opens the app on a search for those words - whether the music starts without one tap is the app's business, and both the tool text and the card say so; only YouTube Music has a known search address today, so any other app can be opened and not searched, and Jarvis says exactly that rather than pretending; opening a media app takes it to the front, so a Live session on that phone is backgrounded by the thing it asked for; and the exact intent behaviour on the owner's own phone is verified separately on the real device, not in this repository.
