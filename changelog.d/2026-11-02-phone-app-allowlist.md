- **The apps Jarvis may open on your phone are now managed by approval card: add one, remove one, in chat or in Settings (2026-11-02).** The owner asked in these words: "any apps that i ask if to open or do something with. i would need to approve a card with the apps i would like it to manipulate first and i can remove or add any android app to that list any time with an approval card... or by going to the settings and changing it there too." PR #1067 gave Jarvis the ability to open a listed app on the phone, but the list that permits it (`[phone_apps]` in `jarvis-framework.toml`) ships EMPTY and could only be filled by hand-editing that file, so the feature could not be used at all without a text editor. It now has a management: a new `phone_apps` model tool (`list` / `add` / `remove`) in chat and in Live on both apps, and two routes for the settings screens - `GET /api/phone/apps` (read-only, the allowed apps by the names the owner wrote, and whether Jarvis can also search in each one) and `POST /api/phone/apps` (ONE app, and it raises ONE approval card first). **Every add and every removal is one card that names BOTH the friendly name and the exact package id** - `Let Jarvis open "YouTube Music" (com.google.android.apps.youtube.music) on your phone?` - and nothing is written until a person approves it; a denied card, a timed-out card, and a call refused before a card exists all leave the settings file byte-for-byte unchanged. **There is no bulk path**: one call carries one app, the tool's schema has no array for apps, and a list where a string belongs is refused in the owner's words before any card. The one line is written through the same config layer the other settings use (`jarvis_phone_apps.write` follows `jarvis_limits.py`/`jarvis_notify_prefs.py`: the owner's own text changed by exactly one line, the whole file re-parsed and compared, an atomic `os.replace`, then `reload_framework()` so the next message sees it - no bare `open(path, "w")` anywhere), and each applied change writes one local audit line, `phone_apps.added` or `phone_apps.removed`, naming the app and the package. The gate mapping needed no new action and no new patch: the tool is put to the gate under the existing `change_setting` key, which the published gate base already maps to `change_own_config` at its existing `ask` tier - the same action the other settings changes use - and `backend/test_phone_app_allowlist.py` proves that mapping is load-bearing (the tool's own name is not a gate key, so without it the gate would answer `unclassified_tool`); pre-fix the suite fails because the tool does not exist. `phone_apps` ships ON in `[tools].enabled`, because a tool that is itself the only way to fill a list that ships empty cannot be gated behind a hand edit of the same file; what it can reach is that ONE table, and `control_phone` - the tool that actually opens apps - is still opt-in, still `ask`, still one card printing every literal adb command. The chat/Live tool and the PC Settings write route are ONE permission model, not two. Honest limit, said plainly: the phone's Settings is a READ-ONLY list plus "ask Jarvis to add an app", not an editor - typing a friendly name AND a package id is deep config editing, which the standing rule keeps off the phone, and the phone is the one device that cannot look a package up; the owner's "or by going to the settings and changing it there too" is answered by the PC's Settings and by the same card from the phone's chat (record: `docs/DECISIONS.md` 2026-11-02, `docs/ARCHITECTURE.md` §8, `docs/JARVIS-API.md` §176). The desktop Settings section and the phone's read-only screen are the remaining half of this slice and are named in the PR body rather than claimed here.
