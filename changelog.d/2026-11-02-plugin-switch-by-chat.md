- **Plugins by chat: Jarvis lists its drop-in plugins and turns ONE on or off, one card per change (2026-11-02).** The owner decided: "Jarvis may list plugins and turn them on/off by chat, one card per change." Two existing facts made this a small door rather than a new system: `jarvis_plugins.py` already discovers every feature folder in `jarvis_plugins\` beside `jarvis_hud.py`, already switches one off with a `disabled` marker in that folder (or `"enabled": false` in its plugin.json), and already names every load, skip and failure in `status()`. Two model tools in `backend/jarvis_agent.py` now reach that from either app's chat: `plugin_list` names every plugin, whether it is on, and why it is off - a `disabled` marker, a hand-edited `plugin.json`, a load that failed (with the loader's own reason), a broken manifest, a folder added after Jarvis started, or a plugin whose folder has gone since (still running until the next restart) - and a missing plugin folder says so instead of showing an empty list. `plugin_switch` turns ONE named plugin on or off. **ON raises ONE approval card under the EXISTING `modify_own_code` action** (a plugin is program code that runs inside Jarvis at start-up, and the gate already ships that action at "ask"); **OFF is immediate and cardless**, the project's own on/off rule, because stopping only narrows what runs. Nothing here approves anything, and the tool is in `NEEDS_A_PERSON` as the belt: a loosened tier cannot switch a plugin on with nobody asked. **What a toggle means is said plainly, never pretended:** the loader runs once at HUD start-up, so neither direction is live in the running process, and every answer says the change lands the next time Jarvis starts and that Jarvis cannot restart itself - nothing restarts the backend. **No second mechanism and no delete:** OFF creates the loader's own `disabled` marker (`O_CREAT|O_EXCL`), ON removes that same marker and only after the folder and its `plugin.json` are still there; no folder is created, moved, renamed or deleted, `plugin.json` is never rewritten, and a plugin switched off in its own manifest is reported and refused as a hand edit. **No bulk, and no new route:** the schema takes one plugin name and an `on`/`off` action with no array, so a call naming two plugins is refused before anything is prepared; there is no `GET`/`POST` for any of this, no Rust command and no app screen, so `tools/check_parity.py` is unchanged and clean, no gate action, tier line, risk row or card wording is invented, and the card is the existing `modify_own_code` row already on the "What asks first" page. Both tools ship ON in `[tools].enabled` (a feature reachable only by hand-editing that same list would not be reachable by chat), are listed in `jarvis_reach.TOOL_NAMES`, sit in the `settings` short-list group, and carry tool-diet hints; `tools/tool_eval/jarvis_tools.json`, `reach-cases.json` and `private-aloud-cases.json` were regenerated by their own generators. The feature is on both apps' Features pages (`plugin-switch`), and `docs/ARCHITECTURE.md` §8 records why neither app has a screen for it. `backend/test_plugin_switch.py` proves the list, the states, the read-only snapshot, the immediate OFF, the one card and the denied/timed-out/loosened refusals, the unknown-name refusal, no bulk, no delete, and a manifest-off plugin left unrewritten; the record is `docs/DECISIONS.md` 2026-11-02 and `docs/JARVIS-API.md` §180.
