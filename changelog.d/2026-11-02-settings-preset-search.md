- **Typing "presets" into the phone's Settings search now says where the focus presets are and opens them, instead of hiding every card and answering "Nothing here matches" (2026-11-02).** The owner's report: *"also, when i search presets in the settings in the android app, nothing comes up."* Asked which presets, he chose the **focus presets**. Measured on `origin/main` with a throwaway JVM probe before any change: the Settings box answered `[]` for **"presets"**, **"preset"**, **"focus"**, **"focus presets"** and **"hardware"** - every one of the five words he might type - while the app's own "Find anything" box already answered `settings.focus-presets -> BRAIN/hardware` for four of them. So the bug was a dead end, not a missing feature: the nine presets are drawn inside the Brain's Hardware plate (`HardwarePlate.kt`'s `FocusPresetsSection`, titled "Hardware"), the Settings box is a filter over Settings' own rows (`SettingsSearch.ROWS`), and there is no honest Settings row to add - they are the PC's presets and applying one raises an approval card there. The fix is the box's third answer: `SettingsSearch.ELSEWHERE` is a hand-written, testable list of features that are not in Settings (one entry today), each naming the catalogue row whose title and `names` are its search words - "presets", "the focus presets", "the focus preset selector" and "focus presets" come straight from `MenuCatalog`'s `settings.focus-presets` row, and "hardware" is the plate's own item key - and each opening the place through `FindAnything`'s existing table, so the Settings row and the Find box can never point at two different places. The screen draws it under the search box as `Not in Settings: Focus presets` / `It is in Brain, under Hardware.` with an `Open` action, and `MainActivity` opens it with the same one-time `pendingSection` + `nav.go` scroll the Find box uses - no new route, no new screen, no switch, no config write, no approval card, and `SettingsSearch.matching`/`ROWS` are untouched, so every existing search answer and the shared cross-app fixture are unchanged. Tests: `SettingsSearchTest` gains five checks that compile only against the new API and pass green (full suite from `jarvis-client`: `gradlew.bat testDebugUnitTest --offline` -> BUILD SUCCESSFUL, exit 0, 282 classes, 3,115 tests, 0 failures, 0 errors, 0 skipped) - the five words find the row and the near-misses ("voice", "security", "zzzz", an all-spaces query) do not, the row's two printed sentences are asserted word for word, the target is Brain's real `hardware` plate (checked against `BrainSections.SECTIONS` and the plates' own headings), every entry is a real *phone* catalogue menu with no `MenuPlaces.SETTINGS` row of its own, the Settings screen really asks for these rows and really calls back, and the Find box's answer is measured to be the same place. Honest limits: nothing here was driven on a real phone - the row, its two lines and the tap that lands on the Hardware plate are NOT-TESTABLE without the device, and this change is compile-and-JVM-tested only; the APK that goes on the phone is still CI's.
