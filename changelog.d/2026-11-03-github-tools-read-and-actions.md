- **Jarvis can read your GitHub, and take three small actions on it - each behind its own card, and it can never merge, push or close (2026-11-03).** The owner's decision was "Read + actions": six tools in `backend/jarvis_github.py`, and one module that talks to `api.github.com` and nothing else. Three read: `github_list` (your repositories, a repo's open pull requests, its open issues, its recent workflow runs - a closed set of four names, never an address the model wrote), `github_read_file` (one file, at an optional branch) and `github_ci_status` (the newest run for a branch or a pull request). Three act, one card each: `github_comment`, `github_open_issue` and `github_rerun_workflow`. All six ask a person every time - the reads included, because a read still sends the GitHub token saved on this PC out to a server - and they are in `NEEDS_A_PERSON` as well as at tier `ask`, so loosening the setting cannot make one run with nobody asked. They are deliberately NOT the existing `github_read` action, which is the scheduled look a "tell me when" GitHub watch makes and must stay `auto`; their own action is `github_inspect`. There is no merge, push, commit, delete or close ANYWHERE: no planner, no endpoint and no tool, and the words say why. The token is never printed, a redirect is refused rather than followed, every answer is bounded, and every failure is a sentence with no HTTP code in it. `backend/github-tools.patch` gives the gate its four actions, since `jarvis_gate.py` is not shipped whole. All six ship SWITCHED OFF, like `github_search`; add the names to `[tools].enabled` and say "connect GitHub". Proved by `backend/test_github_tools.py` (184 checks, no network, no real token: a socket opened anywhere in it fails the run).
