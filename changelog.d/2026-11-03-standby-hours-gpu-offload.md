- **Jarvis can free the graphics cards in hours the owner sets, and wake on the next question (2026-11-03).** The owner asked "jarvis should have the ability to offload the gpus during standby hours: can i set standby hours for you?" and chose "Unload the GPUs in my hours". The keys were already in his `[power]` section and **read by nothing** - the file annotated `schedule_mode` and `idle_mode` `# not read`, and it was right: `jarvis_power.current()` returned a hard-coded `"quiet"` inside the window and never called `should_standby()` at all, so a window he set could never be anything but Quiet and freed nothing. Now `current()` returns `schedule_mode` inside the window and `idle_mode` when the idle timer runs out, still computed from the clock on every call with no background thread flipping a variable and no second copy of the mode anywhere; a mode the owner chose always wins, and a `manual` flag stops the window overruling his own tap until the clock's answer next changes (which his settings file already promised at line 1492). A new `enforce()` makes the clock's answer real: it calls `jarvis_power_switch.set_mode("standby", why="the standby hours", force=True)` - the ONE function here that unloads, the same call a tap on Standby makes - so every model on every card is freed through the existing path and the answer says which, and at the window's end it wakes only a standby its own rules made, warm-up included. `force` is what stops the feature shipping broken: inside the window `current()` already READS standby while the stored mode is still `active`, so without it `set_mode` answers "Already standby." and frees nothing. **Nothing is unloaded while something is using it** - a multi-step task, a turn being answered (`jarvis_events.activity()` at `thinking`/`speaking`/`working`), a Live conversation, or a waiting approval card each hold it off with a plain reason in `status()["last_hold"]`, and the same guard sits in `set_mode` before the card and again after it, so a tap on Standby gets the same 409. The setting is four rows in `jarvis_limits.LIMITS` - "Keep Jarvis quiet during my hours", "Unload the graphics cards during my hours", "My hours start", "My hours end" - so both apps draw it from the one table with **no client change** (kinds `bool`/`time`, `app` `"both"`, `pc_only` False, the unload row a switch over the word `standby`/`quiet`), defaulting to today's behaviour (off, quiet, 23:00-07:00) so a PC that never touches it behaves exactly as before and starts no ticker; all four carry `always_asks` and go to the `change_own_config` card in either direction, and a value set to what it already is raises none.
