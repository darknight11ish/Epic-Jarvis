- **Jarvis only asks for your voice on a locked phone, and that is one setting you can change (2026-11-03).** The owner's ask, in their own words: *"did you fix jarvis needing to confirm my voice when i click the mic for a one time verbal input? … my voice should only need to be confirmed if i say hi jarvis when the phone is locked … when i start jarvis live on my unlocked phone i dont want it to need to confirm my voice. make this a setting i can change"*. Two of the three asks were already true before this change and are now held by a test: the phone's mic press has run no owner check since 2026-11-02 (`jarvis_speech._is_quick_message`, `_QuickMessage`), and "hi Jarvis" on the phone has always been checked. The gap was the third: `jarvis_live.Live.trust_decision()` demanded a full sentence and then ran the strict check on the FIRST clip of every Live session (the 2026-11-01 "verified once per session" rule), so starting Live from an unlocked phone still asked. There is now ONE decision - `backend/jarvis_live.py`'s `voice_check_needed(trigger, device, locked, setting_on)` - with one docstring stating the seven steps in order and exactly four cases: (a) the mic press never checks; (b) "hi Jarvis" while the phone is LOCKED checks, and it is the only check left (an UNLOCKED phone's "hi Jarvis" is meant to skip too, but the wake route cannot carry the lock state until the patch wave, so that clip is still checked today - MORE than the rule asks, never less: DEF-033); (c) Live started from an UNLOCKED phone does not check; (d) ONE setting, `voice_check_locked`, ON by default, and its two directions run opposite to "a check": ON is the EXEMPTION the owner asked for, so turning it ON is the looser direction and raises ONE `change_own_config` approval card, while turning it OFF is at once because it withdraws the exemption and gives the OLD, FULL checks back - the phone's "I am unlocked" is then ignored, and OFF is never "no checks". The phone sends its own screen-lock state as one new field on the EXISTING `POST /api/voice/live` start body (`"locked": true|false`, `jarvis-client`'s `VoiceCheckRule.lockedField`), and nothing else: no new route, no new permission, no new tier. **Fail closed, and the old behaviour is the fallback:** `locked` is believed only when the phone really said true or false; a missing value (every app older than this change sends none) reads as "did not say" and keeps the check, and a session on the DESKTOP keeps the 2026-11-01 rule unchanged because a PC has no locked phone. A phone Live session started from an unlocked phone runs no speaker model at all, and because its "trusted" verdict carries no strictness, nothing that needs a real check is read aloud on it - the session earned no privilege, it simply was not asked to prove itself. The one setting is read and written through the SAME existing Live route (`{"do":"voice_check"}`, with no `enabled` meaning read), so no route was added; its file (`<config>/live/voice-check.json`) holds one boolean and a damaged file reads as ON, never off. **The desktop has no switch for it yet and that is reported, not hidden:** the phone's Settings, Voice card carries the toggle ("Only check my voice on a locked phone"), the spoken phrases work on both apps ("turn off only checking my voice on a locked phone"), and `contract/feature-controls.json` records the missing desktop row as a gap (`planned`, owner `setup-ui`). Proved by two new suites: `backend/test_voice_check_rule.py` - 61 checks, 0 failed - holds the four cases row for row, the fail-closed rows, the card semantics (ON is 202 while one card waits, a denied card changes nothing, OFF withdraws a waiting card), and drives the real `jarvis_speech.hear()` with `jarvis_voice.verify` counted to prove a phone mic press never reaches the speaker model, and `jarvis-client`'s `VoiceCheckRuleTest` holds the phone's copy of the same table plus the start body's exact bytes and the corrected Live-screen sentence. `backend/test_live.py` stays green (414 passed, 0 failed) with its "Live writes no file" pin NARROWED and proved harder rather than dropped: the one save function is cut out of the source before the search, and the file it writes is read back and must hold one boolean and nothing else. The shared `live-cases.json` fixtures are untouched, because the setting deliberately adds no `status` field - a status key would have rewritten both apps' fixture for one boolean.
