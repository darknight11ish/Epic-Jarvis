- **A GitHub watcher has to earn the right to interrupt: `observe` mode, ONE message per pull request, and no approval card lost across a restart (2026-11-04).** A background watcher that speaks about every check is a watcher the owner mutes, so the four mechanisms the owner adopted from the `dsh-superagent` spec (Part II patterns 1, 2, 3 and 5B) are now built natively. **Pattern 1:** `WATCH_MODES = ("off", "observe", "active")`, and a new proactive rule defaults to `observe` - it runs the whole pipeline (poll, batch, gate) and writes one structured decision row instead of interrupting, served by the new `GET /api/watch/decisions?limit=50` with a CLOSED reason code (`ci_all_required_green`, `ci_required_failed`, `ci_still_running_debounced`, `duplicate_sha_state`, `observe_shadow_logged`, `filtered_bot_actor`, ...) and `preview_text`, the exact one-line message that would have been shown. **Pattern 2:** a pull request is one thread, `pr:<number>:<head_sha[:9]>`, because its seven required checks (`rust`, `frontend`, `backend`, `backend-windows`, `credential-manager`, `powershell-5`, `phone-unit-tests`) finish minutes apart: any required failure speaks ONCE immediately, all seven green AND mergeable speaks ONCE, and while any required check is still running with none failed it says nothing (`ci_still_running_debounced`). `audit` and `python-advisories` are informational - red on `main` while merges land - and are dropped by name before any count, so they can never trigger a notification. Idempotent receipts in `watch-receipts.json`, keyed `(pr_number, head_sha, terminal_verdict)`, mean twenty polls of one commit alert once, while a re-run that changes the verdict is a second, genuinely new sentence. **Pattern 3:** the gate is `backend/jarvis_watch_policy.py`, which imports nothing from Jarvis and nothing that can reach a disk, a network or a model - so "a filtered event never reaches the costly stage" is structural, not promised - and `assess()` runs only for a failed REQUIRED check, reading the failing run's log through the same `gh` path the poll uses. No model is called: the summarizer seam exists and nothing passes one. **Pattern 5B:** `backend/jarvis_outbox.py` writes every parked approval card and every job-completion notice to `outbox.json` with a deterministic `(kind, key)` BEFORE it is published (temp file, flush, rename), and `jarvis_jobs._init()` re-announces whatever is still owed, once per process - which closes the restart card loss, where the job row survived but the event that told the apps about it did not. A card is settled by being ANSWERED, not by being announced, so an unanswered card survives a restart; rehydration approves nothing. The limit is stated rather than hidden: this is at-least-once, so a crash between the send and the settle repeats one notice, never loses one. Nothing is always-on - the watcher is a job body (`watch_pr_checks`) that runs only when a job names a pull request, asks `github_read` before it reads GitHub, and starts no thread or timer - and nothing here pushes, merges, labels or comments. `backend/test_watch_ci.py` (139 checks) and `backend/test_outbox.py` (63) are plain Python with a fake clock and a fake `gh` runner, and they prove observe-vs-active (observe calls the notifier ZERO times), the quiet period, fail fast, the all-green settle, informational checks ignored, duplicate-receipt silence, `gate` never calling `assess` for a filtered event, and a crash between the write and the send being delivered exactly once afterwards. Both new modules are shipped whole (twin files in `jarvis-backend/`), the route comes from the drop-in folder `plugins/ready/watch-decisions/` rather than a patch, and `docs/JARVIS-API.md` §185 and `docs/ARCHITECTURE.md` §14 document it.
