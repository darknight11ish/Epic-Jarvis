- **Jarvis can now measure its own token speed on this PC, and the first phase of the self-benchmark is in the backend (2026-11-04).** The owner's ask was for Jarvis to measure its own speed across the local models, the RAM/GPU layer placement and the context sizes, keep a separate history of those runs, and explain the results in plain words. Phase 1 is the measurement engine and its store, with no screens yet: one run is one model + one setup + N repeats on one lane, and a run refuses rather than measuring the queue - a 409 with a sentence when another run is in flight, when an answer is streaming, when Jarvis is on standby, when a task is running, when the lane's Ollama is not running, or when the model is not installed on that lane; a 400 when Ollama's address is not this PC, and a 400 that measures nothing when the POST carries no `confirm` block. **Prompt speed is `(prompt_eval_count - prompt_eval_cached_count) / prompt_eval_duration` and never the naive division**, because `prompt_eval_duration` times only the tokens Ollama actually computed while `prompt_eval_count` counts the whole prompt: in the measured example (318 tokens, 317 cached, 23 ms) the naive sum reports 13,826 tok/s where the model really read one token at 43 - a 318x lie from two correct numbers. A fully cached prompt is reported as "cached - prefill not measured" (never 0, never infinity) and an absent cached count is unknown (never 0). Generation is `eval_count / eval_duration`, BOTH time-to-first-token numbers are stored and the row says so when they differ by more than 15%, VRAM and utilisation are sampled per CARD from `nvidia-smi` (per-process VRAM is `[N/A]` on driver 617.42), and the context really in use plus the `offloaded N/M layers` come from `/api/ps` and the log parser `jarvis_hardware.parse_ollama_log` already had. Rows go to a NEW `~/.openjarvis/bench.jsonl` with its own allowlist, two flat row kinds, a 500-run cap and a 2 MB ceiling; **`speed.jsonl` is never opened**, so the existing chat-speed rows and the screen that reads them are untouched. A run that cannot measure writes `ok: false` + `why` and never a zero, and a run that put part of the model on the processor is labelled PARTIAL and its numbers are never presented as fast. The advice sentence of DESIGN section 9 is here too, and it refuses to compare anything under three runs of the same model. Five routes reach it (`GET /api/bench`, `POST /api/bench/run`, `GET /api/bench/run/{id}`, `POST /api/bench/cancel`, `GET /api/bench/history`), wired by a new `backend/bench.patch` whose two hunks anchor inside `hardware.patch`'s own added blocks and which invents 0 hunks / 0 lines of the owner's original file. NOT done yet, deliberately: the desktop Benchmark panel, the separate History window, the benchmark presets and the `benchmark_results` chat tool, the `/api/bench/advice` route, and the phone's screen - phases 2 to 5. No benchmark has been run for real: every number in `backend/test_bench.py` comes from a fake Ollama reply and fake `nvidia-smi` text, and one real run is a field test, not a test.
