- **Every tool's full dossier, so Jarvis can hold a real conversation about its own abilities (2026-11-04).** A new shipped module, `jarvis_tool_profiles.py`, carries ONE hand-written, code-verified page for each of the 51 tools in `jarvis_agent.TOOLS` and one for each of 11 capability families (memory, files, web, email and calendar, home and phone, computer control, notes, routines and goals, money, coding, self-knowledge). Each page says what the thing is in beginner words, what it really lets the owner do, what it touches, what it honestly refuses or needs switched on first, which other tools it pairs with and what the pair enables, how it is turned on, and the repository files that prove every claim. Since main's D4 (2026-11-04) every tool the model can be offered has an in-app `Settings -> Tools` switch, so each dossier names that row - the 13 that were already on in the shipped list say so and need no action, the three whose own switch decides them name that switch, and `settings-file` stays a documented state that no tool is in. Three pure functions turn a question into either a deterministic plain answer (`answer_about`), `None` when no tool is clearly named so the model answers instead, or a compact context block of at most 1200 characters for a system prompt (`context_for`); `names()` and `profile()` round it out. Nothing here runs a tool, reads a file or opens a connection - it is data plus stdlib only, and the wiring into the chat pipeline is a separate change. `backend/test_tool_profiles.py` proves the coverage against the real dict, the shapes, and the load-bearing claims against the real sources: every tier is re-derived from the shipped `[tools].enabled` list and the asks-first tiers, both off-by-default tools are shown to ship off, REA's `HARD_DENY` is shown to refuse live process capture, and the sandbox's own import allow-list is shown to hold no network module.
