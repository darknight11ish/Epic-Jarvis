The cause was not the chain 5b rule but the probe's isolation. The checker's sandbox gave every probe a fresh home and log folder but left the CONFIG folder alone, so `jarvis_phone_notifications.settings()` read the owner's live `%USERPROFILE%\.openjarvis\phone-notifications.json` (present, `{"enabled": true}`), found it valid, and returned from its "file present" branch. The chain5b mutation puts a text field on the FileNotFoundError branch, so it was never reached and the probe reported PASS on a tree it was supposed to reject. CI never saw it: a runner has no such file, and `backend/run_suites.py` hands each suite a private `OPENJARVIS_CONFIG_DIR`. Now the probe sandbox points `OPENJARVIS_CONFIG_DIR` and `JARVIS_CONFIG_DIR` at an empty folder of its own, so a probe measures the shipped module and never the machine; a new check hands the checker a caller config folder holding a valid settings file and requires the mutation to be caught anyway. Measured from the worktree: `py -3 -B backend/test_injection_chains.py` is 71 passed, 0 skipped, 0 failed (was 65/0/3); `test_base_matches_repo.py` 136/0; `check_stale_twins.py` clean; `test_base_regeneration.py` 39/0.
