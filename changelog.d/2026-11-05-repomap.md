- **Jarvis can map a project's folder without being able to change a single byte of it (2026-11-05).** The first piece of "Jarvis as a project worker", built in the order the 2026-11-05 project-management audit and Gemini's ruling fixed: a **read-only repository map FIRST**, before project-scoped chat and before any staged diff. `backend/jarvis_repomap.py` walks ONE folder that is already on "Folders Jarvis may look in" (the same `jarvis_documents.allowed_path()` boundary the files tool uses, checked again on every file), honours `.gitignore` per directory including `!` negation, reads Python with `ast` and JavaScript, TypeScript, Kotlin and Rust with a conservative signature/import scan, and ranks what it finds for a question by a formula written out in the module docstring: 12 per question word in a declared symbol name, 6 in a file or folder name, 2 in an import, 4 when a matched file imports this one, 1 the other way, plus a small size tie-break. It packs the result into at most 2,000 tokens (default 1,500) counted exactly the way `jarvis_agent.estimate_tokens` counts, listing names and signatures only and never a function's body. It is reached by `GET /api/projects/<id>/map?q=…&tokens=…` on the project store's own route table, and from chat as one more action on the existing `my_files` tool (`map`, by project id or by a listed folder). It writes nothing at all - no index, no cache - runs no program, opens no socket, calls no model, adds no gate action and no card (it is a read, under the existing `read_files_readonly` line), and a folder that is not on the owner's list is refused in one plain sentence rather than guessed at. `project_edit` is still not built: this is the read that makes the later write worth trusting.
