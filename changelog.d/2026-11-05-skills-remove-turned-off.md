- **A skill you turned off can now be removed; before this it could never leave the PC (2026-11-05).** The Skills list in Settings has had Add and Remove since 2026-11-02 (PR #1092): install from a folder, a `.zip` or the read-only Hermes scan behind ONE `modify_own_code` card, and Remove on an installed skill through the same `brain_remove_skill` command the Brain already used. The one thing neither door could reach was a skill that had been TURNED OFF: it is moved to `skills-off\`, and `jarvis_skills.uninstall` resolves a name only under the skills folder, so the Brain's Remove and the phone's Remove both answered "no skill called ..." and the only way out was to turn it back on (one card) and then remove it. The turned-off list now carries its own **Remove...**, with the same "are you sure?", sending `{"name": ..., "remove": true}` to the existing `POST /api/skills/state`: it deletes that one parked folder and its row in `skills-off\.off.json`, and nothing else. No card, because the skill is already out of the load path and nothing is offered from it - the same rule that makes turning one off immediate, and the same rule `jarvis_skills.uninstall` has always followed for an installed one. ONE name per request; a name that is installed is refused (that removal is unchanged and stays the only door to it), `remove` and `on` in one request is refused, and there is no list form. The phone gains nothing here on purpose - its list never shows a turned-off skill, and no route may let a client delete a folder it cannot see (`docs/ARCHITECTURE.md` §8). Proved by `backend/test_skill_menu.py` (200 checks, including the one that shows the old removal really cannot see the parked copy) and `jarvis-desktop/tests/skills-menu.mjs`; recorded in `docs/JARVIS-API.md` §178 and `decisions.d/2026-11-05-skills-remove-turned-off.md`.
