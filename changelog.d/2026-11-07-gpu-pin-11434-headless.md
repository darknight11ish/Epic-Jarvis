- **The Ollama server on port 11434 is pinned to the headless RTX 2080 SUPER by UUID, and the CPU spill ends (2026-11-07).** Both Ollama servers were on the RTX 2060: the everyday lane on 11436 (`qwen3.5:9b`) and Ollama's own tray-app server on 11434 (`qwen3:8b`), whose load plans add up to 15,512 MiB on a 12,288 MiB card. `ollama ps` reported both as "100% GPU, 0 spill" and that is Ollama's load plan, not memory: Windows' own per-process GPU counters (`\GPU Process Memory(*)\Dedicated Usage`) measured the 9B holding only 5,545 MiB in VRAM with 3,856 MiB paged out to system RAM, while the headless 2080 SUPER sat at 0 of its 8,192 MiB. Pinned to `GPU-1f7e38f5-...` on a throwaway 11451 server, the same `qwen3:8b` is fully resident at 6,142 MiB in VRAM against a 5,991 MiB plan (6,141 of 8,192 MiB on the card) and reads 66.38 tok/s cold / 69.38-71.17 warm against 50.4-50.7 on the shared 2060. No repository code starts the 11434 server - the Ollama tray app does - so the deploy step is a logon task that starts that app with `CUDA_VISIBLE_DEVICES` and `OLLAMA_VULKAN=0` set for that process tree only, plus moving the app's own autostart shortcut aside so only one instance starts; a global per-user variable was measured to the same numbers and is NOT recommended, because it would pin every future CUDA process on the PC, other AI tools included. `docs/MODEL-TOPOLOGY.md` carries the evidence, the exact wrapper/task/rollback commands, the task-owned `start-lane.ps1` alternative (also measured), and the deploy verification that does not trust `ollama ps`. No live server was restarted or killed in this change.
