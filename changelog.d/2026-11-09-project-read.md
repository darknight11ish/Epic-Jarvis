- **Jarvis can read one code file inside a folder you listed - and it asks nobody (2026-11-09).** The read half of the approved "Jarvis takes over dev work" plan is one new model tool, `project_read`. It closes a real gap rather than renaming one: `file_read` reads any text file but has **no** check against "Folders Jarvis may look in" at all, and `my_files`' `read` refuses code outright (`TEXT_KINDS` is md/txt/csv), so "read this Python file in my project" had no bounded door. It is a composition of two things that already ship: `jarvis_documents.allowed_path()` - the one folder boundary the files tool uses - asked for the folder and then for the file, and `jarvis_repomap._walk()`, the only `.gitignore`-aware walk in the tree, with that module's own 512 KB per-file cap. So `..` traversal, whole paths (a drive letter, a UNC name), a link that resolves outside the folder, a hidden folder, a "Protected from Jarvis" item and a path the map would not list are all refused - by the existing code, in one plain sentence, never a stack trace - and the two readers cannot disagree about the same file. It adds **no approval card and no gate action**: it is decided under `file_read`'s own `read_files_readonly` (tier `auto`), the same shape the repository map shipped with, and nothing is written, moved or sent. It has its own switch on Settings, "What asks first" (the repo's 2026-11-04 rule makes every offered tool a switch; the switchable count is 61 now), ships OFF like `file_read`, and adds no screen to either app. Said plainly where it matters: "`.gitignore`-aware" is **not** "tracked files only" - an ignored file is skipped, an untracked one that is not ignored is read. Proved by `backend/test_project_read.py`: 81 checks, including the real `jarvis_gate` and the real `_one_call` driven with the shipped tier table, where exactly one gate call is made under `read_files_readonly`, the step records `"outcome": "auto"`, and nothing is left pending.
