- **Jarvis can read one code file inside a folder you listed - and it asks nobody (2026-11-09).** The read half of the approved "Jarvis takes over dev work" plan is one new model tool, `project_read`. It closes a real gap rather than renaming one: `file_read` reads any text file but has **no** check against "Folders Jarvis may look in" at all, and `my_files`' `read` refuses code outright (`TEXT_KINDS` is md/txt/csv), so "read this Python file in my project" had no bounded door. It is a composition of two things that already ship: `jarvis_documents.allowed_path()` - the one folder boundary the files tool uses - asked for the folder and then for the file, and `jarvis_repomap._walk()`, the only `.gitignore`-aware walk in the tree, with that module's own 512 KB per-file cap. So `..` traversal, whole paths (a drive letter, a UNC name), a link that resolves outside the folder, a hidden folder, a "Protected from Jarvis" item and a path the map would not list are all refused - by the existing code, in one plain sentence, never a stack trace - and the two readers cannot disagree about the same file. **It can read a line range, so a big file is never silently cut:** `start_line` and `lines` are optional whole numbers (default 1 and 400, hard cap 2,000, and a slice is also capped at 96 KiB of text, so one answer cannot overflow the model's context). A range returns numbered lines carrying their REAL file line numbers plus `start_line`, `end_line`, `total_lines` and `line_cap`, while a read with neither argument is the whole file exactly as before. When more follows, ONE deterministic footer rides in a new `more` field - never inside `content`, which the model reads as source code - word for word "Showing lines A–B of N; request the next line range to read more"; a file over 64 MiB is not counted line by line, so its footer says the exact total is unknown and that a range can still be asked for, and a whole-file read cut at 512 KB carries the same footer so the next range can be asked for. **And a credential file is refused by name**, with one plain sentence ("That is a credential file ..."), even inside a folder the owner listed: `.env` and `.env.*`, `.netrc`, `.git-credentials`, `.npmrc`, `credentials`, `credentials.json`, `id_rsa`/`id_ed25519`/`id_ecdsa`/`id_dsa`, the `.pem`/`.key`/`.pfx`/`.p12`/`.kdbx`/`.jks` extensions and any path with a `.git` folder in it - while `key.py`, `keys.py`, `env.py` and `credentials_migration.py` still read, because the check is the name only and never opens the file. Said plainly: before this, `id_dsa`, `credentials` and `credentials.json` were genuinely readable, and the rest were already refused by the folder boundary's own list but with the wrong words (a `.env` INSIDE a listed folder was told the folder was not listed). It adds **no approval card and no gate action**: it is decided under `file_read`'s own `read_files_readonly` (tier `auto`), the same shape the repository map shipped with, and nothing is written, moved or sent - proved again with a SHA-256, size and mtime snapshot before and after a whole-file read and a line-range read, with no file added or removed. It has its own switch on Settings, "What asks first" (the repo's 2026-11-04 rule makes every offered tool a switch; the switchable count is 61 now), ships OFF like `file_read`, and adds no screen to either app. Said plainly where it matters: "`.gitignore`-aware" is **not** "tracked files only" - an ignored file is skipped, an untracked one that is not ignored is read. Proved by `backend/test_project_read.py`: 178 checks, including the real `jarvis_gate` and the real `_one_call` driven with the shipped tier table, where exactly one gate call is made under `read_files_readonly`, the step records `"outcome": "auto"`, and nothing is left pending.
