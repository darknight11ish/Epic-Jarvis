- **Jarvis can now write the fix itself inside a failing pull request's isolated copy, one file per card, and the existing carded push carries the commit (2026-11-10, wave 16B).** The 2026-11-10 GitHub record deferred exactly this in its own words - *"The scratch-scoped code-authoring tool that would let fix-and-push write its own fix is deliberately deferred to wave 16B"* - and this is 16B. `github_fix_and_push` gained two stages beside `prepare` and `push`: `read` shows one file from the copy and raises **no card**, because it sends nothing to GitHub, uses no token and changes nothing on this PC (the same rule every local read follows); `write` changes **ONE file** inside that copy and makes **ONE local commit** there, on its **own card** under a new action, `github_fix_write`, which ships `"ask"` in both settings files and is in `jarvis_agent.NEEDS_A_PERSON`, so a loosened tier line still asks. The card shows the pull request, the scratch folder, the file's path, the **exact change as a real unified diff** and the one-line commit message, and says plainly that no token is used and nothing is sent. The write can only reach a file inside the prepared copy for **that one pull request**: the folder must resolve under `JARVIS_GITHUB_SCRATCH_ROOT` and carry the prepare stage's own `.git` note naming the same repository and number, so the owner's live checkout and every other pull request's copy are refused; the path must be relative (a `..`, an absolute path, a drive letter, a UNC address, a NUL, a symlink or a Windows junction are all refused in a plain sentence); `.git` and every file on the **same credential denylist the push stage uses** are refused; a delete/rename/move/chmod argument is refused rather than ignored; only plain UTF-8 text is changed, so a binary or over-1-MB file is refused; and a change too big for one card (the card cap is 4,000 characters) is refused before a card exists, never shown cut. Before writing, `run()` re-reads the file and refuses if it changed since the card was shown (the same TOCTOU pin the merge has). A failed commit puts the file back and unstages it, so the copy is never left dirty. Nothing about the bans changed: force-push, squash/rebase merge, admin bypass, auto-merge, bypassing a required check, pushing to main, deleting or closing anything, approving a pull request, workflow dispatch and gists are all still impossible - `NEVER` lost only the two names that are no longer true (`edit_file`, `write_file`), because one file inside the copy *can* now be written. The push card still prints the real commits, files and `git push origin HEAD:refs/heads/<branch>` command, and still does nothing without its own approval. The tool surface is unchanged in count and switches: ten GitHub tools, all off, and one switch governs the whole fix flow. Proved by a new hermetic `backend/test_github_authoring.py` (96 checks: a real temporary git repository under a temporary scratch root, real git, the happy path with the commit and the card's diff, a new file, every refusal above with the file and the live checkout left untouched, a link escape driven on this PC, the TOCTOU re-check, the no-token/no-socket write, the push card's real commit/file/command and the unapproved push running no git command at all), plus the extended `test_github_tools.py` (599 checks), `test_github_parity.py` (535 checks), `test_short_tool_list.py`, `test_tool_text.py`, `test_card_words.py`, `test_asks_first.py`, `test_reach.py` and `test_github_self_knowledge.py`. `docs/JARVIS-API.md` §190.13 is the envelope and §190.4's old "no tool that edits or commits code" sentence is corrected. Not deployed; the phone surface is unchanged (reads and card decisions only), and the write and push start from the PC.
