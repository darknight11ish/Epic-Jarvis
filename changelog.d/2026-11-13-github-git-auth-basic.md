- **GitHub's git endpoint needs Basic auth, not Bearer - so the prepare clone and the fix push can authenticate again (2026-11-13).** The live field test of `github_open_pr` / `github_fix_and_push` failed with "authentication issue" because `_git_auth_env` built git's `http.extraheader` as `Authorization: Bearer <token>`. GitHub's **REST API** accepts that form, which is why every GitHub read in the app worked, but GitHub's **git** endpoint rejects it: a direct `git ls-remote https://github.com/darknight11ish/jarvis-coding-field-test.git` with the Bearer header returned rc 128 with `remote: invalid credentials` / `fatal: Authentication failed`, while the same command with `Authorization: Basic base64("x-access-token:" + token)` returned rc 0 and listed the refs. `_git_auth_env` now builds the Basic form, and the comment beside it records that measurement. The token still travels only in git's own `GIT_CONFIG_*` environment (`http.extraheader`), never in `argv`, never in the remote URL, never in the folder's config and never in a log line; the one function is still what the prepare clone, the open-PR clone and both pushes use, so the stages cannot drift apart. `test_github_tools.py` decodes what git is actually handed and checks it is `x-access-token:<token>` (not a Bearer header), proves both stages ask that one helper, and `test_github_parity.py`'s two pins moved to the same truth. `docs/JARVIS-API.md` §190.10 (the fix-and-push envelope) now states the Basic form and the reason.
