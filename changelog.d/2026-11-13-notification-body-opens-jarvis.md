- **A toast's body click now names what it wants, and an approval's toast carries a working Open button (2026-11-13).** The owner's report: clicking the body of a "Jarvis Desktop" approval toast did nothing, where Windows' ordinary behaviour is that a click opens the app - and for an approval, that card. Measured on his own PC rather than guessed: the exact toast was still in Windows' own notification store (id 2566, group `jarvis-approval`, delivered 2026-11-13 17:51:50) carrying `activationType="foreground" launch="jarvis-open"`, its words and one Deny button; 34 seconds later Windows logged *"Some toast notifications have been cleared"*, and `jarvis-desktop.log` records **no** launch and no folded second instance at that time - the click reached Windows and stopped there. The installed Start Menu shortcuts carry the AUMID this app claims (`com.jarvis.desktop`) but **no `ToastActivatorCLSID`**, and Microsoft's own table for an unpackaged Win32 app says visuals and actions are supported without a COM activator while in-process activation is not - a body click carries no `arguments` for Windows to launch with, so it has nowhere to go. Changes: `winrt_toast.rs` now reads the toast's own launch marker (`jarvis-open`, or `jarvis-open:<card id>` for an approval) and answers it on **both** activation paths - the single-instance callback for a running Jarvis, and a cold start - which nothing did before; a click naming no card goes through `windows::show_hud` (the tray's, the hotkey's and an ordinary second launch's one door, which un-minimises and focuses), and an approval goes through `commands::open_approval_in_quickbar` with target `hud`, the same command `card-link.js`'s "Open the card" calls, so the toast cannot open a different surface. An approval toast now offers **Open** beside **Deny**, riding exactly the action activation Deny rides and carrying the same marker as its body click, so one press opens the card. Deny's own action XML is byte-for-byte unchanged, no window, tray icon or second focus path is added, and no capability or `tauri.conf.json` change was needed because the toast is still built in Rust. Honest limit, also in the PR body: the install-time `ToastActivatorCLSID` was deliberately not added, so a body click still cannot be delivered on this build - Open is the press that works today, and the body marker will already answer the day the installer (or a COM activator) carries one. Rust tests: six new pure ones (the two actions and the unchanged Deny, an id-less toast, the argv parser against every other marker, a marker round trip through all four toast shapes, and two source pins holding both launch paths and the existing doors), plus the three existing action-count pins moved from one action to two; `cargo fmt --check`, `cargo check`, `cargo clippy -D warnings` and `cargo test` (1271 passed, 0 failed, the two window tests plainly SKIPPED) all green at the desk.
