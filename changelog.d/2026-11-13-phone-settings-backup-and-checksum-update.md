- **The phone can now save its own settings to a locked file, and an update download is checked against a checksum published with the build (2026-11-13, the copy-over wave; adapted from Mobile-Harness, MIT).** Settings -> "Phone settings backup" writes THIS PHONE'S settings - the face and colours, the menus shown, the voice and display switches, which apps Jarvis may open, and which apps may tell Jarvis about a notification - into one password-locked file through Android's own document picker, and restores them onto a new or wiped phone. The file is a versioned container: a small plaintext header, then the typed settings snapshot cut into AES-256-GCM segments bound to their index and a final marker (PBKDF2-HMAC-SHA256, 210,000 rounds, a fresh salt per file; `jarvis-client/.../data/EncryptedBackup.kt` and `data/SettingsBackup.kt`, adapted from Mobile-Harness's `BackupCrypto.kt` under MIT, Copyright (c) 2026 Mobile Harness Contributors, credited in THIRD-PARTY-NOTICES.txt and the APK's own notices). **The pairing token is provably not in it:** it lives in a different preferences file, that file is not on the backup's list, the writer only walks the listed files, and the reader refuses a snapshot naming any file it does not back up - so a restored phone pairs again, exactly as after a reinstall. Chats, saved memories, pictures, caches and logs are excluded for the same reason, and a wrong password, a tampered byte, a truncated file, a foreign file and a newer format each fail closed with plain words and leave the phone untouched; the whole file authenticates before a single preference is written. Separately, the phone's existing update download now also reads `client-latest.json`, which `jarvis-client.yml` publishes beside the `client-latest` APK with the APK's `sha256` and `sizeBytes`, and it is offered for install only when the downloaded file matches BOTH that checksum and the signing certificate pinned in the app (`jarvis-client/.../update/ApkUpdater.kt`, adapted from Mobile-Harness's `AppUpdater.kt` under MIT). The manifest is fetched before the APK, so an unreadable checksum downloads nothing and reports "could not check", never "up to date"; a mismatch is deleted with the reason shown; nothing downloads without the owner's tap and nothing installs itself - the install step is still Android's own installer prompt. Limits, said on the screens: a forgotten backup password cannot be recovered, and restoring needs the app reopened before every screen shows the new values. Neither feature adds a route or sends anything to the PC, so `tools/check_parity.py` classifies nothing new; the docs are `docs/JARVIS-API.md` section 222 and the one-sided note in `docs/ARCHITECTURE.md` section 8. JVM tests: `EncryptedBackupTest` (round trip of every value type, wrong password, tamper, truncation, foreign/unencrypted file, newer container and snapshot, unknown file/type refused, token absence from plaintext and ciphertext, source pins) and `ApkUpdaterTest` (strict manifest parse, URL policy, sha256/size/wrong-file refusals, "no installer code", Install drawn only for Ready, and CI's manifest fields and versionCode pinned to `build.gradle.kts`). No new third-party dependency was added.
