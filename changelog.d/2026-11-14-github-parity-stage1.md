- **Three GitHub reads now hand the model real data instead of a guess: a state filter on `github_list`, the actual unified diff in `github_pr_detail`, and the failing checks by name in `github_ci_status` - plus a measured "Changed files (0)" bug that was hiding a pull request's whole file list (2026-11-14).** `github_list` already had `issues` as a scope; it now takes a `state` filter for `pulls` and `issues` - a closed set of three names (`open`, the default, so every older caller reads what it read before; `closed`; `all`), checked on every scope before any address is built and refused by name when it is not one of the three, with a state on `repos`/`runs` refused rather than silently dropped. `github_ci_status` names every failing check ("rust: failure") instead of only saying the run failed, and shows ONE bounded excerpt (at most 2,000 characters) of the FIRST failing check's log; the run's jobs are one extra fixed GET, made only when the newest run failed, and the log is the same `_job_log` read the fix flow uses - the 302 is read, never followed, and the signed address is fetched with NO Authorization header. `github_pr_detail` shows the changed files' own `patch` (the unified diff) between the one sanitizer's data delimiters, bounded to 20 files and 60,000 characters, with ONE line naming exactly what was left out (files past the cap, files whose diff found no room, and binary/too-large files GitHub sends no patch for). **The bug the field test found is fixed and pinned.** At 23:17 PT the live app read PR #1261, returned the right head commit and base branch, and reported "Number of files changed: 0" while `gh pr view 1261 --json files` said 61 files. Measured with `gh api`: that files answer is **481,180 bytes for 61 files** (GitHub puts every file's `patch` in it), the read layer stops at `MAX_BYTES` (200,000) and marks the answer cut, a cut answer cannot be parsed, and `_read` returned it as "no document, no error" - so `files` became an empty list and the count came from its length. Now a cut answer is an ERROR rather than an empty document, the changed-files page is 20 (178,021 bytes for this PR, under the cap) and is retried at 10 / 5 / 1 if even that is cut, and the count always comes from the pull request's own `changed_files` field - so a page that could not hold every file can never read as zero. Nothing was loosened: no auto-merge, no gist, no admin bypass, and the token is still never printed, logged, put in a git argument or written to a file. `backend/jarvis_tool_profiles.py`'s dossiers now say what the tools really do: the issue-label dossier no longer claims closing an issue is "permanently banned ... no code path" (the owner's 2026-11-10 23:00 decision made `github_issue_state` close ONE issue on its own card), and the CI dossier no longer says "Jarvis never reads the failing log - GitHub keeps it". `docs/JARVIS-API.md` §190.1/§216.1 records the widening and the 481 KB measurement.
