- **The GitHub tool layer refuses hostile input, bounds every answer, and cannot report a false green (2026-11-15).** A new adversarial suite (`backend/test_github_robustness.py`, 511 checks) drives every GitHub planner and the transport boundary with the arguments and answers a hostile model or a hostile network would produce, and it fixed what it proved. Refused now, in one plain sentence and before anything is sent: a repository named `owner/..` (a path step in the URL, not a repository), the direction-override characters that make one line draw as another in a title, body, review, label, commit message or reason, an issue, pull request or run number of 0, and a branch written as `refs/heads/main`, `HEAD`, `main/`, `main.` or `feature/.secret`. Every request is checked against the module's own `https://api.github.com/` prefix at the boundary, so a step built with `@evil.example/x` is refused before a socket opens. No answer is a silent empty list any more: a cut 481-file `pulls/{n}/files` list says what was left out, an unreadable list says it could not be read, a captive-portal page is not "no pull requests", a binary file is not shown as mojibake, and a redirect is named as the reason the token is never followed. Three defects proven against real GitHub the same day are fixed too: a pull request's CI answer now reads the head commit's checks and cannot say "passed" while `audit` is red, the runs list asks for five runs instead of twenty so the scope can answer at all, and reading a directory says it is a directory even when the listing is cut. A 403 rate limit that carries `Retry-After` now says how long to wait. And the pull request scan (`github_pr_scan`) names the checks that are not green on each row instead of only the aggregate one: `blocked - backend finished as failure; also not a success on that commit: audit (failure), backend-shard (3/4) (failure)`, at most three names and then "and N more", and never "running" about a commit whose checks have already failed.
