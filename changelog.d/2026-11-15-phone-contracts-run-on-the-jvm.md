- **The phone's API contracts are proven on the JVM, so a broken route fails a check that is required to merge (2026-11-15).** `ApiContractTest`, `EventStreamContractTest` and `PicturesConfirmContractTest` moved from `app/src/androidTest` to `app/src/test`: 44 tests that assert which route, which header and which body one tap produces, and none of that needed a phone. They used to need one because `JarvisApi` took `ClientSettings` and `TokenStore` directly and both want an Android `Context`; it now takes two one-method interfaces instead - `HostSource` (`baseUrl`, `baseProblem`) and `TokenSource` (`token`), which those two classes already implement - and the suites answer with `FakeHost` and `FakeTokens`. `FakeHost` normalises and judges the address with the same `BaseUrl.normalise` and `PhoneAddress.problem` the app calls, so a test address is measured by the app's own rule, with one deliberate difference: `allowLoopback = true`, because the suite talks to a MockWebServer on 127.0.0.1. The point is which job runs them: the emulator job lives in `Jarvis client`, which is path-filtered on `pull_request` and is not one of the seven required checks, while `testDebugUnitTest` runs in the required `phone-unit-tests` job on every pull request. Two things were needed to make the move real, both measured rather than assumed: the three suites set their host to `127.0.0.1` instead of `server.hostName`, because on a plain computer that name is the machine's own DNS name (here `kubernetes.docker.internal`) and `PhoneAddress` refuses it as off-network - that alone failed 41 of the 44 tests - and `org.json:json:20240303` is now a `testImplementation`, because `testOptions.unitTests.isReturnDefaultValues = true` makes android.jar's `org.json` stub answer null instead of parsing, which failed the other 8. Full JVM suite after both fixes: 3,943 tests, 0 failed, 0 skipped. The Keystore path is still tested on a device, by `TokenStoreTest`.
