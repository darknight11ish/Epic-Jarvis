- **A pull request no longer re-takes the recent-changes module - main does, after the merge (2026-11-15).** `backend/jarvis_recent_changes.py` and its `jarvis-backend/` twin are generated from `changelog.d/`, so every pull request that owed a fragment rewrote the same two lines of both files, and two such PRs always conflicted - the last whole-tree conflict left after the owner's ruling Q1 took the self-code map out of pull requests. The owner's ruling Q2 moves it the same way: a PR adds its fragment and stops there, and `.github/workflows/self-code-map.yml` runs `py -3 tools/gen_recent_changes.py --check` after every merge, naming the one command when main is behind. The check that a PR cannot satisfy is replaced by one that measures honesty instead of freshness: `backend/test_self_knowledge_honesty.py` now proves every bullet the module carries is a real run of the record's own order (an invented, re-worded or dropped bullet still fails), and demands the exact bytes only when `JARVIS_RECENT_CHANGES_STRICT=1`, which the workflow sets. Nothing the owner reads changes: the answer to "what changed in your last update?" is the same sentence from the same shipped module, and a stale module on main still goes red the same day.
