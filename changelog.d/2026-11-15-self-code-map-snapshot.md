- **A feature pull request no longer commits the self-code map (2026-11-15).** The map of Jarvis's own code used to be regenerated by every pull request, because it records every tracked file - and every pull request owes a changelog fragment and a decisions fragment. So two pull requests always wrote the same 330 KB file: six landed in one night and the map forced a full conflict plus a fresh CI round on every one, turning eight merges into about nine hours (the owner's ruling Q1). Now a pull request only has to keep the tree COHERENT - every tracked file owned by exactly one subsystem, every key module, suite and document the generator's table names present - which `backend/test_self_code.py` proves in the required backend job without reading the map at all, and `py -3 tools/gen_self_code_map.py --coherence` runs the same check at the desk. A pull request that adds a module edits the generator's `SUBSYSTEMS` table (that edit is the whole cost) and regenerates nothing. The map itself is a snapshot of `main`, re-taken by one command on a branch off main after a merge. A new workflow, `.github/workflows/self-code-map.yml`, runs the strict `py -3 tools/gen_self_code_map.py --check` on main after every merge and goes red, naming that command, until the snapshot is done - so the map can be one merge behind, never silently wrong. The generator also refuses to WRITE on a dirty tree now: its file lists come from the index while the commit it records comes from HEAD, and a map generated during an in-progress merge was measured on main recording a commit that never had the files it listed. Nothing a person asks Jarvis changes: the map, its reader and its four answers are the same file and the same code.
