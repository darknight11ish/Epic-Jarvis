- **The CI answer counts only the runs it actually read (2026-11-16, DEF-078).** Asked about a pull request, `github_ci_status` judges the head commit's check runs, and when GitHub reported no check runs it fell back to judging the workflow runs on that commit - with the sentence "More than one CI run is on the head commit of pull request #N in owner/repo and at least one did not finish successfully", whatever the list held. With exactly ONE red run and no readable check runs, that was a false count about the owner's own repository, and it asserted a number the reader never managed to verify. The failed-commit sentence now says what was READ about the checks ("GitHub reports no check runs on ...", or "GitHub did not answer with the check runs on ..." when that read could not be parsed) and counts only the runs in the answer - "the one CI run on that commit" for a list of one, "N CI runs are on that commit" for N - so "more than one" is only ever said when it is true. The branch form keeps its own newest-run sentence and both are rendered by the one `_ci_words`, so the two answers cannot drift apart. `backend/test_github_ci_count.py` is the proof: the false count is pinned by name, and 7 of its 22 checks fail against the old renderer while all 22 pass with the fix.
