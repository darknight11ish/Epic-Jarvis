- **`OLLAMA_URL` is checked to be this PC at every place it is read, and a cloud lane whose key read came back empty is answered here instead of sending Jarvis's own token to the provider (2026-11-16).** Three files read the variable straight out of the environment and used whatever they found: `jarvis-backend/jarvis_models.py:71`, `jarvis-backend/jarvis_extract.py:42` and `jarvis-backend/jarvis_hud.py:74` (the third is the live `jarvis_hud.py`'s repo twin). Everywhere else in Jarvis "local" means loopback, so an `OLLAMA_URL` naming any other host would have sent the owner's conversations, extracted facts and notes there while every document still said the model runs on this PC. **One function now does the check - `ollama_url_on_this_pc()` in `jarvis-backend/jarvis_models.py`, the module that already owned the local model's address - and all three reads call it; there is no second copy.** Unset, empty and loopback values behave exactly as before (unset returns `http://127.0.0.1:11434`; empty stays empty, as it did; a loopback value is returned byte-for-byte and each caller keeps its own `.rstrip("/")`). A value naming any other host is refused, not used: this PC's loopback default answers instead, and one plain line on stderr says `OLLAMA_URL is '...', and its host '...' is not this PC, so it was refused and http://127.0.0.1:11434 is used instead (it must be 127.0.0.1, localhost or ::1).` **The `_auth_headers` audit found a real seam and it is fixed in the same PR.** The live builder (`jarvis_hud.py:1711-1725` after the stack) ends `bearer = _api.last_lane_state().get("key") or JARVIS_API_KEY`, and the address it is paired with is chosen separately at `:5919` (`return _state["url"]`). `jarvis_chatbot_api.lane_state()` fills `url` from `cloud_lane()` - whose `ready_for()` reads whether a key is SAVED - and then fills `key` from `lane_key()`, a SECOND Credential Manager read (the module's words: "`lane_key(state["lane"]) or ""`"). A lane that is ready but whose second read comes back empty therefore produces exactly the dangerous state: a provider's address with no key. `_auth_headers` would then fall back to `JARVIS_API_KEY`, so this PC's own pairing token would be sent to `api.deepseek.com`. `backend/ollama-direct.patch` now takes a provider address only when that same resolved state carries a non-empty key (`if _state.get("url") and _state.get("key"):`), so no key means no address and this PC answers instead - the same promise the function already made for a lane it cannot pay for.
