- **A required CI check can no longer open a Playwright browser: the four visible-browser suites now need their own switch for the window (2026-11-17).** The note that a CI log attributed a Playwright `Locator.click` timeout to `backend/test_chatbot_gemini.py` is **confirmed, not a misattribution**. That suite has no `.click(` of its own - the click is in the module it drives, `backend/jarvis_chatbot_web.py:914` (`box.click()`, the message box) and `:933` (`btn.click()`, the send button) - which is why a plain grep for `.click(` found only `test_browser_engine.py` and looked like the wrong suite. The chain was real and is measured. `backend-shard` sets `JARVIS_ALLOW_VISIBLE_BROWSER_TESTS: "1"` so the four suites' 441 code-only checks still run, and since 2026-10-27 (#925) that same required job also runs `python -m playwright install --with-deps chromium` for `test_browser_control_live.py`. So "is Playwright installed?" - the only browser-half gate each suite had - became TRUE in a required job, while `run_suites.py`'s skip-by-name layer was already disarmed by the opt-in, and all four suites really drove Chromium there. Measured on one green run of `main` (2026-11-17): `test_chatbot_sites.py` 486.4 s, `test_chatbot_gemini.py` 117.2 s, `test_support_widget.py` 54.8 s, `test_handoff.py` 12.1 s - against 0.3 s for a genuinely code-only suite in the same shard, and a code-only half cannot take eight minutes. The fix is a second, explicit switch: each suite now asks `JARVIS_RUN_REAL_BROWSER=1` BEFORE it asks whether Playwright is installed, so with only the old opt-in set it runs its code checks and prints one `SKIP the real-browser half: JARVIS_RUN_REAL_BROWSER=1 is not set ...` line. No job in ci.yml sets it, and the two comments that asserted the opposite are corrected - `backend-shard`'s ("this job does not install the package either") and `backend-windows`'s ("No Playwright browser is installed on a runner") - as is the same claim in `scripts/apply-patches.ps1` and `backend/test_browser_test_guard.py`'s own docstring. Proven by `backend/test_browser_test_guard.py` (70 -> 84 checks): every suite must name the new switch, read it itself with only `"1"` accepted, and ask for it on an earlier line than `playwright_installed()`; the sweep job must **still** install a Playwright browser, so the guard rests on the switch and not on a package's absence; and nothing in ci.yml may set the new switch. The owner's workflow is unchanged: neither `tools/update_backend.py` nor `scripts/apply-patches.ps1` ever sets the old opt-in, so a normal update still skips all four suites; running them by hand now needs both variables. Honest limits: no CI run was triggered for this change, and the browser halves were deliberately not executed - the code-only halves were run on this PC with Playwright's browser path emptied (`test_chatbot_sites` 291, `test_chatbot_gemini` 26, `test_handoff` 108, `test_support_widget` 10 passed), with three pre-existing `%TEMP%` access-denied failures that reproduce in three lines on unmodified code.
