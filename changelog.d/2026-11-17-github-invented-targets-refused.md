- **A GitHub repository, owner or branch the model INVENTED is refused, named, before anything is sent (2026-11-17).** On the owner's live install the local 8B model kept naming repositories and branches that were not on GitHub, and `backend/jarvis_github.py` built a request around the invented name anyway — so the owner got a 404 whose words were "there is nothing there - or it is private" (never naming what was wrong, so the model's invention was invisible), and, worse, an invented name that happened to be somebody else's real repository would have received a write-shaped request. Now `run()` resolves what a request names with GitHub BEFORE any of the request's own steps are sent: `GET /repos/{owner}/{name}` for the repository, and `GET .../branches/{name}` for the branch a card names (the CI branch question and both stages of `github_open_pr`, where a wrong branch used to read as "no CI run" or as a confusing git error). Four answers get four sentences and none substitutes anything: a 404 is *"Jarvis asked GitHub about "owner/name" and there is no such repository: either the owner or the repository name is wrong, or it is private and the token saved on this PC cannot see it. Jarvis stopped there and sent nothing else, so nothing on GitHub changed. Check the name exactly as GitHub shows it..."* — the invented name printed; a 3xx redirect or a 200 naming a different `full_name` is a renamed or moved repository, refused rather than followed; anything that is not an answer (no network, a refused token, a 5xx, a body that is not a repository) says *"Jarvis could not check whether ... exists"* and is never turned into "there is no such repository"; and a 200 whose own `permissions.push` is false refuses an ACTION (*"Jarvis found ... but the GitHub account saved on this PC cannot write to it"*) while still allowing the same repository to be READ, because a read changes nothing. There is no argument that skips the check — it is inside `run()`, `r.repo` is recorded by the very planner that built the address, and `run()`'s parameter list is pinned — and a file read's optional `ref` is deliberately NOT branch-checked, because it may be a tag or a commit id. Cost: ONE extra GET per action that names a repository, and it is the first thing that leaves the PC for that action. `github_create_repo` (no existing name) and `github_list`'s `repos` scope are the only tools without it. **And when NO repository is named at all, the answer is an ASK, not a guess:** the name is never filled in from a setting or a default, and nothing here reads a git remote to invent one, so every one of the fourteen repository-naming write tools refuses BEFORE a card is raised, in words that say what could not be resolved (*"Jarvis could not tell which repository this is about: no repository was named, and Jarvis never fills one in from a default or a guess ... Nothing was sent and nobody was asked."*). Proven by a new section of `backend/test_github_tools.py` (1145 → 1167 checks): every repository-naming tool refuses an invented name with that exact sentence and sends ONLY the one check; the invented owner, the invented branch (after exactly two reads and no CI read), the redirect, the substituted `full_name`, the write-permission refusal (and the read that is still allowed), the network failure and the refused token are each driven through the real `run()`; WITH NO REPOSITORY NAMED every one of those tools is an ask that raises no card; and the check BITES — with the pre-fix module restored in the same worktree, 7 checks fail, including the exact-sentence and "only the target check was sent" halves. `jarvis-backend/jarvis_github.py` is byte-identical (`tools/check_stale_twins.py` exit 0). The documented contract is the new 2026-11-17 paragraph in `docs/JARVIS-API.md` §190.1.
