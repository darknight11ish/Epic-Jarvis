- **An unknown lane name is refused by name, not turned into a 503 from Ollama (2026-11-18).** `jarvis_chatbot_api.lane_service()` fails closed now (#1384), so a name outside `CLOUD_LANES` answers `("", "")` and `lane_state()` hands the HUD an empty service. The HUD's `_completions_url()` read "no address" as "the local lane", so an unknown lane name fell through to THIS PC's Ollama with the name still in `body["model"]` - Ollama has no such model, and the owner got a 503 from an endpoint they did not choose. A cloud-intent lane whose service is empty is now refused before any URL is built: a 404 whose body names the lane the client asked for and says nothing was sent ("There is no lane called `<name>` on this PC, so nothing was sent. Pick the local model, or a lane this PC offers, and ask again."). 404 is not one of the degrade loop's `DEGRADABLE` codes, so the refusal cannot become a silent local answer. The check is narrow on purpose: a local-intent fallback lane (the router's replacement model, `decision.inject_memory`) is a local model's name, not a lost cloud lane, and it still reaches Ollama exactly as before. Both apps show the refusal because both share `/api/chat`; no route, wire field or app change. `backend/test_hud_empty_service.py` proves it where `run_suites.py` can run it (it skips `test_ollama_direct.py` by name when the owner file is absent): driving the real helper for the refusal by name, the 404, the untouched body, the local fallback still answering locally, and no URL ever reaching the request builder - plus, in the same suite, the patch applying to the stack's pre-image and reversing byte for byte.
