- **A local turn can always answer: when the saved model cannot run on the lane it picked, the model that lane IS configured for answers instead (2026-11-18).** A private question on the owner's PC routed correctly to the local lane (`X-Jarvis-Route` gate `taint`, `where: local`) and then produced **no answer at all**: `model-state.json` said the everyday model was the Coding preset's pooled three-card model `qwen3-coder-30b-a3b-ud-q3-k-xl` (written by the live install's own preset apply - the repository half of that was merged as PR #1361 the same night), and `jarvis_agent.local_model_refusal` then refused, honestly and in the words the owner was shown, to load a pooled model on the one-card lane. Nothing left the PC and the privacy behaviour was right; the defect was that nothing had asked whether the model the router picked could run where it picked it. The fix has two halves that must ship together. `backend/rebuilt/jarvis_router.py`'s `choose()` now validates the chosen local model against the lane the turn will really use, BEFORE the decision is returned, by asking the refusal authority itself (`jarvis_agent.local_model_refusal`; the "which models are pooled" predicate is not copied anywhere). When the saved model is the one class of refusal a different model can fix (a pooled model at a lane that may not hold it), the decision names **the model that lane is configured for** - read from `jarvis_big_coder.LANES` by port, else `[intelligence] default_model` in the owner's `config.toml`, else the everyday lane's own row - and carries the replacement in the route detail's existing `degraded_from` field: `{"lane": <asked for>, "model": <really used>, "code": "model_cannot_run_on_this_lane", "why": <the refusal>}`, with the reason naming both models. `degraded_from` is omitted on every ordinary turn, so no route header grows. The spill refusal itself is untouched: a pooled model on a one-card lane is still refused and never loaded. The second half is `backend/local-model-guard.patch` plus its line in `apply-patches.ps1` (one hunk in `jarvis_hud.py`, one rewritten line, immediately before `plugin-loader.patch`): the HUD decides "this is a local turn" as `lane == local_model`, so a router-only fallback made `use_tools` false and sent the turn to the plain cloud relay - which resolves a lane name it does not know through `jarvis_chatbot_api.lane_service()`, and an UNKNOWN name falls back to a **cloud provider** (`DEFAULT_LANE` is DeepSeek). Measured here: `lane_service("qwen3.5:9b")` answers `("deepseek_api", "deepseek-flash")`, so with a saved provider key a private prompt could have left the PC - rule 1 broken by a fix meant to protect it. The patch's one line is `use_tools = ((lane == local_model or decision.inject_memory) and _agent_ok)`: `inject_memory` is the signal because every local decision already carries it and no cloud decision ever does, and a new `Decision` flag would be a second thing to keep in step. A local turn whose model is fine is unchanged (absent `degraded_from`, exactly the same route detail), and a cloud turn is not pulled local.
