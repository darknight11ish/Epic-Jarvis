- **A card that cannot say what it would change no longer offers Approve - on the phone and in the desktop HUD - and a cloud settings card shows its detail again (2026-11-18).** The owner was shown a live `change_own_config` card asking to change his cloud settings that rendered with **no detail text** and a normal **Approve**: a blank cheque for a change nobody could read. The backend had sent the detail for both waiting cards; the phone dropped one on the way to the screen. `normalisePendingRow` (jarvis-client `net/PendingRows.kt`) derives the row's `summary` from the detail's first readable key and then **deleted `detail` when it "repeated" that summary** - and for the cloud provider card, `jarvis_presets.apply_cloud` sends exactly `{"text": …}`, a one-key object, so every key was the preview key and the detail was removed. The card never draws that derived `summary` either: `ApprovalCard` passes only `item.notice?.summary` / `notice.full` into `CardSummary.shown`, and those are built from the ACTION NAME (`jarvis_gate.notice_for`), so they can say "Jarvis wants to change one of its settings" but never which one. The sibling cloud card (the escalation switch, `{"text", "costs_money", "pid"}`) kept its detail because of its two extra keys - exactly the "drew one and not the other" the owner saw. Fixed at the cause: the read never drops a detail it can put in words, so the opened card says the actual change again. And the rule that makes the failure safe on both apps, in one place each: a card with **no readable detail** says *"Jarvis did not describe this change. Refresh, or deny it and ask again."*, draws a **Refresh** in Approve's place (a re-read; approves nothing), and keeps **Deny** - it never draws an empty body with a normal Approve. The same rule reaches the phone's **notification**: `ApprovalNotificationPolicy` offers **Review in Jarvis** there instead of an Approve for such a card, the shape a redacted card already had, so the lock screen is not the back door to the same blank cheque (the widget never offers Approve - it opens the app - so nothing changed there). The desktop HUD had its own version of the same hole (`apprDescribe` fell back to "(no detail)" and still offered Approve) and now draws the same rule. The sentence and the action are one shared copy for both apps (`backend/jarvis_card_words.py`'s `NO_DETAIL` / `REFRESH`, through `tools/gen_card_words_cases.py` into each app's contract fixture; the phone's `net/CardDetail.kt` and the HUD's copied constants read them), so the two screens cannot word the blank cheque differently. Nothing about what the backend sends, the gate, a tier or an approval route changed.
