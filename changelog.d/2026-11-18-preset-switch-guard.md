- **A preset switch can no longer load the pooled model on the everyday lane, and a preset no longer answers "applied" without reading the lane (2026-11-18, DEF-088).** Four faults made the A2 field test report success while port 11436 held the pooled `qwen3-coder-30b-a3b-ud-q3-k-xl` at 8,192 tokens with 3.76 GB spilled to the CPU, and each one is fixed with the traffic captured in a test rather than read for in the source. (1) `jarvis_presets._switch_for_the_owner` ran the tripwire smoke test on the **outgoing** model, through `jarvis_models._probe_asker`, against `jarvis_models.OLLAMA` - the everyday lane, one 12 GB card. It now asks `jarvis_models.probe_refusal` first, which is the existing `is_pooled_model` rule, so a pooled outgoing model is never sent there at all; the skip is reported as the tripwire's reason, so the app shows a sentence instead of a smoke test of nothing. (2) `_probe_asker` names `options.num_ctx` on every request **whose window can be established**, resolved by the new `jarvis_models.lane_num_ctx` from the lane's own configured window (`jarvis_big_coder.LANES`: 196,608 on 11436, 16,384 on 11435), from the applied pooled preset on 11450, or from what `/api/ps` says. Where the window cannot be established - an address this program does not know as a lane, which is what `OLLAMA_URL` unset (11434) means on a fresh clone and in CI - the request goes out WITHOUT the field rather than not going out at all, because a guard that silently stops the tripwire is worse than the gap it closes, and naming a guessed window would force a downgrade instead of leaving Ollama's own configured default in charge. (3) The carded `/api/models/switch` road had the same hole in `jarvis_models.switch_to`; its baseline and its after-swap probe now pass through the same guard. (4) `apply_preset` reads the lane back through `verify_lane` before it writes anything, and rolls back and reports the truth when the lane holds a different model, any spill, or the right model at a window smaller than the preset names - an EMPTY lane is not a failure, because the apply records which model chat should use and Ollama loads it on the next turn; a lane that does not answer is. That reader runs only in the real HUD process (`JARVIS_SUITE_RUNNING`, or `__main__` being `jarvis_hud.py` - the same test `_warm_on_startup` uses), because the first version of it read the owner's LIVE lane inside `backend/test_reversible_ui_choices.py`, which loads the base model steward directly and never sets the suite marker. The new `backend/test_preset_switch_lane_guard.py` drives the real apply against a fake lane on its own ephemeral 127.0.0.1 port and asserts, by capturing requests, that **zero** `/api/generate` requests name the pooled model at the everyday lane, that every probe whose window is known carries it, and that a lane holding the coder produces a failure rather than `ok`; the same suite drives `switch_to` and `_default_verify_lane` directly. On the unfixed modules it fails, and the carded road it drives sent 8 requests naming the pooled coder with no window.
