- **A pending check is not a failure (2026-11-20).** The external review's ruling 5.2, from the owner's deploy #4: *"What is failing on pull request 1424?"* was answered "GitHub reports no check runs on pull request #1424 … 2 CI runs are on the head commit and at least one did not finish successfully. 2 failing check(s): CI: pending Jarvis client: pending" while `gh pr checks 1424` showed both checks **pending**. Cause: `_ci_words` treated every workflow run whose conclusion was not in the pass set as red, and a queued/in-progress run has `conclusion: None` - so an unfinished run was counted as a failure and labelled with its own status under a "failing check(s)" headline. `jarvis_github.py` now splits a pull request's head-commit runs with the same three-way judgement `_check_verdict` uses for checks (`_run_verdict`: completed + pass is fine, completed + anything else **failed**, anything not completed **pending**), and the answer groups them honestly: only completed non-pass runs are called failed, a commit whose checks are green but whose runs are still going says the runs are still going, and with no check runs and only pending runs it says "N CI run(s) are still going: names. Nothing is known about them yet - ask again when they finish." The failing headline counts only FAILED runs and says "failed" - never "did not finish successfully". The pull request form also reads the PR head's **commit statuses** (`GET /commits/{sha}/status`) after its three planned reads and merges them into the check list as check-run-shaped entries (`context` → name, success → completed/success, failure/error → completed/failure, pending → in_progress), so the answer is the combined set `gh pr checks` shows; a statuses read that fails is not fatal and the answer says the list is check-runs only. The plan keeps its THREE steps (the pull form's detection reads `steps[-1]`, the check-runs read) - the statuses read happens in `_ci_result`. `tools/field_battery.py` now tolerates `gh pr checks`' exit 8 (checks pending - the pending ground truth used to be thrown away as an error), asks for `--json name,bucket,state`, picks a **settled** pull request for the failing question (a failed check and no pending one) and a pending-but-not-failed one for the running question, counts a number only as its own number (the old substring test read the `1` in "#1400" as "1 failed check"), and never accepts "failed" for the running question. `backend/test_github_ci_count.py` (49 checks, rewritten: the still-going expectation now expects the pending sentence, with new cases for all-pending, failed+pending grouped separately, a status context judged with the checks, a pending status, an unreadable statuses read, and the plan's three steps), `backend/test_github_robustness.py`, `backend/test_github_own_repo.py`, `backend/test_github_tools.py` and `backend/test_field_battery.py` (self-test 30 → 37 cases) prove it; the twin `jarvis-backend/jarvis_github.py` is byte-identical; `test_base_matches_repo.py` 140, `test_base_regeneration.py` 39, `check_stale_twins`, `check_parity`, `check_no_source_pins` and `check_position_pins` clean.
