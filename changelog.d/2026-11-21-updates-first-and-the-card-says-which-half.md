- **The Updates card is first where you look for it, says which half still needs finishing, shows the bounded proof's own step line, and Devices gets a dry-run-first clean-up (2026-11-21).** Four measured complaints and rulings from 2026-11-21 (the owner ~10:12 PT; Gemini's rulings 5.2, 5.4 and 5.6). (1) **Search.** Searching the update words in Settings put the Updates card last or hid it: "update"/"updates" already ranked first, but "upgrade" matched no card at all and "version" ranked About above it. A query made only of UPDATE_WORDS (`update`, `updates`, `upgrade`, `upgrades`, `upgraded`, `upgrading`, `updater`, `updaters`, `version`, `versions`, plus **`sync`** and **`mismatch`** - the two words the version handshake prints when the halves differ) - or the update phrases (`check now`, the card's own button name, and `check for update`/`check for updates`) - now pins the Updates card first in all three places the owner may have searched: the Settings page's filtered results (`settings-search.js`), the app-wide Find list built from the compiled menu catalogue (`palette.js`, which imports the same `asksForUpdates` rule so the boxes cannot disagree), and a one-row quick entry at the top of Settings that opens the card (`settings.html`/`settings.css`). The pin shows the card even when no words on it match ("upgrade"), and a query with any other word in it is left to the ordinary ranking, so no unrelated search is reordered. (2) **A banner at the top of Settings (ruling 5.4).** While the backend half is BEHIND, or a backend half is being finished right now, a banner above every card says so - naming both versions and linking "Go to Updates" - and it clears in place when a version read-back says IN SYNC: no reload, no restart. It re-reads the pair when the window comes back, when a run starts or ends, and on a slow beat while it is on screen; the card keeps its own handshake line underneath. It is deliberately not shown for a backend that is NEWER, two schemes that cannot be compared, or a backend that cannot be reached - "Update everything" is not what fixes any of those. (3) **The Updates card's own line is the release check AND the two versions.** Equal halves with a finished check read "Up to date." followed by the check's own line; a backend behind the desktop reads "Jarvis Desktop 0.2.492 is installed; the backend is 0.2.491 - press Update everything to finish the backend half." with the check's line appended, so a no-newer-release answer can never hide a behind backend; and a backend half that is running now reads "Finishing the backend half now. ... - the card updates when it ends." (the shell marks a live backend half in `update.rs`, and `backend_self.rs` carries it out as `VersionSync.running`). (4) **The bounded proof's own progress line (ruling 5.2).** While the app-path proof runs, the Updates card shows a clean phase-and-count line - `Step 3/4: Live invariants - 8 of 12…` - drawn from the runner's own `PROOF: Step N/M - <phase> - x of y` lines (`module imports` / `instant API answers` / `live invariants` / `look spec & config`). `update_progress.rs` carries only that exact shape (the proof stage's five-minute `PROOF: still running - ...` heartbeat and the older full sweep's suite lines are deliberately NOT steps), so the newest step always wins and a legacy full sweep keeps the card's current words instead of inventing a count. The 5-minute heartbeat and the 15-minute silence bound underneath are untouched: they still end a real hang, and the step line never replaces them. A run whose FILE half has already written VERSION while its own checks are unfinished never reads "Up to date." - it says the two halves are not claimed to match yet and that a restart's handshake will read IN SYNC (the 0.2.492 proof run, ended by the 3-hour ceiling at 20:32:11Z, is the measured case). (5) **Settings -> Devices: "Clean up duplicate/inactive devices" (ruling 5.6).** A new section offers one button; pressing it asks the PC what WOULD be removed and shows the names and how many days ago each was last seen. Anything active in the last 30 days is kept by the PC itself and is never offered, nothing is removed until the owner confirms, and the confirm ends in the PC's own `devices_cleanup` approval card (`POST /api/devices/cleanup`: dry run -> the would-remove list; confirm -> 202 while the card waits, 200 `{removed, kept}` after approval). The page never prunes on load, on a timer, or device by device; a stale link blocks the confirm (it ends in a card) but never the dry run (it only reads). The desktop door (`devices_cleanup` in `devices.rs`, its permission and the settings-surface entry) calls that route and passes 202 through as "waiting", not as a failure. "Both or neither" is untouched: no card, gate, route or approval changed, and the desktop half's install rules are exactly as they were.
