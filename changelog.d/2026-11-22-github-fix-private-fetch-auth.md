- **`github_fix_and_push`'s prepare fetch now carries the same credential as its clone, so a PRIVATE repository can be fixed again (2026-11-22).** The live GitHub proof of 2026-11-21 recorded the defect exactly: `github_open_pr` and `github_merge_pr` worked against a real private repository, and `github_fix_and_push` failed at its prepare stage with `Fetching the pull request did not finish: ... fatal: could not read Username for 'https://github.com': No such file or directory`. `_run_prepare` clones with the token in git's own environment config and then runs `git fetch origin pull/<n>/head:refs/heads/fix-pr-<n>`, and that fetch was the ONE git step in the whole fix-and-push path with no `env` at all: on a private repository it is an unauthenticated read, GitHub answers 401, git falls back to its interactive credential prompt, the prompt cannot run in a non-interactive process, and the write and push stages were never reached. The fetch now takes its environment from the one `_git_auth_env` builder, the same function the clone and both pushes already use - the same `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_0=http.extraheader` / `GIT_CONFIG_VALUE_0` Basic header, still never in `argv`, never in the remote URL and never written to disk. Nothing else moved: the tool still refuses without a saved token, still never prints the token, still raises the same cards, still never force-pushes and still pushes only to the pull request's own branch. The new test is `t_a_private_repository_fix_and_push_carries_the_token_on_the_head_fetch` in `backend/test_github_tools.py`: a `PrivateGit` fake behaves like git against a private repository - a `clone` / `fetch` / `push` succeeds only when its ENVIRONMENT carries the Basic header, and fails in git's own `could not read Username` words when it does not - so the whole prepare -> write -> push flow must finish there, with the head fetch's environment equal to the clone's and to `_git_auth_env(TOKEN)`. `t_a_private_repository_fetch_that_is_refused_is_one_plain_sentence` keeps the other half honest: a fetch refused anyway is still one plain sentence carrying git's own words, with no token, no traceback, no claim that anything was written or pushed, and no half-made scratch folder left behind. It fails on the pre-change tree (the prepare checks go red, and the write stage then finds no folder) and the suite is 1217 checks, 0 failed after; `backend/test_github_parity.py`'s one-helper pin moved from four call sites to five, because the fetch is now one of them. The doc at `docs/JARVIS-API.md` §190.10 already said the clone, the fetch and the push all take the token in git's environment - this makes that sentence true instead of editing it.
