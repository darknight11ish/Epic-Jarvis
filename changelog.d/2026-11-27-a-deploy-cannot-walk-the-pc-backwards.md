- **A deploy can no longer walk the PC backwards to the last release (2026-11-27).** The commit pinning added earlier today preferred `latest.json`'s `commit` unconditionally, and that manifest names the commit the **desktop installer** was built from — which lags `main` between releases. Measured on this PC: a plain deploy read `17a92e5f86de`, an **ancestor** of both `main` (`2c4d54bde`) and the live install it replaced (`c424daa492b3`), and moved the machine backwards until a second run passed `--ref`. When both are known, the **newer** commit now wins, decided by **ancestry** (`git merge-base --is-ancestor` both ways) and never by date: an equal sha keeps the release's own line, a release that is an ancestor of `origin/main` loses and the run says *"deploying it would have moved this PC backwards"*, a release that is the descendant still wins, and a diverged pair deploys `origin/main` and says plainly that neither contains the other. `backend/test_update_backend.py` **598 passed, 0 failed**, with the old rule's two checks replaced by tests for the lagging and the identical case.
