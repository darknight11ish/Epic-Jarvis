- **The one-command updater hands a deploy-managed backend to the deploy tool (2026-11-27).** `scripts/update-jarvis.ps1` now looks, once the backend folder is resolved and before anything patching-shaped runs, for a `DEPLOY-MANIFEST` beside `VERSION`. When both are there the install is deploy-managed, so it hands the whole run to `py -3 -B tools\update_backend.py --repo <repo> --backend <backend> --mode responsive` and exits with that tool's own code (`0` success, `2` a refusal) instead of through its own closing banner, which can only say 0 or 1. It prints one line naming the route it took and the marker it found. No manifest means the old `scripts\apply-patches.ps1` route, unchanged; `-Print` prints the deploy command it would run and starts nothing; `-SkipPatches` still leaves the backend half alone, deploy-managed or not. Proved by `scripts/test-update-jarvis.ps1`, which runs the updater as a program against a throwaway backend carrying both markers and a stub deploy tool that exits 7: the delegate is called with `--repo`, `--backend` and `--mode responsive`, the patcher stub is not called, the 7 comes back, the route line names the marker, and the same folder with the manifest removed prints the patcher-route line - 45 checks pass, and reverting the handoff makes 7 of them fail (measured on 2026-11-27). `$script:TempSource` (line 209) is still assigned nowhere and is deliberately left alone.
