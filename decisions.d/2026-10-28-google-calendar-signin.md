- **2026-10-28 — The Google Calendar connection is both ways, and the sign-in comes back to loopback only:** the owner was asked "For Google Calendar, which do you want?" (a private iCal link, or real Google OAuth) and chose **"Both at once"** - build both, and let him pick one - which reverses the standing sentence in `jarvis_calendar.py` that "there is no Google/Microsoft OAuth flow here and none is planned". What is built: the private iCal link stays exactly as it is (read-only, `jarvis_calendar.py`, no change to it), and beside it `backend/jarvis_google_calendar.py` adds the Google "installed app" authorization-code flow with a **loopback redirect** - `HTTPServer(("127.0.0.1", 0))`, an ephemeral port, `http://127.0.0.1:<port>/callback` - so the browser round trip never leaves this PC and there is nothing to forward, which is how rule 2 (never a public tunnel; no ngrok, no Cloudflare Tunnel, no Tailscale Funnel) is kept rather than bent. PKCE (S256) and a random `state` are required, the state is compared with `hmac.compare_digest` on the callback, and a wrong or missing state is refused WITHOUT exchanging the code - a callback that did not come from the tab this flow opened saves nothing. Scopes: `https://www.googleapis.com/auth/calendar.events` alone, the narrowest scope that can list, create, change and delete events; `calendar.readonly` is deliberately not requested. `access_type=offline` and `prompt=consent` so Google hands back a refresh token every time. The refresh token goes into Windows Credential Manager (`Jarvis Backend/Google Calendar refresh token`) through the existing `jarvis_token_store.WindowsStore`, the client secret into `Jarvis Backend/Google Calendar client secret`, and access tokens live in memory only - never a file, a log line, a route answer, a card, a model prompt or the phone, and both tokens are registered with `jarvis_scrub` by value. The client ID is not a secret and sits in `google-calendar.json` beside `accounts.json`; that file refuses any secret-shaped field. Writes: creating, changing or deleting one event raises ONE approval card at tier `ask` showing the exact event, and nothing is sent to Google before the yes; a denied, timed-out or refused card sends nothing; a change or a delete is refused as stale when the last read of the calendar is more than five minutes old or the event was not in that read (rule 4). Reads are card-free. One-time setup is `docs/GOOGLE-CALENDAR-SETUP.md` plus three commands (`client`, `mode google`, `connect`), because the Settings window has no door of its own to the backend and every Settings card in this program is a Rust command in `src-tauri/src/lib.rs`, which the parallel account-connect work owns. Deliberately NOT done in this slice, and said rather than implied: the Settings row, a model tool, and anything on the phone. Google's own limit is written down rather than hidden: `calendar.events` is a sensitive scope, so a "Testing" app works for the owner alone and Google deletes its refresh token after about 7 days, and publishing it needs Google's verification review.
