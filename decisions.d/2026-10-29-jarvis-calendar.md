- **2026-10-29 — Jarvis's own calendar is on by default, and one local event at a time needs no card:** The owner asked for "a full fledged easy to use calendar built into Jarvis ... disabled but on by default", local-only and shown beside Google Calendar and iCal, never synced out. Two decisions are recorded here. **First, adding, changing or deleting ONE local calendar event is cardless**, and it is the "One job on the schedule" row of `docs/ARCHITECTURE.md`'s cardless table extended, not a new class of exemption: one event per request, no list form, no delete-all and no bulk anything, the audit line carries ids and outcomes only and never the title, place or note, and rule 4's stale-link hold still blocks acting while the event stream is stale wherever the write is drawn. The reasoning is the same as the schedule's - it writes one row on the owner's own PC, changes nothing outside it, and stopping or undoing only makes things quieter - and the write still rides the server's existing origin and token checks, with no new permission model. **Second, the calendar is ON when no settings file says otherwise**, because the owner asked for on by default; OFF hides every surface, refuses writes in words and KEEPS every event, and a damaged settings file is OFF with the reason said rather than a silent on. **The store is wall clock, never an epoch:** `date` and `time` are the record and the epoch is computed on read, so a 09:00 event stays 09:00 across a daylight-saving change; that is the same rule `jarvis_schedule`'s own docstring states for a daily 07:00. What this deliberately does not do: no Google or iCal merge, no invitations, no sharing, no reminder that rings (the field is stored for later), no per-occurrence edit of a repeating event, and no screen in either app yet - S1 is the store, the four routes, the switch and the records, and the HUD card, phone plate and widget build against the contract in `docs/JARVIS-API.md` §164.
