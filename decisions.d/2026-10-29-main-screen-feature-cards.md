- **2026-10-29 — The main screen holds one shared catalogue of feature cards:** The owner's requirement, in their own words: "for features that I would like EASILY accessible in jarvis desk jarvis Android app, make sure I can add them to the main screen through the edit jarvis hud on desktop and make an equivalent edit android hud for the android app." **The contract decided here.** (1) ONE catalogue of feature cards, keyed by the feature's own id in `features/features.json`, so a card can never name a feature that does not exist; 24 cards today, each with which apps draw it, its default, its size and its smallest size. (2) ONE shared choice - a `{version, cards:[{key,on,order}]}` document - that both apps read, so the owner's arrangement is the same on the PC and the phone rather than two separate layouts. (3) Two screens that draw it, each in its own geometry. **What this slice builds:** the catalogue, the one reducer (`applyHomeAction`), the Edit HUD panel, and the main-screen strip - desktop only, with the choice kept in the HUD window's own store. **What it deliberately does not do:** the catalogue contains NO safety surface (approvals, Stop everything, app lock, What asks first, the stale link), so ruling 25's "a layout may never hide the one surface a pending approval must reach" is a property of the data instead of a check somebody could forget. **Why no new permission tier:** a card changes nothing about what Jarvis does - it is a door to a screen that already exists - it raises no approval card, it cannot hide a safety surface, and the document is bounded by the catalogue. It is the same class as `theme` and `hud_layout`, which are saved with no backend call, no pairing token and no approval card. **Still open:** moving the document into the PC's settings store and publishing it at `GET`/`POST /api/home-cards` so the phone reads the same choice, and the phone's own equivalent Edit Android HUD screen; `docs/HUD-MAIN-SCREEN-CARDS-2026-10-29.md` section 7 is that work order.
