- **2026-10-30 — An answer the app does not understand is refused, never drawn as the owner's real day:** The calendar's read had the shape of a fail-open that this project keeps finding: `readCalendar` in the HUD page tested `available !== false`, so every object it did not recognise - the single-event answer `{"ok": true, "event": {...}}` that `?id=` returns, a bare event, an empty body - came out as an AVAILABLE calendar with no events, and the card drew "Nothing in the next 7 days". An empty day is the most reassuring possible lie about the owner's own calendar, and it is unknowable from an answer nobody parsed. So the rule, recorded here because it is general: a client draws a feature's state only from a shape it POSITIVELY recognises. The page now requires a real boolean `available` and, when it is true, an `events` array; anything else becomes `available: false` with its own sentence and draws nothing, and the sheet says the same thing rather than inventing an empty week. The two write handlers had the same bug one step further on - `reply.ok === false` read an answer with no `ok` at all as a SUCCESS and said "Event added." over a write that may never have happened - so they now require `ok: true`. The Settings command applies the same rule in Rust: an answer that does not carry `on` as a real boolean is an error, never "off" and never "on". The same session added the desktop Settings switch for the calendar, and it is deliberately NOT held on a stale link and raises no card either way: it is a preference on this PC that opens no way out of it, the same class as the Anti-Slop filter's switches, and turning it off only narrows what Jarvis draws - every event stays.
