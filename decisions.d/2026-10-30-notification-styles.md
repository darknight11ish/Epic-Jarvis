- **2026-10-30 — Notification styles: a closed look for the phone's notifications, built by talking to Jarvis:** The owner asked, verbatim: *"does jarvis android have custom animated notifications? if not can you build this feature into it? research on girhub repos or more to find out how to add it? i want them customizable and buildable by just chatting to jarvis"*. Decided: the phone's approval-card and reminder/timer notifications may be drawn in a **style the owner describes in their own words**, built the same way "Widgets you describe" is (JARVIS-API §86): the local model turns the words into **JSON on a CLOSED MENU** and nothing else, plain code on the PC checks it, the phone shows a **preview**, and the style is applied only when the owner taps **Add** — so asking never applies anything, and there is **no approval card**, because a style shows nothing new, adds no button and grants no capability. The menu is `name`, `theme` (six colour NAMES — never a colour value), `figure` (six single characters), `motion` (`none`, `pulse`, `flip`, `spinner`), `speed` (three buckets) and `kinds` (`approval`, `reminder`); the phone owns what each name draws. The animation is deliberately one **Android performs itself** inside the notification — a `ViewFlipper` over two frames and an indeterminate `ProgressBar`, both on `RemoteViews`' allow-list — so it keeps running when the app's process is dead, costs no wakeups, and is never a stream of `notify()` frames (which would need the process alive and meet the platform's enqueue cap). The privacy floor is structural: the spec has nowhere to put an email, a fact, a file or a token; the layout receives only the title and body the notifier already had, already redacted; and while the phone is locked, or App lock or "Hide memory lists and chat history" is on, the styled layout is **not used at all** — the notification is exactly what it was before this feature existed. An approval card still offers **Deny only**, still opens the Inbox, and is still never approvable from a notification. Deliberately NOT done, and named rather than hidden: the owner's real face in a notification (those are GL/Compose drawings, and `RemoteViews` refuses every View class it does not know — it would need pre-rendered PNG frames, a later slice); a style-level sound setting (sound belongs to the notification channel, and the approval routing already chooses the channel); styling the ringing alarm, Live, the chatbot line, the hand-off, the watch line, the wake word or the link's own ongoing notification (an animation there is noise); Android 16's `ProgressStyle` live-progress notifications (a different, ongoing-journey feature); any overlay window or in-app arrival animation (a different feature, and a second surface to secure); and any **desktop** styling — a Windows toast is drawn from Windows' own template, so there is no layout to style (`docs/ARCHITECTURE.md` §8). The record is JARVIS-API §167, `backend/test_notification_styles.py`, `jarvis-client/.../NotificationStyleTest.kt`, and the research note `.dsh-scratch/NOTIFICATION-STYLES-2026-10-30-RESEARCH.md`.
