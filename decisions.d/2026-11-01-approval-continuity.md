- **2026-11-01 — An approved step survives a stream that died with it, instead of being dropped:** The owner's report was "approved card, then Jarvis forgets my question": the tap is consumed by `jarvis_gate.decide()`, the app says "Approved. Carrying on." because the gate really said yes, and the turn then finds `out.gone` - the phone closed its stream while the card waited - so it refuses to run the approved tool (nobody is there to read the result) and unwinds. He re-sends, and nothing on the PC remembers the yes, so the new turn answers from scratch without the search he approved. Measured on his own run of 2026-11-01, 15:44-15:47 (`.dsh-scratch/APPROVAL-CONTINUITY-2026-11-01/EVIDENCE.md`): `route turns=7`, `gate.asked`, `gate.approved by=phone`, `agent.chain web_search ran=true ok=true`, then `route turns=7` again 91 ms later and `SPEED rounds=1 tokens=17 tools=False` - the working card turns in the same session read `rounds=2, ~6000 prompt tokens` instead. Decided: keep that one approved step for that one conversation, in memory only, and run it once at the start of the next turn for the same conversation, through the same `prepare()`/`gate`/`execute()` contract, with its result in the transcript the model answers from - so the answer is the one the tap was for. Chosen over "make the card turn never lose its stream" (the client-side fix the evidence could not pin down, and which would leave any other cause of a dead stream losing the same yes) and over "re-raise the card" (a second card for an approval already given, which the owner would reasonably read as a bug). The permission model is deliberately unchanged: the record is written only from the `out.gone` branch that `allowed` and `_a_person_said_yes()` already passed, `owed_record()` tests `_a_person_said_yes()` again for itself, one card still means one action, nothing is auto-approved, and the carried step raises no second card because it already has its yes. Bounded so it cannot become a queue or a replay loop: keyed by the card's own id (`_OWED_DONE`, so a client that re-sends twice still runs it once), dropped after `OWED_TTL_SECONDS` (ten minutes), never carried across conversations, never written to disk, and never written for a denied, timed-out or never-answered card. A carried step that fails says so in code's own words and claims nothing; both the record and the replay are in the audit log (`agent.owed`, `agent.owed_ran`) with names and ids only. Delivered as the whole `jarvis_agent.py` (a module this repository ships whole, in `$SHIPPED`, targeting no patch) in `backend/` and `jarvis-backend/`, and proved headless by `backend/test_approval_continuity.py`, whose regression is red without the fix (6 failing checks) and green with it.
