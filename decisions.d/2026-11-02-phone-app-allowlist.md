- **2026-11-02 — The phone's app allow-list is managed by ONE approval card per app, added or removed, from chat or from the PC's Settings:** The owner asked, in their own words: "any apps that i ask if to open or do something with. i would need to approve a card with the apps i would like it to manipulate first and i can remove or add any android app to that list any time with an approval card... or by going to the settings and changing it there too." Decided: the `[phone_apps]` table that PR #1067 made the whole permission for opening an app on the phone is now managed, because it ships EMPTY and a permission that can only be filled by hand-editing `jarvis-framework.toml` is a permission that cannot be used. Two doors, ONE permission model: a new model tool `phone_apps` (`list` / `add` / `remove`) in chat and Live on both apps, and `GET`/`POST /api/phone/apps` for the settings screens. Every add and every removal raises ONE card that names both the friendly name and the exact package id, nothing is written until a person approves it, a rejection changes nothing, and there is no bulk path - one app per call, refused by the route before a card and refused by the tool's schema. The gate mapping needed no new gate action and no new `backend/*.patch` hunk: the tool resolves through the existing `change_setting` key to `change_own_config`, the same action the other settings changes use, at the `ask` tier it already has; the tool's own name is deliberately NOT a gate key, so the mapping is load-bearing rather than decorative, and `backend/test_phone_app_allowlist.py` proves it and fails pre-fix. The line is written through the same config layer the other settings use - one line of the owner's own text, the whole file re-parsed and compared, an atomic replace, then a framework reload - and an applied add or remove writes one audit line naming the app and the package. `phone_apps` ships ON in `[tools].enabled`, chosen over making it opt-in: a tool that is the only way to fill a list that ships empty cannot itself be behind a hand edit of the same file, and what it can reach is that ONE table, card-first; `control_phone` - which actually opens apps - stays opt-in, `ask`, and one card per plan. THE SURFACE DECISION, with its record reference: add and remove are the PC's Settings and either app's chat; the PHONE's Settings is a READ-ONLY list plus "ask Jarvis to add an app", not an editor, because typing a friendly name AND a package id is deep config editing, which the standing rule keeps off the phone, and the phone is the one device that cannot look a package up - the owner's "or by going to the settings and changing it there too" is answered by the PC's Settings and by the same card from the phone's chat. The phone is not a second authority: the same card approves the same line whichever surface asked. Recorded in `docs/ARCHITECTURE.md` §8 and `docs/JARVIS-API.md` §175.
