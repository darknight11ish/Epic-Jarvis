- **2026-11-02 — Plugins are listed and switched by chat, one card per change, and OFF is immediate:** The owner decided: "Jarvis may list plugins and turn them on/off by chat, one card per change." Decided: two model tools in `backend/jarvis_agent.py` are the door to the drop-in plugin folder `jarvis_plugins.py` already loads - `plugin_list` (read-only: every folder, whether it is on, and why it is off) and `plugin_switch` (ONE named plugin, `on` or `off`). TURNING ONE ON IS CARDED, because a plugin is program code that runs inside the backend at start-up: it goes through the EXISTING gate under `modify_own_code` (the action `jarvis_skills.write_skill` already raises for the same kind of act, already at tier `ask`), reached through the published `skill_manage` `_TOOL_ACTIONS` key, so no gate action, tier line, risk row, card wording or `jarvis_gate.py` patch is invented. TURNING ONE OFF IS IMMEDIATE AND CARDLESS, the project's own on/off rule: stopping only narrows what runs. The tool is also in `NEEDS_A_PERSON`, so a settings file that ever loosened `modify_own_code` still cannot switch a plugin on with nobody asked; a denied or timed-out card changes nothing. NO SECOND MECHANISM AND NO DELETE: the write is the loader's own `disabled` marker file (created with `O_CREAT|O_EXCL`, removed only after the folder and its `plugin.json` are still there) - the same marker `discover()` already reads - and no folder is created, moved, renamed or deleted; a plugin switched off by `"enabled": false` in its own `plugin.json` is reported and refused, because that is a hand edit on the PC, not a chat toggle. THE RUNTIME TRUTH IS SAID, NOT PRETENDED: the loader runs once at HUD start-up, so neither direction is live in the running process; every answer says the change lands the next time Jarvis starts and that Jarvis cannot restart itself, and nothing here restarts anything. NO NEW ROUTE AND NO NEW SCREEN: both tools are model tools, so either app's chat reaches them, but neither app draws a plugin list or a switch (a phone screen would be deep config editing, and a desktop section would be a second door beside the one the owner asked for) - `tools/check_parity.py` is unchanged and clean, and the surface decision is recorded in `docs/ARCHITECTURE.md` §8. Both tools ship ON in `[tools].enabled`, because a feature reachable only by hand-editing that same list would not be reachable by chat; both are listed in `jarvis_reach.TOOL_NAMES`, sit in the `settings` short-list group and carry tool-diet hints, and the feature is on both apps' Features pages (`plugin-switch`). Proved by `backend/test_plugin_switch.py` and the every-tool suites, and recorded in `docs/JARVIS-API.md` §180.
