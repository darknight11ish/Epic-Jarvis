- **2026-11-03 — A bare pasted link is read behind one card, the page is remembered for 15 minutes so a follow-up needs no second card, and a typed "yes" only points at a card while one is really waiting:** Three rules, each measured before it was decided, and what each replaces. **(a) A pasted link is a request.** Gemini's ruling Q2 supersedes the read-a-link slice's own gate of earlier the same day ("a link with no read verb is never read"): a message that is ONLY an `http(s)` address, or an address plus a question about it, now reaches the same read-a-link path and raises the SAME ONE card per URL under the reader's own action (`read_web_page` / `youtube_captions_read`), with the canonical address the card showed on the FIRST LINE of the answer so both apps make it tappable with no rendering change. Nothing is fetched before a person answers, a decline fetches nothing, and a link inside a statement ("here is a link ...") or a browser command ("open <url> in my browser") keeps its own path - the card is the only guard, and a card per paste is the accepted cost of not letting an 8B model guess at an address nothing opened. **(b) One page is kept per conversation, in memory, for 900 seconds.** A follow-up that refers to the page just read ("what does it say about the limescale filter?") is answered from the words already on this PC with NO second card and NO second fetch, quoting around what it finds and saying plainly when the kept characters do not mention it. It is a word-find, never reasoning, and it says so when it finds nothing; the text lives in `jarvis_quick.py`'s own process, capped at one page per chat and eight chats, cleared by a restart, replaced by a new page in the same chat, and never stored on a private turn. This is why no card is needed for the follow-up while a fresh fetch still needs one: nothing new leaves the PC. `jarvis_readpage.py`'s own promise that it writes nothing and keeps nothing is untouched - the kept text never reaches that module and never reaches disk. **(c) A typed decision word answers only while a card is waiting.** The 2026-10-11 behaviour ("approve", "deny", "yes", "no" as the whole message says where the approval window is) was unconditional, so a bare "yes" or "no" in ordinary conversation got the canned "approvals are decided on the card itself" sentence with nothing pending - measured on all four of "yes", "Yes", "yes please" and "no". The intent is now returned only after this PC's own approvals table (`jarvis_gate.pending()`) says a card is really waiting, and otherwise the sentence is left to the model; it still can never approve anything, and a gate that is absent or unreadable counts as nothing waiting, so a broken approvals read can never replace a healthy answer. Deliberately NOT in this change: the "Where this came from" source row for a page read (it needs `read_web_page` in `jarvis_sources.KNOWN_TOOLS` and a seam in `jarvis_hud.py`), and the nine cardless settings-receipt families of ruling Q1 (they need value readers in `jarvis_settings_registry.py`), both of which stay open for their own pull request.
