- **2026-11-03 — The GitHub tools get their own read action at `ask`, never `auto`, and `github_read` is left alone:** The owner's decision was "Read + actions" - Jarvis may read his GitHub (repositories, open pull requests, issues, CI status, one file) and may comment, open an issue and re-run a workflow, each action behind its own card, and it may never merge, push, commit, delete or close. The tempting shape was to reuse `github_read`, which already exists and whose risk row already says "reads public GitHub data". It was refused for a measured reason: `github_read` is the action a "tell me when" GitHub watch makes on a timer, its line in the shipped settings is `auto`, and `jarvis_tellme.py` REFUSES to run a GitHub watch unless it stays `auto` - a look every ten minutes cannot raise a card every ten minutes. Reusing it would either run these new reads at `auto` (the owner's token leaving this PC with nobody asked, on a read the model chose the moment of) or force that line to `ask` and break every GitHub watch. So the on-demand reads are their own action, `github_inspect`, at `ask`: one card per read. Three things were weighed and two rejected. **`auto`** was rejected outright - "it is only a read" is not a reason to spend a credential with nobody looking, and the same call was already made for `github_search` when it was found resolving to `web_research` at `auto`. **A one-per-conversation grant**, the shape the owner chose for web search on 2026-11-01, was rejected here: a web search sends words the owner just asked about, while a GitHub read carries his personal access token and can reach private repositories, and a standing grant would let every later call in that chat spend the credential without a person looking at what was asked. It is the more conservative of the two, and it is also the one that needs no new standing-permission store. **`ask` per read** is what shipped. All six tools are ALSO in `jarvis_agent.NEEDS_A_PERSON`, so the setting says how much Jarvis asks and that set says a read like this is never done with nobody asked - the same belt `github_search` already wears. The three actions are `ask` for the obvious reason and cannot be anything else: a comment and an issue are posted in the owner's name and Jarvis cannot edit or withdraw either, and a re-run can deploy or notify if that workflow does. `github_rerun_workflow`'s risk row is `reversible = "no"` for that reason, even though it changes nothing in the repository. Nothing here is reachable until the owner saves a token ("connect GitHub") and adds the six names to `[tools].enabled`, exactly like `github_search`.
