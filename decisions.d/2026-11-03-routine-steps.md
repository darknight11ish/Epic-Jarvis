- **2026-11-03 — Multi-part reminders are ONE row with two optional columns, not child jobs:** Gemini's Q8/Q9 ruling, and the owner's ask. `schedule.db`'s `jobs` gains nullable `steps` and `step_state` JSON - the same shape the sixteen columns before them took, so an old file opens and a code rollback stays safe. One row, not a parent with children, because every existing path (snooze, the repeat card, `next_due`, both apps' rows) already walks one row, and parent/child would have needed cascade rules in all of them. A part may be TIMED (`offset_min`, or an `at` clock time on the occurrence's own day) or UNTIMED (`offset_min: null`, surfaced when the part before it is answered), and both live in one schema. A part's buttons and destination are the existing action block, validated by the existing `_clean_action`/`_clean_record`, capped at three by Android's own notification ceiling. `due` stays the one cursor: it means "the next moment this row has something to say", so the loop that already fires a reminder fires part 2 and part 3 with no second scheduler, and the part's `fired` mark is written in the same UPDATE so a restart cannot notify one twice. A part more than 12 hours missed while the PC was asleep is marked missed and counted instead of notified - a part is a distinct action rather than a repeat occurrence, so the 2026-09-26 "once, late" rule does not literally apply, but unbounded catch-up is how a feature becomes a nuisance. Creating a routine in chat is cardless, like every one-off reminder since 2026-09-25, and leaves one `jarvis_receipts` entry so Undo survives a restart; pressing Undo raises the ordinary `undo_action` card, because undo is a mutating action and creation is not. Only a part that runs a task raises the existing `schedule_action` card, and its dedupe pair carries the part's index so a second `run-task` part is its own card. Editing an existing reminder's question, buttons or parts is now cardless through the same `edit` verb, which closes the gap JARVIS-API section 21.14 had documented since 2026-11-02. The phone answers parts and never creates or edits one - the standing one-sided rule in ARCHITECTURE section 8, because a part's destination can be this PC's Obsidian vault or a goal/habit id.
