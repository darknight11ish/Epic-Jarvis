- **2026-11-03 — A self portrait is imported registry data, and clearing a conversation is one exact item behind one card:** The owner asked (2026-11-03) that Jarvis be aware of every setting, function and ability it has, open any menu or setting area on request, pull up any old conversation, and clear any memory or conversation on request. Three choices were made rather than built as proposed. First, there is no fourth screens list: `jarvis_self_portrait.places()` imports `jarvis_settings_registry.SECTIONS` and `jarvis_menus.MENUS`, already generated into both apps and test-held to their real ids, and a test fails if any real row is missing. Second, navigation is NOT a new event kind: the model's answer header is sent before the turn runs, so chat navigation stays on the existing per-request `X-Jarvis-Route` field both apps already read, and `resolve_place()` is the exact-alias door for a quick-path fallback. Third, clearing is not a new bulk route: conversation ids already exist per request, `GET /api/conversations` and `GET /api/conversations/<id>` are aliases onto the one History store, and `POST /api/conversations/clear` takes exactly one id and raises ONE approval card (`conversation_clear`, tier ask) naming that chat's title and message count, that it cannot be undone, that the facts learned from it are KEPT, and that copies in older backups remain; denial or timeout deletes nothing and the memory store is never touched. Deleting a chat never forgets a learned fact - that keeps its existing Forget and Forget-a-time-frame flows. The portrait itself is fixed registry data plus live state only: no pairing token, key, account secret, memory or chat text, email or web content, owner path or model-written sentence, and an unreadable value is "unknown", never "off".
