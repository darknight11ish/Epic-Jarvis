- **2026-11-03 — A settings change is receipted only when it really happened, and a chat's "undo" names the receipt the setting's own module wrote:** Q1b closes DEF-031 (nine cardless families that told the owner to "say undo" and wrote nothing to take back) and records the three rules the fix runs on. FIRST, a receipt exists only for a change that REALLY happened: a change that only waits on its card writes none, a sentence that changes nothing writes none, and a value that genuinely cannot be read is changed without a receipt rather than with a guessed "before" - so the wake-word switch is read through `jarvis_speech.wake_state()` before the setter, because a two-state switch is only "the other state" when it really moved (measured: "turn on the wake word" while it was already on wrote a receipt whose undo called `set_wake_enabled(False)`, which is instant and cardless, so "undo" silently switched the microphone OFF; reproduced on the Q1b tree and fixed there). SECOND, when a setting's own module records the receipt (the Anti-Slop filter records one per write: its switch, its mode and each scope), the chat's undo pointer names the id that module RETURNED for that exact change - `jarvis_antislop` already put it on its return value and `jarvis_settings_registry.Outcome` now carries it (`receipt_id`, filled by `_say`) - and never "the newest row in the database", because two rows can share a clock tick and another chat or either Settings screen can write one inside the same change; an empty id writes no pointer and no extra receipt, which degrades to the plain "there is nothing here for me to take back" rather than to a guess. THIRD, that bridge's scope is exactly the three Anti-Slop settings reached through `_run_settings_bool`, `_run_settings_choice` and `_run_settings_antislop_scope`; it does NOT cover "make sure the anti-slop filter is on" (`_run_feature_change_apply`, which takes no `conversation`), and it does not cover the model-facing `change_setting` tool, filed open as DEF-034. The receipts store also follows the environment first now (`jarvis_receipts._config_dir()` reads `OPENJARVIS_CONFIG_DIR`/`JARVIS_CONFIG_DIR` before the framework constant, which is resolved once at import), because a suite that pointed the environment at a temporary folder afterwards was writing real rows into the owner's own `receipts.db`; the load-bearing assumption is written down rather than assumed - the shipped launcher exports those variables before start, so on the owner's PC the two answers agree and no existing undo history moves. The evidence is executable, not read: `backend/test_settings_receipts.py` is 98 checks, 0 failed, 15 registered test functions, one per family plus the no-op and concurrent-write cases, each driven through the real `jarvis_quick.match()`/`run()`.
