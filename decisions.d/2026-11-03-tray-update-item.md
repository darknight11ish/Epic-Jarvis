- **2026-11-03 — The tray's update row is absent unless an update exists, and its press installs the update rather than opening Settings:** The owner, 2026-11-03: *"when i right click the tray icon for jarvis I want a menu option that appears if there is an update to jarvis"*, with the no-update state being the row **absent, not greyed out**. Presence is one pure function, `tray.rs`'s `update_row(Option<&str>) -> Option<String>`: `None` is "no row", `Some` is the text, naming the version when the check gave one (`Update Jarvis to 0.2.411`) and otherwise `Update Jarvis`. Availability is the **existing** check's own result, read from `update::UpdateState` through `update::available_version` - the same answer the Settings Updates card paints - so there is no second network path and the two surfaces cannot name different versions. The row is parented into the "More…" submenu by `Submenu::append` and taken out with `Submenu::remove` (it is that submenu's last row, so no index is needed); Tauri 2.12's `MenuItem` has no `set_visible`, so the menu is where absence has to live, and the same `MenuItem` handle is kept so it can still be re-labelled. Pressing it runs `update::install_from_tray`, which calls the same `install_update` the Settings Install button calls - never a second updater, never a setting or timer, and never anything automatic - after turning the row into "Updating Jarvis to <version>…" and disabling it so a second press cannot start a second download; a toast carries the `INSTALL_CLOSES_AND_RESTARTS` sentence. On Windows a successful install ends the process and the next launch starts with no row; a failure re-reads the state with `check_for_update` and rebuilds the row from the answer, so a stale "Updating…" or a version the endpoint no longer offers cannot linger. **This supersedes the 2026-10-27 decision that the row "still never checks, downloads or installs"**; the Settings Updates card, its notes and its Check button are unchanged, and the tray press is still one explicit press by the owner. **No App-lock gate**, decided by reading `lock.rs` rather than assuming it: `may_open`/`Covered` answers "may this covered *window* be shown now", and its unlock path ends in `open_now(which)` - it would open Settings after Windows Hello, which is not what this row does. The existing update commands themselves (`install_update`, `update_both`) never ask App lock, and the tray's other machine-changing rows (Quit Jarvis, Stop everything, start/stop the backend) are likewise not gated; what this row does is install a signature-verified official release on an explicit press, and it reveals nothing (a public version number). If the owner ever wants it gated while away, the one-line shape already exists in `lock::app_locked`, the same test `live::start` refuses on.
