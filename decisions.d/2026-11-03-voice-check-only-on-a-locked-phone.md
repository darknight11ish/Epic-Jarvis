- **2026-11-03 — Jarvis only asks for your voice on a locked phone, and that is one setting:** The owner's ask, in their own words: *"my voice should only need to be confirmed if i say hi jarvis when the phone is locked … when i start jarvis live on my unlocked phone i dont want it to need to confirm my voice. make this a setting i can change"*. **This SUPERSEDES the 2026-11-01 decision "a Jarvis Live session is verified once, and an answer it can say is said" (`decisions.d/2026-11-01-live-session-verified-once.md`) and the 2026-11-02 decision that followed it (`2026-11-02-live-voice-start-verifies-the-session.md`), but only for the PHONE and only for the trigger:** under those two decisions the first full sentence of every Live session was checked and the result then covered the session, so a session the owner began by pressing Live on a phone he had just unlocked still ran the speaker model on its first clip - exactly what he asked to stop. That check is not cached differently now, it is **removed for that trigger**: the unlock of the phone is the act that proves who is holding it, in the same way the 2026-11-02 decision already treated the phone's mic press as the act. Everything the old decisions protected still holds where it mattered: the **desktop is unchanged** (a PC has no "locked phone", so it keeps the 2026-11-01 rule, its spot check and its read-aloud flags); a **voice-started** session still carries the check in, because "Hey Jarvis, let's talk" is only answered after that clip passed the owner check (2026-11-02, untouched); a phone session that does not say whether it was locked - every app older than this change - keeps the check, so nothing about an old phone changes; approvals are still taps and never voice; and a session that was not checked carries no strictness, so **nothing that needs a real check is read aloud on it** - the rule grants nothing, it only stops asking. **One rule, one place:** `backend/jarvis_live.py`'s `voice_check_needed(trigger, device, locked, setting_on)` answers (a) the mic press never checks, (b) "hi Jarvis" on a LOCKED phone checks (the only check left), (c) Live started from an UNLOCKED phone does not check; the phone's copy is `jarvis-client`'s `voice/VoiceCheckRule.kt`, held to the Python table row for row by its JVM test, and the phone's only power is to SAY whether its own screen was locked - one new `"locked"` field on the existing `POST /api/voice/live` start body, never a new route and never a client-side skip. **The one setting** (`voice_check_locked`, ON by default = the rule above) changes the EXEMPTION, not a check: ON is the owner's own rule - an UNLOCKED phone's Live start, and (once the patch wave can carry the lock state) an UNLOCKED phone's "hi Jarvis", skip the check - and because ON is the looser direction it raises ONE `change_own_config` approval card, while `OFF` is at once and gives the OLD, FULL checks back with the phone's "I am unlocked" then IGNORED - OFF is never "no checks", because withdrawing an exemption must not quietly weaken a gate. It is read and written through the SAME existing Live route (`{"do":"voice_check"}`, no value = read), so no route was added for it. Its `section` in `backend/jarvis_settings_registry.py` is deliberately `None` - the third switch with that reason - because the "voice" Settings card belongs to the "Say Hey Jarvis" feature and `jarvis_feature_guide.switches_for()` would otherwise teach "turn on Say Hey Jarvis" to change this switch (`tools/check_feature_controls.py` caught exactly that). **Chosen over two alternatives:** keeping the check and caching it per session (the 2026-11-01 rule, which is the asking the owner reported), and skipping the check only for the first clip (which would then re-check mid-session against nothing the owner could predict). **The honest gap, recorded rather than hidden:** the desktop has no switch for it yet - the phone's Settings, Voice card draws it, the spoken phrases work on both apps, and `contract/feature-controls.json` carries the desktop row as `planned` / `setup-ui` - and the UNLOCKED WAKE WORD's exemption is not applied yet - `backend/jarvis_speech.py`'s `hear()` decides that check and has no `locked` input until the patch wave carries one, so a wake clip is still checked on an unlocked phone: MORE checks than the rule asks, never fewer, and DEF-033 records it (the rule itself already lives in `jarvis_live`'s one function, so that later hook needs no second copy).
