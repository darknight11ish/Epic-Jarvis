- **2026-11-04 — A voice yes counts for every card, in hands-free mode: the owner's answer, and what it supersedes:** Asked on a clickable card about the one conflict this feature could not settle itself, the owner answered **"A voice yes counts for every card"** (2026-11-04). That is a deliberate reversal, for one mode, of the sentence the 2026-09 security review put in `docs/ARCHITECTURE.md`: *"Never approve-by-voice: the voice check cannot tell a recording from the owner, so a spoken 'yes' answers nothing."* The old sentence is not edited or deleted - it stays in that file, marked SUPERSEDED FOR HANDS-FREE MODE ONLY, with the owner's words and this fragment as the record. **What the new rule is, exactly:** while the owner has turned hands-free mode on, ONE spoken answer may decide ONE waiting card, including a card whose risk row would otherwise demand Windows Hello on the PC or the phone's own lock and signature, and including the cards `jarvis_owner_check.PC_ONLY_ACTIONS` keeps to the PC. **What it is not, and why it is narrower than the old sentence feared:** the mode is OFF by default in both shipped settings files; turning it ON is ONE ask-tier card (`handsfree_enable`, itself a risky approval), and turning it OFF is instant and cardless; the clip is turned into words ON THIS PC (`jarvis_speech._transcribe`) and a client never does speech-to-text; the owner's voice print is checked BEFORE any words are made (`jarvis_voice.verify`), because the voice module's own rule is that a stranger's speech is never turned into words - the brief for this feature said "transcribe, then verify", and that order was refused rather than followed; with no print enrolled a spoken yes is refused outright, so the decision's premise (a check that can run) is never assumed; the answer must be one word from a closed list, inside 60 seconds of the card being read out, for a card that is still waiting; one read-out gets one decision and a second answer is refused; an unclear answer is asked once more and then treated as a DENY; and every confirm calls the SAME `jarvis_gate.decide()` a tap calls, after the same in-memory stamp a Windows Hello approval leaves, from ONE function (`jarvis_handsfree.approve_one`) reachable only through that route, only with the mode on, and only after the voice check passed. **Nothing outside that branch changes:** `jarvis_owner_check.approve_check` gained no hands-free exception and neither gate module imports the new one, so outside hands-free mode a risky approval still needs Windows Hello or the phone's own lock, and a spoken "yes" still answers nothing - `backend/test_handsfree.py` proves both halves. The owner's words are the authority here, not this fragment's reasoning; what the fragment adds is the list of guard rails the implementation owes that authority, so a later reader cannot mistake "a voice yes counts" for "any voice, any words, any time".
