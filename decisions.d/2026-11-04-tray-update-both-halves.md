- **2026-11-04 — The tray's update row runs the both-halves update, and the desktop-only install survives only where the backend half cannot run:** The owner's requirement of 2026-11-03 - *"when i click update on the jarvis hud i want it linked to the back end so both are always updated at the same time"* - and clause (3) of `decisions.d/2026-11-03-desktop-nav-multiwindow-update.md`, *"the desktop-only `install_update` survives ONLY for a PC whose backend half cannot run"*, described the Settings Update press, and one door was left contradicting it: the tray's own "Update Jarvis to <version>" row, added the same day against the old install, still ran `install_from_tray` -> `install_update` alone. A press there therefore updated Jarvis Desktop while the backend stayed behind - on any PC, not only one whose backend half cannot run. Fixed here, because a record that describes one door and not the door the owner actually right-clicks is exactly the stale-comment defect this project treats as a bug rather than a leftover. `update::install_from_tray` now asks `crate::backend_update::locate(&app).blocked` - the field `backend_update_status`, the command the Settings Updates card reads, is built from, so the tray and the card cannot take different views of whether the backend half can run - and where it can, runs `update_both(app, "responsive")`, the pace the Settings Install press uses, through the same one-at-a-time guard. `install_update` remains reachable ONLY in that blocked arm (and from the Settings card's own fallback), and that arm is neither silent nor ever read as "updated": before the install its toast says *"The backend half cannot run on this PC (<why>). Installing Jarvis Desktop on its own - the two may differ until the backend update is finished."*, and after it says *"The BACKEND was NOT updated: <why>"* and sends the owner to the "Update both halves" control once the folders are in place - the same words the Settings card uses, guarded by the same App-lock rule as every other toast that can carry a folder path. Before the both-halves run the tray's toast says what is about to happen (the backend is patched first, then Jarvis Desktop installs, Jarvis closes and starts again, several minutes), because the tray has no card to say it in. The row's states are unchanged - absent while no update exists, "Updating Jarvis to <version>…" and disabled on the press before anything is decided, and rebuilt from truth with `check_for_update` after any ending that returns - and nothing runs without that press. The source-pin test in `update.rs` now slices the function bodies rather than searching the whole file, with `concat!` needles, so a comment cannot satisfy it: the both-halves arm is the one that reaches `update_both`, the desktop-only call is the one inside the blocked arm, and that arm is the one whose words say the BACKEND was NOT updated.
