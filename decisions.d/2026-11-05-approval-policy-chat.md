- **2026-11-05 — What needs a card, how many yeses, and whether it needs Windows Hello is changed through chat, one action and one thing at a time:** The owner asked, in their own words: "i would also like the ability to change what gets an approval card through chat, including if something gets a double confirmation, or a fingerprint/windows hello". One new model tool, `approval_policy`, backed by `backend/jarvis_approval_policy.py`, changes THREE independent dimensions for ONE named action at a time: whether it raises a card at all (the action's own line in `[autonomy.tiers]`, written through `jarvis_asks_first.request_tier` so the existing list of what may be loosened, and its card, are the same ones the Settings page uses), how many yeses it takes (new `[autonomy.confirmations]`, `<action> = 2`; no line is one yes), and whether every yes must also meet Windows Hello on the PC (new `[autonomy.windows_hello]`, `<action> = true`). Both extra tables live in the owner's existing settings file, written with the same one-line discipline as `set_tier`; no second config file exists. THE DIRECTION RULES, which are the safety core and are not negotiable: (1) TIGHTENING - adding a card where there was none, adding a second yes, adding Windows Hello - is instant and raises no card, because it only makes Jarvis ask more, and it withdraws a waiting card that would loosen the same thing; (2) LOOSENING - removing a card, the second yes or Windows Hello - raises ONE card, on the PC, that needs Windows Hello to approve and is refused from any other device before the card exists, and the approval is refused from any other device too (`jarvis_owner_check.PC_ONLY_ACTIONS` holds `change_approval_policy`), with the card's words saying exactly what stops being asked in the owner's words and naming no file the gate protects; (3) NO BULK: one action, one dimension, one call - a body naming a second dimension is refused before anything is read or raised, and the tool is never a plan step; (4) an unknown action is refused before any card in one plain sentence naming the nearest real actions, with their real names in the tool's own data so the model can retry exactly; (5) NOTHING IS AUTO-APPROVED - the policy decides only whether a card is raised, a card that is raised still needs the owner's yes, the event-stream-stale rule is untouched, the app never clears a rush latch or approves in bulk, and the actions whose own module refuses anything but a yes keep their card whatever the settings file says. THE ENFORCEMENT is a drop-in rather than a new patch on the owner's `jarvis_gate.py`: the one place every real approval passes through is `jarvis_owner_check.approve_check`, a shipped module `owner-check.patch` already installs around `POST /api/approve`, so the second yes and the Windows Hello requirement are applied there, against the same settings file the page reads. A first yes runs every check (including Windows Hello when it applies) and approves NOTHING - no stamp is taken, so the gate keeps waiting - and only the second yes stamps the approval the gate believes; the one-yes/two-yes counter is process memory only, so a restart makes the owner confirm twice again, which is the safe direction. Windows Hello on a per-action policy is a PC check, so that action is refused from the phone and prompted on the PC on every yes, even for a card that would otherwise be a "small" one that skips the prompt; and because the phone's approval is one tap plus a one-use signed challenge, a card that needs two yeses is approved on the PC only, said plainly with the existing "answer it on the PC" words. NO APP GETS A WRITE CONTROL: both apps draw the read-only answer in the row's existing note field of "What asks first" (no client changed), and the change itself is a sentence in chat; `docs/ARCHITECTURE.md` section 8 records that, the drop-in choice and why there is no model-free fast-path grammar for these sentences (a regex over "stop asking" is exactly how a sentence gets misread into a loosening, and every loosening still needs the owner's card plus Windows Hello on the PC). Recorded because it changes what the existing permission model reads, and because the direction rules are the promise a later feature must not quietly reverse.
