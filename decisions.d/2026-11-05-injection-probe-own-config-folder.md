- **2026-11-05 — An injection probe measures the shipped module, never the machine's own settings:** The owner's binding brief Q2 said of DEF-048 (3 red checks in `backend/test_injection_chains.py` on this Windows PC, green in Linux CI): **fix the root cause, never environment-skip it**. The defect was not in chain 5b's rule - `jarvis_phone_notifications` really is a settings switch - but in the probe's isolation, and that is the worse shape of the two: a security probe whose verdict depends on a settings file on the host is not measuring the shipped code. `tools/check_injection_chains.py`'s sandbox already gave each probe a fresh `OPENJARVIS_HOME`, `JARVIS_HOME` and `JARVIS_LOG_DIR`, but not the config folder, so `jarvis_phone_notifications.settings()` read the owner's live `~/.openjarvis/phone-notifications.json` and returned from the branch that has the file. The chain5b mutation - which asks the FileNotFoundError branch to carry a text field - was therefore invisible, and the suite was green only where that file is absent (CI). The decision: the sandbox itself owns the whole shape, so it now also points `OPENJARVIS_CONFIG_DIR` and `JARVIS_CONFIG_DIR` at a fresh empty folder, and `backend/test_injection_chains.py` pins it by running the mutated tree with a caller config folder holding a VALID settings file and requiring chain5b to fail anyway. Two alternatives were rejected: setting the variables only in the test's own process (the checker run directly would still read the live folder), and skipping or `ignore`-ing the suite on Windows (a skip is never a pass here, and the owner said so). The cost is deliberate and small: a future probe that genuinely needs a settings file must seed its own sandbox folder explicitly, which is what a probe that measures a settings-dependent path should do anyway.
