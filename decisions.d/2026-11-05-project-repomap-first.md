- **2026-11-05 — A read-only repository map comes first, before project-scoped chat and before any staged diff:** the 2026-11-05 project-management audit put the repo map at rank 2 of its roadmap and offered three choices; the owner chose **A, "read-only repo map first, then a staged diff"**, and Gemini's later ruling made that order binding. The reasoning is in the audit and is recorded here because it constrains everything after it: the map is cheap, deterministic and read-only, so it proves Jarvis can pick the right files before it is given anything that writes; the audit's item 5 (a staged diff and an apply) and item 6 (push / open a PR) stay unbuilt and each needs its own owner decision. What was built: `backend/jarvis_repomap.py` (shipped whole, in `backend/`, `jarvis-backend/` and `_where.py`'s `SHIPPED`), `GET /api/projects/{id}/map` answered by the project store's own route table, and the `map` action on the existing `my_files` tool. The folder rule is the existing one - a project's folder must already be on "Folders Jarvis may look in", and every file the walk would show is passed through `jarvis_documents.allowed_path()` again, so hidden folders, "Protected from Jarvis" items, private places and links that lead outside are refused by the code that already owns that decision rather than by a second list. The map writes nothing (no index, no cache), runs no program, opens no socket, calls no model, adds no gate action and therefore no card: it is a read under the existing `read_files_readonly` line, and what it returns is outside text, marked by the store's own boundary like a file read. It is a PC read reached through chat and through the route; no app screen is added, and `docs/ARCHITECTURE.md` §8 says why while `tools/check_parity.py` classifies the route `BACKEND_ONLY` (not `deliberate`, which would mean the desktop calls it and the phone must not).
