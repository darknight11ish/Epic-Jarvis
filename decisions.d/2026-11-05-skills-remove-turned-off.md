- **2026-11-05 — A turned-off skill can be deleted, and deleting it needs no card:** The owner asked for add and remove in the skills list: "in the skills / plug in list on jarvis, also add an add or remove feature". Measured against `origin/main` before anything was written, BOTH halves already ship since the 2026-11-02 Hermes-skills decision: the Add is `GET /api/skills/menu` plus `POST /api/skills/install` behind ONE `modify_own_code` card (a folder, a `.zip`, or the read-only Hermes scan, and a skill the scanner refuses never becomes a card at all), and the Remove is the one that has always existed (`brain_remove_skill` -> `POST /api/skills/decide` -> `jarvis_skills.uninstall`, with its "are you sure?"), wired into the same Settings card and present on both apps. Nothing requested was duplicated, and no parallel route or command was invented. The one real hole was the TURNED-OFF list: a skill the menu moves to `skills-off\` is beyond `uninstall`, which resolves a name only under the skills folder, so it could be turned back on and never got rid of - in either app. Decided: `POST /api/skills/state` also takes `{"name", "remove": true}` and deletes that ONE parked folder plus its row in `skills-off\.off.json`; **no approval card**, because the copy is already out of the load path - nothing is offered from it and `load()` cannot find it - so the act only takes a capability away, which is the project's own on/off rule and the reason `uninstall` itself has never been carded. For the same reason the brief's "one ask-tier card on removal" was deliberately NOT built: it would have reversed that rule, and the same brief's own requirement 4 asks for the same permission model and wording as the rest of the app. An INSTALLED name is refused by the new door (with the sentence to use Remove), so removing an installed skill stays one door that both apps and the Brain share; `remove` and `on` in one request is refused; ONE name, no list, nothing that could approve or delete in bulk. The phone is deliberately given nothing here, and must not remove a turned-off skill: its list never shows one, the folder is parked on this PC, and no route may let a client delete a folder it cannot see - `tools/check_parity.py` keeps the route `deliberate` with that reason and `docs/ARCHITECTURE.md` §8 records it. No new route, no new Rust command, no new permission, no new gate action and no new patch: `install`, `enable` and `edit` are unchanged, and only the turned-off row gained a button. Proved by `backend/test_skill_menu.py` (including the check that today's removal really cannot see the parked copy) and `jarvis-desktop/tests/skills-menu.mjs`; documented in `docs/JARVIS-API.md` §178.
