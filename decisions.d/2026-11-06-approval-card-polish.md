- **2026-11-06 — The two new approval-card fields are built in one place on the PC, a denial's note rides the existing amend store, and the curator lock has no route:** The owner's ruling of 2026-11-06 (next-sprint PR 2, Hermes borrows #1/#5/#7/#8 plus Q7) asked for four things that could each have been built in each app. They are not. **Hidden bytes and cost** are computed once in `jarvis_gate.pending()` - the function that already turns a database row into the row both apps draw, and the same reason `notice` and `risk` live there - so the desktop and the phone cannot word the same warning two different ways, and there is one place to audit what a card tells a client. The cost object is three real numbers from where they already live (`jarvis_chatbot_api`'s monthly money file and its model price table), and it fails honest: an unreadable ledger or an unpriced model produces `{"why": ...}` rather than a figure, because an invented number on a spending decision is worse than no line at all. **A denial's redirect note** is not a new field on the gate's card row and not a second store: it is written through `jarvis_task_control.amend()`, the same note the card's own "add a note" field has always kept, and it is written BEFORE `jarvis_gate.decide()` so the turn that was waiting reads it together with the answer through `take_amend()` -> `owner_note`. That is why `/api/deny` gained an optional `note` and both apps reach the same store by their own doors (the desktop keeps its decision on the existing Rust `decide_approval` and sends the note through `amend_approval`; the phone sends it through `onAmend`) - one mechanism, no new route for either, and nothing that can approve or grant anything. The note is refused when it is the card's own text (feeding the card's words back as the owner's would be a lie) and when the existing local patterns checker flags credentials (a note is read back to a model, so a pasted password must never travel) - and the denial still goes through in both cases. **The curator lock** is deliberately the PC command line and nothing else (`jarvis_packs.set_locked(..., here=True)`, `py -3 jarvis_packs.py lock <name>`), with no HTTP route: a phone-callable lock or unlock would be a new control over a protection the owner set on the PC, and a route no app calls would be a dead route `tools/check_parity.py` has to excuse. What both apps do show is the lock's EFFECT (a locked pack's install and removal are refused in the owner's exact sentence) and the new provenance tier on the card. **Q7's pill** is a read-only field on the existing `GET /api/asks_first` payload (`tools.new_off`), computed from the shipped template's 19 names (pinned to `backend/rebuilt/jarvis-framework.toml` by test, since the deployed backend cannot read the repository) plus the five this build added, minus the owner's own `[tools].enabled` - no startup notification, no chat card, and no write: turning one on is still `request_tool_enable`'s one Windows Hello card.
