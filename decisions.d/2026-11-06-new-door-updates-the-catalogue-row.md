- **2026-11-06 — A new entry point updates the feature catalogue row in the same PR that builds it:** The owner asked Jarvis in chat whether he could import his Notion notes as Markdown, process them in the Android app and send them to the main Jarvis, and Jarvis said it could not - while the phone's "Send a document" and "Bring in a Notion export" buttons had existed since 2026-11-05 and the live PC answered with notion.can_import: true. The code was right; the self-description was stale. The phone doors landed in `f4c122217` with one contract tweak and no feature row, so `features/features.json` had no row for a document from the phone and still called the Notion import desktop-only with the reason "the phone has no Notion-import screen" - false the day it was written. The model could only answer from what the catalogue and the feature_guide tool told it, so it denied a capability this PC and phone both had. This is the same failure class as docs/JARVIS-API.md 21.12 (2026-10-27). The rule from here: an entry point a person can press - a new phone button, a new Settings door, a new route an app calls - is not finished until the feature row that describes it is in `features/features.json` in the SAME pull request, with its `surface` telling the truth about both apps, its `where` naming the real button, and the generated copies regenerated. `tools/check_feature_list.py` cannot check that `surface` is true (it only checks the shape), so this stays a rule a person keeps, exactly like the one-sided reasons it protects. If the catalogue row cannot be written yet (the screen is not built), the row says that instead of the feature being absent.
