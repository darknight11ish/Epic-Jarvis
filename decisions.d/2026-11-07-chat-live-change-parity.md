- **2026-11-07 — Chat and Jarvis Live change settings through ONE door, so every setting must be reachable in both, and Live never asks for a spoken yes:** The owner's requirement (verbatim): *"also make sure anything that can be changed by chat with jarvis (with an approval card when appropriate) can also be changed in the same manner through jarvis live. i dont want any gaps"* and *"also check if jarvis can also change the settings of these under the hood functions whether through settings or chat or live"*. The audit measured the gaps, not a plumbing problem: Live sends the same `/api/chat` request with `live: true, provenance: "voice"`, so it already shared the route, the agent, the gate and the cards - but only 4 of the 60 switchable tools could be named by the matcher, the tool-switch sentence the owner actually says ("Turn on the browser control tool.") was not a shape the grammar knew, and the model denied that Live could change settings at all. Decisions taken: (1) the spoken names are GENERATED from `jarvis_asks_first.TOOLS_SWITCHABLE` by `tools/gen_tool_targets.py`, with a `--check` drift mode, rather than hand-typed, because a switch Settings draws that chat cannot name is the defect this audit found; (2) the new "turn on/off <name> tool" shape is CLOSED-WORLD - the word "tool" and a whole alias from that table are both required - so a device sentence ("turn off the kitchen light") keeps its own feature and is never read as a tool switch; (3) the card rules are unchanged and were not loosened: ON is still the PC only, ONE card plus Windows Hello, OFF is instant, nothing auto-approves; the only Live difference is WORDING, the one calm line a carded change already got, now also used for a carded tool switch because Live speaks its answer aloud; (4) the Live spoken prompt for a waiting card says the card is TAPPED on the PC or phone, never "say approve" - there is no spoken-approval surface in this project and this pass did not add one (rule 4), so the requested "say approve or tap yes" wording was deliberately not used in favour of the accurate "approve it on your phone or PC"; (5) the false denial is answered deterministically from the code ("yes - a setting change asked through Jarvis Live works exactly like typing it … some settings are PC-only for safety, so their card waits for you to tap it"), in `READ_ONLY_INTENTS`, so it can never take away a "cancel that"; (6) the audit's Live-only tool refusal was investigated read-only and is NOT a Live or taint defect: the route hands the answering turn a request that includes the PC's own recalled-facts system message, `jarvis_agent._TurnWatch.app_context` reads any system message in that request as "the app sent extra text", and `_settings_turn_is_shaped` therefore refuses a model-issued `change_setting` with `SETTINGS_AFTER_OUTSIDE` whenever memory recall fired - typed turns are equally affected, the typed model simply did not call the tool. That finding is recorded here and in `docs/LIVE-DESIGN.md` §3.8b, not fixed in this pass (the fix is in the route that builds `request=` for `run_local_turn`, outside this change's scope, and weakening a safety guard is the owner's call). The permanent proof is `backend/test_live_settings_parity.py`, derived from `jarvis_settings_registry.capability_keys()` so a setting added later without both doors fails the suite.
