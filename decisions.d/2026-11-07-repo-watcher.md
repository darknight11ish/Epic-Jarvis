- **2026-11-07 — Per-repository GitHub watching is a watcher the owner can steer in one sentence, observe-first, and free when nothing changed:** The owner asked: "i can tell jarvis what frequency of notifications or to stop or follow new or any combination of these things through jarvis live and chat". The existing machinery only knew topics (a pull) and a CI watcher for a named pull request, so the per-repository watcher was built INSIDE `jarvis_watch.py` rather than as a parallel system: its items go to the same `/api/watch/decisions` ring buffer through `jarvis_watch_ci`'s store, and its poll runs as a Long Fuse job body (`watch_repos`) registered by the one startup call that already registers the others, requiring `github_read` per run so a scheduled search parks for a ONE-SHOT allow rather than a standing rule. A new watch starts in `observe` mode (it records what it would say and says nothing); the yes that lets it speak is ONE `schedule_repeat` card, reusing the gate's existing action for setting up a repeating watcher rather than adding a gate action or a tier. Every poll is conditional on the stored ETag, so an unchanged repository answers `304 Not Modified` and costs no rate-limit points; public repositories need no token, and a configured token is only ever attached in `jarvis_watch._gh` and never written to a database, a decision row or a log. The one matcher in `jarvis_quick.py` serves both chat and Live because Live turns are the same `/api/chat` route with provenance `voice` + live true.
