- **2026-11-09 — `project_read`: the read half of Jarvis taking over dev work, as a cardless bounded read:** The owner approved the four-slice "Jarvis takes over dev work" plan, and the 2026-11-05 project decision said each previously-unbuilt item needs its own owner decision - so this is this slice's own entry. The slice builds ONE thing: a model tool, `project_read`, that reads one file of code, config or text inside a folder on "Folders Jarvis may look in" or inside a registered project's own folder. **Why it is a new tool and not a change to either existing reader.** `file_read` deliberately has no folder check at all - it is the unbounded read, described that way in `docs/JARVIS-API.md` §35.3, and adding a check there would change a shipped tool both apps already describe; `my_files`' `read` IS bounded but refuses code, because `TEXT_KINDS` is md/txt/csv. So the gap was real and the answer is a composition: the boundary is `jarvis_documents.allowed_path()` (asked for the folder, then for the file), and the `.gitignore` rules and the 512 KB per-file cap are `jarvis_repomap.py`'s own walk and constant - never a second boundary, a second ignore matcher or a second cap. **The architecture ruling of 2026-11-09 12:30 PT (Gemini, Q3) made four things a condition of the write half being authorised, and this entry records all four as built.** (1) A read can ask for a LINE RANGE: `start_line` and `lines` are optional whole numbers (1-based; default 1 and 400; hard cap 2,000 lines and 96 KiB of text per answer), and a range returns numbered lines with their real file line numbers, `start_line`, `end_line`, `total_lines` and `line_cap`. A read with neither argument stays the whole-file read, byte for byte. (2) The truncation footer is deterministic and lives in a NEW `more` field, never in `content` (the model reads `content` as source code): "Showing lines A–B of N; request the next line range to read more", with a second fixed sentence when the file is over 64 MiB and the exact total is not counted, plus a byte-cap sentence when the 96 KiB answer limit stopped the slice first. The total is counted by streaming the file, so a large file can never silently overflow the model's context; a whole-file read cut at 512 KB carries the same footer. (3) A CREDENTIAL FILE is refused 100% of the time, by NAME, with one plain sentence naming the reason, after the boundary/walk checks and before the file is opened: `.env`/`.env.*`, `.netrc`, `.git-credentials`, `.npmrc`, `credentials`, `credentials.json`, `id_rsa`/`id_ed25519`/`id_ecdsa`/`id_dsa` (with or without a suffix), the `.pem`/`.key`/`.pfx`/`.p12`/`.kdbx`/`.jks` extensions, and any path with a `.git` folder in it. The predicate is pinned on both sides: `key.py`, `keys.py`, `env.py` and `credentials_migration.py` are ordinary source and still read. Measured before this change, `id_dsa`, `credentials` and `credentials.json` really were readable, and the others were already refused by the boundary's own protected-name list but answered with the wrong sentence (a `.env` inside a listed folder was told the folder was not on the list) - so the refusal is both new for three names and newly TRUE in words for the rest. (4) The zero-mutation proof is explicit: a temp tree's every file is recorded by relative path, size, mtime_ns and SHA-256 before and after a whole-file read and a line-range read, and nothing is added, removed or changed; the cardless proof through the real `jarvis_gate` and `_one_call` is kept. **The decision that matters for permissions:** it raises NO approval card and adds NO gate action, because a read changes nothing. It reuses `file_read`'s own action (`read_files_readonly`, tier `auto` in the shipped `[autonomy.tiers]`) by declaring the tool with `gate_lookup_name=lambda args: "file_read"` - the same shape `decisions.d/2026-11-05-project-repomap-first.md` records for the map - so `jarvis_gate.py`, its `_TOOL_ACTIONS` table and its tier lines are untouched and no `.patch` is added. **It is a Tools-page switch row, and that is the repo's law rather than this slice's choice:** since the owner's 2026-11-04 decision every offered tool has a switch, and `NOT_A_SWITCH` is a closed set pinned by `backend/test_asks_first.py`, so the row joins `TIER_UNLISTED` beside `file_read` and `my_files` and the switchable count moves 60 -> 61 (the desktop mirror and the two generated contract fixtures move with it). It ships OFF - no line in the shipped `[tools].enabled`, exactly like `file_read` - so turning it on is the owner's own card plus Windows Hello. **Two honest limits, written down rather than left to be discovered:** "`.gitignore`-aware" is not "tracked files only" - `_walk` never asks git, so an untracked file that is not ignored IS readable, and any later slice that needs "only what git tracks" must add that rule rather than assume this one has it; and `jarvis_sources.KNOWN_TOOLS` does not name this tool yet, so an answer built on this read carries no "where this came from" chip (one line, later, deliberately not taken here). **Nothing about rule 1 changes:** no network, no socket, no model call inside the module, the result is marked `outside_text` and the turn latches private, and `project_edit` - the code-writing tool - remains unbuilt.
