- **2026-11-09 — `project_read`: the read half of Jarvis taking over dev work, as a cardless bounded read:** The owner approved the four-slice "Jarvis takes over dev work" plan, and the 2026-11-05 project decision said each previously-unbuilt item needs its own owner decision - so this is this slice's own entry. The slice builds ONE thing: a model tool, `project_read`, that reads one file of code, config or text inside a folder on "Folders Jarvis may look in" or inside a registered project's own folder. **Why it is a new tool and not a change to either existing reader.** `file_read` deliberately has no folder check at all - it is the unbounded read, described that way in `docs/JARVIS-API.md` §35.3, and adding a check there would change a shipped tool both apps already describe; `my_files`' `read` IS bounded but refuses code, because `TEXT_KINDS` is md/txt/csv. So the gap was real and the answer is a composition: the boundary is `jarvis_documents.allowed_path()` (asked for the folder, then for the file), and the `.gitignore` rules and the 512 KB per-file cap are `jarvis_repomap.py`'s own walk and constant - never a second boundary, a second ignore matcher or a second cap. **The decision that matters for permissions:** it raises NO approval card and adds NO gate action, because a read changes nothing. It reuses `file_read`'s own action (`read_files_readonly`, tier `auto` in the shipped `[autonomy.tiers]`) by declaring the tool with `gate_lookup_name=lambda args: "file_read"` - the same shape `decisions.d/2026-11-05-project-repomap-first.md` records for the map - so `jarvis_gate.py`, its `_TOOL_ACTIONS` table and its tier lines are untouched and no `.patch` is added. **It is a Tools-page switch row, and that is the repo's law rather than this slice's choice:** since the owner's 2026-11-04 decision every offered tool has a switch, and `NOT_A_SWITCH` is a closed set pinned by `backend/test_asks_first.py`, so the row joins `TIER_UNLISTED` beside `file_read` and `my_files` and the switchable count moves 60 -> 61 (the desktop mirror and the two generated contract fixtures move with it). It ships OFF - no line in the shipped `[tools].enabled`, exactly like `file_read` - so turning it on is the owner's own card plus Windows Hello. **Two honest limits, written down rather than left to be discovered:** "`.gitignore`-aware" is not "tracked files only" - `_walk` never asks git, so an untracked file that is not ignored IS readable, and any later slice that needs "only what git tracks" must add that rule rather than assume this one has it; and `jarvis_sources.KNOWN_TOOLS` does not name this tool yet, so an answer built on this read carries no "where this came from" chip (one line, later, deliberately not taken here). **Nothing about rule 1 changes:** no network, no socket, no model call inside the module, the result is marked `outside_text` and the turn latches private, and `project_edit` - the code-writing tool - remains unbuilt.
