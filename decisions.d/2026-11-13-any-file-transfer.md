- **2026-11-13 — Any file type from the phone, up to 2 GiB, with one constant behind every number:** The owner asked to "transfer any file type through the jarvis android app to my computer ... up to a reasonably large size". This replaces exactly two paragraphs of `JARVIS-API.md` §196 and nothing else: the type allowlist (eight documents plus eight photos) and the 50 MiB cap. **Any extension is now stored as a PLAIN FILE** in `<a listed folder>\From my phone\` - a `.zip`, an `.exe`, a `.dat`, a video, a file with no extension - and the safety shape is unchanged: it is never run, opened, parsed, converted, indexed, OCR'd or shown to a model, the ONE `receive_uploaded_document` card (tier `ask`, in `HARD_LIMITS` and `MUST_ASK`) is still raised before a byte is written, and the file's name, size and folder are still on the card. A known document or photo extension still has its BYTES checked at `finish` (`%PDF-`, its Office zip members, UTF-8 for text, and the 64-byte photo header), because a program renamed `.pdf` must not be stored under a PDF's name; an unfamiliar kind claims nothing and is not inspected. A `.zip` on this purpose is stored and never unpacked; the Notion purpose's zip is a different door and is untouched. The chat picture path (`ChatPicture`/`goesToPicture`) is untouched too, and a photo on the folder door remains a plain copy. **The ceiling is 2 GiB, and it is ONE named constant** - `jarvis_upload.MAX_FILE_BYTES` - read by the card's own limit line, by the too-big refusal sentence (through `_cap_words`) and by the phone's pre-check (`Upload.DOCUMENT_MAX`, which `UploadTest` parses out of that Python line, so a copy cannot drift); the old `MAX_DOC_BYTES` name remains only as `MAX_DOC_BYTES = MAX_FILE_BYTES`. 2 GiB is achievable in this design rather than guessed: it is 2,048 requests of the existing 1 MiB chunk (each about 1.37 MB of base64 + JSON, a third of the server's 4 MiB `MAX_BODY`), the same loop that already carries a 4 GiB Notion export, and `STAGING_MAX` (4 GiB) holds one full 2 GiB file - two in flight at once are refused with `FULL`, which is the existing behaviour and is said in the module. The reader's own `MAX_DOC_BYTES` (50 MiB) is a DIFFERENT number and is unchanged: a landed document bigger than it is findable by name and simply not opened, and the card says so for that case. The phone's picker is `*/*`, its progress chip now also moves during the one unavoidable measuring read (bytes read), and a refusal shows the PC's own sentence verbatim. **What is not claimed:** no 2 GiB transfer was written to disk in a test - the large-file proof raises the constant to 4 KiB and sends a real 4,000-byte file through begin/chunk/finish - and a file whose name starts with a dot, carries a path, or is a Windows reserved name is still refused, because `jarvis_documents.allowed_path` could never read it once landed.
