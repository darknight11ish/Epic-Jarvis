- **2026-11-13 — Git's endpoint takes Basic auth, not Bearer; GitHub's REST API takes either (measured on the owner's PC):** the live field test of `github_open_pr` (prepare clone) and `github_fix_and_push` (push) failed with "authentication issue" while every GitHub READ worked, and the difference was the header form, not the token. Measured on the owner's PC on 2026-11-13 against `https://github.com/darknight11ish/jarvis-coding-field-test.git`: `git ls-remote` with `Authorization: Bearer <token>` exited **128** with `remote: invalid credentials` / `fatal: Authentication failed`, and the same command with `Authorization: Basic base64("x-access-token:" + token)` exited **0** and listed the refs. So `backend/jarvis_github.py`'s `_git_auth_env` now builds the Basic form - `x-access-token` as the user name, the token as the password, base64 of the pair - and the comment beside the function keeps that measurement so nobody "simplifies" it back to Bearer because the REST API accepts it. The token itself is unchanged in every other respect: it stays in git's own `GIT_CONFIG_*` environment (`http.extraheader`), out of `argv`, out of the remote URL, out of the folder's config, and out of every log line and card; the prepare clone, the open-PR clone and both pushes keep going through the one function, and `test_github_tools.py` now decodes what git is really handed (plus a bite-proof that the old Bearer value fails it). Replaced: nothing in behaviour or in the permission model - only the header form the git steps hand over.
