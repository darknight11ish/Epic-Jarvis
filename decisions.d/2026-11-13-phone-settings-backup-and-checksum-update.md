- **2026-11-13 — The phone may back up its own settings, never the pairing token, and a phone update is checksum-pinned as well as signature-pinned:** the owner approved copying Mobile-Harness's encrypted backup and sha256 manifest under MIT (`COPY-OVER-SPEC-2026-11-13.md`, sections A1-A2), and the two adaptations land together in one PR with `docs/JARVIS-API.md` section 219 and a one-sided note in `docs/ARCHITECTURE.md` section 8. **Backup scope is SETTINGS ONLY, and that is the decision rather than an implementation detail.** The file carries the phone's own settings - appearance, menus, voice and display switches, the app-control list and the notification allow-list - and deliberately nothing else: the pairing token stays in the Android Keystore in its own preferences file (so a restored phone pairs again, which is the property that makes the file safe to keep anywhere), and chats, saved memories, pictures, model caches and logs are not settings. The writer only walks an explicit allow-list and the reader refuses a snapshot naming a file it does not back up, so the exclusion is enforced twice and does not depend on the save path being careful. The container keeps the adapted project's versioned header, PBKDF2-HMAC-SHA256 and segmented AES-256-GCM with per-segment AAD, but a password is now required (Mobile-Harness also offered an unencrypted file) and a newer format is refused with its own sentence; the whole file authenticates before any preference is written, so "half restored, then the tag failed" cannot happen. A password shorter than 8 characters is refused when saving and accepted when restoring, because an old file's password is whatever it is. **The updater keeps its existing gates and gains one.** The phone already downloaded its own `client-latest` APK and checked the signing certificate pinned in the app (2026-10-11); the decision was NOT to replace that with AppUpdater but to adapt only the manifest half, so a download must now match the `client-latest.json` that CI publishes beside the APK (size and SHA-256) AND the pinned certificate. The manifest is read before the APK on the owner's tap, so a missing checksum downloads nothing and is reported as "could not check" rather than "up to date"; a mismatch is deleted with the reason; nothing downloads without a tap and nothing installs itself, because the install step remains Android's installer prompt. CI's side: the publish step writes the manifest from the file it just hashed, verifies it names that exact file, uploads it with the APK and keeps it when older assets are deleted; its `versionCode` is `1000000000 + GITHUB_RUN_NUMBER`, the same number `build.gradle.kts` gives the build, pinned equal by a test so producer and consumer cannot drift. Both features are phone-only because the artefact and the device are: the file is this phone's settings and the updater installs on Android, and the desktop keeps its own separately coded updater and its own PC backup card (the previous sentence in `ARCHITECTURE.md` saying the phone "does not install or update Jarvis" was stale and is corrected in the same note). No route, no card and no new third-party dependency; a wrong password, a tampered or truncated file and a newer format all fail closed with plain words.
