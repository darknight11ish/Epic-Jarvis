- **2026-11-13 — A probe set must name every revision a patch ever had, and an older copy of a block is replaced in place, never skipped and never duplicated:** the 2026-11-13 field test proved the rule this project had been applying since 2026-11-05 ("one probe from every `update` block") is still too weak for a patch that grows IN PLACE, and the live install paid for it. `backend/github-tools.patch`'s block was extended four times while its two probes stayed rows of the original ten-tool block; the live `jarvis_gate.py` carried that older block, so both probes matched, the tool reported `already present: 234; to insert: none`, and 82 of the 174 added rows were absent - including `github_open_pr`, `github_fix_write` and the other Step-2 writes, whose cards then could not be approved (`action_for_tool("github_open_pr") == ("unclassified_tool", False)`). Decided: an entry's probes must include a line from EVERY generation of the patch, not one per `update` block, because an extension appends its rows inside a block whose older rows are already on the live file; and when the live file holds an OLDER copy of the block, the correct carrier is an `adapted_hunks` OLD -> NEW pair that REPLACES it in place - skipping it silently and inserting a second copy are both wrong, and a second copy of `_TOOL_ACTIONS.update`/`_RISK.update` rows is exactly the duplicate this decision forbids. `plan_deltas` retains one fallback: if the OLD block appears zero times AND the patch's own pre-image appears exactly once, the file is a PRISTINE pre-image (an install older than the whole patch) and the patch's own hunk is replayed - no guess, because both counts are checked. Anything else (the OLD block missing and the pre-image missing, or a duplicated OLD block) is still REFUSED by name. The measured old block is carried as `tools/hud-deltas/gate-github-tools-old.txt` (96 lines, byte-identical to the live gate, sha256 3de2f78d...) and the current one as `gate-github-tools-new.txt` (173 lines, the patch's own added block), and `backend/test_reconcile_live_backend.py` rebuilds the measured live shape hermetically, proves the old probe pair PRESENT and the fixed entry ABSENT, carries the upgrade byte for byte, proves the second plan is a no-op, and proves the pristine fallback lands exactly the published base. What this deliberately does NOT claim: it does not cover a future extension that adds rows strictly in the MIDDLE without changing any probed row, and it does not implement the whole-file SHA-256 comparison DEF-035 also asks for - DEF-035 stays open. The desk hotfix applied on 2026-11-13 (rows appended to the end of the live gate, 223,701 -> 234,706 bytes) is a separate manual repair, not this change, and this branch writes no live file.
