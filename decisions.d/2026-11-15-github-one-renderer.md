- **2026-11-15 — One renderer for the CI answer, parameterised by the evidence, so a branch and a pull request cannot drift apart:** The owner's ruling Q2 of 2026-11-15 found `backend/jarvis_github.py` answering ONE question - which checks are red, which are still running - in two functions, `_ci_words` for a branch or repository read and `_pr_ci_words` for a pull request. Both are now ONE `_ci_words(doc, evidence, *, checks_doc=None, who="")`, called by both call sites in `_ci_result`. The parameter is the EVIDENCE, not a second rule: `who` is non-empty exactly when the question is about one commit, and it both selects the commit sentences and names the commit in them; `checks_doc` carries that commit's own check runs; a branch or repository read passes neither and judges the newest run, because `/actions/runs?branch=<branch>` answers runs over TIME, on different commits. `checks_doc=None` together with a non-empty `who` is a commit whose check runs could not be read, NOT a branch read - that distinction is the one thing the first attempt got wrong, and the old-versus-new equivalence harness caught it before anything was pushed. Everything that decides or names a red check was already shared and stays shared: `_scan_checks` decides failed and running, `_ci_failed_lines` names each red check and shows ONE bounded excerpt of the first failing job's log, and a new `_red_lines` prepares that evidence identically for the three failed-commit sentences. NO user-visible sentence changed: the old module from `HEAD` and the new one were driven over 695 sentence pairs - both forms, every status and conclusion, every evidence shape, every check/runs combination - and all 695 came out identical. They did disagree on 30 of those pairs, and both wordings are kept because the evidence really differs: a pull request with no readable check runs judges every run on its commit ("More than one CI run is on the head commit of ... and at least one did not finish successfully"), where a branch read reports only the newest run; and an unreadable runs answer says "GitHub answered without saying anything about CI" to a branch while a pull request says "There is no recent CI run there to report". Those differences are now one documented parameter instead of two code paths that could each be edited alone, which is the owner's whole point: the two answers cannot drift apart.
