Three decisions follow. (1) The pin may be SUPPLIED or LEFT OUT: when any of `head_sha`, `title` and `base_ref` is missing or unusable, `plan_merge_pr` makes ONE `GET` of the pull request and pins the head, title and base branch GitHub reports, so the card names the real commit and approving it merges. That cannot weaken the pin - the value read BECOMES the pin, and `run()` still re-reads and refuses if it moved after the card. (2) A supplied `head_sha` that is not the pull request's head is refused before the card is raised, because a card that can never merge is worse than no card. (3) An approved GitHub write whose run fails is reported to the owner by CODE, in the module's own words, inside the answer - a no-op explained only by the model is not acceptable. Deliberately NOT done: reading the pull request on EVERY merge card. That would put a GET in front of every approval and force a fake network seam through every existing planner test (the suite's `NoSocket`); the shape taken catches the measured failure - no usable pin, or a pin that disagrees - without that cost, and `_run_merge`'s refusal is now true either way. Nothing is auto-approved, one card is still one action, nothing is retried, and the merge stays pinned to one exact 40-character commit.
