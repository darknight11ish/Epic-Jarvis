- **2026-11-15 — A note's own YAML `aliases:` list is the registry, and an alias beats a file-name lookalike:** The owner reported that "my workout log" could not be found after a create, and that the fallback answer said "I'm not sure where your new note is yet". The decision is to resolve a note by what Obsidian itself already reads, in this order: an exact vault path when the owner actually named a path (a slash, or a `.md`/`.txt` ending), then an exact value of the note's own frontmatter `aliases:` list, then an exact title, then a title that contains the words. The alias step is deliberately BEFORE the title step because the owner's vault holds an unrelated root file called `Workout log.md` while the intended note is `Private & Shared/Workout/Workout Log.md`, whose frontmatter says `aliases: [workout log, my workout log]`; a filename that merely looks like the owner's name must not steal it. Two matches are never guessed - the answer asks which note was meant. The registry travels with the note, needs no index, no model and no state from an earlier conversation, and is read fresh each time by `jarvis_notes_edit.find_name()`. The same decision fixes the two create bugs: a create-shaped sentence is never the daily note's (the tail of a create request went into `2026-11-15.md`), and a title that is really a sentence is refused rather than turned into a file name (the measured file was `Workout Log, pin it, and add using todays date that i used the punching bag.md`, 0 bytes). A dated append ("add to my workout log that ...") files under a `## YYYY-MM-DD` heading, newest last, keeps the one `edit_vault_note` card and the File Guardian copy, and adds bytes by insertion only. Nothing else is in scope: no heading/block/frontmatter patching and no search index - those are later phases. Proved by `backend/test_notes_create_find_append.py` on a temporary vault, and by a read-only resolution against the owner's real vault.
