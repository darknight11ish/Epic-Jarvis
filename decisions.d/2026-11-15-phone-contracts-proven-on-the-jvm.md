- **2026-11-15 — The phone's API contracts are proven on the JVM, not on an emulator:** The phone's API-contract suites assert the wire - which route, which header, which body, how many requests one tap makes - and they lived in `androidTest` only because `JarvisApi` took `ClientSettings` and `TokenStore`, both of which need an Android `Context`. A test that needs an emulator is a test that runs in the `Jarvis client` workflow, which is path-filtered on `pull_request` (a pull request that touches no phone file does not start it at all) and which is not one of the seven required checks - so the phone's contracts were proven by a job that a merge cannot be gated on. The decision: `JarvisApi` depends on two one-method interfaces, `HostSource` (`baseUrl`, `baseProblem`) and `TokenSource` (`token`), which `ClientSettings` and `TokenStore` implement and which a test can answer from memory; the three suites live in `app/src/test` and run in the required `phone-unit-tests` job. The seam is two functions wide because those two functions are the whole of what the client asks of either, measured by grepping every `settings.` use in the file - it is not a general injection framework. What the move cost, and must be kept: the tests target `127.0.0.1` rather than `server.hostName` (on a plain computer that is the machine's own DNS name, which `PhoneAddress` refuses as off-network), and the real `org.json` is a test dependency, because `isReturnDefaultValues = true` makes android.jar's stub answer null instead of parsing. The device-only half stays on the device: `TokenStoreTest` still proves the Keystore with the real Keystore.
