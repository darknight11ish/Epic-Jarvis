- **2026-11-15 — The source commit is recorded beside `VERSION`, and the preflight names MIXED COMMITS instead of blocking:** Owner ruling Q8 (Gemini, Principal Architect, 2026-11-15) asked for each artifact's source `HEAD` sha to be recorded in its manifest/version metadata, and for a clear MIXED COMMITS warning when they differ, after three pieces the owner runs were measured at three commits with nothing saying so - desktop 0.2.458 from `7a8fe7d`, the APK from `2aacc71ba`, and the live backend's `VERSION` at 0.2.456 from `04d4748cf`. **Where it is recorded, and why there.** The desktop's `latest.json` gains a `commit` field (from the workflow's `$GITHUB_SHA`, the same value the release notes already name in prose), because a manifest is the one thing a program reads. The phone needed nothing: `client-latest.json` already carries `commit` and the APK's own `BuildConfig.GIT_SHA` is what its update check already compares. The backend's sha goes BESIDE `VERSION` as `SOURCE-COMMIT`, written by the one tool that writes `VERSION` (`tools/reconcile_live_backend.py`, from the `--ref` commit it already resolves for its ref guard), and deliberately NOT inside it: `VERSION` is the shared release marker the desktop HUD compares character for character ("MISMATCH: the backend 0.2.421, but this HUD expects 0.2.433") and every other reader parses it as a bare version number, so a sha in it would break every one of those reads. The record is deterministic (no timestamp), so a second `--apply` plans nothing, and a deploy that cannot read its commit writes no record at all - it says `SOURCE-COMMIT: skipped (...)` rather than inventing a sha. **The comparison, and its honest limit.** The preflight's new `commits` check (the existing read-only status surface, extended rather than a second one) reads the desktop's start-up log line and the backend's `SOURCE-COMMIT`, and says MIXED COMMITS when two pieces that name a commit disagree; a record older than the `VERSION` it sits beside is not believed, and a piece that does not say is said to not say. It is WARN-only by design - the ruling wants visibility so an urgent single-piece fix is still installable - it raises no card, and it never fetches: the phone's installed APK is therefore reported as not readable from this PC rather than looked up on GitHub, and making the phone report into the PC would be a new feature in two apps, not a record that was already there. Both facts it reports are local: a commit written at build time into the binary, and a commit written at deploy time into the backend's folder.
