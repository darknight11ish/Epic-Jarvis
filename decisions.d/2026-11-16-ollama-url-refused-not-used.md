- **2026-11-16 — A non-loopback `OLLAMA_URL` is refused at the read and the loopback model answers instead, rather than the value being used or the backend refusing to start:** the three reads (`jarvis-backend/jarvis_models.py`, `jarvis-backend/jarvis_extract.py`, `jarvis-backend/jarvis_hud.py`) now share one function, `ollama_url_on_this_pc()`. It returns the value only when its host is `127.0.0.1`, `localhost` or `::1`; otherwise it prints one plain sentence naming the variable and what was wrong, and returns the loopback default. Decided this way because the alternative readings are both wrong for this program: using the value is the defect (the owner's conversations, extracted facts and notes would leave the PC while every document says the model is here), and stopping the backend is a worse failure than the one being prevented - a stale or mistyped environment variable on the owner's own PC should cost him the cloud-looking address, not his assistant. The fallback also matches what the rest of the stack already does for a lane it cannot use (answer locally, spend nothing). Two behaviours were deliberately left exactly as they were: an unset variable still means `http://127.0.0.1:11434`, and an empty one still stays empty - a useless value is not silently turned into a working one - so no PC that never set the variable sees any change. The refusal is deduplicated per distinct value, because all three modules read it at import and three identical lines at every boot would be noise. Recorded with it: a provider's address is now used only when the same resolved lane carries a non-empty key, because that key is a second Credential Manager read and `_auth_headers` would otherwise fall back to Jarvis's own pairing token (see the changelog fragment for the quoted lines).
