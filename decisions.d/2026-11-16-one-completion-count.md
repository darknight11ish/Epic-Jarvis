- **2026-11-16 — One completion count:** Gemini's ruling R7 said to have `jarvis_agent.py` record `completion_tokens` directly alongside `prompt_tokens` and `cached_tokens`, so `speed.jsonl` and cloud cost accounting use one unified source of truth. It now does: the model's own count - `usage.completion_tokens` on the `/v1` wire, and Ollama's `eval_count` on the native one, which `_native_as_chunk` already mapped into that same key - is summed over the turn's tool rounds, returned with the turn, handed to the speed record through `jarvis_speed.note_prompt()`, and written to the row under its own name. For an answer the model counted, the speed row's `tokens` and `token_source` now come from that count (`usage`) instead of this PC counting content pieces (`deltas`), so the figure a speed row shows and the figure `jarvis_chatbot_api.cost_of()` prices as its completion term are one number, from one place. An answer that carries no count records `None` - said as unknown, never written as 0 - and the row falls back to `deltas` with the field absent. Deliberately not done, and not a smaller version of this: the `characters ÷ 3` estimator is unchanged, the estimators are not unified, and no limit, tier, cap or gate row is touched - that is separate work with its own re-pinning cost. What this does not claim: a real local turn is still never priced, because a local lane has no service to charge; the unification is that both readers take one recorded number, not that a local answer now appears on a cloud bill.
