- **2026-11-16 — A fact that arrived with the request is live; a stored fact is aged, never presented as live:** the phone's own facts (`X-Jarvis-Device`) answer *"what model of phone am I using right now"* and *"are you connected to my phone"* only by that rule. `jarvis_surface` now stores when the facts arrived (`device_age()`), and keeps the newest report any phone has sent this process with its own time (`last_age()`). A fact from THIS request is live - and for "are you connected", the request from the phone is itself the live proof that the phone is reaching the PC. A stored one is returned with its age ("43 minutes ago") and said to be stored, not live. When nothing has arrived, the answer says it does not know yet and names no phone; it does not borrow a pairing record, because a record has a pairing name rather than a model, and PR #1292 already removed a "connected right now" claim built from the roster's `reach` flag, which is a capability and not a liveness probe. A request that is not the phone's still reads the pairing records, but always with the age of their own last check-in and the sentence "a pairing is a record, not a live connection". The rule, for every future awareness answer built on a client header: **a fact that arrived with the request is live; a fact stored from an hour ago is returned with its age and never presented as live** - and if nothing arrived, the answer says so instead of naming whatever the store happens to hold. The same facts could settle the phone's Android version, screen and app build, and "what Android version is my phone" is deliberately left unwired for now: the owner asked for the model question, and every extra matcher is a hijack risk. "Is my phone connected" keeps its existing roster answer.
