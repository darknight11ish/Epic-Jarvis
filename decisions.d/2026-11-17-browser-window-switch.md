- **2026-11-17 — A browser window needs its own switch, separate from "this suite may run":** the four suites that drive `jarvis_chatbot_web`'s visible launch had ONE variable, `JARVIS_ALLOW_VISIBLE_BROWSER_TESTS`, doing two jobs: it let the suite run at all, and - through the suites' own "is Playwright installed?" check - it let a window open. Those two jobs pulled in opposite directions. CI needs the first job (the 441 code-only checks) and must never have the second (a required check must never be able to depend on Playwright), and the required `backend-shard` job now does both of the things that used to keep them apart: it sets that variable AND installs Playwright's Chromium for `test_browser_control_live.py`. Measured 2026-11-17 on a green run: all four suites really drove a browser there (486 s, 117 s, 55 s and 12 s, against 0.3 s for a code-only suite), and a Playwright page click had timed out in that job. So the window got its own switch, `JARVIS_RUN_REAL_BROWSER=1`, asked for BEFORE the Playwright check, and no job in `ci.yml` sets it - `backend/test_browser_test_guard.py` now fails if one ever does, so the rule is enforced rather than remembered. What it costs the owner, stated rather than hidden: running those four suites by hand to WATCH them now needs two variables instead of one, and the suite prints the second one's name when it skips (`SKIP the real-browser half: JARVIS_RUN_REAL_BROWSER=1 is not set ...`). What it deliberately does not change: a normal `run_suites.py` still skips all four by name (the old opt-in stays unset in the updater and in `apply-patches.ps1`), the 441 code checks still run in both required backend jobs, no route or permission moved, and the suites' code-only halves are untouched. What is not claimed: the guard covers the four suites that import `jarvis_chatbot_web`, not every backend suite that could ever launch a browser - `jarvis_browser_control.py`'s own visible default is pinned separately and this change does not widen that. **Same day, second half - the browser install itself left the required job.** A switch that stops a *window* does not stop a *browser*: `backend-shard` still installed Playwright's Chromium for `test_browser_control_live.py`, so a REQUIRED check could still launch one, and "no job sets the switch" rested on people rather than on a mechanism. The ruling is therefore that required CI must not even be ABLE to launch a browser, and the install was removed. The trade is explicit, not a dropped test: the one suite that needed it is skipped BY NAME in the required sweep when the package is absent (printed, counted, named in `SKIPPED BY NAME` - never a pass), and runs for real in a new INFORMATIONAL `backend-browser-live` job that installs Playwright and Chromium and demands the runner's `ok` line. `backend/test_browser_test_guard.py` pins that no required backend job installs Playwright, that the only two jobs which do are the required `frontend-shard` (its own page tests ARE browser tests - the exception is named, not hidden) and the informational one, and that the live-suite skip is the loud kind. What it costs, stated rather than hidden: one more informational CI job (about three minutes a run), and the live suite no longer gates a merge - its coverage is kept, its vote is not. What it deliberately does not change: nothing required gains a browser, `JARVIS_RUN_REAL_BROWSER` still gates a desk run, and the desktop page tests keep their browser.
