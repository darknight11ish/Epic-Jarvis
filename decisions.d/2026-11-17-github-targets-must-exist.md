- **2026-11-17 — A GitHub target GitHub does not report is REFUSED, never substituted (Q5):** every GitHub request that names a repository is now resolved against GitHub BEFORE its own request is sent — one `GET /repos/{owner}/{name}` for the repository and one `GET .../branches/{name}` for a branch a card names — and a name that is not there is refused in a sentence that prints the name, with nothing defaulted to a guessed repository and no argument on `run()` that skips it. The judgement calls the owner would care about, and why each went the way it did: (1) **REFUSE, never substitute.** GitHub answers a renamed or moved repository with a redirect, and a request could be followed or rewritten to the new name — that would act on a repository nobody named, so a 3xx and a 200 whose `full_name` differs are both refused, the second naming the other repository so the owner can choose it deliberately next time. (2) **Reads are checked too, not only writes.** The extra GET costs one round trip per action, and it buys the naming: without it a 404 on any endpoint is "there is nothing there - or it is private", which describes neither the invented name nor the model's mistake. It also makes the check uniform, so there is no "this tool is exempt" list to drift. (3) **A failure is not a missing repository.** No answer, a refused token, a 5xx or an unreadable body says *"could not check whether ... exists"* — because "there is no such repository" is a claim about GitHub that a network failure cannot support, and the same rule as BLOCKED-is-never-a-pass applies to a name. (4) **`permissions.push` false refuses an ACTION only.** That is the "it exists but it was never your intent" half, and it uses GitHub's own answer rather than the repository's owner, so an organisation repo the owner really can write to still works; a READ of that same repository stays allowed, because a GET changes nothing and refusing it would block looking at a public repository for no safety gain. Missing `permissions` (an answer that proves existence but says nothing about writing) is NOT turned into a refusal — Jarvis does not invent one from silence, and the write's own answer still decides. (5) **A file read's `ref` is not branch-checked.** That argument may be a branch, a tag or a full commit id, and `/branches/` would refuse a perfectly good commit — so the read keeps relying on GitHub's own answer for it, and only a name that is unambiguously a branch (the CI branch and the open-pull-request base) is resolved this way. (6) **The name always comes from the request; an absent name is an ASK before a card, never a default.** `_check_repo` refuses a missing name before a card exists, and says what could not be resolved. There is deliberately NO git-remote fallback: nothing in this backend has a "current workspace" the GitHub tools could read a remote from, and reading whatever folder the backend happens to run in would be the same wrong-repository failure in a different form. If the owner wants a remote-based resolver later, it needs a workspace concept of its own rather than a convenience default bolted on here. It deliberately does not add a new gate action, a new card, a new tool or a new permission: it only refuses earlier and in better words, and `github_create_repo` (which names no existing repository) is not gated. Proven by the new section of `backend/test_github_tools.py` — which fails 7 checks against the pre-fix module — and recorded in `docs/JARVIS-API.md` §190.1.
