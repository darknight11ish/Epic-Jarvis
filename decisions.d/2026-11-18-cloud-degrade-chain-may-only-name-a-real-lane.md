- **2026-11-18 — A degrade step may only land on a lane the code has, and the update tool may rewrite that one stale value:** `jarvis_router.degrade()` used to return the next name in `[budget] degrade_chain` whatever it was, and the owner's live file still named `jarvis-bulk` and `jarvis-critic` - two cloud lanes the owner's 2026-10-27 decision removed from the code. The consequence was not a crash but three real cloud attempts where one was intended: `jarvis_chatbot_api.lane_service()` maps an unknown lane name to the CHOSEN cloud service, so a 429 on `jarvis-escalate` stepped to "jarvis-bulk", then "jarvis-critic", each a second and third request to the same provider with the same key - and the lane that finally answered was not in the caller's lane list, so `jarvis_hud`'s `if lane in lanes: budget.spend()` did not count the call, and the per-minute/per-day budget that exists to absorb rate limits could be walked around by them. **The decision:** `degrade()` filters the configured chain to the lane names this module can actually serve (`cloud_lanes()` of the caller's own list) plus the local model as the floor, and drops anything else rather than substituting a name; local is still checked first and is still the unconditional bottom. **And the file itself is corrected rather than left lying:** `backend/_apply_toml_tiers.py` - already the one script `scripts/apply-patches.ps1` runs on every update because it is the one thing allowed to write this file - now also replaces a `[budget] degrade_chain` that names something outside the shipped chain and the configured local model (`[intelligence] default_model`) with the shipped chain, preserving every other byte and the line endings, with one backup first and a refusal instead of a guess when the key is absent or written over several lines; an empty chain or one naming the owner's local model is his choice and is left alone. That is a deliberate, narrow exception to the tool's "never touch a key the owner already has" rule, and it is limited to a value that names something the code does not have - a stale schema, not a preference. The router half reaches the owner's PC on the same backend update (a shipped module); the configuration half reaches it through the script the update already runs, and `scripts/apply-patches.ps1` now says a line of his settings file was corrected instead of changing it silently.
