- **2026-11-18 — The hybrid/cloud settings are asked about and changed from chat, and no answer claims more than a file says:** the owner asked to be able to ask Jarvis through the phone's chat what the cloud provider and escalation settings are and to change them ("i should be able to ask jarvis through chat on phone to change the provider and adjust these particular settings and get clarity"). The decision has three parts. **(1) The questions are deterministic reads of three files, never the model:** `jarvis_cloud_settings.py` (a new module, shipped whole, called by `jarvis_quick.py`'s fast path) answers "which cloud provider am I using?", "am I on cloud?", "is escalation on?", "will you send things to the cloud by yourself?", "what's my cap?", "how much have I spent this month?" and "what does escalation actually do?" from `cloud-choice.json`, `escalate-cloud.json` and `chatbot\api-money.json`, naming the file and its last-saved date in every sentence, and saying "not set up" in plain words with its meaning when a file is missing - which replaces the old behaviour where several of these went to the model (or to the apps-only spending door) and could be answered from a guess. The answer to what escalation does always carries the refusal list the router enforces (email, files, notes, credentials, stored memory, a picture, the screen, a private question, a pasted secret, a conversation that has read outside text) and the gates that still stop a turn. **(2) The changes add no second mechanism:** the service goes through `jarvis_presets.apply_cloud` (the Presets Cloud row's ONE `change_own_config` card), the standing switch through `jarvis_presets.cloud_escalate` (ON is one card and nothing is written before the yes; OFF is instant and cardless - the existing rule kept unchanged), and the monthly cap through `jarvis_chatbot_limits.change`, the exact function behind `POST /api/chatbot/money` - so the question "can the cap be changed from chat?" is answered by an existing route: a raise is ONE `raise_api_limit` card (tier ask, Windows Hello on the PC or the asking phone's own fingerprint) and writes nothing before the yes, while a lowering is cardless because it only ever spends less. A provider name the PC does not know is refused with the list read from `jarvis_chatbot_api.PRESETS`, and a known name is left to the older cloud-provider door so the two doors cannot compete for one sentence. **(3) The hook is small and in one place:** one matcher call in `jarvis_quick.match()` beside the other cloud/capability answers, one runner block, and two dispatch lines; the read answers are in `READ_ONLY_INTENTS` and `_PRIVATE_DETERMINISTIC_READS`, the change is deliberately not. Stated limits, so nobody reads more into it: the chat answers are read fresh on every call and never cached; "not set up" (no file) and "cannot be read" (a broken file) are different sentences because deleting a file forgets a setting while a broken one must not read as off; no key is ever read (the module never touches `key_saved` or Credential Manager); and the phone needs no client change because the answers and cards ride `/api/chat`. Proof: `backend/test_cloud_settings_chat.py`; docs: `docs/JARVIS-API.md` section 227.
