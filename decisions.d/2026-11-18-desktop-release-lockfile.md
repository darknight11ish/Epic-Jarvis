- **2026-11-18 — The desktop release lockfile is synced, and the strict install is kept:** one cause, eight failed `Desktop release` runs, a one-file fix. When #1319 added the bindings pilot's `typescript ^5.9.3` devDependency to `jarvis-desktop/package.json`, `jarvis-desktop/package-lock.json` was not regenerated; the release workflow's `npm ci` - the only place that reads the lockfile - then refused every main merge from #1319's own merge (`8858a2db8`, 2026-11-16 22:56Z) through #1375 (2026-11-18 17:05Z), all eight with the same `npm error Missing: typescript@5.9.3 from lock file`, so the rolling `desktop-latest` release stayed at 0.2.465 from `589ba09`. (`main` carries eight such runs, not the seven the brief names: #1319, #1332, #1358, #1359, #1365, #1367, #1368 and #1375. A ninth, #1361, was cancelled by the workflow's own `cancel-in-progress` concurrency when the next merge arrived 90 seconds later, so it never reached `npm ci`.) The fix is the missing lockfile entries only, generated with the desktop's own package manager, `npm install --package-lock-only` on npm 12.0.2 / Node 22.23.2: 16 lines added, 1 line changed, and no dependency version moved. Three things were deliberately left alone. (1) `npm ci` stays `npm ci` - switching to `npm install` would hide the drift the strict install exists to surface, and the strict install is exactly what failed. (2) The workflow's pins (`node-version: "22"`, the action SHAs) are current and not the cause: the runner's npm 10.9.9 installs from the fixed lockfile cleanly, so no workflow change is owed. (3) No lockfile-sync gate was added to CI in this fix even though it would have caught the drift - the required `frontend` job never runs `npm ci` (it only runs `npm install --no-save playwright`), which is how #1319 merged green; adding that gate belongs in its own CI change, not inside a one-file release repair. Until it exists the release workflow's own `npm ci` is the gate, and the eight red runs are the evidence that it fires.
