- **2026-11-18 — The favourite flag becomes a resolver tier, asked last, and it selects a note without showing its words:** the owner's `favorite: true` front matter was written on create and by a carded `set_property` edit, and exactly one reader consumed it - the yes/no "is my X note favourited?" answer - so "add this to my favourite note, especially if I made them my favorite" resolved nothing at all. This is the first behaviour that flag has. **The four judgement calls:** (1) **It is a fourth tier in the ONE resolver, not a second resolver** - `path -> basename -> alias -> favourite`, added where `RESOLVE_TIERS` is stated and consumed, so every note tool that already routes through `jarvis_notes.resolve_note` gets it and no door grows its own idea of a name. (2) **It sits LAST** because a favourite is a DESCRIPTION of a note, never its name: any explicit vault path, file name or note `aliases:` value was already asked and won, so a favourite can never override the owner naming a note, and the tier can only turn a would-be refusal into a choice after every real name tier has said no. (3) **It fires only on the favourite words themselves** - "favourite"/"favorite" and their plurals and short forms, which is what `_note_key` leaves after it drops "my/the/a/an" and a trailing "note" - so a plain note question ("garden bucket", "favourite colour") keeps its old refusal and a favourite is never picked for it; the flag is not a fallback for an unknown name. (4) **None is an honest refusal and never a create:** with no flagged note the answer names what was looked for, and `create_target` returns that same refusal even when `create_target_if_missing` is True, because describing an existing note must never produce a new note called `favourite.md`. Two spellings are read (`favorite` and the British `favourite`, so a hand-written note counts) but only the US one is ever written; the value must be true-ish and must be a top-level key inside a front matter that CLOSES, the same rules the chat's own flag reader used on 2026-11-17 when an unclosed block answered "Yes, pinned" for a property the note did not have. **What was deliberately NOT done, and stays a separate change:** the favourite's content is not put in a prompt, nothing ranks or filters by the flag, `/api/notes/list` and both plates are untouched, and no route, card or approval was added - reading a vault is not a gated action. This PR is selection; "favourites as context" is recall, and it is not this PR.
