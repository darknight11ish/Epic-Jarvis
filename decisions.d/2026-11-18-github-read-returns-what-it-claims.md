- **2026-11-18 — The GitHub read layer pages a long list instead of refusing it, names the newest run's head commit when a branch read is asked for the latest commit, and answers "which pull requests on Epic-Jarvis are ready to merge?" on the deterministic fast path:** the owner's live field battery failed on the deployed b8de6ef15 in three measured places (`.dsh-scratch/wave21/coverage/GITHUB-FIELD-FAIL.md`), and the ruling is that the read returns what it claims rather than either raising the byte cap or hiding the gap. (1) **PAGE, DO NOT RAISE THE CAP.** `MAX_BYTES = 200_000` is a hard cut on ONE GET; a ten-row open pull request list measured 227,073 characters (the field run's ten were reported even larger), so the JSON could not be parsed and the answer was the cut sentence with no number in it - a false-looking "I cannot read your GitHub" about a list GitHub had really sent. Raising the cap would move the same failure by one row, so the fix is `LIST_PAGE = 5` and `_list_pages`: after a CUT, the SAME list is read five rows at a time and joined, de-duplicated by GitHub's own number, up to the `PER_PAGE` rows the single read was allowed to ask for. The same paging serves the read-only PR cockpit, whose header says "At least N open pull request(s)" when it reached `MAX_PRS` (the count is not claimed as the whole list), and a page that was itself cut is salvaged row by row and the answer says it may be short. An ordinary small list still costs exactly one read - paging runs only after a cut - and when even the pages answer nothing usable the cut sentence is still what the reader gets, so nothing silently becomes an empty list. (2) **SAY THE COMMIT THE READ ACTUALLY HAS.** "What is the latest commit on main?" is answered by the branch CI read - the read the quick lane chose as the one that names a commit - and it rendered only how the newest run ended, never the commit, so the field battery's sha check could never pass. `_ci_words`'s branch/repository form now ends with "The newest run's head commit is <full 40-hex sha>: <subject>", and it is said AS THE RUN'S OWN COMMIT: this read does not measure the branch tip, so it must not claim to (measured live 2026-11-18: the newest run's `head_sha` was the same commit `gh api .../commits/main` named, but the sentence is worded from what was read). Changing the branch form also puts the commit in the model's own `github_ci_status(branch)` answer, which previously could not name one either. (3) **READINESS IS A FAST-PATH SHAPE, BUT ONLY ABOUT HIS OWN REPOSITORY.** The field sentence puts "on Epic-Jarvis" in the middle, which `_GITHUB_MY_PRS` does not match, so it reached the model and came back asking for owner/name. A new `_GITHUB_READY` matcher sends it to the read-only PR cockpit (`plan_scan_prs`) - each open pull request's own merge state and checks, the same verdict the merge gate uses, so the answer can only repeat GitHub's - and its middle words accept ONLY phrases naming the owner's own repository ("on Epic-Jarvis", "in my repo", "this repository", "on GitHub"), so a foreign repo named in the sentence falls through to the model, whose tool resolves a real owner/name. Decision #1348 kept by #1382 is untouched: reads may resolve the owner's own repository when he named it without owner/name; writes still refuse an ambiguous name. What this deliberately does NOT do: it does not raise `MAX_BYTES`, it does not add a separate commit API read (the run's own object carries the sha and subject), and it does not put readiness questions about somebody else's repository on the fast path.
