- **2026-11-18 — The HUD refuses an empty service by name; it never falls back to the local endpoint:** The ruling, quoted: "`lane_service()` returning `("", "")` (never a cloud URL) is right — AND the HUD manual-lane path must explicitly check for `("", "")` and refuse with a clear error naming the invalid lane rather than letting an empty service pass downstream." `jarvis_hud.py`'s `_completions_url()` turns a cloud lane name into a service and an address through `jarvis_chatbot_api.lane_state()`; after #1384 that answer is `("", "")` for every name outside `CLOUD_LANES`, and "no address" used to mean "the local lane", so an unknown lane name went to Ollama with the name still on the request - a 503 from an endpoint the owner did not choose. From 2026-11-18 a cloud-intent lane whose service is empty is refused BEFORE any URL is built: a 404 whose body is one plain sentence naming the lane the client asked for ("There is no lane called `<name>` on this PC, so nothing was sent."), with the next step in the same sentence. The 404 is deliberate - it is not one of the degrade loop's `DEGRADABLE` codes, so the refusal cannot become a silent local answer, and `_open`'s existing `except urllib.error.HTTPError` reader is what shows the sentence to both apps. The check is narrow: a local-intent fallback lane (`decision.inject_memory`) is a local model's name, not a lost cloud lane, so it still reaches this PC's Ollama exactly as before. It ships inside `backend/ollama-direct.patch`, where the lane-to-address decision already lives - no new patch, route, wire field or app change.
