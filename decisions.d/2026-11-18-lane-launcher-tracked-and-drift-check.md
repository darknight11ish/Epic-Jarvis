- **2026-11-18 — Track the lane launcher in the repository and make the repository admit when the PC cannot honour its lane table:** `scripts/start-lane.ps1` is now a tracked copy of the live launcher the owner's Windows logon tasks run, and `tools/check_lane_launcher.py` compares it with the live file, with Task Scheduler, with `nvidia-smi -L`, and - the part CI can prove - with the lane table in `backend/jarvis_presets.py`. The judgement calls, all made against the 2026-11-18 failure (a pull request said the everyday lane on 11436 spans all three cards; CI was green; the machine's task passes one `-GpuUuid`, and a measured load grew the 2060 by 3,713 MiB and the other two cards by 0 MiB each): (1) **A COPY WITH A HEADER, NOT A BYTE-IDENTICAL MIRROR.** The header must say it is a copy, where the live file lives and that editing it alone changes nothing, so the copy cannot be mistaken for the running thing - but then it can never be byte-identical, so the comparison splits at a marked END line and compares only the live body, line for line, ignoring line-ending style alone. The header also carries a machine-readable TASK/GPU table (the two logon tasks' names, lanes, ports, exact `-GpuUuid` values and contexts, and the three card UUIDs), because the `-GpuUuid` that decides a lane's cards is passed by the TASK, not written in the launcher file; without that record the repository half could not be checked off the owner's PC. (2) **THE LANE TABLE IS THE AUTHORITY, AND THE CHECK IS HERMETIC.** The comparison parses (`ast`, never imports) `jarvis_presets.LANES` - the same table the apps render - and compares each lane's `card` claim with the cards its tracked task grants. A lane claiming "all three cards" while its task passes one UUID FAILS and names the exact value it should carry (all three UUIDs, comma-separated, in `nvidia-smi -L` order); a named card must be the card the task pins. The on-demand pooled lane has no logon task, and is NOT judged - comparing it would invent a grant that does not exist - and the run says so rather than passing silently. (3) **"NOT CHECKED" IS EXIT 3, NOT 0 AND NOT 1.** There is no live launcher on a fresh machine or a CI runner, so sections 2-4 print the exact sentence "not checked: no live launcher on this machine" and the process exits 3, never a pass; section 1 is hermetic, so CI still gets a real verdict on the repository half, and `--repo-only` runs only that half. (4) **THE DEPLOY REFUSES THE ONE-STEP.** `tools/reconcile_live_backend.py` runs the preflight BEFORE it plans and refuses both the dry run and the apply (exit 2, nothing written) when the repository and the machine disagree, printing "2-step deploy: update the lane task" with the exact task and the exact `-GpuUuid` it should carry; `--allow-lane-launcher-mismatch` is the explicit override and says out loud the disagreement is NOT fixed. A warning was rejected: a one-step deploy that leaves the machine unable to serve the model the repository names is exactly the failure this closes. (5) **NOTHING LIVE WAS TOUCHED.** No task, launcher, lane or model changed - this PR only makes the disagreement visible; when a later change really wants the everyday lane on all three cards, its PR updates the tracked task table (and CI then requires the lane table to match it) and the machine's task is step 2 of the deploy.
