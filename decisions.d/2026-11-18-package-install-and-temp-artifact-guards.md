- **2026-11-18 — A package install is refused when it would write into the repository, and its leftovers are checked for:** Decided after the 2026-11-18 incident - a delegated agent ran pip with the repository root as its working directory and TMP/TEMP inside the tree, and seventeen `pip-metadata-*`/`pip-unpack-*` folders sat at the root, untracked and one `git add -A` from being committed. `tools/check_package_install_context.py` refuses that context for pip and for uv BEFORE the install runs, names the offending folder and says the fix ("run the install from a scratch directory, or set TMP/TEMP outside the repo"), and has a `--run -- <command>` wrapper so the delegate path can let the guard do the refusing instead of remembering a rule. A context it cannot judge - an unknown manager, a platform that is neither Windows nor POSIX - is printed as "not checked: <why>" and exits 3, never a pass; that is the project's BLOCKED-is-never-a-pass rule, and it is why this guard may not quietly return 0 on a machine it does not understand. `tools/check_package_manager_temp_artifacts.py` is deliberately the second half rather than duplication: a guard that is bypassed must not be followed by silence, so a tracked or untracked root path matching pip's temporary folders, a root `*.dist-info` or a tracked root `node_modules` fails the check, which then names each path and the command that removes it. It looks at the root only, not inside the tree, because a `pip-*` name in a test fixture and a temp folder under the ignored `.dsh-scratch/` are legitimate and the incident's folders were at the root. Both run in the audit job, and the install guard's step sits before that job's own pip install, so a working directory or TMP regression stops the install rather than being discovered after it. No existing check was weakened: the required jobs' behaviour is unchanged, and `backend/test_package_install_guards.py` proves every branch can fail on fixtures it makes and removes.
