- **2026-11-18 — A preset apply has to PROVE the lane, and a tripwire guard must never quietly switch the check off:** `apply_preset` now reads the target lane's `/api/ps` through a `verify_lane` seam and refuses - rolling the model record, the lane pointer and the chosen preset back - unless the lane shows the model the preset names, with no CPU spill and at a window no smaller than the preset's own. The judgement calls in that check, all made against the A2 field test (DEF-088: a `general` apply reported success while 11436 served the pooled coder at 8,192): (1) **an EMPTY lane is not a failure.** A preset apply records which model chat should use; Ollama loads it on the next turn at the lane's own window, so failing "nothing is loaded" would red-flag the most ordinary apply there is. Only a model that is not the preset's, any spill at all, a window smaller than the preset names, or a lane that does not answer is a failure - "could not tell" is never a pass. (2) **A probe names the window whenever it can, and never goes silent when it cannot.** Every tripwire request carries `options.num_ctx` from the lane's own configured window; for an address this program does not know as a lane (`OLLAMA_URL` unset means 11434, so every fresh clone and every CI run) the request goes out without the field - `main`'s own request - because a guard that stops the smoke test there is a check disabled by a guard, worse than the gap it closes, and naming a guessed window would force the downgrade instead of leaving Ollama's configured default in charge. The first cut of this refused on "window unknown" and turned `backend/test_reversible_ui_choices.py` red: that suite loads the base model steward with no `OLLAMA_URL`, so the refusal fired and the tripwire it asserts never ran. (3) **A pooled outgoing model is SKIPPED, not re-aimed at the pooled lane.** The alternative - probing it on the pooled address - would still load a stale name there and cannot answer "how did the old model answer" after `apply_preset` has stopped that server; a skip cannot load the wrong model on the wrong card even when the pooled lane is down. (4) **The lane reader is for the real HUD process only.** Two things decide that: `JARVIS_SUITE_RUNNING`, and the process actually running `jarvis_hud.py` (the same test `_warm_on_startup` uses, and the real backend on this PC is `python.exe ...\jarvis_hud.py`). The second half is there because the first was not enough: a suite that loads the base's model steward directly never sets the marker, and the reader answered from the owner's LIVE 11435 mid-test. Inside anything else the default says `checked: false` and that it is NOT a pass; a suite that wants the real reader passes `_default_verify_lane` itself with a fake lane of its own, which is how `backend/test_preset_switch_lane_guard.py` proves it. This is a bug fix with no permission, route or approval-tier change: the two `switch_model` cards, the app-click rule, and the receipt/Undo path are exactly as they were.
