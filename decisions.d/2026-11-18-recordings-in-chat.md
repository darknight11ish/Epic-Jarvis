- **2026-11-18 — A recording attached in chat is transcribed by `jarvis_media_read`, and its decode is the one thing the attachment reader writes:** the owner's report was that an `.m4a` voice memo could not be attached from the app's chat "Attach a file" row. The cause was not a missing feature but a picker narrower than the PC's capability: the chat row offered the eight document types, while the PC's own audio reader already read `.wav .mp3 .m4a .aac .flac .ogg .opus .wma` for a file in a listed folder. So the chat row now offers exactly those eight (the canonical type plus the aliases a provider really reports, `audio/x-m4a` beside `audio/mp4`; the extension decides before any provider type), and `jarvis_attached_file` routes the bytes to that SAME reader's new bytes door - the local speech model on this PC, never the document converter, never the phone. **Where the bytes go, decided deliberately:** a WAV is decoded in memory with no ffmpeg and no file; a COMPRESSED recording (M4A, MP3, AAC, FLAC, OGG, OPUS, WMA) is copied to ONE private temporary file for the length of the decode only and deleted in a `finally`, because an MP4/M4A keeps its index at the end and ffmpeg cannot decode one from a pipe (measured: a 100 KB non-faststart `.m4a` on stdin produced a 78-byte WAV header and "partial file", while the same bytes through a real file decoded). That copy has a random name, is never the owner's file name, is never indexed or kept, and `backend/test_media_read.py` proves it is gone after a read and after a refusal. This is a deliberate, narrow exception to `jarvis_attached_file`'s "never written to disk" promise, which still holds for every DOCUMENT. **The refusal is the reader's own:** with no ffmpeg the owner reads `jarvis_media_read.NO_FFMPEG` verbatim - no second sentence is invented - and a busy or speechless recording keeps that reader's own words too. **The picker is not `*/*`:** it keeps the rule "every type the PC has a reader for", so a type the PC cannot read is not offered; no offered document type was found unreadable, so nothing was removed. Video is deliberately NOT offered in this row even though the reader can read one (one attachment is at most 2.5 MB, and the row is the owner's voice memo), and the desktop's own attach list keeps its eight document types in its own lane - both said in `docs/ARCHITECTURE.md` section 8 and `docs/JARVIS-API.md` section 163.6. The read is still decided under the existing `read_files_readonly` gate before a byte is touched, the conversation is still marked as having read outside text, and the wire format is unchanged.
