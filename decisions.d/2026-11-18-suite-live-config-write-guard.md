- **2026-11-18 — A suite or probe cannot write the owner's live settings, and the guard reads the project's own marker:** The review ruled, verbatim: "Keep the harness rule (`scratch --config-dir` only) AND add a fail-fast guard so `JARVIS_SUITE_RUNNING` / probe helpers cannot write to `~/.openjarvis/` without breaking legitimate owner-card flows." The incident it answers: a lane admitted it briefly wrote the owner's live config while probing - it turned the escalation switch off and lowered his money cap to $5, then restored both - and while it did, the app showed him a card saying "$5.00 of $5.00" while the money file said $10.00. What was built, and the judgement calls: (1) **the marker is the one the project already uses, never a second mechanism.** `backend/_where.py` already sets `JARVIS_SUITE_RUNNING=1` for every suite, and two shipped behaviours already read it, so the guard reads that same variable; a new "is this a test" flag would be a second thing to keep right and could disagree with the first. (2) **the live folder is the owner's `~/.openjarvis`, resolved from `~`, never from `CONFIG_DIR`.** A process with `OPENJARVIS_CONFIG_DIR` / `JARVIS_CONFIG_DIR` pointing somewhere temporary is already safe - that is exactly what `backend/run_suites.py` gives every suite - so the guard exists for the target that reached the owner's own folder anyway (a hard-coded default, a resolver that ran before the override was set, or a probe that built the path itself), and an override that names the live folder is still the live folder. (3) **it refuses by raising, never by redirecting silently.** A silent redirect would let a suite that believes it wrote the live path report a pass it never earned, so `refuse_live_config_write(path)` raises `LiveConfigWriteRefused` naming the file, saying nothing was written, and asking for a temporary `--config-dir` / `OPENJARVIS_CONFIG_DIR`; it is called before any folder or file is created, so a refused write leaves the owner's folder exactly as it was. (4) **reads stay allowed and the live backend is untouched.** A suite may still read the owner's live settings and ledger - that is how the battery measures - and no shipped module ever SETS the marker, so the live HUD process cannot trip the guard and the owner's card flows that write these files are unchanged; a test without the marker writes and reads the same files normally. It is wired into the writers this branch owns: `chatbot/api-money.json` (`jarvis_chatbot_api._save`, the monthly cap and spending ledger in one file) and `model-state.json` (`jarvis_models`), and `backend/test_live_config_write_guard.py` proves all four arms with the real writers; the guard itself is also asked about the two preset files and refuses both live paths by name. **The honest scope limit:** `escalate-cloud.json` and `cloud-choice.json` are written only by `jarvis_presets.py`, which this lane's brief forbids touching (a parallel lane owns it), so those two writer calls are not wired here - each is one call to the same guard and is a follow-up for that file's owner, and the harness rule (scratch lanes pass a temporary settings folder) covers them in the meantime. The base-only `jarvis_models.py` half reaches the owner's PC on the next base install, the same route every base-only fix takes.
