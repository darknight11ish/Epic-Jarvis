- **2026-11-18 — The tool diet gets a named-thing floor instead of more hint words:** the owner's live battery (eight questions about his own GitHub repository, 17:57Z) showed the deepest cause of Jarvis denying abilities it has. `TOOL_DIET_DEFAULT` ships ON, and `tool_diet_selection` shows a model only the tools whose hint patterns match its words. Every GitHub tool's hints open with `github` - but the owner names his repository "Epic-Jarvis", not "GitHub" - so "what is the latest commit on main in Epic-Jarvis?" matched only `web_search` ("latest") and `feature_guide` (a settings tool, whose `\bis the .* (?:on|off)\b` hint matched "is the … on" by accident). Two incidental matches counted as a "recognised subject", so the safe full-list fallback did not fire either, and every GitHub tool was hidden. A model cannot call a tool it cannot see, and it then truthfully reported the limitation as if it were the product's. **What was chosen, and what was rejected.** Not more hint words: a hint is a score, so a competing word can beat it, the top-K cap can crowd it out, and every new phrasing would need its own word - while the live failure was never about a missing word, it was about the owner's object words being different from the tools' description words. Not a description-matching floor either: every GitHub description contains "commit" and "repository", so that would have added ten tools to one question. The chosen rule is a floor: `NAMED_ACTION_TOOLS` maps the owner's own object words (repository, pull request/PR, commit, branch, defect register, workflow/CI) and his repository's own name (from `jarvis_github.OWN_REPO`, so there is no second copy of it) to the READ tools that answer about that thing; `named_action_floor` adds those to whatever the hints chose, first, and the cap grows to fit them rather than cutting them. Hints are unchanged for everything else, so with no named thing the diet is byte-for-byte the top-K it was. **Why it is safe for a small model:** the floor adds at most the few reads for the things actually named (the battery's worst case is 3 tools, the eight average 3.9 against 10.8 before), it never adds a write tool on its own, it never exceeds the owner's enabled list, and it cannot make the list bigger than the diet cap for an ordinary question because it does not fire there - the ordinary controls still trim to 1-2 tools. **Why it does not weaken approval:** it changes only the SHOWN list. `check_call` reads `names`, the allowed list, and `_one_call` puts every call to `jarvis_gate` exactly as before, so hiding a tool was never refusing it and showing one is not running it; no gate table, no tier and no configuration line is touched (every GitHub read is card-free by the existing `github_inspect` auto row and all seven enabled GitHub writes remain in `NEEDS_A_PERSON` and raise their own card). **Honest limits:** the floor only knows the object words in its table; a question that names a GitHub thing in words outside it (a "milestone", a "release", "the head sha") is still dieted by hints alone - the fix covers the five objects the owner's own battery named, not every GitHub noun. It also cannot fix the other half of the same live run: where the tool was offered, the 9B model still chose not to call it or called it with a bare repository name, which is the deterministic fast path's lane (#1382).
