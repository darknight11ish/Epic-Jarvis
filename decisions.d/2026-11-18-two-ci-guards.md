(1) THE CAPABILITY SPLIT. `backend/test_capability_answers.py`'s 5,410-question reach ratchet caught a real cross-PR break on 2026-11-18 (two PRs each touched `backend/jarvis_quick.py`, each was green alone, and merged they changed each other's behaviour - main is red on "no ordinary shape lost its row", `cloud-escalation 63 < 65`), so the ruling's shape is implemented: every PR runs a CORE subset of 239 pinned cases - one ordinary question naming each of the 184 catalogue rows' own title, plus the 53 sweep answers the capability fix changed (the review's "~230"; its "180" was the live audit's row count), plus TWO dated known losses ("Does Jarvis escalate to the cloud?" and "What is cloud escalation?" now answer `cloud_settings` - tonight's red) that are printed as KNOWN LOST on every run, never counted as passes, and fail the step if any NEW case loses its row; the full sweep runs only when `features/features.json` or `backend/jarvis_feature_catalogue.py` (or its twin) changed. Measured 2026-11-18 (three runs): the suite with the sweep 32-36 s, without it 10.4-12.7 s, the `--core` shortcut 3.8-4.1 s, so the every-PR run is cheaper than before by about 22 s and the exhaustive ratchet is paid only when the catalogue moves. The path filter is computed in the workflow from `git diff` against the pull request's base sha, because ci.yml's `pull_request` trigger deliberately has no `paths:` filter (a filtered pull request would never report a required check) and GitHub has no per-job path filter. A core case is a question the full sweep already asks, generated by the same `_ordinary_shapes`, and `backend/test_capability_core_subset.py` proves the subset relation and that the mode switch fails closed. (2) THE LOCKFILE GATE. #1319 added `typescript` to `jarvis-desktop/package.json` without regenerating the lockfile, and eight `Desktop release` runs failed at `npm ci` for two days; the release-repair lane (#1386) deliberately left the gate to "its own CI change", which is this one. `tools/check_desktop_lockfile.py` makes the same three comparisons `npm ci` makes - a dependency missing from the lockfile's root package, a range disagreement, a missing resolved `node_modules/<name>` entry - plus name/version, with no npm, node or network, and prints `FIX   cd jarvis-desktop && npm install --package-lock-only`. It runs in the REQUIRED `frontend-shard` job (shard 1, about 0.2 s), which fans into the ruleset's required `frontend` check, NOT in `audit`: `audit` is informational and cannot hold a merge, which is exactly how two days passed. The release workflow keeps `npm ci` - `npm install` would hide the drift the strict install exists to surface - and `backend/test_desktop_lockfile_sync.py` proves the check fails on a deliberately desynced fixture pair, passes on the real one, and is wired into the required chain.
