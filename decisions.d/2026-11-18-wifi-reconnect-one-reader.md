- **2026-11-18 — The Wi-Fi reconnect row reads the PC's yes-or-no ONCE, and an unreadable state is never drawn as off:** the owner reported the Settings row saying "The auto Wi-Fi reconnect is already on. Nothing was changed." over an unticked box. Read from the tree before changing anything: the state was ON (the shipped default, with no `wifi_reconnect.json`), and the answer was right - `jarvis_wifi.enabled()`/`state()` return it, the GET/POST route sends it as the JSON boolean `enabled`, and the chat/Live sentences are composed from the same call. The widget was wrong, and it was wrong twice over from one answer: `jarvis-desktop/src/wifi-reconnect-settings.js` ticked the box from `view.on` (a field no answer has ever carried - so `view.on === true` was never true, and the box stayed unticked in every state) while it worded the line from `view.words`. The ruling is that one page may not read one answer two ways: `readWifi()` is now that page's ONLY reader of the PC's yes-or-no, it takes `enabled` and nothing else for the state, `paint()` ticks the box from its `on` and `describe()` words the line from the same `on`, so the tick and the sentence cannot disagree even if a future answer's `words` is stale or wrong. Three consequences are deliberate. (1) **The state word is the page's, not the backend sentence's:** `words` is still the PC's own sentence, but it is now used only where there is no on/off to name (a waiting card, a refused change) or as the last-check detail (`last_words`), because a sentence that can say a state is a second reader. (2) **Unknown is not off:** an answer without a boolean `enabled` is drawn unticked, greyed and said as unknown, and a PC whose saved setting file is damaged (`known: false`) is said as damaged - the same rule the Rust command already applies ("a state that cannot be read is not the same as a switch that is turned off"). (3) **The row's own copy says what it means:** "On to start, as you asked" became "On by default, as you asked; the switch shows whether it is on right now", because the old sentence read as a live state and was quoted back by the owner as one. Both apps were checked and only one changes: the phone deliberately has no Wi-Fi reconnect row - it cannot act on this PC's link, the route refuses every other device, and `tools/check_parity.py` carries `/api/wifi-reconnect` as `deliberate` with its reason written in ARCHITECTURE section 8. What this does NOT do, stated so the fix is not read as larger than it is: a card approved after the page has shown "waiting" is not re-read by this page on its own (that was already true and is unchanged), and the page still shows no network name, no password and no key. Tests: `jarvis-desktop/tests/wifi-reconnect.mjs` (12 runtime checks against the real page and a fake PC - both states, the owner's "already on" sequence, contradicting `words`, unknown/damaged answers, the waiting card, a refused change, and that a load writes nothing) and `backend/test_wifi_reconnect.py`'s new "the switch and the answer" checks (the route carries a real boolean `enabled`; the state and the chat/Live sentence name the same state in both positions).
