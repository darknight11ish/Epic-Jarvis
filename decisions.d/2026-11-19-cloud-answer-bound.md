- **2026-11-19 — A cloud answer is BOUNDED, not truncated, and a twice-failed coding turn gets a third chance at the cloud:** the external review's rulings 6.5 and 6.1, implemented together because both are about the same measured turn. **6.5, in the review's words:** "Add a concise-by-default instruction + a generous safety ceiling (`max_tokens = 4096` for standard escalations, `8192` for coding/deep analysis) - do NOT aggressively truncate hard answers." The measurement behind it: one escalated turn cost $0.002747-$0.0039 and was almost entirely output (2,152 completion against 84 prompt tokens, about 99% of the cost), so cost per turn is a length control - and a truncated hard answer costs MORE, because the owner pays for the retry. Chosen: `jarvis_chatbot_api.cloud_request_body()` is the one composer of a cloud request's messages and `max_tokens`; it sends a concise-by-default instruction as the request's only system message, in front of the owner's newest turn (user turns only, so the cloud lane's privacy cut is unchanged), and bounds `max_tokens` to 4,096 standard / 8,192 coding-or-deep. Those numbers are a ceiling, never a target: the measured turn's 2,152 is well under both, and the bound can only LOWER what the month's money check already priced. The second tier uses EXISTING signals rather than a new classifier - the router's own 0-1 complexity score (0.40 is Stage 1; 0.70 is the top band it already grows answers across) and `jarvis_router.is_coding_turn()`, which reads the Coding preset's own trigger words, a coder model's name, or the caller's tool-in-play answer. It is wired in `_open` in the HUD relay through `ollama-direct.patch`, the one function every hop of the degrade loop builds its request through, deliberately not one caller. The relay's existing cap call is not weakened: the composer records its ceiling on the lane state, and `cloud_request_cap()` can only lower the request to it, so a reasoning-inside lane that was being sent cap + 8,000 room (up to 16,000) is now bounded without ever passing the limit. **6.1, in the review's words:** "Keep the deterministic `complexity >= 0.40` pre-gate as Stage 1, and pair it with a 2-strike / local-failure fallback for coding tasks - do NOT replace it with raw log-probs." Chosen: Stage 1 is untouched; `jarvis_router` gains `note_local_failure(conversation)` / `local_failure_strikes()` / `reset_local_failures()` and a `choose(..., conversation=, coding=)` seam. After TWO local failures in the SAME conversation, a coding turn may pass the complexity stage even under 0.40; everything else still runs, in the same order - the cloud-model, no-lane, Lockdown, taint, image, file, screen, private and pasted-secret gates above it, the budget gate after it, and gate 6's owner-yes/standing-switch requirement at the end. So one failure does not fire it, a non-coding turn never does, and a private turn with two failures still stays on this PC; the count is keyed by conversation so a new conversation starts at zero, the store is bounded and holds counts only. **Rejected, and why:** lowering or removing the 0.40 pre-gate (the ruling keeps it, and a log-prob classifier has no measured evidence here), and putting the instruction in one client or one lane instead of the shared composer (every other escalation would miss it). **Honest limits:** this PR implements the router half of 6.1 - no HUD caller records failures yet, which is a separate change; the 6.5 patch line reaches a fresh install through the patch stack, and the owner's already-deployed HUD needs the usual deploy step (the reconcile delta table was outside this brief).
