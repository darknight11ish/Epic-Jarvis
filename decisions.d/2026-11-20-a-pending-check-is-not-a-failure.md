- **2026-11-20 — A check that has not finished is not a failure:** the external review's ruling 5.2, quoted: "(1) `plan_ci` must never classify `pending`/`queued`/`in_progress` statuses as 'failing' - group honestly as pending vs failing vs passing. (2) Read the PR's combined check set (both check-runs and commit statuses on the PR head) to match `gh pr checks`, and update `tools/field_battery.py` to compare against a settled PR and never treat `pending` as a failure." The measured bug was deploy #4's answer about pull request #1424: the owner asked *"What is failing on pull request 1424?"* and the answer said "2 CI runs are on the head commit and at least one did not finish successfully … 2 failing check(s): CI: pending Jarvis client: pending" while `gh pr checks 1424` showed both checks PENDING. Chosen: ONE helper, `_run_verdict`, splits workflow runs exactly as `_check_verdict` splits check runs - a completed run with `success`/`neutral`/`skipped` is fine, a completed run with anything else is FAILED, and a run that is not completed is PENDING (a queued or in-progress run has `conclusion: None`); `_run_split` feeds the failing headline (which now counts only failed runs and says "failed", never "did not finish successfully") and a separate still-going sentence, so a green-checks commit with runs still going says they are still going and a no-check-runs commit with only pending runs says "N CI run(s) are still going: names. Nothing is known about them yet - ask again when they finish." For the combined source, `_ci_result` makes the extra read after the plan's three (the plan is deliberately unchanged: its last step is the check-runs read the pull form is detected by) and `_ci_combined_checks` merges `/commits/{sha}/status` into the check list as check-run-shaped entries; a failed statuses read keeps the check-runs list and says it is check-runs only, because a failed read is not a claim that no status exists. **Rejected, and why:** adding the statuses read as a fourth planner step (it would change the plan's advertised shape and the `steps[-1]` detection); treating `conclusion: None` as red anywhere (the bug itself); calling a pending status or pending run "failing" to keep a simpler two-way split (the ruling names three groups, and "not finished" is not evidence of a failure); and treating an unreadable statuses answer as "no statuses" (a read failure is not an empty result - the same BLOCKED-is-never-a-pass rule the rest of the module follows). The battery side: `gh pr checks` exits 8 while checks are pending and `gh_json` rejected that, so the pending ground truth was thrown away - `_gh_checks` now accepts 0 and 8, reads `name,bucket,state`, the failing question requires a settled PR (gh `fail` and no `pending`), the running question requires pending without failed, and the answer checks match a count as its own number so the `1` in "#1400" cannot pass as a failing check count.
