- **2026-11-21 — PM5's production executor is an in-process scheduler tick owned by the Rust HUD:** Gemini's ruling 6 (2026-11-21) defines the executor PM3 deferred, and this supersedes the "no executor is defined" state: the thing that decides WHEN the next step runs is a timer inside the always-running desktop process (the Tauri Rust side that owns the HUD window and the tray), and the thing that decides HOW one step runs stays the existing `jarvis_tasks.JobList.tick()`, reused not re-invented. The backing state is on disk so steps survive app restarts, and the four reasons the HUD owns the clock are the ruling's own: the HUD is the always-on local orchestrator (started at login, and its Rust side already runs an always-on loop that works with no window open); cancellation is immediate (Stop is never gated, and the process that draws the button owns the timer, so no OS scheduler's cycle is in the way); live progress reaches the phone over the one existing `/api/events` stream and `/api/tasks` shape instead of a new channel; and there is no OS task-scheduler overhead (no Windows scheduled task registration, no separate service, no elevation, and nothing keeps running after the app quits). The invariants the build must keep are recorded in `docs/PM5-HUD-SCHEDULER-TICK.md` (STATUS: NEXT BUILD - NOT STARTED; nothing built, and no code, route, card or permission changed): one step at a time per task (the lease compare-and-set and one-step-per-tick rule, at most `MAX_IN_FLIGHT` 3); the owner's approval cards untouched (approving a job never approves a step, a timeout is not a no, rule 4 still holds); no new permission (no gate row, no card class, no new phone route, and the HUD page still holds no token); a failed step leaves honest state (the job fails, never the tick, and an action that might have left the machine is `outcome_unknown`); progress to the phone on the existing event stream/API shape; restart recovery from disk (the backend's `boot_once()` and lease rules, and a HUD restart simply resumes calling); and the existing `jarvis_tasks.tick()` semantics reused, not re-invented. The acceptance tests PM5 owes are named there: start, cancel, survive-restart, progress, live-progress, phone-read and failure-honesty. ONE design question is deliberately left for Gemini: where the persistent state lives and its schema - the existing `jarvis_tasks` SQLite store plus the loop's own control fact, or a Rust-owned file beside the desktop's state with the job state still in the store - because building the wrong store first is how a second copy of the truth gets made; no PM5 code is written until that is answered. What this changes today is the record, not the program: PM3's deferred Run Step dispatch now has a defined executor to land on, PM4's Run Step button is still not built, and `docs/ARCHITECTURE.md` section 8's "not built" list stays true for the build.
