- **2026-11-21 — Updates is the one card pinned first, a version line never outlives its moment, the card shows the bounded proof's own steps, and devices are cleaned only after a dry run:** the owner's four measured complaints of 2026-11-21 ~10:12 PT and Gemini's rulings 5.2, 5.4 and 5.6, settled in one change. (1) *"when i search updates in the settings i have to scroll all the way to the bottom of the list to find the update section for jarvis. it should be at the top of the list."* The ruling: a query made ONLY of update words (`update`, `updates`, `upgrade`, `upgrades`, `upgraded`, `upgrading`, `updater`, `updaters`, `version`, `versions`, and the handshake's own `sync`/`mismatch`) or of the update phrases (`check now`, the card's own button name, `check for update`/`check for updates`) pins the Updates card first in every box that can search for it - the Settings results, the app-wide Find list, and a one-row quick entry above the jump list - and shows it even when its own text contains none of the query ("upgrade" matched nothing). This is deliberately NOT a general "Updates always first" rule: a query with any other word in it is ranked as before, so no unrelated search is reordered. The Settings search and the palette import ONE vocabulary (`settings-search.js`'s `asksForUpdates`) rather than each keeping a copy, because the two boxes must never disagree about what "the update card" means. (2) Ruling 5.4's banner: while the backend half is behind or a backend half is being finished right now, a banner at the TOP of Settings - above every card - says so, names both versions and links to the Updates card, and it clears in place on a version read-back that says IN SYNC. It is a view of the same handshake the card reads, not a second state: a backend that is newer, two schemes that cannot be compared, and an unreachable backend get no banner, because "Update everything" is not what fixes any of them. (3) *"when i go to updates in settings it says none available when i click check for updates"* - true of a NEWER release, and misleading mid-update. The card's state line is now the release check AND the two versions together: equal halves with a finished check say "Up to date." plus the check's own line; a backend behind the desktop says which desktop is installed, which backend it found, and that "Update everything" is the one press that finishes it, with the check's line appended so a no-newer answer can never hide the back half; a backend half that is live right now says "Finishing the backend half now" and that the card updates when it ends. The "running" fact comes from the shell (`update.rs` marks a live backend half; `backend_self.rs` sends it to the page), never from a page guessing at elapsed time. And while a run has written its FILE half but not finished its own checks - the measured 0.2.492 proof run ended by the 3-hour ceiling at 20:32:11Z - the card does NOT say "Up to date.": it says the two halves are not claimed to match yet and names the restart whose handshake reads IN SYNC. (4) *"MISMATCH: the backend 0.2.491, but this HUD expects 0.2.492 ... this usually clears on its own" stayed visible after the backend half had finished.* The HUD's version line is now ONE note rewritten in place: the mismatch, the run's "finishing the backend half now" opening, and every ending (whose words carry the versions RE-READ after the attempt) replace each other; an "ok"/"in-sync" read-back removes it. A warning about a mismatch is never left standing after the mismatch is gone, and no manual restart is needed for the page to tell the truth. (5) Ruling 5.2's progress line: the app-path proof is the bounded 4-phase subset (5.1), and it now prints `PROOF: Step N/M - <phase> - x of y` lines that `update_progress.rs` carries verbatim as `VersionSync`'s sibling field `proof`, which the Updates card renders as one clean line (`Step 3/4: Live invariants - 8 of 12…`). Only that exact shape is a step: the proof stage's five-minute `PROOF: still running - ...` heartbeat (the silence guard's sign of life) and the older full sweep's suite lines are NOT, so a legacy run keeps the card's existing words rather than inventing a count. The 5-minute heartbeat and the 15-minute silence bound stay underneath exactly as they were - the card line is drawn from the same output, never a replacement for that guard. (6) Ruling 5.6: Settings -> Devices gets an owner-card-approved, **dry-run-first** "Clean up duplicate/inactive devices" button. Press -> the PC's own `would_remove` list, with names and days since each was last seen; anything active within 30 days is preserved by the PC and never offered; nothing is auto-pruned on load or on a timer; only the confirm applies it, and that press ends in the PC's own `devices_cleanup` approval card (`POST /api/devices/cleanup`: dry run -> the list; confirm -> 202 while the card waits, 200 `{removed, kept}` after approval). The dry run is a read and is never held on a stale link; the confirm is an action and is. The desktop's `devices_cleanup` command is the one door to that route (`devices.rs`, registered in `lib.rs`, its own permission in the settings-surface set). Untouched on purpose: both-or-neither, the install gate, the approval model, and the tray - these are the cards' words, one line's lifetime, and one housekeeping door, not a new update path.
