- **2026-11-21 — Updates is the one card pinned first, and a version line never outlives its moment:** three owner reports from 2026-11-21 ~10:12 PT, settled in one change. (1) *"when i search updates in the settings i have to scroll all the way to the bottom of the list to find the update section for jarvis. it should be at the top of the list."* The ruling: a query made ONLY of update words (`update`, `updates`, `upgrade`, `upgrades`, `upgraded`, `upgrading`, `updater`, `updaters`, `version`, `versions`) pins the Updates card first in every box that can search for it - the Settings results, the app-wide Find list, and a new one-row quick entry above the jump list - and shows it even when its own text contains none of the query ("upgrade" matched nothing). This is deliberately NOT a general "Updates always first" rule: a query with any other word in it is ranked as before, so no unrelated search is reordered. The Settings search and the palette import ONE vocabulary (`settings-search.js`'s `asksForUpdates`) rather than each keeping a copy, because the two boxes must never disagree about what "the update card" means. (2) *"when i go to updates in settings it says none available when i click check for updates"* - true of a NEWER release, and misleading mid-update. The card's state line is now the release check AND the two versions together: equal halves with a finished check say "Up to date." plus the check's own line; a backend behind the desktop says which desktop is installed, which backend it found, and that "Update everything" is the one press that finishes it, with the check's line appended so a no-newer answer can never hide the back half; a backend half that is live right now says "Finishing the backend half now" and that the card updates when it ends. The "running" fact comes from the shell (`update.rs` marks a live backend half; `backend_self.rs` sends it to the page), never from a page guessing at elapsed time. (3) *"MISMATCH: the backend 0.2.491, but this HUD expects 0.2.492 ... this usually clears on its own" stayed visible after the backend half had finished.* The HUD's version line is now ONE note rewritten in place: the mismatch, the run's "finishing the backend half now" opening, and every ending (whose words carry the versions RE-READ after the attempt) replace each other; an "ok"/"in-sync" read-back removes it. A warning about a mismatch is never left standing after the mismatch is gone, and no manual restart is needed for the page to tell the truth. Untouched on purpose: both-or-neither, the install gate, the approval model, and the tray - this is the card's words and the line's lifetime, not a new update path.
