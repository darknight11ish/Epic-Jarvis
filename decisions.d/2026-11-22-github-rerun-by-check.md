- **2026-11-22 — A named check can be re-run, and the CI answer names its run:** The external review's ruling 5.2 (15:45 PT, item 5.2) was to extend `github_rerun_workflow` to accept `(pr, check_name)` and resolve `run_id` internally, AND to include `run_id` in `github_ci_status`'s output, because "That avoids adding a new gate row or base-file repair while immediately unblocking the 30B model." The measured failure: on the live app the owner asked for "the face-shots check on PR 1471 in darknight11ish/Epic-Jarvis" to be run again, the model tried, looped for about 48 seconds and gave up saying it could not find the workflow run id - no read the model has returned one. Both halves of the ruling are built exactly, and the shape that keeps the safety story intact is that the resolution is a PLANNING read, not a new action: three GETs (the pull request, its head commit's check runs, that commit's workflow runs) change nothing, and the id they find BECOMES the run id on the card, the same reason `plan_merge_pr` already reads the pull request itself (2026-11-15) - a card has to name the run it will re-run, so the id must be read before the card exists. The request built is the same ONE `POST .../actions/runs/{id}/rerun` under the SAME `github_rerun_workflow` action at `ask`, through the same plan/describe/run split; no gate row, no new action, no second card, no base-file repair. The match is case-insensitive and tolerant only of a suffix after a separator, so a matrix leg ("face-shots (2/2)") matches "face-shots" while `backend` never matches `backend-windows`; a FAILING match is preferred over a passing one, because after a red CI answer that is what the question means. A name that matches nothing is refused in ONE plain sentence that prints the check, the pull request and the repository; a name that matches more than one RUN is refused in ONE sentence that prints every candidate and points at the run id, because picking one for the owner would be a guess about which CI to spend. Nothing is re-run in either case, and neither refusal raises a card. `github_ci_status` keeps every sentence it had and adds the facts: the failing check's own run id and attempt, every run id on a pull request's head commit, and the newest run's id and attempt on a branch read - so a model reading CI can act on the answer even without the check form.
