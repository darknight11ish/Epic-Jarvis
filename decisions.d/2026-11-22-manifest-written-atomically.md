- **2026-11-22 — The deploy manifest is renamed into place, never written in place:** the external architecture review's ruling 5.5 named the window, and it is a real one because a `DEPLOY-MANIFEST` is the updater's deploy evidence: `tools/update_backend.py` refuses the whole update in a corrupt marker's own words, so a truncated record left by a killed write is worse than an old valid one. The fix is the smallest one that removes the window - `tools/reconcile_live_backend.py`'s `apply_deploy_manifest` writes the identical planned bytes to a sibling `DEPLOY-MANIFEST.tmp` and calls `os.replace(tmp, target)`, which is atomic on one filesystem, so a killed process leaves either the old valid record or the new valid record. The success path is unchanged on purpose: same deterministic bytes, same seal, same backup of the old record, same read-back proof, no new option, no new output line and no new route. It deliberately does NOT `fsync` the temp file before the rename: the failure this answers is a killed or crashed process, which the rename covers, not a power loss that would need durable ordering; if power-loss durability is ever required, `fsync` on the file and its folder is the addition, and that is a separate decision. A rename that fails is reported as a failed write and leaves the old record intact; a sibling `.tmp` file may remain until the next run overwrites it, which is harmless because nothing reads it. Proved by `t_a_manifest_write_killed_before_the_rename_keeps_the_old_valid_record` in `backend/test_reconcile_live_backend.py`, which monkeypatches `os.replace` to raise between the temp write and the rename, checks the complete new record was in the temp file, and checks the old manifest's bytes and its parse; it fails on the pre-change tree and the full suite is 894 checks, 0 failed after.
