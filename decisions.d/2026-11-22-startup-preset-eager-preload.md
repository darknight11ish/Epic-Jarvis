- **2026-11-22 — A preset the owner marks loads eagerly at start-up, and the reconcile runs only when it cannot:** The owner asked for the General preset to be "the default that loads anytime jarvis is reset" and to "set the default presets that load when atlas is restarted through chat or settings", and chose eager preload (~a minute, ~15 GiB of card memory) over a lazy first-message load. The setting is its own file, `startup-preset.json` (`{"preset": "<id>"}`, absent means none), deliberately NOT `presets-choice.json` - that file records the last apply and the restart reconcile deletes it when the on-demand pooled lane is gone, which is right for a click and wrong for a choice made on purpose. Setting it raises ONE `change_own_config` card (tier `ask`) and writes nothing before the yes; clearing is a tightening and is instant; an unknown id, the Cloud row and a pending preset refuse before any card. The start-up step applies the preset through the ROUTE's own road (`_apply_body(..., owner_ui=True)`, exactly what `POST /api/work/apply` runs) rather than a second implementation, and raises no second card because the card that saved the setting was the yes. **It also asks for `keep_alive: -1` on that same load**, because idle eviction defeats an eager start-up preset: measured on this PC, General was applied at 02:41 and Ollama's idle timer had unloaded it by 10:30 (`/api/ps` on 11450 empty while `/api/work` said `chosen: "general"`). The option travels the existing loader (`_apply_body` -> `apply_preset` -> `start_lane` -> `start_pooled_lane` -> `load_coder` -> `load`, one extra field on the `/api/generate` body it already sends) and every other caller sends exactly what it sent before. It is bounded twice, by rules that already exist: one preset's model at a time means any later apply ends this lane first (so no second copy is resident), and the owner's rest hours - `[power]`'s `schedule_enabled`/`quiet_start`/`quiet_end` via `jarvis_power.schedule_drop()`, the same reader the power rules use - turn the hold off when a window is active, or when the clock cannot be read, with the reason recorded. There is no `[energy]` rest-hours setting (that section is the measured-watts record), so none was invented. Order is the rule: the restart reconcile deletes the remembered choice, so it runs only when the configured preset could not load - and then it runs exactly as before, with both sentences kept in `restart_reconcile` (`preset` is the start-up preset, `remembered_preset` the choice that was cleared), so a start that cannot do what the owner set is never silent. The load runs in ONE daemon thread so it never delays the HUD's first request; with no start-up preset the reconcile stays synchronous and byte-for-byte what it was. The chat sentences need a start marker as well as the word "preset", so "use the General preset" still applies now and does not become a setting. No gate row is added (`change_own_config` covers a config change), no phone route, and the desktop Settings page belongs to another lane. The route is wired by `jarvis_presets.install()` (the module `presets.patch` installs), so no patch dispatches or needed changing for it. Proved by `backend/test_startup_preset.py` (111 checks; the failed-apply fallback row is the one that fails on the pre-change tree; the stacked-chain row rebuilds `jarvis_hud.py` from the real patch stack with `_stack.stand_in`, installs every wrapper after the presets block and proves the new path still reaches the writer, and `jarvis_quick.answer()` is proved to execute the sentence through the same writer), `backend/test_pooled_lane.py`'s new `t_a_pooled_start_can_ask_the_model_to_stay_resident`, and `backend/test_presets_owner_ui.py`'s "exactly three literal callers" pin, which now names the start-up preload as the third with its reason.
