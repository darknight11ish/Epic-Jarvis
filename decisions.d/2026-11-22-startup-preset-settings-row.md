- **2026-11-22 — The start-up preset is chosen from Settings through ONE narrow command, not a general route poster:** The owner asked for the General preset to be "the default that loads anytime jarvis is reset" and for it to be settable from the app, and the backend lane had shipped `startup-preset.json`, `POST /api/work/startup-preset` and `GET /api/work`'s read-only `startup_preset` block with only a chat sentence to set it. This change adds the Settings row and the one desktop command behind it. The command is deliberately `set_startup_preset` and nothing wider: it accepts one preset id (the empty string clears it), posts it to that ONE route, and returns the route's JSON unchanged. A generic "post any route" command was rejected - the page holds no token precisely so that a script in it cannot reach an arbitrary route, and one narrow door keeps the widening reviewable. The answer is passed through rather than re-worded by Rust because the route is the thing that knows whether a card is waiting, was approved, was Denied (a 200 with `ok: false` and `card: true`) or refused before any card (400/409); the page repeats the PC's sentence and only supplies a fallback when the PC said nothing. The read reuses `get_focus_presets` (`GET /api/work`), so no second read command was added and the row knows no preset id or name of its own. Setting a preset is a standing change to what the PC does on its own every time it starts, so it keeps the PC's ONE `change_own_config` card and nothing is written before the yes; clearing is a tightening and stays instant. The row states the card rule in plain words before the press, and its own note says a chat sentence writes the same setting, so the value is refreshed when the card is opened and when a stale link comes back rather than claimed live. Desktop-only on purpose: the setting is a per-PC choice, the route stays PC-only, and neither the phone nor the HUD gains a control.
