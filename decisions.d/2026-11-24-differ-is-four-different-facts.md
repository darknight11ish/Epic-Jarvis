The comparison was true and useless, and the sentence beside it claimed success, so a correct update read as a broken one. `jarvis-desktop` now asks git (`merge-base --is-ancestor`) instead of comparing the two version numbers, because the version is a CI run number and two different trees legitimately both call themselves 0.2.502. The answer is one of five: `Same` (one release - the only case in which "Both halves are done" may be said at all), `BackendAhead` (the app's commit is an ancestor of the backend's: newer, benign, and the sentence says so and says the next desktop update catches up), `AppAhead` (the backend is older than the app talking to it - the one direction that must be fixed, naming "Update everything"), `Unrelated` (neither commit contains the other, so nothing may be claimed about which is newer, and the sentence says to read the log rather than guess), and `Unknown` (a commit or git could not be read). The rules that make this safe rather than decorative: the completion clause is derived from the SAME classification, so a card can no longer claim "done" beside a difference; an unreadable answer is `Unknown` and never `Same`, so a missing or failing git can never read as a match; and the classification stays a pure function of the two commits plus git's two ancestry answers, so every sentence is provable without a repository.
