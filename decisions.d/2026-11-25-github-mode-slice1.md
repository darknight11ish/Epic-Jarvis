- **2026-11-25 — Full GitHub mode is a second standing permission, and it is GitHub-shaped only:** the owner asked for "a full github mode that gives full parity with less restrictions and less cards ... enabled in chat or settings and forwards anything necessary to the cloud api", and this slice adopts it as ONE PC setting, `<settings>/github-mode.json`, that is both the mode's state and a second gate-6 standing yes beside the Presets menu's Cloud switch (`escalate-cloud.json`). The standing-permission rule in `docs/ARCHITECTURE.md` said one action only; it now names exactly two, and the reasons the second is narrower are the decision itself. (1) **One file, not two facts.** The design first wrote the mode as a setting and the standing yes as a second file; two records one switch must keep in step disagree on the day "off" is on, so the mode and the standing yes are the same file, written only after the mode's own card and read only by `jarvis_router.github_mode_escalation()`. (2) **GitHub-shaped only.** The reader is consulted at gate 6, after every privacy gate, and only when `github_shaped_turn()` says the newest message is about GitHub work - a repository, a branch, a pull request, CI, a workflow, a merge or a push. A second whole-cloud switch is wider than the owner asked for and would make the card's words false, so the Presets switch stays the one that covers every hard question. (3) **It lifts no refusal and loosens no tier.** Lockdown, taint, pictures, attached files, screen words, private topics, pasted secrets and the self-repository gate all still answer local first; merge, push, open a PR, comment, re-run, create-repo, workflow, labels, edit-PR and review each keep their own `ask` tier and their `NEEDS_A_PERSON` entry, and a verdict with nobody asked is still refused when the mode is on. (4) **The per-file approval is the second standing permission**, and it is the same shape the web-search grant already established: `github_fix_write` only, keyed on the request's own conversation id, capped at 8 hours, in memory only, ended instantly by turning the mode off or by Lockdown, and logged through the gate's `grant_made`/`granted`/`grant_ended` lines without ever writing the conversation id down. It is written only after the mode's card was approved on the PC with Windows Hello - the model can ask, never decide. (5) **Both doors, one implementation.** The Settings row and the chat tool call the same `jarvis_asks_first.set_github_mode`, so they raise the same card and cannot disagree; ON is refused away from the PC with `403 pc_only`, OFF is instant from either app. The desktop row, the phone row and the API page read one payload object, `tools.github_mode`, with `on`, `can_enable`, `effect` and `where`; the phone reads only that object and may send its OFF through the existing `POST /api/asks_first/tools`, while every per-tool switch stays desktop-only.
