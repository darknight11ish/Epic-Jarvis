- **2026-11-26 — A naming word is what makes "add a note" a create:** Measured on main at `b854e7138` with `JARVIS_BACKEND` cleared, `Q.match("add a note titled Ideas 2027")` answered `note_change_refused` while `Q.match("create a note titled Ideas 2027")` answered `note_create {"name": "Ideas 2027"}`. Two regexes in `backend/jarvis_quick.py` and its `jarvis-backend/` twin disagreed about the same words: `_NOTE_CREATE_NAMED` accepted only `create|make|start`, while `_NOTE_CREATE_REFUSED` accepted `add` and the bare `new note` shape, so a fully named create was claimed by the refusal first. The ruling: `add` is a create verb and the bare "new note called X" is a create shape, but only when one of the three naming words follows the note noun. That requirement is the safety of the change and must not be relaxed - without it "add a note Ideas 2027" would start creating a named note instead of filing the owner's words into the daily note, and "add a note" would ask for a name where there is nothing to file. Deliberately unchanged: the four-fact reader `_CREATE_NOTE_HEAD` (so "add a note called X and pin it" still asks for the name rather than dropping the pin clause), `_NOTE_CREATE_SHAPE` (so "add a note" stays the refusal and not the ask), and the lane's own name rule. Two measured limits are recorded rather than hidden: PR #1525's API/tool-call half of DEF-105 is open and not in main at `b854e7138`, so `jarvis_note_capture.note_name_problem` still refuses the sentence on that path; and the chat create lane is `jarvis_notes_edit.handle_create`, not `jarvis_note_capture`, so after this route change "add a note titled delete everything" is filed as `delete everything.md` in a throwaway vault - exactly as "create a note called delete everything" already was on unmodified main.
