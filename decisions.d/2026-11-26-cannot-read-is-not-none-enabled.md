- **2026-11-26 — "Cannot read it" is a different answer from "none switched on", and a wake phrase is a setting, not a catalogue word:** Two of the three measured honesty defects the awareness audit found are fixed here; the third is filed and pinned, not half-fixed. WHAT WAS DECIDED FOR H2 (a failed settings read reported as a fact). One reader decides, and it can say "I could not read it". `jarvis_asks_first.tools_enabled_read()` returns `{"names": set|None, "why": str, "path": str}`; `names` is None exactly when the read failed, and `why` is a plain sentence naming which read failed (no reader on this PC / file not found / could not be read / could not be parsed / no TOML reader). `tools_enabled_set()` stays as the set-only view because four of its five callers only DRAW - the "New — currently off" pills, the GitHub group card, the tool page's rows and the tool route's own before/after - and none of them has a place to put an unknown; a caller that TELLS the owner a count now uses the new read. `jarvis_self_portrait.tool_inventory()` is that caller and returns `enabled=None` plus the reason, which is the contract its own docstring has promised since 2026-11-04; the five tool count answers in `jarvis_quick.py` already had the "I cannot read which of them" branch for `enabled is None`, so no answer text had to change. An empty configuration is proved against the file itself before it is called "names no tool", because `load_framework()` returns `{}` for both an empty file and an unparseable one. Two answers keep their old shape on purpose: the tool page still DRAWS every switch off when the file cannot be read (it has no words), and `_run_tools_settings` marks nothing but does not say why - both live in `jarvis_quick.py`/`jarvis_settings_registry.py`, which this lane may not edit. WHAT WAS DECIDED FOR H3/H4 (the wrong wake phrase). The catalogue row's title is a PHRASE ("Say \"Hey Jarvis\""), generated from `features/features.json:59` into `backend/jarvis_feature_catalogue.py`, and a phrase typed at generation time cannot know which phrase a given PC answers to. The 2026-11-25 ruling is explicit that an existing PC is never re-pointed, so a PC left on `hey_jarvis` must be told `hey_jarvis`. The ruling therefore is: THE ONE LIVE WORD IN A FEATURE ANSWER IS READ, NOT TYPED. `jarvis_feature_guide.display_title(row)` reads `[voice] wake_phrase` through `jarvis_framework.section("voice")` at answer time and returns `Say "Hey Atlas"` / `Say "Hey Jarvis"` / `Say the phrase this PC listens for (I cannot read which one it is right now: ...)`, and every answer that names the wake row goes through it. Only DISPLAY is overridden: `find`/`find_exact`/`_name_tokens` and `_feature_facts()` keep the catalogue's own title, so no question moves lane and the facts the model's tool returns still say what the feature list says. TWO EXISTING SUITE PINS MOVED WITH THE BEHAVIOUR, because they required the catalogue's stale title IN THE ANSWER (`backend/test_feature_guide.py`: eight `row["title"] in text` checks; `backend/test_feature_detail.py`: the "quote >=5 own fields" walk).
