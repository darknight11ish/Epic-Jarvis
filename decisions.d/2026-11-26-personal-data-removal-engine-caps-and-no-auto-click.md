- **2026-11-26 — The data removal engine files at most 20 brokers per card and 250 emails a day, never clicks a confirmation link, and is the only place allowed to say a listing is gone:** PR 2 of the personal data removal tool puts the local engine behind four decisions, and each one is a boundary rather than a feature. (1) **The batch rides the EXISTING `send_email` ask-tier action**, one card per batch instead of one card per email: what the card authorizes really is mail leaving this PC from the owner's own account, and reusing the action means no new gate row, no new tier line and no new settings key - the route PR 1 took with `change_own_config`, and the route that keeps a settings file which has already loosened `send_email` from turning a consent into nothing (a loosened tier is refused with the tier named, before any card). The caps are hard and are the spec's own numbers: **20 brokers per card** is applied when the batch is picked, so a card can never name 21, and **250 a day** is counted from the tracker's own `sent_at` for today rather than from a counter in a file, so restarting this PC cannot reset it and the second batch of a day is smaller rather than refused after the fact. A denial, a timeout, a refusal and a crash all send **nothing** and write **nothing**: the request rows are written only inside the card's own decision and only after a person's yes, which is what makes "deny writes nothing" a property of the code rather than a promise. (2) **A confirmation link is never clicked for the owner.** The scan moves the row to `needs_verify_click` and stops there: an automated click on a deletion confirmation is exactly the kind of action this tool must not take on his behalf, and a request he has not really confirmed is not a removal. An ID request moves the row to the same status with a note saying it is his own step, and the note never copies the broker's words back, because a reply can quote the very address the tool is asking it to delete. (3) **`removed` is written in ONE place, and only for evidence.** A broker's completion email moves the row to `pending_window` and no further - the window is still running and a company's own sentence is not a listing that is gone. The verify pass marks a row removed only when its `verify_after` has passed and a recorded `listing_url` answers **200** with enough text to be a page, no CAPTCHA/Turnstile/Cloudflare interstitial and none of the owner's own markers on it; a 403, a 404, a timeout, an empty body and a challenge page are all `unverified` and change no status. A confirmed removal sets `relist_check_at = +90 days`, because brokers re-scrape public sources and a removal is not a one-off erasure. (4) **The broker directory is cached, never vendored.** Optery's Open-Source Data Broker Directory is 766 KB of third-party data under **CC BY-NC-SA 4.0** (Optery, Inc.); this product is non-commercial by the owner's own ruling, so the licence is compatible, and the credit and the source URL are written into the cache itself so they travel with the data. It is downloaded to `~/.openjarvis/privacy/brokers.json` on the owner's PC and never committed: a snapshot in the repository would be stale the week it landed, would make every refresh a code change, and would put a third party's data into a public tree. Entries with neither a privacy email nor an opt-out page are counted and left out rather than imported as dead ends. Two things stay exactly as PR 1 left them: **the module is still NOT in `_where.SHIPPED`** - every call site stays a guarded import, so the published base, which does not carry it, imports and behaves as before, and PR 3 moves it into `SHIPPED` with the adapter that completes the feature - and **no Optery call is made and no Optery key is stored** in this slice.
