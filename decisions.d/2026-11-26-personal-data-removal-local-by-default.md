- **2026-11-26 — Personal data removal ships local by default, and a cloud mode is opt-in behind a consent card:** the owner asked for a data-broker removal tool with both a 100% local engine and an optional commercial API (Optery), selectable in Settings and in chat. The default is `local`, and that is a decision rather than a convenience: the whole point of the tool is that the owner's home address stops sitting on strangers' computers, so the version that puts it on ONE more computer — a paid broker's cloud API — must be his own yes and never a default. `local` does the work on this PC with his own Gmail App Password and the free open-source broker directory, and the brokers that hide behind a CAPTCHA or a Turnstile form go on a checklist with a direct link instead of being worked around; `optery_api` and `hybrid` automate those forms and add before/after screenshots, and they cost money and send his name, address, phone number and email address to Optery over HTTPS. So switching to either one raises ONE consent card that names exactly those four kinds of detail and the fact that they leave this PC, and a denied, timed-out or withdrawn card leaves the mode untouched — the card is the ask, and nothing writes `privacy-removal.json` before a person's yes. The card rides the EXISTING `change_own_config` ask-tier action rather than inventing a gate row, the route `jarvis_phone_apps.py` took on 2026-11-02, so a settings file that has loosened that action below "ask" gets a refusal instead of a cardless change (and `test_privacy_removal.py` proves that too). Three further rulings ride with it: (1) `JARVIS_CONFIG_DIR` is read FIRST by this module — ahead of `OPENJARVIS_CONFIG_DIR`, which most of the backend prefers — because a suite that pointed only the second one at a temp folder could write into the owner's real `privacy/` folder, and that is the one bug this tool cannot afford; (2) the owner's details live only at `%USERPROFILE%\.openjarvis\privacy\profile.json`, outside this repository, and may reach a person, an answer or a card ONLY through `mask_value()` — a label and the last four characters — with the full values searched for in every sentence the module can produce; (3) the module is deliberately NOT in `_where.SHIPPED` for this slice, per the owner's ruling that only the pull request wiring the live caller may register it, so it is named in `NOT_SHIPPED` and in `REPO_ONLY_IMPORTS` with those reasons and every call site is a guarded import — which keeps the published base, which does not carry it, working exactly as it did. What this slice does NOT do, said plainly: no email is sent, no directory is downloaded, no Optery call is made and no key is stored — PR 2 brings the local engine and the carded batch sender, PR 3 the Optery adapter and the move into `SHIPPED`.
