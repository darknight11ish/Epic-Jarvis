- **2026-11-27 — a GitHub request is work, not a feature, and never an app:** the owner's own chat, verbatim, twice in one session. *"Can you do a pull request on the Epic Jarvis GitHub to fix this?"* was answered with the feature list, and *"can you open a pull request for me"* was read as an instruction to open a program called "a pull request". The cause is the same in both: the lanes that answer **questions about features** and **"can you <X>"** and **"open <thing>"** all keyed on words that a GitHub request happens to contain - "setting", "open", the word "pull request" itself is a noun they never expected. **The rule this records:** a sentence that asks for a pull request or names one is handed to the model, which is the only lane that can actually do it; the feature list and the app-opener both decline it. That is deliberately a *refusal to answer*, not a new answer - inventing a deterministic "yes, I will open a pull request" sentence would be a promise this fast path cannot keep, since the work needs a token, a branch and a card. The same day's second fix is the same family from the other side: *"what tools are currently off"* fell to the model because the pattern allowed no adverb between "are" and "off", so the answer to a question the project could already answer depended on one word. `backend/test_capability_answers.py` carries both, and both checks state the old behaviour as failures.
