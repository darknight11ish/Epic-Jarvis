- **2026-11-27 — Q2 — the safe-rmtree rule is enforced as a hard tier plus a downward ratchet:** the owner's ruling, after a lane's scratch helper ran `rmtree(".")` on this PC and deleted the working tree and most of `.git`. **Enforced in the job that can stop a merge** (`backend`), not in `audit`, because a rule whose whole purpose is that no run can delete the tree cannot live in a job that holds nothing. **Two tiers, decided on the argument's own TEXT:** `""`, `"."`, `".."`, `Path.home()` and `os.path.expanduser("~")` fail on the spot and are never ratcheted or allowlisted; every other untraceable site is a ceiling in `tools/safe-rmtree-baseline.json` that may only go down. **Why the text and not the checker's own DANGER kind:** that kind is a fallback label, so an untraceable module constant like `rmtree(TMP)` — a `tempfile.mkdtemp()` scratch dir in twenty backend tests — is reported as *"the home directory"* and a tier built on it hard-failed all twenty on the first run. The hard tier must name what was written, never what the tracer guessed. **The deviation, stated plainly:** the ruling also wanted every unguarded dynamic path in `tools/` to fail outright; measured, that is 22 existing sites in a benchmark harness that removes its own venv and scratch trees, so those sit on the ceiling too and any NEW one fails. Making CI red on them would have blocked every pull request until an unordered tooling rewrite finished — the opposite of the rule's purpose. **The ratchet has its own proof:** `write_baseline` refuses to write a larger set, and the suite asserts both that a new site is refused and that the recorded ceiling is not overwritten.
