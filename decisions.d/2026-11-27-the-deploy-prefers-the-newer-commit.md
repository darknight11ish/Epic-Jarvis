- **2026-11-27 — the deploy prefers the newer commit, decided by ancestry, not the release marker:** DEF-100's second half, measured the expensive way on this PC. The pinning added by #1534 read the published release's `commit` first and used it unconditionally; that field names the commit the **desktop installer** was built from, and a release lags `main` by design between releases. A plain deploy therefore wrote `17a92e5f86de` — an **ancestor** of both `main` and the live install — and **downgraded the owner's machine**, which only a second run with `--ref 2c4d54bde` undid. **The rule now:** when both the release commit and `origin/main` resolve, the NEWER one is deployed, and "newer" means **ancestry** — `git merge-base --is-ancestor` asked both ways — never a date, a version string or which source was read first. Equal shas keep the release's own line so the log still says where it came from; a release that is an ancestor loses and the run says *"deploying it would have moved this PC backwards"*; a release that is the descendant still wins, because a release cut ahead of `main` is the one case the marker is genuinely ahead; and a diverged pair deploys `origin/main` and says plainly that neither contains the other, rather than presenting the newer-looking one as the newer one. **This is the second DEF-100 finding of the night and the more dangerous one:** the earlier failure mode was deploying a stale local checkout, and the fix for it introduced deploying a stale *release* — the lesson recorded here is that a pin's correctness is about the DIRECTION between two commits, not about which source is more trustworthy.
