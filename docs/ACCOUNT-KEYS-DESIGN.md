# Keys and accounts set up inside Jarvis — a design note to approve

**Status: the owner approved it, and parts A, B and C are built** (branch
`next-account-keys-design`, 2026-10-06). Part C — giving the idle cloud lane a
real transport — is built too: §5 records what was built and where, and §7's
Decision 6 is answered.

You asked (CLAUDE.md, the short list, 2026-10-06) that "anything needing a key or
a sign-in should be settable in the Jarvis app itself", desktop only. This note
says what that means in practice, what is already done, what is genuinely new
work, and the six decisions that are yours before anything is built.

Read the "Decisions" section and the "Build plan" at the end. Everything before
them is the evidence.

---

## 1. The short version

1. **A keys box is small work.** The pattern already exists and is tested. Four
   account secrets (email user and password, the private calendar link, the Home
   Assistant token) already have boxes in Settings → Accounts.

2. **The hard part is not the keys. It is the money limits.** You already
   decided a monthly spending limit must exist before API chatbots are used for
   real. Today that limit can only be set on the command line, and that was
   deliberate: raising a limit is a loosening, so there is no route for it.
   Putting it in the app reverses a written decision, and it needs an approval
   card plus Windows Hello on the PC.

3. **So keys in the app and limits in the app are ONE decision, not two.** A
   key box alone would leave you with a key that still cannot be used until you
   open PowerShell. That is worse than today, because the app would look
   finished and not be.

4. **One thing to fix or drop: the cloud escalation lane.** Its key file is
   empty, nothing reads it, and no transport exists for that lane. Do not build
   a key box for it. Either point the lane at the code we already have, or
   delete the offer and its status dot.

---

## 2. What "a key" means here, in plain words

Three different things are all loosely called "a key". They behave differently,
and this note keeps them apart:

- **An API key.** A long password that lets Jarvis use a paid service on your
  account — OpenAI, Groq, and so on. Anyone holding it can spend your money
  there.
- **A credential or secret in the rule-3 sense.** The same care applies: never
  written into a log, sent only to the one service it belongs to, and never
  written to disk in plain text.
- **A money limit.** Not a secret at all. It is a number — "$5 a month for
  OpenAI" — that only exists to protect your card.

The rule-3 home for both a key and a secret is **Windows Credential Manager**:
Windows' own small locked store, tied to your Windows login. Jarvis already uses
it for the pairing token, the web-search keys, and four account secrets.

### 3.2 Chatbot API keys — command line only, six services

`backend/jarvis_chatbot_api.py` holds six services in one table
(`PRESETS`, lines 238-292): OpenAI, DeepSeek, Mistral, xAI (Grok), OpenRouter
and Groq. Each one's key has its own Credential Manager name, generated by the

```
KEY_TARGETS = {pid: f"Jarvis Backend/{PRESETS[pid].company} API key" for pid in PRESETS}
```

— `backend/jarvis_chatbot_api.py:298`

The key is added with one line, `py -3 jarvis_chatbot_api.py key openai`, pasted
at a hidden prompt (the command-line code is at lines 1507-1527). The module's
own docstring says what `save_key` is for: **"For the owner's own command line;
there is NO route for it."** (`jarvis_chatbot_api.py:386-388`). The key is never
in an environment variable and never in a file (lines 55-60).

**Nothing in the desktop app mentions those six services.** A search of
`jarvis-desktop/src-tauri/src` for `openai`, `deepseek`, `mistral`, `groq`,
`openrouter` finds only the unrelated `get_api_settings`/`set_api_settings`
commands. The only place the apps show one is a read-only line for how much of
the money limit is left (`jarvis-desktop/src/chatbot.js:123,203`).

### 3.3 The money limit — command line only, and on purpose

This is the part the note exists for. The module records the reasoning itself:

> "Setting, raising and lowering a limit, and correcting a price, are done on
> the PC's command line only — the same place a key is added — because raising a
> limit is a loosening. There is no route for any of it; both apps only read
> it."
> — `backend/jarvis_chatbot_api.py:96-99`

The same is written in the API reference: "raising a limit is a loosening, so
there is no route for it (or for a price) and neither app can change one"
(`docs/JARVIS-API.md:13962-13965`). Setting, raising and lowering all go through
one function, `set_limit` (line 780), and one command line, `limit <service>
<dollars|none>` (usage at lines 1434-1435).

**No limit, no conversation.** A service with a key but no limit is not ready at
all (`ready_for`, line 1358-1371; `no_limit_words`, line 854).

### 3.4 Where the owner meets these walls today

The newest cloud feature makes the wall visible in the app. "Grade this better"

That is the strongest practical argument for building the boxes.

## 4. The one real decision: keys and limits together

### 4.1 Why they cannot be split

- A key with no limit means the service is still unusable (`ready_for`,
  `jarvis_chatbot_api.py:1371`).
- A limit with no way to raise it means you are back in PowerShell the first
  time you need more room — which is exactly when the app should be enough.
- Shipping a key box alone would put a "Saved" message next to a feature that
  still cannot run. That is the "looks live and is not" failure the feature
  review already found once on this PC (`docs/FEATURE-REVIEW-2026-10-04.md:400`).

### 4.2 What reversing the decision costs

Raising a limit is a loosening, so in this project's own pattern it gets:

- **ONE approval card** naming the service, the old amount and the new amount
  (`set_limit` already returns both, `jarvis_chatbot_api.py:806-808`), and
- **Windows Hello on the PC**, because a card whose action is on the
  owner-check list is refused from any other device and always asks Hello on
  this one (`backend/jarvis_owner_check.py:624-691`; the list is at line 125).

That machinery exists and is tested (`backend/test_owner_check.py`). What does
not exist yet is the gate action and the route. That is the real work in this
plan.

### 4.3 A limit that only goes down

This is worth saying separately, because it is the one place where the two
directions want different treatment.

- **Raising** loosens. Card plus Windows Hello, as above.
- **Lowering** tightens. Everywhere else in Jarvis, "it only makes a turn
  stricter" means no card (`docs/JARVIS-API.md:700`).

But the check that forces Windows Hello is attached to the **action name**, not
to the direction (`jarvis_owner_check.py:639-641,666`). So one action covering
both directions means Hello is asked for both. Two actions — say
`raise_api_limit` and `lower_api_limit` — allow Hello only on the raise, at the
cost of two names, two tests and a rule that has to be kept in step.

This is decision 3 below.

## 5. The cloud escalation lane, and `cloud-keys.env`

The background, verified:

- `cloud-keys.env` sits in the state folder and **nothing in the repository
  reads it** (`docs/FEATURE-REVIEW-2026-10-04.md:325`). It is an empty
  plain-text key file. A plain-text key file breaks rule 3, so it must never be
  revived — not even as a fallback.
- The lane itself has **no transport**. The chat route sends a non-local lane to
  `JARVIS_URL`, and the patch that added that says so in its own words: "this
  project has no other cloud-lane transport today", unimplemented "on a machine
  with no `litellm-proxy.yaml`, which is every machine so far"
  (`backend/ollama-direct.patch:7-20`).
- On this PC the lane is advertised anyway, because `litellm-proxy.yaml` exists
  and the HUD reads lane names out of it (`docs/FEATURE-REVIEW-2026-10-04.md:392-402`).

**Recommendation: do not build a key box for this lane.** The two honest
options:

- **Point it at `jarvis_chatbot_api.py`.** That code already does HTTPS, pins
  the host, refuses redirects, keeps the key in Credential Manager, counts
  spending and enforces the monthly limit. This removes the LiteLLM dependency
  entirely (the review calls this "already half-built", lines 403-408).
- **Or delete the offer, the lane list and the status dot.** Smaller, equally
  honest, and it stops the app looking like it can do something it cannot.

Either way, `OPENROUTER_KEY_1` and `LITELLM_MASTER_KEY` should be retired from
your Windows environment variables.

saved, a model with no price, the limit reached, or a message the limit cannot
cover. This is the strict reading of your own rule ("a money limit comes
before API chatbots are used for real"), and it means the cloud offer can
disappear rather than overspend.

### Your PC: what to remove, and why

Nothing in the repository was deleted from your machine. Two things there are
now leftovers, and both are safe to remove by hand:

1. **`~/.openjarvis/cloud-keys.env`** (the 1-byte file). No repository code
   ever read it. A plain-text key file breaks rule 3, so it must not be
   revived — not even as a fallback. Delete the file.
2. **The user environment variables `OPENROUTER_KEY_1` and
   `LITELLM_MASTER_KEY`.** Windows stores user environment variables as plain

   `[Environment]::SetEnvironmentVariable("OPENROUTER_KEY_1", $null, "User")`
   and the same for `LITELLM_MASTER_KEY`, then sign out and back in.

`litellm-proxy.yaml` in the same folder is now read by nothing either. It can
stay (harmless) or go; it is your file, so nothing here deletes it.

## 6. The rules this design must not break

Quoted from `CLAUDE.md` (the five rules, lines 101-124 of the committed
branch copy; the same five, shorter, at the top of the main checkout's working
copy, lines 17-25):

- **Rule 3 — the one that does the work here.** "API keys are allowed in the
  app ... Any key still gets the same care the pairing token already gets: never
  logged, sent only to the one service it authenticates against, and kept out
  of anything the app writes to disk in plain text."
- **Rule 1 — stays on the local model.** "Anything touching email, files,
  credentials or stored memory stays on the local model." A key going to its own
  service is not the local model's business, and nothing private travels with
  it.
- **Rule 4 — nothing auto-approves.** "The app never auto-approves anything, and
  blocks acting when the event stream is stale." Every write from an app is held
  on a stale event stream today, and a limit change must be too.
- **The own-networks-only rule for plain `http://`.** Plain unscrambled
  `http://` is allowed only to this PC, the home network, Tailscale or Meshnet,
  and refused to the open internet. Every one of the six services is `https` to
  its own pinned host (`jarvis_chatbot_api.py:480-488`), and the design must not
  add a way around that.
- **The phone is never asked for an account secret.** Both the short list
  (line 36-37 of the main working copy) and rule 3's own section say so. Every
  box in this design is **desktop only**, in the Settings window, with no route
  the phone can call.

Two more consequences worth writing down now:

- **A secret must never be echoed back.** The Accounts page never shows a saved
  value again, only whether one is saved (`docs/JARVIS-API.md:8471-8472`). The
  keys box must behave the same way: type once, see "Saved", never see the value
  again.
- **The key list has one owner: the Python side.** The Credential Manager names
  are generated in `jarvis_chatbot_api.py:298` from `PRESETS`. If the desktop
  hard-codes a second copy (as `ACCOUNT_SECRET_TARGETS` does for four names),
  the two can drift, and the failure is silent and ugly: the app says "Saved"
  under a name the backend never reads. This is why decision 1 below bundles a
  check with the keys box.

## 7. Decisions for the owner

Each one has the recommendation first. Nothing is built until you answer.

### Decision 1 — keys and limits together?

- **Yes — one piece of work, keys and limits together** *(recommended)*. The
  app is genuinely useful the day it lands.
- **Keys only, for now.** Quicker, but a saved key still cannot be used until
  you open PowerShell.

### Decision 2 — should typing a secret ask for Windows Hello?

Right now it does not, and that is a written decision. Reversing it means the
secret no longer goes straight into Credential Manager from Rust; it goes
through the backend, so a card can be raised and Hello asked.

- **Leave it as it is — no card, no Hello** *(recommended)*. It matches the
  existing Accounts page, it is quicker, and Hello protects against someone at
  your keyboard, not against a program already on the PC (which can write to
  Credential Manager directly anyway).
- **Ask for Windows Hello when a secret is entered.** Stronger against a
  shoulder-surfer or a borrowed laptop. Costs real work: the secret would have
  to travel to the backend and back, which it does not do today — and that is a
  change to a security shape, not just a new box.

### Decision 3 — who may lower a limit, and does lowering need a card?

- **Raising: card plus Windows Hello. Lowering: no card, both apps**
  *(recommended)*. Two actions internally, so Hello lands only on the loosening.
  More code and two tests, but the rule stays honest.
- **One action for both: card plus Windows Hello either way.** Simpler and
  safer by accident. Annoying the one time you want to spend less.
- **Raising and lowering both stay on the command line.** Keep the limit out of
  the app entirely. Then decision 1 becomes "keys only", and the "looks
  finished" problem in §4.1 comes back.

### Decision 4 — may the price list be edited in the app, and what happens when a price is wrong?

The context: every default price is a guess written from memory
(`jarvis_chatbot_api.py:546-566`, all marked UNVERIFIED). A price that is too
low means Jarvis can spend past your limit without noticing; a price that is too
high means it stops early and looks broken. There is no way for Jarvis to know
which — only the service's own bill does.

- **Yes, editable in the app, and every price Jarvis uses shows where it came
  from and when it was set** *(recommended)*. Correcting a price is not a
  loosening, so no card is needed. The spend line keeps saying "about".
- **Show the list read-only, correction on the command line only.** Fewer moving
  parts, and the "wrong price" risk stays where it already is.
- **Leave prices entirely alone for now.** Then this decision moves to a later
  piece of work.

### Decision 5 — which service gets the first box?

- **OpenRouter** *(recommended)*. You already have an `OPENROUTER_KEY_1` on this
  PC, so it can be tested the same day, and OpenRouter reports a **real** cost
  per answer, which Jarvis counts instead of estimating
  (`jarvis_chatbot_api.py:1261-1264`) — the best case for trusting the limit.
- **Groq.** Also simple, and its own free tier means no card is needed to try
  it.
- **All six at once.** The code path is identical for all six; only the names,
  the models and the prices differ.

### Decision 6 — what happens to the cloud lane?

**ANSWERED 2026-10-06: the first option.** The lane goes through
`jarvis_chatbot_api.py`, with **DeepSeek** behind it — the owner chose DeepSeek
knowing its spending limit is an estimate rather than an exact figure. The two
environment variables are to be retired by hand (§5, "Your PC: what to
remove"). The options as they were put:

- **Point it at `jarvis_chatbot_api.py`, and retire the two environment
  variables** *(recommended)*. The lane becomes real, and a plain-text key in
  your environment goes away.
- **Delete the offer, the lane list and the status dot.** Smaller, and honest
  about what Jarvis does not have.
- **Delete `cloud-keys.env` either way.** Not a question — a plain-text key file
  breaks rule 3. Listed here only so it is not forgotten.

## 8. Build plan, once approved

Ordered, with honest sizes. "Small" means a day's work at most of wiring, in the
shape of code that already exists and is tested. "Real" means design plus tests
plus a security review pass.

**Step 0 — answer the decisions above.** No code.

**Step 1 — the six keys boxes. Small.**
Add six names to a table beside `ACCOUNT_SECRET_TARGETS`, six rows on the
Accounts page, and a test that the desktop's table and the Python side's
`KEY_TARGETS` name exactly the same six Credential Manager names. Save and
remove go straight to Credential Manager from Rust, like the existing four. The
page shows only "Not set" / "Saved", plus each service's one-line "where to make
a key" address (`Preset.key_where`, `jarvis_chatbot_api.py:214`).

**Step 2 — the key-list drift check. Small, and part of Step 1.**
One test that fails when the two tables disagree about a service or a name. The
existing account-secret test proves the pattern (`backend/test_account_secrets.py:263`).
Without it, Step 1 creates a silent failure mode: a key saved under a name the
backend never reads.

**Step 3 — the monthly limit route. The real work.**
A gate action, a card that names the service and both amounts, the tier set to
`ask` in the settings file, and a route the desktop can call. The backend half
of `set_limit` already exists and already validates its input
(`jarvis_chatbot_api.py:780-808`); the new part is the card, the tier and the
route, plus the rule that a change is refused unless the event stream is fresh.
Windows Hello comes free if the action is added to `PC_ONLY_ACTIONS`
(`jarvis_owner_check.py:125`) — but see decision 3, because that also means
Hello on every lowering.

**Step 4 — the limit in the desktop page. Small, once Step 3 exists.**
A number box per service with the current amount, the amount used this month,
and the "about" wording the apps already show (`money_view`,
`jarvis_chatbot_api.py:951-977`). Held on a stale event stream, like every write.

**Step 5 — the price list. Small, and only if decision 4 says yes.**
The same screen, showing each model's price, where the number came from
("yours" or "default, unverified") and the date it was set. Editing writes the
same fields `set_price` already writes (line 824-825).

**Step 6 — the cloud lane. A separate piece of work, and it needs its own
decision.** §5. Do not fold it into Step 3. **BUILT — see §5, "Part C, built".**

**Step 7 — the related secrets of §3.5. Each needs its own look, not this
plan.** The GitHub token is the odd one: `jarvis_tellme` reads the environment
variable for itself, so it would not see a Credential Manager value at all.
That is a small correctness fix worth doing on its own, before any box is added
for it.

### Known unknowns — stated plainly, with how to check each

- **Whether your PC already has any of these environment variables set** is
  unknown from here. `docs/FEATURE-REVIEW-2026-10-04.md:398` found
  `OPENROUTER_KEY_1` and `LITELLM_MASTER_KEY`; nothing was found for the other
  names, but that is not the same as proving they are absent. One line checks
  all of them:

  ```powershell
  Get-ChildItem Env: | Where-Object { $_.Name -match 'JARVIS_|GITHUB|JOPLIN|OBSIDIAN|CALDAV|OPENROUTER|LITELLM|OPENAI|GROQ|MISTRAL|DEEPSEEK|XAI' } | Select-Object Name
  ```

  It prints **names only**, never values. For the four account secrets the
  Accounts page already shows this, because a box stays disabled while the
  environment variable wins (`docs/JARVIS-API.md:8462-8463`).

- **Which keys are already in Credential Manager** is also unknown from here.
  `py -3 jarvis_chatbot_api.py status` lists the six, and `py -3
  jarvis_search.py status` the web-search three.

- **Whether Windows Hello is set up on this PC** is checked by the app already
  (`jarvis-desktop/src-tauri/src/lock.rs:321-334`; the refusal wording is
  `backend/jarvis_owner_check.py:91-93`). If it is not set up, the "no lock, no
  risky approval" rule means a limit change is refused until it is.

- **Whether the six services' addresses and cap fields are right** is partly
  unverified in the code itself — DeepSeek's cap field could not be confirmed,
  and xAI's request path was read from xAI's own client rather than its API
  reference (`jarvis_chatbot_api.py:130-157`). **None of the six has ever been
  reached for real** — the module's own header says so (`jarvis_chatbot_api.py:8`).
  That does not block Steps 1-2; it does mean the first real test of a key is
  also the first real test of the adapter.

- **The price list is unverified by definition.** Correcting it in the app makes
  a wrong number easier to fix, not more likely to be right.
