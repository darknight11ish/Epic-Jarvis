# At rest: what is encrypted, what is not, and what happens on Forget (2026-10-18)

Audit DATA D2/D3/D4, from the merged SECPRIV audit. Read against `origin/main`
`928dce9c` and the live `~/.openjarvis` on this PC, read-only. This page is the
**threat model and the deletion statement**; it records decisions in words, and
where code was needed it says whether that code is in (`this slice`) or still
open. **Nothing here claims encryption that has not been measured.**

## The threat model in one paragraph

Jarvis runs as the owner's Windows account and decrypts what it shows. So the
honest statement is: **anything this page calls "plaintext" is readable by any
process running as that account, by a local administrator, and by any backup or
sync tool that can read the profile folder.** Encryption here is about the disk
leaving the machine - a stolen drive, a resold PC, a copied profile, a sync
folder - not about hiding data from the logged-in owner. That boundary is the
reason the chat text, the `.jbak` archives and (since this slice) the weekly
snapshots are sealed, and it is the standard the remaining stores are measured
against.

## Old plaintext snapshots - the owner's command, not the tool's

The plaintext snapshots already on this PC (`~/jarvis-data-snapshots/jarvis-snap-*`
and any in the chosen folder) are **NOT deleted by the backup tool**. The next
sealed run names them, says the encrypted `.jbak` archives are untouched, and
prints the exact one-line command. After seeing a sealed snapshot and confirming
the `.jbak` archives, the owner runs:

```powershell
Remove-Item -LiteralPath @('<full path to each jarvis-snap-* folder>') -Recurse -Force
```

`-LiteralPath` so a name can never be a pattern; `-Recurse -Force` because they
are folders. The tool prints the filled-in version after each sealed run, and
`status` prints it too. That the encrypted backup keeps its snapshot: a `jarvis-snap-*`
name is only ever a copy; deleting it does not touch a `.jbak` archive or the
sealed snapshot just written.

## Deletion reachability - what Forget and Delete actually reach

- **Forget a fact / Erase the words** (`jarvis_memory.erase`): the live row, its
  FTS entry, its meaning vector, review cards, day-rounded repeat times and every
  copy in `memory.db`; then `secure_delete` + VACUUM + checkpoint (`this slice`
  adds, after that) `receipts.purge_words` and `guardian.purge_words` so the
  words cannot come back from a receipt summary/snapshot or an **unpinned**
  guardian blob.
- **Delete one conversation** (`jarvis_chat_log.delete`): the rows, with
  `secure_delete` + VACUUM (hourly), and now its user words are scrubbed from
  receipts (`this slice`).
- **NOT reached:** `.jbak` archives (up to 5, by design - a backup is a copy at a
  point in time), old plaintext snapshots (the owner deletes those), the sealed
  snapshots' history, `logs/`, desktop/backend logs, `guardian` **pinned**
  copies, other files a tool wrote, and anything a phone/screen already showed.
  No UI sentence claims more: the receipt's own words say "put back", not
  "erase".
- **Verification now in the suite:** `test_receipts.py` proves the cap and the
  purge; `test_chat_log.py` proves deleting a conversation removes its words
  from a receipt; `test_file_guardian.py` proves an erased fact's words leave
  unpinned guardian copies while a pinned one survives; `test_data_backup.py`
  proves a sealed snapshot directory contains no plaintext SQLite/canary.

## Backup recovery code - the blast radius

One recovery code unlocks one `.jbak`: chat-history key and deck key travel
inside it (`jarvis_backup.py:95-105`), by necessity, so a restore can reopen the
data. That makes the code a **single secret for history + decks + all data**.
The code is 20 chars, shown once, never written to a file or log; a new backup
gets a new code; restoring is card + Windows Hello gated. Recommend: keep the
code off this PC and rotate it by making a new backup and deleting an old one
(KEEP = 5). The sealed weekly snapshots use a **different** key (Credential
Manager, this account) - a lost Windows profile loses them, and the `.jbak`
archives are the disaster-recovery path.

## Decisions recorded

**Accepted now (documented, not fixed):** memory.db/voiceprint/schedule/etc
plaintext under a profile ACL; guardian plaintext-gzip with quota-only pruning;
logs plain with retention; biometric voice files still plain (encryption
deferred); all covered by the DACL boundary above and the disk-leaves-machine
protection where sealed.

**Open (needs its own tested slice):** encrypt `memory.db` (then voiceprint and
schedule) with the chat-history pattern and a migration; encrypt the biometric
voice JSON files with a migration-aware voice-suite pass; add a guardian TTL;
strip the `.before-*` config snapshots; scan logs/crash notes for private text
beyond the token shapes.

## How to check this on the PC (read-only)

```powershell
py -3 tools/check_openjarvis_acl.py
py -3 tools/jarvis_data_backup.py status
py -3 tools/jarvis_data_backup.py verify <newest .jba>
```

The backup tool's own output says whether the last run was sealed and names any
old plaintext snapshot with the removal command. Nothing in this page needed a
running Jarvis, and no live database was modified to write it.
