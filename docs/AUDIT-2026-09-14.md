# Audit — Jarvis Android, 14 Sep 2026

Five reviewers: security/protocol, concurrency & resource lifecycle, Compose/Glance,
build supply chain & licensing, platform correctness. Every finding below was
re-checked against the cited lines before it was written down; where a reviewer's
reasoning did not survive that check it is recorded under **Corrections** rather
than dropped silently.

Two codebases, and they are not equally exposed:

| | lines | status |
| --- | --- | --- |
| `jarvis-android/` | ~5,100 | superseded by the `ANDROID-BUILD.md` contract, but it is the APK that has been installed |
| `jarvis-client/` | 435 | live, step 0 only — no networking, no audio, no approvals yet |

Most of what follows is in `jarvis-android/`. That matters for triage: if the plan
is to let `jarvis-client` supersede it, a defect there is a *lesson for the rewrite*
rather than a patch. If the phone keeps running the old APK, four of these are live.

## Critical

### C1 — `hostOf` userinfo bypass sends the token and the microphone to a public host in the clear
`jarvis-android/.../data/JarvisSettings.kt:117-123`

```kotlin
return authority.substringBefore(':').takeUnless { it.isEmpty() }
```

The authority is split on `:` before `@`, so userinfo is never stripped.
`ws://100.64.0.1:8080@evil.com/api/mobile/ws` → `hostOf` returns `100.64.0.1`,
`isCleartextTargetPrivate` says yes, and OkHttp — which parses the URL correctly —
dials **evil.com** over plaintext carrying `Authorization: Bearer <token>`, every
approval request, and the uplink PCM.

This breaks rule 1 and rule 3 at once. The guard that exists specifically because
the network security config cannot express a CIDR range is the thing that fails.

*Fix:* parse with `okhttp3.HttpUrl` (or `java.net.URI`) and read `.host`, instead of
hand-splitting. The hand-split exists to avoid a dependency in a settings class; the
dependency is already on the classpath.

### C2 — `submitApprovalDecision` is a signing oracle
`jarvis-android/.../JarvisApplication.kt`

It signs whatever `requestId` it is handed. There is no check that the id is in
`_pendingApprovals`. It is reachable from `ApprovalActionCallback`, which reads
`PARAM_ID` out of Glance `ActionParameters`, and from the notification receiver.
Anything that can get an id into that path gets a valid HMAC for an arbitrary
decision — the desktop's verifier is correct and will accept it, because the
signature is genuine.

*Fix:* refuse to sign an id that is not currently pending, and make that refusal
visible rather than silent.

### C3 — Nothing gates approving on the event stream being live (rule 4, both directions)
`jarvis-android/.../network/WebSocketEvents.kt:65`, `JarvisApplication.kt`

`expires_at_ms` is parsed and never read — one occurrence in 5,144 lines. And no
code path checks `ConnectionState.CONNECTED` before accepting a decision. So:

- an **expired** approval stays tappable, and re-signs with a fresh
  `decided_at_ms` that sails through the desktop's skew window;
- an **offline** approval clears the card and buzzes "confirm" while the decision
  goes into an in-memory queue (see H7).

Rule 4 says the app blocks acting when the event stream is stale. It does not.

*Fix:* honour `expiresAtMs` in both the card and the notification; require
`CONNECTED` to submit, and say so on the button rather than failing after the tap.

### C4 — `jarvis-client`'s cleartext check matches hosts the platform will block — and this is the live app
`jarvis-client/.../platform/PlatformReadiness.kt:33-39`

```kotlin
private val CLEARTEXT_SUFFIXES = listOf(".ts.net", "ts.net", "localhost", "127.0.0.1")
return CLEARTEXT_SUFFIXES.any { h == it || h.endsWith(it) }
```

The bare `"ts.net"` entry plus `endsWith` means `notmyts.net` and `evilts.net`
report **permitted**. The network security config itself is correct — `<domain
includeSubdomains="true">ts.net</domain>` matches `ts.net` and `*.ts.net` and
nothing else — so the readiness screen lies in the safe direction here (it promises
access the platform will refuse), but it is the one screen whose entire job is
making the policy legible, and the same predicate shape is what C1 got wrong.

*Fix:* drop the bare `"ts.net"`, keep `".ts.net"`, and add an explicit `h == "ts.net"`.

## High

### H1 — CI picks which app to build by directory read order
`.github/workflows/android-apk.yml:54`

```sh
settings=$(find . -maxdepth 3 -name 'settings.gradle*' -not -path '*/build/*' | head -n1)
```

Two Gradle roots now match. `head -n1` takes whichever `find` emits first, which is
`readdir` order — not a choice. In this checkout the command returns
`./jarvis-client/settings.gradle.kts`; on the runner for the commit that introduced
`jarvis-client` it returned `./jarvis-android` (verified in the run log). So the
workflow whose path filter is `jarvis-android/**` builds whichever root the
filesystem hands it first, and the `epic-jarvis-debug-apk` artifact could be either
app with no way to tell from the artifact name.

The comment three lines above the filter says the scoping was meant to keep the two
apart. The generic fallback defeats it. This is mine and it is the most consequential
of the build findings.

*Fix:* hard-code `dir: jarvis-android` in this workflow, or scope the find to
`./jarvis-android`.

### H2 — The only unit tests in the repo never run, and the step reports success
`.github/workflows/android-apk.yml:131-141`

`jarvis-client/app/src/` contains only `main/`. When the detect step lands on the
client, `testDebugUnitTest` reports `NO-SOURCE`, exits 0, green check. The four real
test classes — `ApprovalSignerTest`, `NoteDiffTest`, `QuickNoteSerializationTest`,
`TelemetryProtocolTest` — are never compiled. `jarvis-client.yml` has no test step
at all. The comment above the step claims tests gate the APK.

`ApprovalSignerTest` is the thing that pins the canonical HMAC payload the desktop
verifies. That is exactly the test you cannot afford to have silently skipped.

*Fix:* fix H1; add a test step to `jarvis-client.yml`; assert the results XML is
non-empty so `NO-SOURCE` cannot pass for green.

### H3 — Release signing is plumbed to nothing
`grep -rn "signingConfig\|storeFile" --include=*.kts .` → no matches.

CI decodes `ANDROID_KEYSTORE_BASE64` to disk and exports four `SIGNING_*` variables
into the Gradle build. No build script reads any of them. `assembleRelease` emits
`app-release-unsigned.apk` and CI uploads it as `epic-jarvis-release-apk`. It will
not install. `README.md:15-18` says the opposite.

Compounding: `jarvis-android/app/build.gradle.kts:25` sets `applicationIdSuffix = ""`,
so debug and release share `com.jarvis.assistant` — a debug sideload and a release
build collide with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`.

*Fix:* given rule 5 (sideloaded, never Play), the honest fix is to **delete** the
keystore plumbing and the README claim rather than add a signing config for a
release build that has no distribution channel.

### H4 — A replaced approval renders the old diff under a button that submits the new one
`jarvis-android/.../ui/approval/ApprovalDialog.kt:60`, `JarvisApplication.kt:256-257`,
`HudScreen.kt:163`

The runtime explicitly *replaces* an approval that reuses an id
(`filterNot { it.id == event.id } + event`). The LazyColumn key is `it.id` and the
parsed diff is `remember(request.id)`. Both survive the swap. So the card keeps
showing the superseded diff while Approve signs a decision on the revised request.

The user approves a note edit they have not read. That is the failure mode the whole
diff viewer exists to prevent.

*Fix:* `remember(request)`, not `remember(request.id)`.

### H5 — The approval widget does not redraw when an approval's content is replaced
`jarvis-android/.../data/repository/WidgetDataRepository.kt:115-118`

```kotlin
.map { list -> list.map(ApprovalRequestEvent::id) }
.distinctUntilChanged()
```

Same-id replacement produces an identical id list, so `ApprovalWidget().updateAll`
never fires. The home-screen card shows the old action text with live Approve/Deny
buttons wired to the new request — H4 again, on a surface with no diff to check
against.

*Fix:* distinct on the mapped item content, not on ids.

### H6 — Widget redraw/ping feedback loop
`widget/launcher/QuickLauncherWidget.kt:43` → `JarvisApplication.kt:299` →
`WidgetDataRepository.kt:128-139`

`provideGlance` calls `measureLatency()`. The pong writes a new RTT into
`_latencyMs`. The repository's `combine(socket.state, latencyMs).distinctUntilChanged()`
fires — RTT jitters by a millisecond nearly every round, so the distinct never
catches — and calls `updateAll` on both widgets, which re-runs `provideGlance`,
which probes again.

While the link is up: continuous widget redraw, a tight ping loop on the socket,
measurable battery drain, and eventually AppWidget update throttling. I wrote the
comment at line 42 arguing that probing on redraw avoids a background timer; it
creates a worse one.

*Fix:* delete the probe from `provideGlance`, or drop `latencyMs` from that combine.

### H7 — An approval taken on a cold process is lost with no trace
`widget/approval/ApprovalActionCallback.kt:28-32`, `notifications/ApprovalNotificationManager.kt:185-186`

Process not running; user taps Approve on the lock screen. `initialize()` starts an
**asynchronous** dial; `submitApprovalDecision` runs immediately, `socket.send`
returns false, the message goes into a `ConcurrentLinkedQueue`. `onReceive` returns,
the importance boost lapses, the process is reaped. The queue is memory-only.

Quick notes are persisted to `PendingNoteStore` for exactly this reason. Approvals
are not. The comment at `ApprovalActionCallback.kt:28-30` asserts that staying in
the suspending callback prevents this; it does not, because the send is async.

*Fix:* persist the signed decision before returning, replay from `onConnected()`.

### H8 — An approval request can be dropped into a log line by audio backpressure
`network/JarvisWebSocketManager.kt:52-55,187-189`, `JarvisApplication.kt:130`

One collector handles every event sequentially, and on `telemetry_request` it calls
`collectTelemetrySnapshot()` synchronously — three `registerReceiver` binder
round-trips plus camera enumeration, tens to hundreds of ms. Base64 audio chunks
arrive at ~50/s and fill `extraBufferCapacity = 128`. The `ApprovalRequestEvent`
that lands next hits `tryEmit` → false → `Log.w("event buffer full")`, and is gone.
The user never sees it; the desktop blocks on a gate that will never be answered.

*Fix:* a `Channel` with `SUSPEND` so the socket applies backpressure instead of
discarding; move telemetry collection off the collector.

## Licensing

No `LICENSE`, `NOTICE` or attribution file exists. No vendored source, no `libs/`,
`jniLibs/`, `assets/` or bundled binaries other than the two wrapper JARs. All
third-party exposure is Maven coordinates.

- **Everything that ships in either APK is Apache-2.0.** AndroidX, Compose, Glance,
  OkHttp, Okio, kotlinx-serialization, kotlinx-coroutines, kotlin-stdlib — all of it.
- **The only non-permissive licence in the repo is EPL-1.0 (JUnit 4.13.2)**, in
  `testImplementation` scope in both projects, never packaged. EPL-1.0 is file-level
  copyleft: it reaches modified EPL files only, never code that links against it. No
  obligation arises.
- **No GPL, LGPL, AGPL or CC BY-NC-SA anywhere**, declared or transitive. Checked
  deliberately.
- The `excludes += "/META-INF/{AL2.0,LGPL2.1}"` line in both build files is Android
  Studio template boilerplate for a JNA resource collision. JNA only enters an Android
  graph via `kotlinx-coroutines-debug` ← `kotlinx-coroutines-test`; neither project
  declares either. The exclusion is a no-op and is **not** evidence of LGPL code.
- `server/jarvis_mobile_ws.py` imports Python stdlib only. Zero licence surface.
- `README.md:2` says "based on openjarvis". No vendored upstream source is in the
  tracked tree — every `.kt` and `.py` is first-party with no copyright headers or
  SPDX identifiers. If anything was copied by hand rather than reimplemented, that
  upstream's licence applies and nothing here records it. Worth confirming from your
  own memory of the port; I cannot tell from the tree.

**Verdict:** licence risk for a non-commercial sideloaded build is effectively zero.

On "pull anything helpful from GitHub": nothing here needs vendoring. Every gap the
audit found is fixed by changing this repo's own code, not by importing someone
else's — and vendoring would add the one thing the tree currently does not have,
which is a third-party licence obligation to track. Deliberately nothing was copied in.

## Corrections

Two reviewer claims did not survive checking, and are recorded here rather than
quietly dropped.

**The audio "process crash" is not a crash.** The reviewer argued that releasing the
`AudioTrack`/`AudioRecord` while a coroutine is blocked in the native call makes that
call throw, and that because `AudioPlayer.kt:101` and `AudioStreamer.kt:84` are
unguarded and the scopes carry no `CoroutineExceptionHandler`, the exception reaches
the default handler. The scope part is right — `SupervisorJob` does not swallow
`launch` exceptions. But the platform does not throw here: `AudioTrack.write` and
`AudioRecord.read` both **return `ERROR_INVALID_OPERATION`** when the object is
uninitialised, which is the state `release()` leaves it in, and the JNI holds a strong
reference so the in-flight call is not a use-after-free. Both loops already handle a
non-positive return (`if (written <= 0) break`, `if (read < 0) … break`). The race is
real and the ordering should still be fixed — `stop()`, then `cancelAndJoin()`, then
`release()` — but it degrades to a truncated buffer, not a crash. Same correction
applies to the reviewer's finding that `startRecording()` outside the `try` can crash:
it throws only when the recorder is uninitialised, which is already checked on the
line above.

**The wrapper JARs are not a defect.** The licensing reviewer flagged that both
`gradle-wrapper.jar`s are the Gradle 8.14.x wrapper while the projects declare
8.11.1 and 9.6.0, and read that as evidence they were hand-copied between projects
rather than generated. The hash is right — both are `7d3a4ac4…`, and that is
authentic Gradle. The inference is wrong: `gradle wrapper` writes the JAR belonging
to the Gradle that runs it, not to the version named in `distributionUrl`, and the
dev container's Gradle is 8.14.3. Two projects generated from the same machine
having identical wrapper JARs at different distribution versions is the expected
outcome. The real finding in that area is S1 alone.

**CI has not been shipping the wrong APK.** The reviewer stated the
`epic-jarvis-debug-apk` artifact "actually contains the client APK". It does not — the
detect job on the relevant run logged `gradle dir: ./jarvis-android`. The defect is
real but it is *nondeterminism*, not a known-wrong result: `find | head -n1` returns
whichever root the filesystem enumerates first, and that differs between this checkout
and the runner. H1 is written to the verified version.

## Platform correctness

Every claim here was checked against `developer.android.com` and then against the
manifest and XML in the tree.

### P1 — Capture keeps running after the `microphone` promotion is refused
`service/JarvisForegroundService.kt:106-116`

`startInForeground()` catches *any* exception from
`startForeground(..., FOREGROUND_SERVICE_TYPE_MICROPHONE)` and silently re-posts the
same notification as `specialUse`. Nothing tells `AudioStreamer` to stop.

`microphone` is a while-in-use type: starting one from the background throws
`SecurityException`. Concretely — Jarvis is the selected recognizer, another app calls
`SpeechRecognizer.startListening()` with no Jarvis activity visible, the promotion
throws, line 113 downgrades, `AudioRecord` keeps running under a non-microphone FGS so
the platform mutes it, `micActive` stays true, the notification says "Listening", and
the desktop receives an endless stream of silence. One `Log.e` records it.

*Fix:* in the `wantsMicType` catch branch, `stopMic()` and surface the failure.

### P2 — The microphone is opened before the service is promoted
`JarvisApplication.kt:433` vs `:439`

`streamer.start()` — which calls `AudioRecord.startRecording()` — runs at 433.
`_micActive.value = true`, the only thing that drives the `combine` collector in
`JarvisForegroundService.kt:52-60` to request the `microphone` type, is set at 439,
and that collector is dispatched through a channel, so the promotion is asynchronous
even on the main thread.

The audio policy evaluates mic eligibility at `startRecording()`. Screen off, HUD not
visible: the first chunks reaching the desktop are zeroed.

*Fix:* promote first, await it, and abort the start if it throws. P1 and P2 are the
same bug from two ends.

### P3 — All three widgets are missing `android:initialLayout`
`res/xml/widget_approval_info.xml`, `widget_launcher_info.xml`, `widget_telemetry_info.xml`

Verified: none of the three declares it, and none declares `previewLayout` or
`previewImage` either. It is a required `<appwidget-provider>` attribute, and Glance
specifically requires `@layout/glance_default_loading_layout`. With it at `0`,
`AppWidgetHostView` falls back to the system error view — the user sees "Problem
loading widget" until the first `updateAll` lands, and the picker cell is blank.

AAPT does not enforce this, which is why the build has been green.

*Fix:* add `android:initialLayout="@layout/glance_default_loading_layout"` to all three.

### P4 — The recognition service is gated behind a signature permission, so nothing can bind to it
`AndroidManifest.xml:114-124`

```xml
<service android:name=".service.JarvisRecognitionService"
    android:exported="true"
    android:permission="android.permission.BIND_VOICE_INTERACTION">
```

`BIND_VOICE_INTERACTION` is documented as "must be required by a
`VoiceInteractionService`, to ensure that only the system can bind to it" —
protection level `signature`. `RecognitionService` documents no bind permission, and
`BIND_SPEECH_RECOGNIZER` does not exist in the public SDK. A third-party app
constructing a `SpeechRecognizer` binds from its own process, cannot hold a signature
permission, and gets `ERROR_CLIENT` with no callbacks.

The recognizer role is advertised and unusable by every caller. The permission is
correct on `JarvisVoiceService` and `JarvisInteractionSessionService`; it is wrong
here only.

*Fix:* remove `android:permission` from this one `<service>` element.

### P5 — `jarvis-client`'s link service dies permanently on its first sticky restart
`jarvis-client/.../service/EventService.kt:40,67-79`

`START_STICKY` is the only recovery from a system kill, and a sticky restart happens
with the app in the background, which is not on the FGS background-start exemption
list. The client manifest has no exemption path at all — verified: no
`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` (which `jarvis-android` does declare), no boot
receiver. So `ForegroundServiceStartNotAllowedException` is caught at :74, `stopSelf()`
runs, and the link is gone with one logcat line.

That defeats the ">6 hours without the app being foregrounded" property the file's own
header comment claims `specialUse` buys.

*Fix:* declare `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`, prompt for it on the readiness
screen, and report the failure instead of silently stopping.

### P6 — Neither app survives a reboot
Neither manifest declares `RECEIVE_BOOT_COMPLETED` or a `BOOT_COMPLETED` receiver.
`JarvisForegroundService` starts only from `MainActivity` and `JarvisInteractionSession`;
`EventService` only from the client's button. Reboot overnight and approvals stop
arriving until the app is opened by hand, with nothing to indicate anything is wrong.

`BOOT_COMPLETED` is an explicit FGS background-start exemption, so this is allowed.

### P7 — `CAMERA` is requested at runtime and never used
`AndroidManifest.xml:22`, `MainActivity.kt:205`

The only camera-adjacent feature is the torch, and `setTorchMode()` requires no
permission. Verified: `Manifest.permission.CAMERA` appears exactly once in the whole
tree — in the request itself.

It is requested in the same `RequestMultiplePermissions` batch as `RECORD_AUDIO`. A
user who balks at "Jarvis wants camera access" and rejects the batch loses the
microphone — the app's core function — for a capability that does not exist.

*Fix:* drop it from both places.

### P8 — `android.permission.FLASHLIGHT` is not a platform permission
`AndroidManifest.xml:23`. Not in `Manifest.permission`; silently ignored by the package
manager. Harmless, but it reads as if torch access were permission-gated, and it can
surface in Settings on OEM builds that still define the legacy name. Delete it.

### P9 — `EventService.onTimeout(startId)` overrides the wrong overload
`jarvis-client/.../service/EventService.kt:49-52`

The Android 15 budget calls `onTimeout(int, int)` (API 35). The one-argument form is
dispatched only for `shortService`. The client's range is API 33-36, so the safety net
the comment at :43-48 describes is not armed on any Android 15 or 16 device — and the
type change it anticipates would produce exactly the fatal `RemoteServiceException` it
claims to prevent.

*Fix:* also override `onTimeout(startId: Int, fgsType: Int)` behind an
`SDK_INT >= 35` guard.

### P10 — `jarvis-client` has no launcher icon
No `android:icon`/`android:roundIcon` and no `mipmap` resources — verified,
`res/` contains only `values/` and `xml/`. Ships with the system placeholder in the
launcher, in Settings, and as the notification badge.

### P11 — The QS tile can leave two collectors writing to one `Tile`
`service/QuickCaptureTileService.kt:30-38`. `onStartListening()` does not cancel a
previous `watcher`. The normal open/close cycle is clean because `onStopListening()`
does cancel; SystemUI re-binds are the gap. Cosmetic — a stale connection state for a
frame. One-line fix.

### Platform items checked and clear

- `TileService.startActivityAndCollapse` API-34 split, `FLAG_IMMUTABLE` PendingIntent,
  and `unlockAndRun` for the locked case — all correct.
- `<property>` on a `<service>` at minSdk 28 — safe; pre-31 parsers skip unknown child
  tags, so installation on 28-30 is unaffected.
- `FOREGROUND_SERVICE_TYPE_SPECIAL_USE` guarded to API 34, falling back to `0` on
  29-33 — correct, and `0` is a legal subset of the declared types.
- `VibratorManager` API-31 guard with the deprecated fallback; `Tile.subtitle` API-29
  guard; `<monochrome>` at minSdk 28 — all correct.
- The assistant registration chain is right end to end: `voice_interaction_service.xml`
  names both the session and recognition services, all three components exist, and the
  `BIND_VOICE_INTERACTION` requirement is correct on the two that need it. P4 is the
  only defect in it.
- `PROPERTY_SPECIAL_USE_FGS_SUBTYPE` present and non-empty in both modules — the
  documented prerequisite for `specialUse`.
- Notification channels are created before any `startForeground` that uses them, in
  both modules. `IMPORTANCE_MIN`/`LOW` is legal for an FGS notification.

## Addendum — the visual contract, and a gap that blocks step 7

Two things checked after `jarvis-client` was pointed at the real API. Both are
findings about the *contract*, not about this repository's code.

### `shell.html` carries a second, stale copy of the pattern defaults

`jarvis-visual-spec.json` exists so that the three renderers read one set of
numbers rather than each carrying its own — its own note says so. But every
fallback in `_resolveRaw()` is a pre-audit constant that no longer matches the
spec it sits beside:

| pattern | spec `params` | `_resolveRaw` fallback |
| --- | --- | --- |
| `flicker` | `rate_hz: 1.2`, `depth: 0.25` | `q.rate_hz \|\| 7`, `q.depth ?? .55` |
| `strobe` | `period_s: 0.8` | `q.period_s \|\| .7` |
| `rainbow` | `sat: 0.82` | `q.sat ?? .8` |

In normal operation none of these fire: `Object.assign({}, P.params, bind.params)`
always supplies the spec's value first. They are reachable two ways, though —
a binding that sets a param explicitly to `0`, because `||` treats zero as
absent (`rate_hz: 0` resolves to **7 Hz**), and any future pattern definition
that omits a key.

The flicker one is the one worth naming. 7 Hz times the documented 2.3×
harmonic is **16.1 Hz**, which sits inside the 11–25 Hz photosensitive band the
first audit found and fixed — and `limits.flash.flicker_rate_hz_max` is 1.3
precisely to keep it out. The governor inside `resolve()` is the backstop and
would clamp it to three transitions a second, so this is defence-in-depth
working rather than an exposure. But the spec says the limit is enforced in
three places, and one of the three currently disagrees with the other two.

*Suggested fix, on the spec side:* replace `||` with `??` throughout
`_resolveRaw`, and set each fallback to the spec's own value — or delete the
fallbacks, since `P.params` is always merged in first and a missing key is a
spec bug worth failing loudly on.

The Kotlin port took its values from the spec rather than from `shell.html`, so
it does not inherit this.

### A gap I filled by inventing an endpoint, then removed

While wiring the inbox I wrote `GET /api/holds` and built a UI section on it.
That route is not in the contract. `POST /api/holds/cancel` is — so the API can
stop a message inside its send window but has nothing that *lists* them, and a
phone has no way to learn a handle.

Inventing the missing half is precisely the mistake that produced
`jarvis-android`'s protocol, and it would have failed the same way: quietly, as
a 404 that renders an empty section, so the feature would have looked built and
never worked. Both the call and the section are gone; `cancelHold` stays with a
note, ready for whenever something serves a handle.

Recording it because catching it in my own diff a commit later is not the same
as not doing it, and the rule in §12 is the one I was already quoting at the
time.

### Backend gaps, collected

Four now, all the same shape — the brief asks for something the API cannot do:

1. **No audio transport.** Blocks step 7 entirely. See below.
2. **No route that sets power mode.** `/api/status` reports it, nothing writes
   it, so the quick-settings tile toggles mute instead.
3. **Nothing serves `face_state`.** §6 warns against re-deriving it client-side
   and no endpoint returns it. Composed locally, with `banked` taken from the
   `attention` event, which *is* served. The desktop thread reached the same
   conclusion independently — it is the first entry in its own
   `API-DISAGREEMENTS.md`.
4. **No route that lists send-holds.** Above.

### Step 7 (the voice loop) has no transport in the API

`ANDROID-BUILD.md` §2 step 7 asks for "wake word → speak → hear" and calls it
the whole point of the phone client. `JARVIS-API.md` §4 has no endpoint that
moves audio in either direction: nothing accepts microphone PCM, nothing serves
synthesised speech. `capabilities.voice` reports whether the *desktop's* voice
stack is installed, and `setLevel`/`setSpeechLevel` are inputs to the face
renderer, not transport. §8's "not yet in the API" list and §12's backend-gaps
list both omit it.

`JARVIS-EXPLAINED.md` §3 explains why, probably without meaning to: the wake
word, the voice-print gate and barge-in all run against the **desktop's**
microphone. There is no phone in that design yet.

So the phone can render a speaking face — it does — but it cannot participate in
a voice turn. The two ways to close that are not equivalent:

1. **Add an audio endpoint server-side.** Uplink PCM plus a TTS stream. Keeps
   the voice-print gate where it is, which matters: that gate is what decides
   whether the speaker is the owner, and moving it to a handset that can be
   picked up by anyone would weaken it.
2. **Do speech on the phone.** Sends the owner's voice through a phone-side
   model and hands the desktop text. This puts a second transcription path
   outside the privacy boundary and leaves the voice-print gate with nothing to
   check, so it is the wrong shape rather than merely the harder one.

§12 is explicit that a missing endpoint gets added server-side rather than
synthesised on the phone — and the last time a protocol was invented to fill a
gap, the result was `jarvis-android`. So this is reported rather than built.
