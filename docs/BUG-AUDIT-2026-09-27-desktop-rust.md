# Desktop Rust bug audit, 2026-09-27

Scope: the Rust half of the Tauri desktop app: `jarvis-desktop/src-tauri/src/*.rs`,
`permissions/` and `capabilities/`. I looked hardest at the code added on
2026-09-27, which no audit had read yet:

- the floating face (`windows.rs`, `commands.rs` `get_floating`/`set_floating`,
  `hotkeys.rs`, `tray.rs`, `lib.rs`, `capabilities/floating.json`);
- "open a chat" (`commands.rs` `quick_intent_from_route` and the check inside
  `pump_chat`);
- the second-card "suggest" wiring (`set_second_card_suggest`, `build.rs`,
  `permissions/surfaces.toml`, `permissions/autogenerated/set_second_card_suggest.toml`);
- whether the settings-registry feature really touched no Rust.

After that I did a lighter sweep of the rest: the App lock (`lock.rs`), the
approval path (`answer_approval`), and code that writes files or starts
programs. I fixed nothing. This is a report only.

## In plain words (for the owner)

1. **"Open the web search settings" by voice or chat does nothing on the PC.**
   Jarvis answers "Opening Web search in Settings.", but the Settings window
   never opens. The PC's backend sends the right signal, and the page knows
   what to do with it. But the Rust in between passes on only a fixed list of
   fields, and this new field is not on that list. So the page never gets it.
   The settings-registry report was right that it changed no Rust. That is the
   problem: it needed a one-line Rust change. The phone is not affected.
2. **Two Settings buttons are refused before they do anything.** "Find it for
   me" (it looks for Python) and the "hang and crash notes" list are both
   refused by the app's own permission check. That check only lets a window call
   a command that `build.rs` lists, and these two were never added to it.
   Settings then shows "Command crash_notes not allowed by ACL" or a failed
   search.
3. **Turning the floating face on from Settings may freeze the app.** Tauri's
   own documentation for the exact version we use says: on Windows, creating a
   window inside a simple (non-`async`) command deadlocks. `set_floating` is such
   a command, and so are two older ones (`open_faces`, `open_fix_place`). I cannot
   run Windows here, so I am not sure it freezes. **Please test it:** Settings →
   Appearance → tick "Floating face". Turning it on from the tray or with
   Alt+Shift+F is not affected.
4. **The floating face's window can read the full approval queue, email text
   included.** It does not show any of it, and App lock does not cover that
   window, which is on purpose. But its permissions are wider than its own
   description says. Yesterday's audit (#6) found the same problem in two other
   windows, and it was fixed there by taking the permission away.
5. **Four small things.**
   - The "Floating face" box in Settings does not update when the tray or the
     hotkey turns the face on or off.
   - Quitting within about 3 seconds of turning the face off, or moving it, can
     undo that change on the next start.
   - If you had already set any Jarvis hotkey to Alt+Shift+F, the new default
     clashes with it. The startup message then wrongly blames "another
     application", and Settings refuses to save any hotkey until you change one
     of the two.
   - The first "Check for tool updates" raises an approval card, but unlike the
     other buttons that raise a card, it is not held back while the link to the
     PC is reconnecting.

**App lock and the floating face:** leaving the floating window outside App lock
is done correctly. It only shows the face. It has no buttons and no permission
to approve, deny, add notes or control tasks. Its "open a chat" goes through the
lock like every other way to the Jarvis bar. Finding 4 is the one caveat.

**Build checks:** all clean. `cargo fmt --check`: clean. I emptied the build
cache first (`cargo clean --target x86_64-pc-windows-msvc -p jarvis-desktop`),
then ran `cargo check --target x86_64-pc-windows-msvc --all-targets` and
`cargo clippy --target x86_64-pc-windows-msvc --all-targets -- -D warnings`.
Both recompiled the crate and passed. The only warning was the expected,
harmless "GNU compiler is not supported". `cargo test` needs Windows, so it was
not run.

## Detailed findings

### 1. "Open <a settings section>" never reaches the desktop page

**Severity:** medium. A new feature does nothing on the desktop. Nothing unsafe
happens. **Confidence:** high, from reading every step of the path. I did not
run the desktop app.

The path, step by step:

- The backend adds the field. `backend/jarvis_quick.py:2892-2898` (`route_fields`):
  `if res.open_settings: ... out["open_settings"] = res.open_settings`, inside
  the `X-Jarvis-Route` header.
- The page reads it. `main.js:955`, inside `applyHeaderRoute`:
  `openSettingsFromRoute(state.turnRoute);`. Then `main.js:974`:
  `const place = route && typeof route.open_settings === "string" ? route.open_settings : "";`
- In the real app (Tauri), `applyHeaderRoute` gets its `route` only from the
  line that Rust builds (`main.js:2374-2376`):
  `if (line.startsWith(ROUTE_LINE_PREFIX)) { applyHeaderRoute(JSON.parse(line.slice(ROUTE_LINE_PREFIX.length)));`
- Rust builds that line in `route_line_from_header` (`commands.rs:1784-1844`),
  and copies only fields it names:
  ```rust
  for key in ["lane", "where", "gate", "second_card"] {
  ```
  After those it copies `injected_facts`, `injected_sensitive`, `temporary`,
  `remember_off`, `memory_ids` and `turn_id`. `open_settings` is not on the list.
  The comment above the call says so directly (`commands.rs:2071-2073`): "Only
  those fields ... go to the page."
- The page reads the whole header only in `streamViaFetch` (`main.js:2464-2465`).
  That is the browser-preview path, used only outside Tauri.

So in the installed app, `route.open_settings` is always `undefined`,
`openSettingsFromRoute` returns straight away, and Settings never opens. The
answer text still says "Opening <name> in Settings."

**About the claim "the settings-registry feature touched no Rust".** I checked
it, and it is literally true:
- `git show --stat 344c9408` lists no file under `jarvis-desktop/src-tauri`.
- `git diff 24ca2172 959bd719 -- jarvis-desktop/src-tauri` (the merge compared
  with its first parent) is empty.

But the feature needed a Rust change, so "no Rust" is exactly the bug.
`docs/JARVIS-API.md:8628` also says "`main.js`'s `applyHeaderRoute` reads
`open_settings`". That is true only in the browser preview.

**Smallest fix:** in `route_line_from_header`, pass on `open_settings` when it is
a short string of lower-case letters, digits and `-`. `settings.js` looks the id
up with `getElementById`, so an allow-list shape is enough. Add a Rust test.
When this is fixed, the path will go through `open_fix_place`, so fix #3 at the
same time.

### 2. `crash_notes` and `find_python` are refused from every window

**Severity:** medium. Two Settings features are dead: the crash-notes list
(feasibility I99) and "Find it for me" for the Python path. **Confidence:**
high. I checked the Tauri 2.11.5 source and this repo's generated ACL.

- `build.rs:14-16` says: "Anything added to `generate_handler!` in lib.rs must be
  added here too, or it is reachable from nowhere and the failure is a runtime
  'not allowed on window' rather than a compile error."
- `lib.rs:824-825` registers `crash_notes::crash_notes` and `pyfind::find_python`.
  Neither name appears anywhere in `build.rs`. There is no
  `permissions/autogenerated/crash_notes.toml` or `find_python.toml`, and no
  `allow-crash-notes` or `allow-find-python` in `surfaces.toml` or any
  capability. The freshly generated `gen/schemas/acl-manifests.json` has no
  permission for either.
- Tauri 2.11.5, `webview/mod.rs:1823`: when the app has an ACL manifest (it
  does, `build.rs:18`) and no permission allows the command, the call is
  rejected: `Command {} not allowed by ACL`.
- Callers: `settings.js:430` `await invoke("find_python")` and `settings.js:870`
  `notes = await invoke("crash_notes")`. The second one writes the error text
  into `crashNotesState`, so the owner sees the ACL message.

A related weak spot: `chat_sources`, `get_tool_updates` and `check_tool_updates`
(`lib.rs:812`, `lib.rs:870-871`) are not in `build.rs` either. They work today only
because their `permissions/autogenerated/*.toml` files were committed and are
granted in `surfaces.toml`. Nothing regenerates or checks those files, so this
will break the same way the next time one is deleted or renamed. A small test
comparing `generate_handler!` with `build.rs` (the way `tests/security.mjs`
compares capability lists) would catch the whole class.

**Smallest fix:** add all five names to `build.rs`. Put `allow-crash-notes` and
`allow-find-python` in `settings-surface`: Settings is the only caller, and it is
behind App lock. Add the check described above.

### 3. `set_floating` creates a window inside a plain command (may freeze on Windows)

**Severity:** medium if it happens: the whole app stops responding and has to be
ended in Task Manager. **Confidence:** medium. It rests on Tauri's own
documentation. I could not run it, because it needs Windows.

- `commands.rs:3043-3044`: `#[tauri::command] pub fn set_floating(...)` is not
  `async`. When it is turned on, it calls `windows::show_floating`. The first
  time in a run, that builds the window (`windows.rs:1047`,
  `tauri::WebviewWindowBuilder::new(...).build()`).
- Tauri 2.11.5, `webview/webview_window.rs:115-116`: "On Windows, this function
  deadlocks when used in a synchronous command or event handlers, see [the
  Webview2 issue]. You should use `async` commands and separate threads when
  creating windows."
- Why it applies here: a plain command runs inline, on the main thread, inside
  the WebView2 request callback. `ipc/protocol.rs:75` calls `webview.on_message`
  from inside the custom-protocol handler.
- The same shape already exists in `open_faces` (`commands.rs:589`, Settings'
  "Open Faces") and in `open_fix_place` (`plain_errors.rs:243`, "Show me where").
  `open_fix_place` builds the Settings window when it is not open. It is also
  the path finding 1's fix will use.

If "Open Faces" in Settings already works on your PC, this is less likely than
the documentation suggests. That is why the confidence is medium, not high.

The tray's and the hotkey's Alt+Shift+F are different. They run in the event
loop, not in a WebView2 callback. The tray has always built the Brain,
Settings and Faces that way.

**Smallest fix:** make `set_floating`, `open_faces` and `open_fix_place`
`async fn`. Tauri then runs them off the main thread. `tauri-runtime-wry`'s
`send_user_message` (`lib.rs:235-255`) sends the window creation to the event
loop, so nothing else has to change.

**Test on the PC:** open Settings → Appearance → tick "Floating face". Test it
once when the face has not been opened yet in this run, since only the first
time builds the window.

### 4. The floating window can read the whole approval queue

**Severity:** low. Its page is this app's own code and shows only the face.
Release builds have no developer tools (`Cargo.toml:145`: devtools only with a
feature). **Confidence:** high.

- `capabilities/floating.json:10` grants `core:event:allow-listen`, and line 14
  grants `jarvis-link`. That set includes `allow-get-pending-approvals`
  (`surfaces.toml:18`).
- `floating.js` calls `startLink()`. `jarvis-link.js:1156` listens to
  `approvals-changed`, and `jarvis-link.js:1186` calls `get_pending_approvals`.
  Both carry every waiting card in full. `stream.rs:1098-1102` emits
  `{"count", "items"}` with the rows as they are, and the 2026-09-26 audit
  showed those rows include `detail`, which for an email is its whole text.
  `jarvis-link.js:1166` also receives every event frame (`stream.rs:766`).
- The window is outside App lock on purpose (`windows.rs` `show_floating` doc;
  `lock.rs:102-107` `Covered` has no floating entry). So the full text is held
  in a page that stays up while the PC is locked.
- `floating.json`'s description says "jarvis-link (link/approval count, for
  which face state to show - never the approval's own text)". That is untrue in
  the same way as yesterday's finding #6. That finding was fixed for Faces and
  the first-run window by removing `core:event:allow-listen`, and `lib.rs:276-283`
  explains why an event cannot be aimed away from a window that can listen.

For fairness: the widget, also outside App lock, holds the same grants. It needs
them, because it shows cards. The floating window does not.

**Smallest fix:** give the floating page only what it uses: the link state and
the appearance, with no `core:event:allow-listen`, and have it re-read
`get_link_state` on a timer. If you keep it as it is, correct the description in
`floating.json` and add a line to `docs/ARCHITECTURE.md`.

### 5. The Settings "Floating face" box goes out of date

**Severity:** low. The display is wrong, but the switch still works.
**Confidence:** high.

- `settings.js:702-711`: `paintFloating()` reads `get_floating` once, when the
  page loads. Nothing repaints it later.
- The tray and the hotkey (`windows.rs:1125-1135` `toggle_floating`) and a close
  of the window (`windows.rs:1100-1108`, `CloseRequested` sets
  `enabled = false`) change the setting without emitting any event.

So with Settings open, pressing Alt+Shift+F leaves the box showing the old state.
Clicking the box always sends its own new state, so the second click puts things
right. The owner still sees a box that disagrees with the screen.

**Smallest fix:** emit a small `floating-changed` event (a plain true/false) from
`set_floating` and `toggle_floating`, and repaint on it in `settings.js`.

### 6. A change in the last seconds before Quit can be lost

**Severity:** low. **Confidence:** high about the code. How often it happens
depends on timing.

- `FloatingState::update` only marks the prefs "dirty". They are written by the
  telemetry tick every `TELEMETRY_INTERVAL` (3 s, `lib.rs:76`, `lib.rs:430-445`).
- On exit, `lib.rs:1274-1297` forces the event-stream resume point
  (`stream::save_resume_now`) and stops the backend. It does not flush
  `WidgetState` or `FloatingState`.

So if you turn the face off (or drag it) and choose Quit within about 3 s,
`floating.json` still says it is on, and it reopens on the next start. The
widget had the same gap before; the floating face copied it.

**Smallest fix:** call both `flush`es next to `save_resume_now` in `ExitRequested`
and `Exit`.

### 7. An existing Alt+Shift+F binding clashes with the new default

**Severity:** low. It only affects an owner who had already set some action to
Alt+Shift+F. **Confidence:** high about Jarvis's code. For Windows' side I
relied on how `RegisterHotKey` is documented to behave, not on a test.

- `hotkeys.rs:175-198` `configured()` takes each saved binding and the default
  for any action with none saved. So after the update, a saved `Alt+Shift+F`
  sits next to the new `toggle_floating` default `Alt+Shift+F`. Nothing checks
  for a clash there.
- `apply()` (`hotkeys.rs:247-287`) registers them in the `ACTIONS` order.
  `toggle_floating` is last, so the older action keeps the key. The floating
  face's registration then fails (`global-hotkey-0.8.0` `platform_impl/windows/mod.rs:96`,
  `RegisterHotKey`).
- The startup notification (`lib.rs:1235-1243`) then says the key "could not be
  registered — another application owns it". That is wrong: Jarvis owns it.
- `set_hotkeys` (`hotkeys.rs:343-349`) starts from `configured()` and runs
  `validate`. So every save from Settings is refused ("`Alt+Shift+F` is on both
  ...") until you move one of the two.

**Smallest fix:** in `configured()`, when a DEFAULT (not a saved value) collides
with a saved binding, leave that action unbound and give a plain reason. Also
word the notification differently when the clash is with Jarvis's own key.

### 8. The first "Check for tool updates" is not held on a stale link

**Severity:** low. It only raises a card, and a card cannot be approved while the
link is stale. **Confidence:** high about the code. Whether this is a bug is a
question of house rule.

- `tool_updates.rs:123-135` `check_tool_updates` posts `/api/tool_updates/check`
  without checking `link().stale`. The first check ever raises an approval card
  (its own test, `the_first_ever_check_waits_for_a_card`).
- The other commands that raise a card hold it while the link is stale, with this
  reason (`commands.rs` `set_second_card` doc and `:3444`): "the card it raises
  should be answered by someone looking at a live queue". `set_briefing` and
  `set_backup_folder` (`backup.rs`) do the same.

**Smallest fix:** add the same stale check at the start of `check_tool_updates`.

## Possible, not verified

- **"Open a chat" typed into a bar that is already open may shrink it for a
  moment.** `pump_chat` calls `show_quickbar`, and `show_quickbar_unlocked`
  (`windows.rs:300-321`) always resizes to the input row (`QUICKBAR_BASE_HEIGHT`)
  and re-centres. That happens while the page is streaming the answer. The page
  only grows the window during a stream (`main.js:657`,
  `if (state.phase === "streaming" && height < lastReportedHeight) return;`), and
  `lastReportedHeight` is never reset (`main.js:640-680`). So until the height
  changes by 2 px or more, the answer card may be clipped, and a bar the owner
  had dragged jumps back to the centre. I have not run it. Simplest guard: skip
  `show_quickbar` when the bar is already visible.
- **A hidden floating face keeps its window alive.** Turning it off only hides the
  window (`windows.rs:1114-1122`). The WebView stays until the app exits, which
  goes against its own reason for being "built on demand" (`windows.rs` doc:
  "a hidden webview living for the run of the app would be pure cost").
  `faces.html:4466-4467` stops its animation on `visibilitychange`. I did not
  check whether WebView2 marks a page hidden when Tauri hides its window.
- **The embedded face frame is same-origin and not sandboxed.** `floating.html`
  (and `widget.html:110`) load `faces.html` in an `<iframe>` without `sandbox`.
  A same-origin frame can reach its parent page's objects, so the claim that
  the face "never holds a Tauri permission of its own" rests on `faces.html`
  never doing so. That is true today, since it is this app's own file. I did
  not test whether Tauri's IPC is also injected into sub-frames.
- **`pyfind.rs` can leave a child running.** On a timeout, `run_and_capture`
  (`pyfind.rs:262-264`) kills only the program it started. With the `py`
  launcher, the real `python.exe` it started keeps running. If `try_wait` itself
  fails (`:272`), the child is not killed at all. None of this matters until
  finding 2 is fixed, because `find_python` cannot be reached today.

## Areas read and found fine

- **The floating face outside App lock.** `lock.rs:102-126`'s `Covered` lists only
  the Jarvis bar, Brain, Settings and HUD, and `spawn_watch` hides only those.
  The floating window grants no `approvals`, `task-control`, `widget-surface`,
  `focus` or `private-reveal`, so it cannot approve, deny, add a note, or steer a
  task. `answer_approval`'s widget-under-lock check (`commands.rs:2276-2283`) is
  keyed on the widget's label and does not need a floating entry. On screen it
  shows only a state id and the face. Finding 4 is the one caveat.
- **"Open a chat" and App lock.** `pump_chat` (`commands.rs:2105-2118`) calls
  `windows::show_quickbar`, which calls `lock::may_open` first
  (`windows.rs:291-296`). When locked, Windows Hello is asked and the bar opens
  only after it passes. It approves nothing. `quick_intent_from_route` handles
  bad JSON (`.ok()?`) and a missing or non-string field. A `focus-input` sent to
  a bar that stays hidden while locked only focuses a hidden text box.
- **Focus stealing.** The floating window is built with `.focused(false)`.
  `tao-0.35.3` keeps its "don't focus" mark for the life of the window
  (`window.rs:1147`, `window_state.rs:329-333`; the mark is cleared only on a
  local copy), so every later `show()` uses `SW_SHOWNOACTIVATE`.
- **Floating state and files.** `FloatingState`'s lock recovers if poisoned
  (`unwrap_or_else(into_inner)`). A missing or damaged `floating.json` falls back
  to "off, no position". A saved position is checked with `position_is_visible`
  before use. Close is turned into hide and "off".
- **The second-card "suggest" wiring.** `set_second_card_suggest` accepts only
  `struggle` or `correction`, is held on a stale link, and is granted only to
  Settings (`settings-surface`, `surfaces.toml:340`). `build.rs`, the
  autogenerated `.toml` and `lib.rs` agree. `mark_answer`'s new
  `conversation_id` is sent only after `valid_conversation_id`. Errors carry the
  backend's own sentence, never the token.
- **The approval path.** `answer_approval` still checks, in order: a refused
  option id, a stale link, the widget under App lock, an email from the widget,
  Windows Hello, the link again, and the backend's owner-check refusal. The
  2026-09-26 finding 5 is fixed: `waiting_email` now returns `true` for an id it
  cannot find (`commands.rs:3096-3099`).
- **Crash notes (as code).** `scrub` only cuts text at character boundaries.
  `to_ascii_lowercase` keeps byte positions the same, and the value scan stops
  at the first non-ASCII byte. The panic hook takes only `WRITE_LOCK`, never
  while already holding it, and `logfile::log` takes no lock. So a panic
  inside the hook cannot deadlock it.
- **Backups.** `set_backup_folder` checks the link before the folder dialog, and
  `post` checks it again after, so a long wait at the dialog cannot send on a
  stale link. The recovery code is never put in an error.
- **Hotkeys, apart from finding 7.** The new action has a unique id, and its
  default parses and does not clash with the other defaults (the existing
  `the_defaults_do_not_collide` test covers it). The handler resolves the key
  against the live bindings.
- **Commands and permissions for the new code.** `get_floating`, `set_floating`
  and `set_second_card_suggest` are each in `lib.rs`, `build.rs`,
  `permissions/autogenerated/` and exactly one set in `surfaces.toml`, and only
  Settings is granted them.
- **Checks run.**
  - `cargo fmt --check`: clean.
  - `cargo clean --target x86_64-pc-windows-msvc -p jarvis-desktop`, then
    `cargo check --target x86_64-pc-windows-msvc --all-targets` and
    `cargo clippy --target x86_64-pc-windows-msvc --all-targets -- -D warnings`:
    both clean. The only warning was the expected "GNU compiler is not supported
    for this target".
  - A script compared the `generate_handler!` list in `lib.rs` with `build.rs`,
    `permissions/autogenerated/` and `surfaces.toml`. That is how finding 2 was
    found.
  - `cargo test` needs Windows and was not run.
