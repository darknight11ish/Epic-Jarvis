# Bug audit, 2026-10-07

A full pass over `main` (the repository's default branch), its patch stack, its
own suites, the pull requests open at the time, its performance, its upstream
dependencies, and the gap between what its comments claim and what its code
does.

**What this document is.** The findings, the fixes that were made, and the
things left for the owner to decide. The machine-readable detail behind each
finding - every `path:line`, every command, every measurement - is in the
per-stream reports listed at the end.

**Scope note.** The working checkout was on the side branch
`feat/plug-and-play-modules`. Every finding below was taken from a throwaway
worktree of the real `main`, so nothing here describes that side branch.

## 1. The fixes in this pull request

Thirteen files change. Each fix was verified by compiling the file, running its
own suite, or reproducing the before-and-after behaviour.

### 1.1 A short named secret was never redacted - rule 3 broken for exactly that case

`backend/jarvis_scrub.py` applied one floor (`_MIN_KNOWN = 8`) to every secret.
That floor exists so a short *unlabelled* value ("1", "yes") is not replaced
everywhere - but it was also applied to secrets whose **name says they are
secrets**, so `HUD_TOKEN=abc1234` (seven characters) went into the log in clear.
Reproduced: `scrub_text("...token abc1234...")` returned it verbatim, while
`abc12345` was redacted.

Fixed by splitting the two cases: `_MIN_NAMED = 4` for name-marked secrets
(`HUD_TOKEN`, `JARVIS_IMAP_PASSWORD`, the token file, the CalDAV
user-and-password blob), with `_MIN_KNOWN = 8` left alone for registered and
free-text values. The existing control test - *"a value under 8 characters is
not replaced everywhere"* - still passes, which is the point: the deliberate
behaviour is kept and only the loophole is closed.

### 1.2 The config writer overwrote the live file before making its backup

`backend/_apply_toml_tiers.py` wrote the live `jarvis-framework.toml` **first**
and the timestamped backup **second**, while its own docstring promised the copy
is made "before it writes". A failure between the two (no space, a locked file,
power loss) left the approval-tier table changed with no undo copy - and the
next line still printed "Your copy from before the change: \<path\>" for a file
that did not exist.

Fixed: the backup is written first, and if it cannot be written the live file is
left alone.

### 1.3 A Python < 3.10 compatibility shim that could never install

`backend/_where.py` probed for `Path.write_text(newline=...)` by running
`Path("").write_text("", newline="\n")`. `Path("")` is the current directory, so
this raises `IsADirectoryError` or `PermissionError` - never the `TypeError`
being tested for - and an outer `except Exception: pass` swallowed it. On a
Python 3.9 machine the shim silently never installed, and all 84
`write_text(..., newline=)` call sites would have raised `TypeError`.

Fixed by asking the signature directly
(`inspect.signature(Path.write_text).parameters`), which cannot be defeated by a
permission or a path and never touches a file.

### 1.4 A truncated approval card could still be approved - the second half of rule 4

**The most important fix here, because it is the same mistake this project had
already learned once.**

The gate stores a card's `detail` as `json.dumps(detail)[:4000]`, so a long
command arrives **truncated**. `jarvis-link.js` marks that `cutOff`, and
`main.js` and `widget.js` disable their Approve button on it - and that disabled
button was the *entire* enforcement. `commands.rs`'s `answer_approval`, the one
command that actually sends a decision, never re-checked it.

The comment five lines above that same function explains why that is not enough,
for rule 4's staleness rule: *"A disabled button is a courtesy, not a gate: any
window holding the `approvals` capability reaches this directly."* After the
staleness rule was moved into Rust, the cut-off rule was left behind in the
webviews.

Fixed in three parts: `stream.rs` gains a pure, tested `detail_was_cut_off()`
and a `GATE_DETAIL_LIMIT`; `commands.rs` gains `waiting_cut_off()` and refuses
an **Approve** on a cut-off card; and `tests/approvals-contract.mjs` gains three
drift guards so the two sides cannot disagree about where the cut is.

**Deny deliberately still works** on such a card. Refusing costs a retry, and
trapping the owner with an undismissable card would be worse than the bug. This
matches how the email rule and the App-lock widget rule already gate Approve
alone.

### 1.5 The Jarvis bar's "Erase the words" silently lost its warning

The quickbar's "Also delete the chat it came from?" asks how many **other**
facts that chat taught, because deleting the chat forgets none of them. That
count comes from `brain_conversation_facts`, which was granted only by the
`brain-memory` permission set. The Brain holds that set; the Jarvis bar does
not. So the bar's call was refused by Tauri, the refusal was swallowed into the
number `0`, and the bar said "some other facts stay" where the Brain named the
count - two surfaces disagreeing about the same question.

Fixed by adding `allow-brain-conversation-facts` to the `memory-used` set,
beside the two calls it is part of.

### 1.6 Picture mode told the owner to pull a model that does not exist

`backend/jarvis_screen_picture.py` set `DEFAULT_MODEL = "minicpm-v:4.6"`, and
the copy-paste line the screen shows the owner was
`ollama pull 'minicpm-v:4.6'`. That page is a **404**, and the `minicpm-v`
model's tags are `latest, 8b, 8b-2.6-q2_K ... 8b-2.6-fp16` - there is no `4.6`
tag. The real model is a *different name*: `minicpm-v4.6`.

The old comment on that line said the tag was unverified, and
`docs/MODEL-TOPOLOGY.md` said plainly *"`minicpm-v:4.6` is a guess"* - so this
resolves a known unknown rather than contradicting a decision.

Fixed in `DEFAULT_MODEL`, and the generator that produces the fixture was
changed to **read** the tag from the module instead of spelling it out a second
time - which is how the wrong tag survived in two places.

### 1.7 A read-only-looking tool that wrote 15.9 MB

`tools/gen_source_bundle.py` had **no argument handling at all**, so any
argument - `--check`, a typo, a flag meant for another tool - performed the full
write of the 15.9 MB, gitignored `docs/SOURCE-BUNDLE.md`. That matters because
the file's **absence is itself a checked claim**: `docs/CLAIMS.tsv` row D01 is
`no-file:docs/SOURCE-BUNDLE.md`, judged by `tools/check_claims.py`. A stray
argument used to turn the `audit` CI job red from a command that looked
read-only.

Fixed: it now answers `--check` (compare, write nothing, exit 1 if stale),
`-h`/`--help`, and **refuses** an argument it does not know instead of obeying
it.

### 1.8 The HUD's prompt window slid one exchange every turn

`jarvis_hud.html` sent `S.messages.slice(-12)`. Past the twelfth message that
drops the oldest one on **every** turn, so the message part of the prompt
differed from its first token every turn and nothing could be reused from the
model's cache. Measured over a twelve-turn exchange: **0 messages reused and
5,822 of 7,279 message tokens (80%) re-read**, forever.

The Jarvis bar (`chat-history.js`, `MAX_EXCHANGES`/`MAX_CHARS`) and the phone
(`ChatHistory.kt`) already trim in **blocks** - this page was the odd one out.
Fixed with `windowForPrompt`/`promptWindow`, which keep a sticky count of how
many messages have been dropped and move the boundary only when the
conversation genuinely outgrows the window. Measured after the fix: turns
between drops reuse **8-10 messages**.

Two real bugs were caught in the first attempts by the test written for it, and
are worth recording: deriving the drop from the current length made it slide
exactly as before, and a stale count larger than the conversation **blanked the
prompt entirely**. `jarvis-desktop/tests/hud-prompt-window.mjs` is a new
browser-free suite that holds both.

### 1.9 Two Critical defects that arrived with the merged money-limit work

The six chatbot API keys and their monthly money limits merged into `main`
during this audit (PR #86). Two defects in that work are live in `main`, and are
fixed here.

**A `"lower_limit"` that raises was applied with no card.** The direction guard
in `jarvis_chatbot_limits.py` checked only one way, and the unguarded way was
the one that matters: `{"action": "lower_limit", "dollars": 500}` against a `$1`
limit walked straight to `set_limit(..., 500)` - a **loosening with no approval
card and no Windows Hello**, up to the $10,000 ceiling. The module's own
docstring already promised the opposite. Fixed by deciding the direction from
the numbers, both ways: anything above the current limit is a raise, whatever it
called itself.

**A price of `$0` made the limit inert.** The price check accepted zero, and
with a zero price every answer counted as `$0.000000`, so the month never
advanced and the limit could never stop anything (measured: three huge answers
left the month at `$0.000000 of $1.0`). Fixed by requiring a price above zero,
with a message saying that removing the limit or the key is how to stop paying -
not a price of nothing.

## 2. Verified, and left alone

The audit looked hard at the things that would matter most if they were wrong,
and they were not:

- **The patch stack is sound.** 124 `.patch` files on disk = 124 in
  `$PATCHES`, 0 unlisted, 0 missing, 0 duplicated; **367 of 367 hunks** have
  header counts matching their bodies; `_where.SHIPPED` equals
  `apply-patches.ps1`'s `$SHIPPED` (same 163 entries, same order).
- **No drift between `backend/` and `jarvis-backend/`**: 153 same-named modules
  byte-identical, plus the 10 rebuilt ones.
- **The prompt's stable prefix really is stable.** The persona and recalled-fact
  blocks were assembled twice, 1.2 s apart, through the shipped functions:
  **18,579 bytes, byte-identical**. Dates come from each fact's own `created`,
  never from "now". The `memory-prefix.patch` fix genuinely holds.
- **The desktop's command registration and capability grants are correct**: all
  272 JS `invoke` names are registered, and after closing each page over its
  imports and diffing against its capability file there is no window invoking an
  ungranted command (the one exception was 1.5).
- **The phone's rules hold**: `X-Jarvis-Client: hud` on every request including
  the two no-key pairing routes; the token under Keystore with a triple-redacted
  crash log; no auto-approve or bulk approve anywhere; the staleness rule at
  ~100 call sites; no client-side speech-to-text; all 25 `PendingIntent`s
  immutable; the address allowlist enforced at the single URL builder.
- **The claims register is honest.** 118 claim rows examined: **109 of the 111
  definite rows held exactly as written**, 7 are marked unverifiable and say so.
  `tools/check_claims.py` exits 0 on clean `main`. No new false safety claim was
  found.
- **Zero security advisories** against any of the 78 pinned Python versions, and
  CI already gates both `cargo deny check advisories` and
  `tools/check_python_advisories.py`.

## 3. What is left, and why

Four things are written down rather than fixed, because fixing them is a
decision rather than a correction.

### 3.1 The cloud lane's spend recording needs the owner's file (Critical, unresolved)

A cloud-lane answer is claimed to be checked against the month's limit before it
is sent. Whether the answer is then **recorded** could not be settled from this
repository: the path that would do it runs through `jarvis_hud.py`, which is the
owner's file and never in the repository. `jarvis_quiz_cloud.py` delegates to
`ApiChatbot`, which does record - so the gap, if it is one, is in the HUD's own
lane rather than in the driver.

**What to do about it:** confirm on the PC whether a cloud answer moves
`spent_of` for that service. If it does not, the monthly limit cannot stop
anything on that lane, and the fix belongs in a patch against `jarvis_hud.py`.

### 3.2 199 MB of the repository is six revisions of one launch video

`videos/` is 199.20 MB of the tree's 296.40 MB - **67% of the repository** -
across six revisions, each with a landscape and a vertical `.mp4` plus a
`composition/` source tree. Ten `.mp4`s hold 184.04 MB of it. There is no Git
LFS anywhere and `.gitattributes` has no `*.mp4` binary rule.

Every other duplicate in the tree is pinned by a test, so this is essentially
all of the reclaimable space. `CLAUDE.md` records *"never replace a launch
video"*, so moving or removing them contradicts a written instruction until the
owner rules. **Nothing was deleted.**

### 3.3 The phone's approval widget does not notice App lock being switched on

`JarvisRuntime.kt` combines `_pending,_link,_stale` but not `settings.security`,
while `widget/ApprovalWidget.kt` reads it at draw time and the provider has
`updatePeriodMillis="0"`. A card already on the home screen keeps its full
notice title and body, and a one-tap Deny, indefinitely. The job 13 lines below
carries the exact missing line with a comment saying why it matters.

### 3.4 Smaller, recorded findings

- **`screen-captured` / `capture-failed`** are declared, listened for and
  documented as live, but nothing in Rust ever emits them - so the quickbar's
  picture-attachment path is unreachable and four suites drive the dead path
  with `window.__emit`.
- **`jarvis-android`** keeps a bearer token and an HMAC secret in plain
  `SharedPreferences`, against rule 3, and CI still builds that module even
  though it cannot talk to Jarvis at all.
- **`check_claims.py` judges the working tree, not git**, so untracked files
  produce false "a claim regressed" errors - it bit twice during this audit.
- **40 `CLAIMS.tsv` rows cite `CLAUDE.md:<line>`, and that column is never
  validated.** It has already drifted (B18 cites `:998` for the 60,000 shader
  budget, which is at `:1004`), and `ci.yml`'s `paths-ignore` means a
  CLAUDE.md-only push starts no workflow at all.
- **`verify-toolchain.yml`**, whose stated job is to pin every `uses:` to an
  immutable commit, resolves four actions to moving tags while the rest of the
  repo pins commits.
- **Two CI steps have no test behind them**: `tests/shots.mjs` collects page
  console errors and only prints them, and `tests/sheet.mjs` asserts nothing.
- **Upstream drift**, from 178 dependencies checked: Obscura is pinned at
  v0.2.3 while v0.2.4 has landed (212 commits), on the project's highest-trust
  downloaded executable; and the hardware research is a stale snapshot (Ollama
  `b2da9e4` when v0.40.0 is current, llama.cpp `b11081` when `b11460` is).
