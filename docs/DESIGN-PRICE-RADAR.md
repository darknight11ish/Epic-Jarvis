# Design: the flight price radar (anti-surveillance stack, slice F1)

**Status: F1 is built, READ-ONLY, and OFF by default.** It is the flight engine
and the price-history store of the anti-surveillance price radar the owner
approved on 2026-10-21. Nothing ties it to an app, a route, a schedule or a
card yet: `[price_radar] enabled = false` in both shipped
`jarvis-framework.toml` copies, and no check runs until the owner turns it on
with one approval card. The endpoint it reads is **unofficial** (Google's
public Flights search page, not a published API) and can change or break
without notice. **"Flight radar" is NOT a booking tool** - there is no cart,
no seat hold, no checkout and no booking/PNR path anywhere in it.

| item | state |
|---|---|
| The engine | `backend/jarvis_price_radar.py` (+ byte-identical `jarvis-backend/` twin, shipped whole): pure-stdlib `tfs` protobuf builder + tolerant page parser + SQLite price history. |
| New dependencies | **None.** Standard library only; the endpoint is read with `urllib` through the project's own `jarvis_local_http.public_urlopen` (which re-checks private addresses at the connection) and its redirect-refusing handler. |
| The switch | `[price_radar] enabled = false` (both toml copies). On = one `change_own_config` card; off = immediate. |
| F2 / F3 | **Not in this module.** Multi-source product pages + steering are F2's own shipped module `backend/jarvis_price_sources.py`; proxies/multi-exit are F3. F1 exposes the integration points in §7 and imports neither. |
| Tests | `backend/test_price_radar.py`, 119 checks, no network: byte-parity `tfs` goldens from the MIT reference, parser fixtures, store semantics, SSRF, challenge, switch, disclosure words. |

## 1. Why the public page, not the RPC

`punitarani/fli` documents this in `fli/search/_tfs.py`: since 2026-08 the
`FlightsFrontendService` RPCs (`GetShoppingResults`, `GetCalendarGraph`)
require an `x-goog-batchexecute-bgr` header that only the page's own
JavaScript can produce, bound to the exact request bytes, so every plain HTTP
client gets a payload-less `wrb.fr` row carrying error 13. The public search
page is not gated that way: it serves the same rows inline in an
`AF_initDataCallback` blob keyed `ds:1`, addressed by a `tfs` protobuf
parameter. F1 builds that parameter and reads that blob.

**Honest consequence:** this is an unofficial interface. Its shape was
recorded by two MIT projects and by the fixtures in this repository, not
promised by anyone. It may break; when it does the store records
`unavailable`/`stale`, invents no price, and says so.

## 2. The `tfs` builder (adapted from punitarani/fli and fast-flights, both MIT)

The wire layout is ported from `fli/search/_proto.py` (its comment block "tfs
is the itinerary parameter" lists the whole message) and
`fli/search/_tfs.py` (`build_tfs`, `page_url`). Field positions:

| field | meaning |
|---|---|
| 1 = 28, 2 = 2 | constants |
| 3 (repeated) | one travel direction: 3.2 date, 3.4 selected leg (repeated), 3.5 stop ceiling (zero-based), 3.6/3.7 carrier include/exclude, 3.13 origin, 3.14 destination, 3.15 layover airport, 3.17/3.18 layover minute bounds |
| 8 (repeated) | passenger kind per traveller: 1 adult, 2 child, 3 infant on lap, 4 infant in own seat |
| 9 | cabin: 1 economy, 2 premium economy, 3 business, 4 first |
| 14 = 1 | constant |
| 19 | 2 one-way, 1 round trip (multi-city is not available through this page) |

Two details are load-bearing and tested:

* **`MaxStops.ANY` must leave field 3.5 out.** Writing `0` means "non-stop",
  not "any" - a malformed token is answered by Google as a *different query*,
  quietly.
* **The two infant codes are different money.** A lap infant is ~10% of the
  adult fare and an infant in its own seat ~100%; transposing them returns a
  plausible wrong fare instead of an error.

**Byte parity is the proof.** The suite stores the `tfs` golden values recorded
by the Python reference implementation (`fli-js/tests/search/tfs.test.ts`'s
`TFS_GOLDENS`, generated by `fli/search/_proto.py` and
`fli/search/_tfs.py`; pinned from `punitarani/fli` main commit `881aee5`,
read 2026-10-21) and asserts **every one of the 34** is byte-identical to this
module's builder.

**A date window is N read-only queries, not one call.** The public page takes
one departure date, so `date_window(date, days)` returns the ISO dates and the
caller spaces their checks by the poll floor; it never fires a burst. (The
calendar RPC that would return a matrix is the gated one in §1 - not used.)

## 3. The parser (tolerant, integer cents, never invents a price)

Positions come from `fli/search/_decoders.py` (`parse_flight_row`:
`row[0]` detail, `row[1]` price block, `detail[2]` legs, `detail[9]`
duration) cross-checked with `fast_flights/parser.py` (`parse_js`: fare at
`k[1][0][1]`, legs at `flight[2]`, duration at `[11]`). The parser:

* extracts `lowest_price_cents` (integer whole cents), airline code, stops,
  duration and the optional low/typical/high price level;
* converts a price only when the currency's minor unit is known (a small
  table of 2-decimal and 0-decimal currencies). An unknown currency makes the
  answer `unavailable`, never a guessed cents number;
* is tolerant row by row: a malformed row is skipped, unknown fields are
  ignored, a page without the payload is `unavailable` with a reason - it
  never raises at the caller and never produces a fake price;
* keeps **numbers**, not the page's prose: the store records cents/airline
  code/stops/duration, and the page text is outside text handled by §5.

## 4. The store (`price-radar.db` in the settings folder)

SQLite, versioned schema via `PRAGMA user_version` (idempotent migration),
short-lived connections only, and the project's #673 pragmas (WAL,
`synchronous=NORMAL`, `busy_timeout`, `temp_store=MEMORY`) through
`jarvis_sqlite.connect`. Two tables: `routes` (origin, destination, dates,
cabin, max stops, currency, `target_price_cents`, next check time) and
`snapshots` (checked_at, lowest_price_cents, airline, stops, duration,
price_level, stale, stale_reason).

* **Last-known-good + stale on failure.** A failed, blocked or unavailable
  check records `stale: true` with a reason and **no price**; the previous
  good snapshot is never overwritten and nothing is alerted. This mirrors
  `jarvis_tellme`'s page-watch semantics, including the watermark rule: an
  unchanged check is silent.
* **The diff is outside text.** A real change (price drop/rise, airline,
  stops, duration) becomes one plain sentence in whole dollars plus the
  per-result footer and the target/low-price notes. It also latches
  `jarvis_gate.latch_taint(why="price_radar")`, so a turn shaped by it is
  outside text and nothing read from the page is learned or logged - the same
  rule `jarvis_tellme` applies (`why="page_watch"`).
* **The poll floor is hard.** `next_check_at` is at least
  `POLL_FLOOR_SECONDS = 300` seconds out, with seeded +/-30% jitter, so no
  check can fire on a robotic tick or faster than every five minutes.

## 5. The hard refusal invariants (each tested)

1. **No checkout / cart-add / seat-hold / PNR endpoints.** The module has
   exactly one request: a GET of the single public search-page URL. No
   POST/PUT semantics exist, and the URL allowlist refuses any other path
   (the test names `/travel/flights/booking` and checkout paths explicitly).
2. **No authenticated or login-walled scraping.** The request carries no
   `Cookie`, `Authorization`, or cache validators, and the module never reads
   the vault or the token store. The test spies on the outgoing request.
3. **No CAPTCHA solving or challenge bypass.** HTTP 403/429 raises
   `BlockedBySiteChallenge`; the store records `stale: true` with reason
   `blocked_by_site_challenge` and the check stops. **One attempt, no retry
   loop** - the test counts the opener calls.
4. **Strict SSRF block.** `page_problem(url)` accepts only `https://` +
   exactly `www.google.com` + exactly `/travel/flights` + only the query keys
   this module writes (`tfs`, `hl`, `gl`, `curr`) with no port, userinfo or
   fragment; loopback/RFC1918/link-local/CGNAT, other hosts and other paths
   are refused before a request is built. Redirects are refused outright by
   a redirect handler (no cross-host or private-IP redirect target).
5. **No proxy support in F1.** `proxy_urls` and exit labels are F3's; F1
   sends every request directly (and the default opener goes through
   `jarvis_local_http.public_urlopen`, which re-checks private addresses at
   the connection). No public proxy lists exist anywhere.
6. **Hard poll floor >= 300 s with +/-30% jitter** (see §4).

The disclosure the owner approved, in the module as constants so F2/F3 reuse
it verbatim:

* switch/approval card: *"Checks public product and flight prices without
  sending cookies, saved logins, or tracking tags, using standard browser
  headers so repeated checks aren't linked together. It only reads public
  prices and never logs in, holds seats, or starts a checkout."*
* per result: *"Checked as a new visitor (no cookies or account used)."*
* steering row (F2): *"This store showed two different prices at the same
  time: $X.XX (Desktop · via search referral) vs. $Y.YY (Mobile · direct)."*
* proxy used (F3): *"Checked via configured proxy (`<exit_label>`)."*

## 6. Privacy

The only thing F1 keeps is **numbers**: a route, whole-cent prices, an airline
code, stops, duration, and the reason a check failed. It never stores the page,
its prose, the request, or any response body; it prints and logs nothing (the
suite proves it with captured stdout/stderr and a logging handler). The page's
words are outside text: a real change latches the gate taint and the cards say
so. No cookies, no account, no session, no redirect, no proxy.

## 7. What F2 and F3 wire in (F1 imports them lazily, only when the switch is on)

* `install_f2()` - called by `enabled()` the FIRST time the switch reads true.
  It imports `jarvis_price_sources.py` lazily and calls that module's
  `install_into()`, so a base without F2 runs exactly as F1 does today and an
  off switch never imports the item module. The call is idempotent.
* `set_sources(sources)` / `sources()` - F2 (`jarvis_price_sources.py`)
  installs its two source objects, `searxng` and `steering` (each with
  `name`, `fetch()` and `render()`; `SearxngPriceSource` and
  `SteeringProbeSource` in that module).
* `register_alert_renderer(fn)` - F2 installs its card renderer (`alert_renderer`);
  `alert_text(store, route_id)` uses it, and falls back to F1's core words
  (diff + footer + the unofficial note). The renderer adds the approved
  steering row only when the change says steering was detected.
* `PriceStore(path=None)` - passed explicitly to F2's sources; F2 calls
  `add_route` / `record` / `record_stale` / `diff` on the same store, so the
  history and the outside-text rules are one implementation.
* **the four disclosure constants/functions in §5 are F1's and stay here ONCE.**
  F2 delegates through `jarvis_price_radar` (`result_footer()`,
  `steering_row()`, `proxy_note()` in the F2 module are thin wrappers) and
  carries no second copy of any sentence - its test holds that with an `ast`
  check.
* `[price_radar] searxng_url = "http://127.0.0.1:8888"` is in BOTH shipped
  toml copies (the docker-compose host mapping; the container's own port is
  8080). It is the address F2's SearXNG query dials; an override must be an
  address `jarvis_search`'s own rule accepts (this PC or the owner's own
  networks).

F2 and F3 therefore add their files and their transports; the wiring is one
lazy `install_f2()` in F1's switch getter, not a second radar. The combined
feature is still a price radar, never a booking flow.

## 8. Switch, one-sidedness, and what is not measured

* `[price_radar] enabled = false` in both shipped toml copies. Turning it on is
  one `change_own_config` approval card; turning it off is immediate (it only
  takes something away). No scheduled checks run until it is on, and the F2
  sources are not even imported until it is on.
* **Backend only, for now, and there is no app surface to be one-sided about:**
  no route, no chat tool, no card, no Settings row in either app is added by
  F1. When F2/F3 make it visible, the desktop/phone split (if any) belongs in
  `docs/ARCHITECTURE.md` §8 with the same rule the other features follow.
* **Not measured:** the endpoint's stability and the real page payload on the
  owner's network. The suite uses recorded reference goldens and synthetic
  payload fixtures only - **no live request is made anywhere in it**. Enabling
  the switch is the first real measurement, and the PR says so.
* F1 does not claim Google's prices are the lowest available; that is F2's
  cross-check, and neither is a booking tool.
