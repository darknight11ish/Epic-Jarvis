# Android UI audit — 14 September 2026

Six reviewers, working independently against `jarvis-client` on
`claude/android-apk-build-q435fi`, the shared visual spec, `JARVIS-API.md`, and
the desktop on `origin/claude/jarvis-desktop-tauri-vey6bc`:

| Reviewer | Brief |
|---|---|
| Interaction / IA | Menus, flows, ease of use, what is unreachable |
| Visual direction | Shape and feel; what to delete |
| Compose feasibility | What a mid-range phone can actually afford, priced |
| Colour science | Themes, contrast, colour-vision deficiency, photosensitivity |
| Brain-view IA | What "Jarvis's brain, viewable on the phone" should contain |
| Desktop parity | Where the two clients disagree, and which disagreements matter |

**Every claim below was re-verified before it was acted on.** Two claims from
the earlier round did not survive checking, so nothing here is relayed on
trust. Where a reviewer's number is quoted, it was re-derived independently —
all twelve contrast figures spot-checked reproduced exactly, and the colour
pipeline reproduced the spec's own five recorded ΔE-2000 pairs to the decimal.

## 1. What was actually broken

Ranked by consequence, not by how hard it was to find.

### 1.1 An approval never made a sound

The app had **one** notification channel: `jarvis_link`, `IMPORTANCE_LOW`, with
`setSilent(true)`. There was no approval notification of any kind.

So a decision could arrive, sit in the queue and expire with the phone
face-down on a table having made no sound and shown nothing. That is the entire
reason the foreground service holds an SSE connection open in the background —
the battery was being spent and the delivery it paid for did not exist.

Fixed: a second channel at `IMPORTANCE_HIGH`, posted and cancelled against the
live queue, so approving on the desktop clears the phone's notification too.

Two deliberate refusals in that fix:

- **No Approve/Deny actions on the notification.** Both gates that make a
  decision safe live inside the app: the staleness check, which refuses to send
  a decision the phone cannot confirm is still live, and the fingerprint on
  anything outbound or irreversible. A notification action routes around both,
  from the lock screen. Tapping opens the card — one extra tap, and the whole
  safety model.
- **A `raised` item never raises the alarm level.** `raised` is a quoted
  assertion from whoever wrote the message, which is exactly what a phishing
  attempt sets. It changes the wording and nothing else. Giving it
  `PRIORITY_MAX` or a full-screen intent would hand an attacker the volume
  control.

### 1.2 The interruption budget always read "0 of 0"

`GET /api/attention` returns the budget **nested**:
`{budget: {limit, spent, remaining, blocked_by, muted}, pending, banked, …}`.
The app modelled it flat — copied from the shape of the `attention` *event*,
which genuinely is flat.

Because every field is defaulted and `ignoreUnknownKeys` is on, the parse
**succeeded** and returned `remaining = 0, limit = 0, blocked_by = null` on
every call, for ever. Only `pending` and `banked` are top-level and parsed
correctly.

A budget line reading "0 of 5 spoken interruptions left today" says the budget
is exhausted. Saying that by accident is the one thing it must never do.

The mute switch had a second version of the same bug: it read
`blocked_by == "muted"`, and `muted` is its own field on the budget, so the
switch could never be on regardless of the real state.

### 1.3 The face claimed Jarvis had errored whenever the phone lost Wi-Fi

`faceState()` returned `FaceState.ERROR` for any link state other than
`CONNECTED`. The spec's error face is a **reversed** motion with a hitch and a
shake — a deliberately alarming thing, shown for a three-second blip between
two cell towers.

It also keyed on the enum, and the stream reports `OFFLINE` from the second
retry onward while still retrying, so a grace period written against the enum
would have expired about a second in. It now keys on time since the link
dropped, and face state is a flow rather than a function call, because a grace
that expires on a timer is not re-read by a function nothing is watching.

### 1.4 Approval sat below banked in the face precedence

```
was:  error > listening/thinking/speaking > banked > approval > standby > idle
now:  error > approval > listening/thinking/speaking > banked > standby > idle
```

`banked` and `pending` are separate queues, so `banked == true` with something
waiting is entirely reachable. When it happened the phone rendered `BANKED`:
solid neutral, `rate 0.0` — the clock literally stops — dimmed to 0.45, no
knock ping, no waiting clock. The state that exists to pull the eye was
suppressed by the state that exists to be ignored, on the device most likely to
be the only one in the room. The desktop tray has had the right order all along.

### 1.5 The pattern engine skipped rule 1

The reference is one line in `shell.html`:

```js
const q = Object.assign({}, P.params, bind.params || {});
```

The pattern's own params are the base; the binding overrides key by key. The
desktop ports this literally. Android did not port it at all: `Binding` carried
a *kind* and one generic set of defaults shared by all twelve patterns, so an
unset key fell back to 4.5 seconds and a 360° span whatever pattern it belonged
to.

Measured against the reference over 600 samples per pattern, six of the eight
implemented kinds diverged once unbound — up to 209/255 on a channel. A bound
`sweep` rendered as a full rainbow (span 90 → 360). An unbound `gradient` ran
ice→ice instead of azure→magenta. A comet's tail was a darkened head that
collapsed into it at the loop extreme, so the comet had no tail.

It was invisible only because the eight shipped bindings hardcode their merged
result — and **one of them had already drifted**: standby breathed at 11s
against the desktop's 4.5, visibly a different grey. 11 is the midpoint of
`randomise.timing.breathe.standby: [9, 13]`, a rule for *generating* bindings
applied by mistake to a shipped one.

Bindings now carry a pattern and merge over its params. The three missing kinds
(`step_cycle`, `flicker`, `temperature`) are implemented, so Randomise can no
longer roll an outcome that renders nothing.

### 1.6 Two photosensitivity limits were unenforced

`limits.flash` has four numbers. Two were implemented (`max_transitions_per_s`,
`min_luma_delta`) and two were not: `strobe_max_s` and `flicker_rate_hz_max`.
The state most likely to strobe is error, which lasts until someone fixes
whatever is wrong. Both are enforced now inside `resolve()`, which the spec
names as the only path to a colour.

### 1.7 Smaller, all verified

- Only `Arc` was ever reachable: `FaceView` takes `face` and `bindings` and
  `HomeScreen` passed neither. No picker, no Randomise, nothing persisted.
- Zero `BackHandler` in the codebase. System back from the inbox left the app.
- The checks screen rendered inside the `link == CONNECTED` branch — hidden
  exactly when you need it.
- `paired` was `remember`, not `rememberSaveable`, while the other two flags
  were: a rotation could bounce a paired device back to pairing.
- `onNewIntent` was not overridden under `launchMode="singleTask"`.
- The digest's "open the approval" discarded the id.
- `ChatSession.error` was written to a flow nothing collected: a failed send
  looked exactly like one still thinking, permanently.
- `VersionInfo.can()` had no callers.
- `StatusInfo.lane` and `.model` were parsed and discarded — zero readers. The
  desktop carries "this left your machine" as a violet route badge across two
  surfaces; the phone had no representation of it at all.
- The rush chip printed the count twice: the scanner already folds "(4th time
  today)" into `text`.
- The brief did not carry "Marking read approves nothing."
- The link bar said "N banked" about a number that counts the digest, and a
  boolean that is usually false.

## 2. Performance: what was priced, and what was refused

The frame budget on an Adreno 610-class phone at 60 Hz is 16.7 ms, with a
practical app-side target of 8 ms on the UI thread.

**The single largest cost was the glow.** `Brush.radialGradient` was built
*inside* the draw: a new `ArrayList`, two boxed `Color`s, a new `ShaderBrush`
and — because a `ShaderBrush` caches its native shader per instance — a fresh
`RadialGradient` and gradient ramp, every active frame. At radius 2.1× it
covers essentially the whole canvas, roughly **thirty times the fill of the
entire particle field**. The most expensive thing on screen was also the thing
being rebuilt sixty times a second. Estimated 0.6–1.4 ms → 0.1–0.2 ms as a
cached sprite with a tint, and it now composites additively, which is what the
spec's own canvas fallback for bloom asks for and what `SrcOver` was not.

Also fixed: Fullerene's per-frame `ArrayList` of 62 `Triple`s plus ~186 boxed
`Float`s (~15,000 objects a second), a per-frame `Random` allocation in the
synthetic voice envelope, and a frame clock that woke at the display rate
during BANKED (2 fps) and STANDBY (15 fps) to decide to do nothing — across
what the spec itself calls nine tenths of screen-on time.

**Refused, with reasons:**

| | Why not |
|---|---|
| Live frosted glass / blur behind sheets | Est. 8–20 ms. The most-requested "cutting edge" effect and the most expensive. |
| `Modifier.blur` / `RenderEffect` on the face | Est. 2–5 ms against 0.15 ms for a gradient that reproduces the halo *exactly* — the halo is a smooth monotonic falloff, so there is no structure for a blur to preserve. API 33 did not change that arithmetic; availability was never the reason. |
| Full-screen animated shader background | Est. 4–12 ms **continuously**, whether or not anything is happening. A battery decision as much as a frame one. |
| Grain, chromatic aberration | On the spec's explicit `never` list for the phone tier. |
| An ambient particle field behind the UI | There already is one. It is the face, it is the product, and it is bounded to 260 dp. |
| Elevation shadows as decoration | Each is an outline shadow rasterised per frame while scrolling; 20 cards ≈ 2–8 ms. This design is flat plates and hairlines. |
| 120 Hz | Halves every budget above, for motion that is slow rotation and breathing. |
| An animated node graph for the brain | See §4. |

The one-line version: **the phone can afford one animated surface, at one
bounded size, with no full-screen per-pixel pass.** Everything cutting-edge
that fits inside that sentence is affordable; everything that does not costs
more than the whole reactor does today.

## 3. The theme system

Six themes: **Reactor** (default), **Void** (true black), **Graphite**,
**Ember Dusk**, **Daylight**, **High Contrast**.

The structural rule is that a theme owns the chrome and never a state colour.
Colours split three ways:

- **Free to the theme** — surfaces, text tiers, hairlines. Nothing the face or
  the desktop reads.
- **Constrained** — `ok`/`warn`/`bad` pick a *step*, never a *family*, because
  `randomise.state_rules` pins approval and error to verdant/amber/rose and
  refuses to move them. "A green alarm is a design you have to explain." A
  theme must not be able to break a rule the randomiser cannot.
- **Not the theme's at all** — every state colour, and the accent.

**The accent is derived, not chosen.** It is the idle binding's colour, walked
along its own family until it clears the theme's contrast floor. There is no
accent picker and deliberately so: re-roll idle to violet and the caret, focus
ring and selection become violet on *both* clients, because both compute the
same function from the same bindings. The chrome cannot disagree with the face
because it has no opinion of its own. The walk stays inside the family — going
toward white would desaturate the hue, and the hue is the thing that was bound.

Two results worth stating plainly:

**A fully light theme is not buildable here, and Daylight does not pretend to
be one.** Every face composites additively (`globalCompositeOperation
'lighter'`, and the bloom sprite too). A light source on a white page is not
dim, it is *absent* — the reactor would be a white disc on a white card.
Converting to source-over would mean rewriting twenty faces and would still
lose the glow, which is the product. So Daylight is light chrome with the
reactor in a dark inset well: a dark gauge face in a light dashboard, which is
what real instruments do. It earns its place on the text screens and outdoors.

**High Contrast does not touch the semantic trio.** Raising it to step 5 is the
obvious move; it buys contrast nothing needed (step 4 already clears AAA at
8.43:1) and collapses ok-versus-bad under deuteranopia from 8.2 to **4.6** —
the exact separation the spec already ruled unacceptable elsewhere. The pale
steps converge toward white, and white has no hue to lose.

### Accessibility, measured

Worst text contrast anywhere in the system is **4.57:1** (Reactor and Void
`text-lo` on `surface-2`), clearing AA by 0.07. Every tier is measured against
the *worst* of its three surfaces, not the darkest, which is how a tier ends up
failing on exactly one card.

The governing colour-vision figure is **ok/bad at 8.2 ΔE to a deuteranope**.
`verdant-4` and `rose-4` differ by 99.7 units on the red-green axis and by
**1.2** once simulated — both become nearly the same beige. So **ok and bad are
never distinguished by colour alone**: the affirmative action is filled and the
destructive one is outlined, and the two remain distinguishable with the colour
removed entirely.

A third hairline token exists — `hairlineFocus` — because the decorative ones
measure 1.2–2.0:1, which is correct for a card edge and wrong for anything that
is the *sole* indicator of focus or selection. Reaching for `hairlineStrong`
when you mean focus is the most likely accessibility regression in the file;
the values differ by a factor of two.

### The photosensitivity hazard theming introduces

A theme change does not go through `resolve()`, so the flash governor cannot
see it: the governor measures the *state* colour and a theme changes the
surface underneath it. Every dark-to-dark switch is genuinely below the
threshold (all five dark grounds sit in Y ∈ [0.0000, 0.0064]); anything to or
from Daylight is a swing of ΔY 0.87 and counts.

Closed with a 500 ms crossfade at full display rate plus a 500 ms dwell
**enforced in the store, not the UI**, so a double-tap or a system light/dark
flap cannot get past it either. That is 1.0 opposing transitions a second
against a budget of three. The "follow the system" setting also defers: it
never fires while the face is listening, thinking, speaking, approving or
erroring, because a ground that changes mid-approval is exactly the "is it
telling me something?" ambiguity the waiting clock exists to remove.

## 4. The brain screen

**State of Mind**, reached by tapping the face.

It is a status board, not an animated node graph, and that is a measurement
rather than a preference: **there is no 60 fps content in this data.** The
active model changes every few seconds, the routing lane changes per request,
VRAM samples arrive around 1 Hz, memory facts and jobs are event-driven.
Animating it at the display rate spends the frame budget interpolating nothing.
Text is what kills it — roughly 0.15–0.6 ms per uncached measurement, so twenty
node labels at 60 fps is 3–12 ms, more than the rest of the screen combined.

A graph that re-lays-out on every glance is also *harder* to read: a fact you
have to re-find is worse than a row that stays in the same place.

Order, which is a ranking by consequence:

1. **Rush latch** — from `/api/content-risk`. First, because it changes how
   everything below should be read; it is the only thing on the screen that is
   adversarial by construction. Quote rendered as a quote, source named and
   never quoted, and a line saying nothing is approved from here.
2. **Freshness** — whether any of it can be trusted. A stale board full of
   numbers is worse than no board.
3. **Doing** — activity, power, route (local/cloud/offline, with cloud in the
   desktop's violet), model, whether anything is held.
4. **Attention budget** — now that it parses.
5. **Background work** — with each job's *frozen* capability set, because "a
   job can never gain more while it runs" is only checkable if you can see what
   it was approved with.
6. **Compute, memory queue, findings, audit chain, skills.**
7. **This backend** — the capability list the app itself branches on, so "why
   is that button missing" has an answer.

The memory section shows the **review queue**, never the corpus: `/api/graph`
is desktop-only by the contract's own instruction, and a memory graph is not a
thing to read on a phone. What belongs there is the short list of facts waiting
for a yes or no.

The face is parked while this screen is open. Two animated canvases on a
mid-range GPU is exactly where the budget goes.

## 5. Backend gaps

These are things the contract does not provide. None is routed around.

1. **No audio transport.** Blocks the voice loop entirely (step 7).
2. **No power-set route.** The QS tile toggles mute instead.
3. **Nothing serves `face_state`.** §5 says the server resolves it; no route
   does, so the client re-derives it and the two clients can disagree. The
   composition rule should be in the spec rather than described in prose in two
   places.
4. **No route lists send-holds.** `POST /api/holds/cancel` exists; nothing
   gives a phone a handle to cancel.
5. **No UI-preference sync.** `POST /api/config` is 501 by design and none of
   the 38 endpoints reads or writes a preference. So the theme and bindings are
   per-device and the picker says so rather than faking sync. Chrome *should*
   stay per-device — a phone is used outdoors, a desktop bar floats in a room —
   but **bindings should eventually sync**, because they are a shared
   vocabulary rather than a taste. A phone whose `thinking` is violet while the
   desktop's is green has learned a private language.
6. **Five routes documented by existence only.** `/api/compute`,
   `/api/memory/pending`, `/api/ledger`, `/api/skills` and `/api/initiative`
   have a line of description each and no field names. Rather than invent keys
   — the mistake that produced the other client's protocol, and one that fails
   silently as a panel that looks built — these are fetched as raw JSON and
   rendered from whatever actually comes back. When the contract grows the
   shapes they become real models.

## 6. Spec disagreements to take back upstream

1. `states.standby.default` resolves to a 4.5 s breathe;
   `randomise.timing.breathe.standby` says 9–13. Android had picked the latter.
   Fixed to follow `states[].default`, which is what the resolver reads — but
   the spec holds both opinions.
2. `limits.flash.why_these_numbers` says the stated flicker rate "must stay
   below the limit divided by 2.3", which caps it at 0.57 Hz and makes the
   spec's own `flicker` default of 1.2 Hz illegal. The numbers are
   self-consistent (1.3 × 2.3 = 2.99, just under three transitions a second);
   the sentence explaining them is not.
3. `randomise.separation` is a proxy — hue-ring distance and step difference —
   and by it the **shipped defaults fail**: idle `ice-3` against speaking
   `ice-4` is distance 0, step difference 1. Measured, they are a healthy 15.6.
   The proxy is too crude and should gain a measured gate beside it.
4. `colour_science.note` says re-binding approval to verdant-5 gives 41 / 18.7.
   Re-measured on an instrument that reproduces all five of the spec's own
   recorded pairs exactly, it is **44.0 / 23.6**. The conclusion survives and
   improves; the figure should be corrected.
5. Unrecorded and worth adding: **standby and banked separate by only 7.0–7.7
   ΔE in every vision model**, and they share idle's motion table. It is safe
   only because banked's `rate: 0.0` stops the clock dead against standby's 0.5,
   plus the notch ring. That makes the stopped clock and the notches
   **accessibility features, not decoration** — one careless "let's just redraw
   banked at 2 fps like standby" destroys the distinction.
6. Three desktop surfaces carry off-palette state colours (`--ok: #3ddc97`,
   `--warn: #ffc860`, `--bad: #ff6b7a`, and a fourth error red in the HUD).
   Android's are exact. The spotlight's miniature reactor takes its *state*
   colours from *chrome* tokens, so the two faces already disagree slightly by
   construction — and totally, the moment anyone presses Randomise.

## 6a. Second pass, 14 Sep — after the corrected `shell.html` arrived

The desktop fixed `_resolveRaw`'s duplicated defaults; I had ported the version
before that fix. So both engines were re-implemented in Python and diffed over
600 samples of all twelve patterns. **Ten were byte-identical. Two were not.**

- **`flicker` was the wrong algorithm, not a wrong constant.** The reference
  walks the family's palette ramp by a hash and quantises to a step. Mine was a
  pair of sine oscillators lifting one base colour — smooth where the reference
  steps, periodic where it should be irregular, **117/255 out** on the hot
  channel. It also honoured a bound colour, which the reference deliberately
  ignores: the family *is* the binding for that pattern.
- **`temperature` darkened its structural colour by 0.55 against 0.50.** 13/255.

`tools/gen_golden.py` now emits 640 samples from a faithful port of the
reference switch, and `PatternGoldenTest` replays them. The value is entirely in
where the expected values come from — every earlier face test compared Kotlin
constants to other Kotlin constants, which is why two drifts survived a green
suite.

Also found in the same pass:

- **`/api/pending` returns `{"available", "pending", "history"}`** — not a bare
  array and not `items`. The client matched neither, so every arriving approval
  would have rendered as "nothing waiting". Four list routes, four different
  keys. See §1.
- **The strobe floor was 0.4s, which permits five opposing transitions a second
  against a limit of three.** Taken from the pattern's `safety` prose, which is
  wrong by a factor of two — the same factor the desktop hit from the other
  side.
- **The biometric prompt threw on every use.** A negative button alongside
  `DEVICE_CREDENTIAL` makes `PromptInfo.Builder.build()` raise, and the build
  call sat outside the guard.
- **Step 6 was never built.** No `setFrameRate`, no mode enumeration, no
  readout — so on a 90/120/144 Hz panel the face was being handed 60 vsyncs a
  second. Now asks for the highest rate at the current resolution, and the
  checks screen reports panel / asked-for / achieved separately, because
  nothing on Android reports why a request was refused.
- **Capabilities were displayed but never branched on**, where §2 says a
  capability reporting false means hide the UI for it.

## 7. Not done

- **The wake word.** Not blocked on the API any more — see
  [`docs/WAKE-WORD.md`](WAKE-WORD.md). It needs a keyword-spotter model that
  cannot be fetched from this build environment, and a `microphone` foreground
  service type the app does not hold, which makes the microphone indicator
  permanent while armed.
- **Push-to-talk has never met a real microphone.** CI compiles and unit-tests;
  it cannot hold a button. The WAV encoding, resampling and verdict handling
  are tested; capture, playback and the permission flow are not.
- **IBM Plex Sans is not bundled.** No font CDN is reachable from the build
  environment. The type scale rides the platform font at the right weights and
  tracking; dropping the TTFs into `res/font/` and pointing `JarvisType.sans`
  at them is the only change needed.
- **Band-batched `drawPoints`/`drawLines`.** Estimated 1–2.5 ms saving on the
  particle faces and the best remaining perf-per-hour item — and deliberately
  left undone, because the spec is explicit that it must not be taken on
  faith: *"Measured in a software-GL container it was ~48 ms per frame
  slower."* `renderer.point_batch.calibration` requires measuring both paths on
  the device and keeping the faster, with ties going to canvas. Nothing in this
  build environment can run that measurement, so shipping the batch blind would
  be doing the one thing the spec names as the mistake.
- **Generating `Spec.kt`'s non-palette constants from the JSON.** `Palette.kt`
  is generated; the rest is still transcribed, now with `SpecDriftTest` reading
  the spec as a test resource so a drift is a test failure rather than a silent
  re-colour. It caught two on its first run.
