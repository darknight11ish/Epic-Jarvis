# UI audit, 2026-10-05: both apps together

A user-interface audit of the desktop app and the Android app, judged against
what this program actually is - and against how other assistants solve the same
problems. Read-only: nothing was changed.

**What "effective" means here**, stated before any judging, because this is not
a consumer product and the usual benchmarks do not apply:

| The app is | So the UI must |
|---|---|
| One owner, one PC, one phone | Optimise for one person's memory of their own tool, not for a stranger's first-run comprehension - but see §4 on onboarding |
| A local model that takes seconds | Never block on the model; show state while it works; keep the fast paths working when the model is asleep |
| Approval-gated: nothing acts without a card | Make the card the best-designed surface in the app, and make Deny as easy as Approve |
| Ambient: a spotlight, a widget, an always-on-top face | Be glanceable - correct at a glance, silent when nothing is happening |
| Private by construction | Show *what it can reach* and *what left the PC* better than anyone, because that is the product's whole claim |
| Hand-built, no framework, no bundler | Earn its complexity: every panel, card and window must justify its maintenance |

**How this audit was done.** Three source-level passes (desktop visual system and
interaction, Android Material/accessibility, cross-app information architecture
and states), plus the measurable checks in §1 that were run by hand. Two limits
worth stating up front: **nothing was rendered** - no browser automation
(Playwright is not installed; the project's own suites say so) and the app is not
running - so every judgement about appearance comes from the CSS, the Compose
code and the design documents rather than from looking at it. And the phone
cannot be built here (no Android SDK).

## 1. What is measurably right (so the findings below are read in proportion)

This project's UI engineering is better than most commercial apps of this size,
and three facts prove it.

**1.1 The theme is token-driven, and a build check enforces it.** Running the
project's own checker:

```
python3 scripts/check-tokens.py
→ style.css 0 unreachable, widget.css 0, settings.css 0, brain.css 0,
  theme.css 0 (5 defining blocks), projects.css 0, forget-range.css 0,
  retirement.css 0, jarvis_hud.html 0, TOTAL 0
```

`theme.css` states the rule - "a literal colour belongs in `:root` or in a
`[data-theme]` block. Anywhere else it is a bug, and `scripts/check-tokens.mjs`
fails the build for it" - and the checker runs in CI (`.github/workflows/ci.yml:89`).
The file also records the bug it was written to fix: 94 colours had been welded
into component rules, so "switch the theme" could only ever move part of the UI.
**A one-owner app with four themes and a working palette guard is unusual.**

**1.2 Contrast is checked against two backdrops, not one.** `tests/themecheck.mjs`
holds 25 pairs (body text, muted, faint, accent-as-boundary, focus ring, five
graph hues, the ok/warn/bad state words) against five theme blocks, and checks
each pair **twice** - over black and over white - because these windows are
translucent and "the desktop behind them is not ours to choose". The High
Contrast theme is held to 7:1 for text where the others take 4.5:1. The CSS also
records the failures it found and fixed: `--text-faint` measured **2.37:1** over
white, and muted text on the old translucent sunken well measured **2.21:1**.
That is a real accessibility process, not a claim.

*Two caveats, both findings:* the check needs Playwright, so it only runs in CI -
a plain `node tests/themecheck.mjs` refuses with "These UI tests need Playwright"
- and `theme.css:23` names a file that does not exist (`scripts/check-contrast.mjs`;
the real guard is `tests/themecheck.mjs`). See §3.6.

**1.3 The phone's type scale was reasoned about rather than copied.**
`JarvisTheme.kt:219-231`: "14px at 60cm on a monitor and 14sp at 30cm in a hand
are not the same apparent size, and matching the numbers would make the phone
read small... Body is 17sp, not Material's 14. This is a thing you read at arm's
length with one hand, often outdoors." The relationships between sizes are shared
with the desktop; the numbers are not. That is the right call, and most apps get
it wrong.

**What that means for the rest of this document:** the problems here are
structural, not sloppy. Almost nothing is a broken colour or an unlabelled
button. What needs work is **how much there is, where it lives, and what it says
when there is nothing to say.**

**1.4 There is a written contract for the things the two apps must agree on -
and it is measured, not decorative.** `docs/SHARED-LOOK.md` sorts every colour in
both apps into three classes (the theme's freely / the theme's but constrained /
nobody's but `resolve()`'s), and states the rule that makes the class system
matter: **"a state colour must never come from a chrome token, on either
client"** - because the spotlight's reactor takes its approval/error colour from
a chrome token, so the face already disagreed with the phone about what Jarvis was
doing, "slightly, and by construction rather than by accident". It also measures
colour-blind separation rather than asserting it: on white, one candidate step has
better hue separation for a deuteranope (ΔE 9.8 against 7.5) but fails AA for
text at 4.39:1, so hue carries the *mark* tier (3:1, icons and fills) and words
carry the *ink* tier (4.5:1) - "a label is present and hue was never doing the
distinguishing".

That is a stronger accessibility argument than most shipped apps make. It also
records its own starting problem honestly: **the desktop shipped four colour
vocabularies across four surfaces, and the phone's tokens were transcribed by eye
from `jarvis_hud.html`, three of them a digit off.** Whether that consolidation
finished in the desktop's own sheets is the desktop pass's job to say.

## 2. What good looks like for this class of program

The comparison the owner asked for, kept to the patterns that actually apply to a
one-owner, local, approval-gated assistant. Sources are the competitor research
behind [COMPETITORS-2026-10-05.md](COMPETITORS-2026-10-05.md).

### 2.1 The permission prompt is the product

This is where every 2026 assistant is being judged, because it is where one of
them failed publicly.

| Product | How it presents an action | What a local, no-account app can take |
|---|---|---|
| **OpenAI Dots** | Four **Custom Rules** per action - act without asking / act if pre-approved / ask first / hand off - plus a per-app access list, and background research that is read-only by policy | The *shape*: one screen where the owner sets rules per app, and the distinction between what runs unattended (reads) and what stops for a human (anything touching an account). **Not** the first rule |
| **Meta Muse** | A separate host-side checker (Sentinel) with grants that are one-time, session, task, time-bounded **or perpetual** - and whose developer-tool wording let an owner believe "Allow Always" still covered sensitive decisions, after which Muse accepted a lowball price **and sent the buyer the owner's home address** | The lesson: **a permission is only as good as its wording**. Scope must be on the card in words a tired person cannot misread, and "always" must not exist |
| **Microsoft Copilot** | Copilot Actions runs under a **separate agent account** with its own isolated desktop and four folders by default; disabled by default; asks for anything more | The isolation pattern - and a reminder that "off by default" plus "asks for more" is the accepted enterprise shape |
| **Apple Siri** | Explicitly **request-based, not an agent loop**; on-device orchestration sends only a handful of relevant items | That restraint is presentable: a card that names exactly what was read is the local equivalent of a stateless request |
| **Jarvis** | One card per action, no standing grant, no approve-all, Windows Hello on risky cards, blocked on a stale link, plus a 100-row "What asks first" page | The strictest model in the field - and the worst explainer of it (see §4) |

**Effective-practice checklist for an approval card**, from the above plus the
classic human-factors literature on consent: the action in plain words; the exact
arguments; **what it does not grant** ("this one action only"); what shaped the
request ("this conversation has read your email"); what happens if you refuse;
Deny as easy as Approve (button parity, not a hidden dismiss); no pre-selected
risky option; and, for a repeat, an explicit count ("3 of 5 cards this turn").

### 2.2 Showing what the assistant did

Dots reports progress and asks questions; Muse keeps an activity trail; Copilot
Recall keeps a timeline; agent frameworks (OpenHands, suna) replay every step.
Jarvis already sends a past-approvals list that **both apps ignore**
(`JARVIS-API` §41), and its `step` event is deliberately unpublished for privacy.
The gap is not the data - it is that no screen answers "what has it been doing?".

### 2.3 Memory the owner can see and correct

ChatGPT's single "enable memory" switch has been criticised for hiding what it
holds; Claude's user-curated memory is the best of the commercial ones; Muse puts
`MEMORY.md` on disk where the owner can read it. Jarvis is ahead on *control*
(every fact listed, dated, Forget, Erase-the-words, "what did I believe then")
and behind on *presentation*: there is no single printable "what I know about
you" page, which is the thing that makes control feel real.

### 2.4 Findability at scale

Raycast, PowerToys Command Palette and Flow Launcher all exist because a
capable tool accumulates more actions than a menu can hold. Jarvis has **104 menu
entries three levels deep, 34 settings cards behind 33 jump links, 10 hotkeys
(two unbound), 22 tray rows and 93 spoken phrases** - and no palette. The
project has already decided the palette must be built inside Tauri (an external
launcher would hold the pairing token), which is the right call; it just has not
been built.

### 2.5 Voice and ambient state

Siri, Gemini Live and Alexa+ all answer the "did it hear me?" question with a
sound or a visible state. Jarvis has the "I heard you" switch (off by default,
the owner's choice), a listening indicator, and five animated faces whose state
colour carries meaning. The faces are the app's most distinctive UI asset, and
§1.4 shows the state-colour system behind them is measured - but a state that is
carried by colour alone needs a second channel (shape, motion or a word) for
anyone who cannot distinguish hue. That applies to the state dots in both apps
too; `SHARED-LOOK.md` addresses it for the tier where a label is present.

### 2.6 Accessibility in assistants specifically

The commercial assistants are not good at this - streaming chat UIs routinely
break screen readers (no live region, focus lost after a streamed answer, text
inserted without announcement). Jarvis's audit trail includes TalkBack work
(unlabelled switches fixed, High Contrast fallback, a font-scale test) and the
Android pass in this audit counts `contentDescription` coverage. What is
unusual and worth keeping: the project treats accessibility as a *release*
criterion (`test_untested` style guards, `ThemeContrastTest.kt`, the 4.5:1
contrast suite), not a backlog item.

### 2.7 The six patterns to avoid

1. **"Always allow" as a default** - Muse's home-address incident.
2. **A permission screen that describes capability instead of actions** - the
   same incident's root cause.
3. **Auto-approval offered first in a menu** - Dots' first Custom Rule.
4. **Silent failure** - the app is full of `catch { }` paths; a control that
   cannot appear must say why, not vanish (this is the "Grade this better" bug
   from the [feature review](FEATURE-REVIEW-2026-10-04.md) C1 #3).
5. **A settings page as the answer to a navigation problem** - 34 cards is a
   findability bug wearing a settings costume.
6. **Colour as the only carrier of state** - for the faces, the state dots and
   the graph hues.

Three source-level passes were run against this document: the **desktop** visual
system and interaction, the **phone's** Material/accessibility and navigation, and
the **cross-app information architecture**. The phone pass is complete (§3.1);
the other two are added below as they land.

point of failure for the bar**: the quickbar is `skipTaskbar`, hidden, and hides

Faces (tray + Settings button) and the two voice cards are defensible - but
"Voice" and "Jarvis's voice" should be renamed to "Your voice and how strict" and

names.

### 3.3 Cross-app information architecture - complete

**Counts first.** §0's corrections come from this pass; the older audits' figures
(19 or 21 settings cards, 39 registry sections, 13 phone screens, "22 preflight
checks" attributed to the phone) are stale and should not be re-quoted.
`docs/COHESIVENESS-AUDIT-2026-09-30.md` in particular says "19 cards", "208 ported
/ 33 one-sided" and names menu groups (`group.goals`, `group.memory`) that **do
not exist** - the real six are study, goals-projects, graphics-cards, chatbots,
finance, home. Do not cite that audit for numbers.

**The one finding that shows the owner something untrue** - same class as
[BUG-AUDIT](BUG-AUDIT-2026-10-05.md)'s silent features:

> **"What Jarvis can reach" reports an empty list as a broken install.** On the
> desktop, `reach.js:83` is `if (!rows.length) return { available: false, why: MISSING }`,
> where `MISSING` says *"Your PC's Jarvis cannot list what it can reach yet - run
> apply-patches.ps1 on the PC."* If the list is simply empty, the owner is told to
> re-run the installer. On the phone the loop renders nothing and the heading jumps
> straight to "Tools the AI model is offered" (`ReachPlate.kt:77-91`). **One
> sentence each**, and the desktop's is actively wrong.

**The structural difference between the two apps**, which explains most of the
rest: the desktop is **ambient** (a window is already on screen, or a hotkey
brings it), and the phone is **navigational - with its top-level navigation off by
default**. The nav row is hidden until swiped (`AppearanceStore.kt:688`), so
*everything* on the phone costs one extra undiscoverable gesture, and the five
commonest tasks have no shared shape: asking a question is `Alt+Space` on the PC
and two taps on the phone; finding a setting is three steps versus two to four;
"what happened" lives in eight places under five names. Only voice is the same on
both. **One default flipped - show the nav row, keep "hide" as an option - makes
every phone task one step cheaper**, and it is the cheapest structural win in this
whole audit.

**Four real wording disagreements** (the shared-words machinery is otherwise
genuinely honoured - the approval card's sentences and ~25 plate titles are
identical in both apps by contract):

1. **"Expired" versus "Timed out" inside the phone itself**: the card says
   "Expired - ask the desktop to raise this again" (`ApprovalCard.kt:324`) while
   the phone's own filter and the desktop's list say "Timed out"
   (`InboxScreen.kt:403`, `card-words.js:48`). One concept, two words, one screen.
2. **"Background jobs" / "Background work" / "Running jobs"** for the same thing
   across three files.
3. The phone's **jump list** calls the screen "Picture mode (Look at this)" while
   its own plate title says "Look at this and Watch with me"
   (`SettingsJump.kt:42` vs `LookPlate.kt:53`).
4. **Activity has two homes** - Brain → Work on the desktop, Inbox on the phone -
   with the same name. That is the worst kind of disagreement, because the owner
   cannot learn it.
   Plus "Memory (model view)" in the phone catalogue against plain "Memory" on the
   desktop, and ~60 stale `Mind` comments in each app (no user-visible string says
   Mind any more, so this matters only to reviewers).

**Depth and reachability.** The 104-entry catalogue is at most **four decisions**
deep and the two deepest paths are rare - depth is not the problem. The problems
are concentration and the first step: the desktop's Work tab holds **16 cards in
one uninterrupted column** with no sub-headings (the catalogue already carries
`data-menu-group` on four groups, so this is a `brain.js` change, not a redesign),
and the phone's Brain is ~40 sections with three headings and **no jump list** -
the desktop's own fix was ported to Settings but never to Brain.

**The approval flow, traced end to end, is the most carefully built thing in the
repo**: stale-link refusal lives in Rust rather than the webview, a disabled
button is explicitly called "a courtesy, not a gate", the second-decision race has

"Expired"/"Timed out" split; the phone's heavy-card delay ("Approve unlocks in a

like a hang; and a card that needs a **choice** cannot be approved at all -
`commands.rs:2413-2423` refuses `option_id` with a long technical sentence
("approving needs a server route that can carry the choice") that reaches the
owner verbatim. And one state is never handled: **a risky card that expires while
App lock is on**, whose only record is the Activity list behind that same lock.

**First run, re-scored.** Setup stays **2/10** - the two worst blockers are both
still open and neither is an app problem: `INSTALL.md` step 3 still says "there is
no download link. The backend is not a public project", and the desktop has no
installer (empty updater key). **Customising is no longer 5/10 - call it 7/10**:

## 4. Measured findings (run by hand)

### 4.1 Finding: `theme.css` documents a contrast guard that does not exist under that name

- **Where:** `jarvis-desktop/src/theme.css:23` names `scripts/check-contrast.mjs`.
- **What is true:** there is no `check-contrast.mjs` anywhere in the repository.
  The real guard is `jarvis-desktop/tests/themecheck.mjs`, which imports its
  maths from `tests/contrast.mjs`. So the *guard* exists and is good; the
  *pointer* is stale.
- **Why it matters:** this is the same defect class as the rest of this week's
  audit - a document promising something the tree does not contain. It is also
  the kind of drift that costs a new session an hour ("where is the contrast
  check?"), and this project's own rules say a named file must exist.
- **Severity: Low.** **Fix:** correct the comment to name `tests/themecheck.mjs`,
  and mention that it needs Playwright so it runs in CI, not locally.
- **Confidence: Confirmed** (searched the whole tree; ran the checker that does
  exist; attempted the Playwright one and read its refusal message).

### 4.2 Finding: the two apps do not share a typeface, and it is the only real TODO in the codebase

- **Where:** `jarvis-client/.../ui/theme/JarvisTheme.kt:227-231`.
- **What it says:** "the product's own face is IBM Plex Sans, bundled on the
  desktop under the OFL. It is not bundled here - no font CDN is reachable from
  this build environment - so this rides the platform font at the right weights
  and tracking. Dropping the TTFs into `res/font/` and pointing `sans` at them is
  the only change needed."
- **Why it matters:** `docs/SHARED-LOOK.md` exists so the two apps look like one
  product; the desktop sets IBM Plex Sans and the phone sets Roboto. A shared
  palette, shared iconography and shared wording with a different typeface is
  still recognisably two products - and this is the *only* unresolved TODO in
  roughly 300,000 lines of shipped code, which suggests it was forgotten rather
  than decided.
- **Severity: Medium** (it is the cheapest remaining thing that would make the
  two apps feel like one).
- **Fix:** bundle the two or three weights in `jarvis-client/app/src/main/res/font/`
  (OFL permits it; credit already exists in `THIRD-PARTY-NOTICES.txt`), point
  `JarvisType.sans` at them, and keep the current size/tracking scale.
- **Confidence: Confirmed** (the comment is explicit; the desktop bundles IBM
  Plex Sans under `jarvis-desktop/src/`).

## 5. Onboarding, which the passes will say more about

The measured facts, so they are not lost in the detail:

- `docs/INSTALL.md` is **1,263 lines / 60 numbered steps**; the "Quick start" is
  10 steps and is genuinely the shortest path to a first chat.
- Step 3 is "have your backend folder ready (section 1.3 - **there is no
  download for it**)". The project's own ease audit called this the point where
  "everyone but you stops, after installing 3 programs".
- The desktop's `onboarding.html` is **three static screens**.
- The phone's first run is `ReadinessScreen.kt` plus **22 preflight checks**.
- The project's own scores: first-time setup **2/10**, customising **5/10**,
  "settings are spread over about 11 places" (7/10 for finding things).
- Against that: every competitor installs by signing in (Dots, Muse, Copilot),
  and Dots ships a permission walkthrough per app rather than a settings page.

**The one structural conclusion that does not depend on any pass:** the app's
onboarding teaches *nothing about the product's central idea* - the approval
card. A new owner meets their first card with no explanation of what it grants,
what it does not, or what happens if they refuse. Every competitor with an
agentic product puts that explanation first (Dots: four named rules per action;
Muse: Sentinel with a stated scope), and the one that got it wrong - Muse's
"Allow Always" that leaked a home address - shows what the explanation is for.
**Jarvis's card wording is good; its absence from onboarding is the gap.**

## Method limits

- Nothing was rendered: no Playwright, no running app, no Android build. Every
  appearance judgement comes from CSS, Compose source and the design docs.
- The contrast pairs could not be re-run here (Playwright is absent); §1.2
  reports what the suite checks and what the CSS records, not a fresh run.
- **CSS and layout are unaudited, not clean.** The desktop front-end bug pass
  explicitly did not reach a systematic sweep of fixed heights, `overflow`,
  z-index, narrow-width flex/grid or per-theme contrast (`BUG-AUDIT-2026-10-05.md`
  §2.3), and the UI passes below are the only attempt at it. Treat any claim
  about how a panel *looks* at a given window width as unverified.
- Related: `npm run test:ui` aborts at suite 10 of 56 on a machine without
  Playwright (`BUG-AUDIT-2026-10-05.md` F2), so the UI suites after that point
  only ever run in CI. That is why several of these judgements rest on reading
  rather than on a suite result.
- Findings from the three passes are source-level. Anything needing a device -
  real touch latency, TalkBack speech, the face renderer's frame cost, the
  phone's outdoor readability - is unverified and marked as such where it
  appears.
