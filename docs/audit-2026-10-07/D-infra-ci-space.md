## D-findings

### D1. `tools/gen_source_bundle.py` accepts `--check`, ignores it, and writes the one file that fails the D01 claim

**Where:** `tools/gen_source_bundle.py:107-111` (`out = os.path.join(ROOT, "docs", "SOURCE-BUNDLE.md")` … `with open(out, "w", …)`), reached unconditionally from `tools/gen_source_bundle.py:130` (`sys.exit(main())` — the file never reads `sys.argv`). The claim it breaks: `docs/CLAIMS.tsv:146` (`D01 … no-file:docs/SOURCE-BUNDLE.md`). The documented way to run it: `docs/README.md:136` — "regenerated from the tree in one line whenever a reviewer wants it: `py -3 tools/gen_source_bundle.py`". The CI step that fails: `.github/workflows/ci.yml:1181`.

**What happens.** `gen_source_bundle.py` is the only `tools/gen_*.py` with no argument handling at all. Every other one answers `--check` (`gen_sky_places.py:76-77`, `gen_animal_cases.py:71-84`, `gen_notices.py:429-435`, …); `gen_gemini_bundles.py` at least *rejects* an unknown flag. This one silently does the write. Measured in this worktree: after I ran `python tools/gen_source_bundle.py --check` as part of the audit, `docs/SOURCE-BUNDLE.md` existed at **15,957,887 bytes (15.22 MB)**. `python tools/check_claims.py` then exited **1** with:

```
D01  the source bundle really is gone from the tree, as the documents page recorded
     check: no-file:docs/SOURCE-BUNDLE.md
     says:  docs/SOURCE-BUNDLE.md is still there
```

I deleted the file I had created and re-ran `check_claims.py`; D01 disappeared. So the loop is: the reviewer's documented command → a 15 MB ignored file → the `audit` CI job red on the next run, with no link between the two in either direction.

**Confidence:** high — reproduced in both directions.
**Severity:** medium. It is the only way found in this audit to turn a required CI job red by following the repository's own instructions.
**Obvious or subtle:** subtle. Nothing in `gen_source_bundle.py` or `check_claims.py` mentions the other.
**Fix:** one of — (a) add the `--check` branch to `gen_source_bundle.py` (`have = OUT.read_text(...) if OUT.exists() else ""; if check: return 0 if have == text else 1`), matching `gen_sky_places.py:76-77`; or (b) make `check_claims.py`'s `no-file` kind ignore a path that `git check-ignore` reports.

### D2. `tools/check_claims.py` judges the working directory, not git, so untracked scratch reports false claim failures

**Where:** `tools/check_claims.py:294-326` (the `no-file` / `file` / `grep` / `absent` kinds all resolve a path on disk), and `backend/test_shipped_modules.py:279-287`, whose evidence is `sorted(p.name for p in HERE.glob("*.py"))` compared against `_where.SHIPPED`.

**What happens.** Both checks are declared as claims about the *repository* (`docs/CLAIMS.tsv:146`, `:151`), but both read whatever is in the folder. Three false failures appeared in this worktree during the audit, one per mechanism:

| Claim | Reported | Real cause |
|---|---|---|
| D01 | `docs/SOURCE-BUNDLE.md is still there` | a gitignored, regenerable file (**D1**) |
| B17 | `backend/run_suites_audit.py is shipped` | an untracked scratch helper in `backend/` (mtime 23:11 today, not in `git ls-files`) |
| D06 | `no private, generated or superseded file is in the base` | an untracked, gitignored `jarvis-backend/__pycache__/` created by an import |

Reproduce the last two with:

```powershell
git -C $w status --porcelain --ignored -- jarvis-backend      # !! jarvis-backend/__pycache__/
git -C $w ls-files backend/run_suites_audit.py                # (nothing)
```

Both are gone from a clean checkout, so neither is a defect on `main`. The defect is that a red `audit` job can be produced by any scratch file in `backend/` or any `__pycache__` in `jarvis-backend/`, and the message the owner sees says a *claim regressed* rather than "there is a stray file".

**What I could not determine, plainly.** Whether `check_claims.py` is red on real CI, I cannot say from this sandbox. After removing the three artefacts above, the only remaining failure is B17's `t_the_settings_diff_reports_what_differs` (`backend/test_shipped_modules.py:427-455`), which shells out with `subprocess.run(..., capture_output=True)` — and the DSH sandbox refuses piped child stdio, so it can never pass here. I hand-ran all five of its sub-checks against `backend/rebuilt/jarvis-framework.toml` with `backend/_config_diff.py` and **all five passed** (`Same settings` + exit 0; `[meta] owner:  yours "Someone"   repository "Mario"`; `[meta] commercial = False`; `[meta] my_own = 1` + "kept"; exit 2 + `Could not read`). So B17 is most likely environmental too — but that is an inference, not a measurement, and it needs a run somewhere pipes work.

**Confidence:** high for the sensitivity; the CI verdict is unproven here and stated as such.
**Severity:** low-medium. It costs trust in the register rather than breaking a product path.
**Obvious or subtle:** subtle.
**Fix:** make the path-shaped kinds consult git — `no-file`/`file` via `git ls-files --error-unmatch <path>`, and `backend/test_shipped_modules.py:279` via `git ls-files backend/*.py` instead of `HERE.glob("*.py")`.

### D3. `verify-toolchain.yml`'s "pin every `uses:`" probe resolves action tags the repository no longer uses

**Where:** `.github/workflows/verify-toolchain.yml:36-40` versus the actual pins at `.github/workflows/ci.yml:65`, `:91`, `:92`, and `.github/workflows/android-apk.yml:93`.

**What happens.** The step's stated purpose, in its own comment at `verify-toolchain.yml:24-26`, is "Needed to pin every `uses:` to an immutable commit rather than a tag that its owner can move under us". Its loop is hard-coded:

```
"actions/checkout:v4"
"actions/setup-java:v4"
"actions/upload-artifact:v4"
"android-actions/setup-android:v3"
```

The repository pins **`actions/checkout@… # v5.0.1`**, **`actions/setup-java@… # v5.0.0`**, **`actions/upload-artifact@… # v6.0.0`**, **`android-actions/setup-android@… # v4.0.4`** — every one a major version past what the probe asks for. It also never mentions four actions the workflows do use (`actions/setup-python` v6.0.0, `actions/download-artifact` v7.0.0, `Swatinem/rust-cache` v2.9.2, `taiki-e/install-action` v2.87.20). So anyone re-running it to check a pin gets a table of SHAs for code that is not in the repository.

**Confidence:** high — both sides read off the files.
**Severity:** low. The probe is manual/self-triggered (`verify-toolchain.yml:10-13`) and pins are currently correct.
**Obvious or subtle:** subtle. The list looks plausible and the workflow is rarely run.
**Fix:** replace the four literals with a loop that reads them out of the workflows, e.g. `grep -rhoE 'uses: [^ ]+@[0-9a-f]{40} #[^ ]+' .github/workflows/` and resolve the tag in the trailing comment.

### D4. 40 `docs/CLAIMS.tsv` rows cite `CLAUDE.md:<line>`, nothing validates that column, the cited lines have already drifted, and a `CLAUDE.md`-only push starts no workflow

**Where:** `docs/CLAIMS.tsv` (40 rows of 150 whose `source` matches `^CLAUDE\.md:\d+$`); `tools/check_claims.py:439` and `:449`, the only two places `source` appears — both are `print` statements inside failure messages; `.github/workflows/ci.yml:24-26`, `paths-ignore: ["CLAUDE.md", "README.md"]`.

**What happens.** The register's whole premise (`tools/check_claims.py:2`, `:27-48`) is that prose which is checked by nobody rots. The `source` column is prose checked by nobody: it is printed when a check fails and never read otherwise. Two of the 40 citations have already drifted:

| Row | `docs/CLAIMS.tsv` source | What is actually at that line | Where the text is now |
|---|---|---|---|
| B18 | `CLAUDE.md:998` (the 60,000 shader budget) | "and dozing sleepy (a heavy lid). It is painted in the surface shading, not…" | `CLAUDE.md:1004` — "60,000 shader budget still holds." |
| A01 | `CLAUDE.md:1816` (the notification settings screen) | "an exit code; a half-patched backend gets a one-line restore; a running Jarvis" | `CLAUDE.md:1820-1821` — "(1) a notification settings screen in / both apps (per kind: on/off, style, Test button, quiet hours…" |

On top of that, `ci.yml:24-26` skips the *entire* CI workflow when the only changed file is `CLAUDE.md` — so the one file these 40 citations point into can be rewritten by a commit that runs nothing at all. The `paths-ignore` itself is correct for the checks that exist (I grepped: no test, tool or workflow reads the root `README.md` or `CLAUDE.md` as evidence); the gap is that the source column creates a dependency the filter does not know about.

**Confidence:** high for the drift (line numbers read directly) and for the column never being validated (only two `source` references exist).
**Severity:** medium. It is a silent-rot path in the mechanism built to stop silent rot.
**Obvious or subtle:** subtle.
**Fix:** either validate `source` — for `CLAUDE.md:<n>` check the line exists and, cheaply, that a distinctive word from the row's `claim` appears within ±20 lines — or drop the line numbers and cite `CLAUDE.md` plus a heading name, which does not drift.

### D5. `.gitattributes` lists every media type as binary except `*.mp4`, while `videos/` carries 184 MB of them

**Where:** `.gitattributes:24-34`. The block reads "Binary, so git never inspects or converts them" and names `*.png`, `*.ico`, `*.icns`, `*.woff`, `*.woff2`, `*.jpg`, `*.jpeg`, `*.wav`, `*.mp3`, `*.onnx`. `*.mp4` is absent, under the blanket `* text=auto eol=lf` at `.gitattributes:11`.

**What happens.** Ten tracked `.mp4` files totalling 192,976,451 B (184.04 MB) — plus everything under `videos/` — fall through to `text=auto`, which makes git sniff each one to decide text-or-binary. The video files, the posters and the compositions sit inside a repository whose own comment says why the explicit list exists. There is no `.lfsconfig`, no `.gitattributes` `filter=lfs` line, and no LFS rule anywhere (`git grep -nI 'filter=lfs|lfs' -- .gitattributes .gitignore .github docs/INSTALL.md` → nothing), which is the other half of **S1/S4**: 184 MB of video is carried as ordinary blobs, so every clone of this repository pays the full 199.20 MB and no history rewrite can shrink without one.

**Confidence:** high. The omission is a fact; the practical cost is small (git's content sniff normally classifies an `.mp4` as binary on its own).
**Severity:** low.
**Obvious or subtle:** obvious once the list is read next to `videos/` — and it is exactly the kind of gap the file was written to prevent.
**Fix:** add `*.mp4 binary` (and `*.mov binary` if any appear) to `.gitattributes:24-34`. If the owner picks the LFS route for S1/S4, the `filter=lfs` lines go in the same block.

### D6. The "45 duplicated fixture pairs" figure from the 2026-10-05 audit does not reproduce, and the pairs it names are enforced rather than reclaimable

**Where:** the claim is quoted in `docs/FEATURE-REVIEW-2026-10-04.md:297` and `:533` area; the measured truth is `backend/test_pairing_cases.py:40-46` (the guard), `backend/test_model_chat_cases.py:35-41`, `backend/test_own_network_cases.py:43-49`.

**What happens.** Hashing every tracked file (`Get-FileHash -Algorithm MD5`, all 3,182) and grouping gives **42** byte-identical pairs between `jarvis-client/app/src/test/resources/contract/` and `jarvis-desktop/tests/fixtures/`, or **44** if every file under `jarvis-client/app/src/test/resources/` is allowed to pair with any `jarvis-desktop/tests/fixtures/` file. def t_both_copies_are_current():

    doc = G.document()

**Confidence:** high for the counts and for the guard.
**Severity:** low.
**Obvious or subtle:** subtle — the number reads like a measured count and has been carried forward.
**Fix:** correct the figure where it is quoted, and note beside it that the pairs are test-enforced (S6) so the saving is zero without a design change.

### D8. A CI `--check` step (`gen_sky_cases.py`) dies with an uncaught `IndexError` when its throwaway config folder cannot be written

**Where:** `tools/gen_sky_cases.py:26` (`_TMP = tempfile.mkdtemp(prefix="jarvis-sky-cases-")`, at *import* time), `:63-66` (`SK.request_weather("open_meteo", …, spawn=held.append)` then `held[0]()`), and the step that runs it: `.github/workflows/ci.yml:256` (`python tools/gen_sky_cases.py --check`, inside the "Sky - the phone's golden fixture matches sky.js" step).

**What happens.** The module makes a throwaway folder and points every settings write at it (`:26-34`). `request_weather(...)` only queues a card if it could persist the request; when that write fails it returns without calling `spawn`, so `held` is empty and `held[0]()` at `:66` raises `IndexError: list index out of range` — which is what I measured:

```
gen_sky_cases.py  code=1  IndexError: list index out of range
```

The check itself is not at fault: on a runner that can write its temp folder, `:96-103` compares both committed copies against freshly rendered text and a missing file fails (`:97-98`, `not p.exists() or … != text`). The defect is the failure mode. A `--check` step whose purpose is to say "these two fixtures are stale" instead reports an `IndexError` from an unrelated line, with nothing naming the cause; the same shape appears in `gen_projects_cases.py` (`KeyError: 'project'`).

I could not go further: in this sandbox `backend/test_sky.py` and `backend/test_projects.py` also exit 1 with no `N passed` summary line, for the same write-denial reason, so they cannot be used to decide whether the committed fixtures are fresh. **The CI verdict for `ci.yml:256` is therefore unproven here** and should be treated as open, not as a confirmed red step.

**Confidence:** high that this is the mechanism observed; medium that it is a product defect rather than an environment artefact.
**Severity:** low in CI (a runner's temp dir is writable); medium as diagnosability, which is the whole point of a `--check` step.
**Obvious or subtle:** subtle — the traceback points at line 66, five lines away from the write that actually failed.
