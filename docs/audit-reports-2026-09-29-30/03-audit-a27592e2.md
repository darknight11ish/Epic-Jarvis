## Proven bugs, worst first

**1. Goals: a draft's steps stay blank after "Show" (medium-low; only with "Windows Hello for memory lists" on)**
- `brain/goals.rs:redact_goals` blanks every step's text while the lists are hidden (`s.insert("step", "")`, `"by"`).
- `brain.js:6581-6584` `workingPlan()` copies the plan once into `draftPlans` (`if (!draftPlans.has(goal.id)) draftPlans.set(goal.id, goal.plan.map(...))`) and never refreshes it.
- To trigger it, open Brain → Work → Goals while the lists are hidden and a draft goal exists, then press Show.
- The draft's editor keeps showing empty step boxes. `planIsValid` rejects blank steps, so Accept refuses, and the owner has to retype the plan.
- I ran it against the repo's own test mock, which mirrors Rust's blanking (`g1.mjs`, scratchpad). Output: `step while hidden: ""`, then `step after Show (PC now sends real words): ""`. The real step was "contact installers".
- Fix: build the working plan from the plan again once `goal.hidden` flips to false, or don't cache while `goal.hidden`.

**2. Projects, app task: the paste box keeps the change text after a successful paste (medium-low)**
- `projects-panel.js:333-335`: `const out = await write("app_task_files", ...); if (out) delete state.pastes[t.task];`.
- `write()` (line 257-273) runs `await showProjects()` in its `finally`. That repaints the whole task card, and line 809 rebuilds the box with `area.value = state.pastes[t.task] || ""` while the old text is still stored. The `delete` runs only after the repaint, so the text stays visible.
- To trigger it, paste a change and press "Add to this task".
- The toast says "Added to this task", but the box still holds the same change. A second press adds it again.
- I ran it: in a copy of `tests/projects.mjs` I printed the box value right after a successful paste. Result: `BOX AFTER SUCCESSFUL PASTE: "<<<FILE src/App.tsx>>>\nexport const x = 1;\n<<<END>>>\n<<<DELETE old.txt>>>"`. The existing test never checks that the box is emptied.
- Fix: delete `state.pastes[t.task]` before the refresh, for example `write(...)` then delete inside `write`'s success path, or clear it first and restore it on failure.

**3. Chatbot card: Pause/Stop/Resume lose keyboard focus every 4 seconds while a conversation runs (low; Stop matters)**
- `brain.js:5449-5452` re-reads every `CHATBOT_POLL_MS` (4 s) while a conversation is live. `paintChatbot` then does `box.replaceChildren(...out)` (line 5442), and that includes the `.row-actions` buttons built at 5361-5366 and 5432-5436.
- Only the limits row is protected from this (comment at 5195-5199); the action buttons are not.
- A keyboard user tabbing to Stop is bumped back to the page on the next poll. A mouse press that straddles a repaint (down on the old node, up on the new one) can lose the click.
- I ran it: with `CASES.running`, I focused the Stop button, emitted an activity event to trigger a re-read, and waited 600 ms. `document.activeElement` went from "Stop" to the `<body>`.
- Fix: rebuild the "now" block only when its content key changes (as `paintChatbotLog` already does with `logKey`), or restore focus to the same action after repaint.

**4. `showProjects` drops a refresh that arrives during another read (low)**
- `projects-panel.js:232-234`: `if (state.reading) return;`, with no "read again" flag. The chatbot and goals loaders do have one (`cb.again`, `gl.again`).
- Every change ends in `write()` → `showProjects()`. If a background read is already in flight when the owner acts (merge, discard, paste), the post-change refresh is silently skipped. The screen can then show pre-change state, for example Merge still offered, until something else triggers a re-read.

## What I tried and found clean

- **Pairing, QR and device key (`devices.rs`, `devices.js`, `devices-words.js`)**
  - The QR text is turned into an SVG in Rust and dropped. The page receives only the picture, the typed code and the counts; `SESSION_FIELDS` is a whitelist.
  - `pair_start` and `Bring it back` are held on a stale link; `Remove` and `Retire` are not, on purpose.
  - The capture guard is switched on before the code goes to the page and off when the session ends.
  - No `println!`/`eprintln!` in `devices.rs` prints the QR text, the code or a token.
  - All `dv-*` element ids exist in `settings.html` (checked with a loop). Device and phone names are set with `textContent`.
  - The desktop never holds a device key; only the shared token exists here, and it is a separate matter (next line).
- **Token storage:** `token_store.rs` uses Windows Credential Manager; `set_api_settings` refuses a plain-text fallback and restores the previous state on any failure. No log line in `token_store.rs` or `commands.rs` prints the token.
- **Allowed server address:** `validate_base`, `own_network_problem` and `typed_host` check two readings of the host and cover odd numeric spellings, an `@`, and IPv6. `jarvis_base` returns an empty string for a refused address, and `jarvis_headers` refuses before any request goes out. There is no fallback to this PC. `jarvis_client` uses `.no_proxy()` and never follows redirects.
- **Headers:** every request path I read goes through `jarvis_headers`, which sends `X-Jarvis-Client`. This covers `devices.rs`, `brain/goals.rs`, `brain/chatbot.rs`, `brain/projects.rs`, `hud_proxy.rs` and `screen_work.rs`.
- **Stale stream and approvals:**
  - The event stream goes stale after `SILENCE_TIMEOUT` with no keepalive, and `hello_may_clear_stale` needs a good queue read before clearing it.
  - `decide_approval` re-checks the link before and after Windows Hello.
  - The widget cannot approve under App lock or approve an email; those go to the Jarvis bar.
  - Notifications can only deny.
  - The HUD proxy has an exact list of allowed reads and cannot approve at all.
  - Every write in `brain/goals.rs`, `brain/chatbot.rs` (except Stop and Pause, on purpose) and `brain/projects.rs` calls `require_link_live` or an equivalent.
- **Injection and markup:**
  - Every `innerHTML` that touches server or model text goes through `renderMarkdown`, which escapes `&<>"'` first, or through `escapeHtml`. Chatbot text, transcripts and diffs use `textContent`.
  - `open_external_url` allows only validated http(s).
- **Events and parsing:** the SSE parser has an oversized-frame cap. The panic-prone spots I checked (`crash_notes.rs` uses `to_ascii_lowercase`, `chatbot.rs` checks `ids.len() >= 2` before `ids[0]`) do not panic.
- **Command permissions:** `python3 tools/check_command_acl.py` printed "269 commands, generate_handler! and build.rs agree."
- **Talk-to-type (`talk_type.rs`):** the state machine re-checks link, lock and mic after each await, and Stop bumps a generation counter. No bug found.
- **Models cache (`models-cache.js`):** it strips live-only fields before writing and never throws. `load()` keeps the last good read when a live read fails. No bug found.
